자동충전 대상 선정과 한도·잔액 계산

개요​

자동충전에서는 신청 금액을 그대로 카드사에 보내지 않았다. 기관에 남은 예치금과 카드별 추가 충전 가능 금액을 계산하고, 하나의 카드에 여러 사례의 요청이 연결된 경우 누적 요청을 제한해야 했다. 이 조건을 단계적으로 계산하는 SQL을 작성했다.

문제: 서로 다른 기준의 금액을 한 요청으로 합치기​

기준확인할 내용
기관예치금에서 이미 사용·요청된 충전과 완료된 환불을 반영한 가용 금액
카드충전·환불·승인·승인 취소를 반영한 현재 잔액과 추가 충전 가능 금액
사례별 신청총 신청 금액에서 이미 처리한 금액을 제외한 미처리분
카드별 여러 신청각 신청은 유효해도 합계가 카드 한도를 넘는지 여부
처리 이력기존 요청이 진행 중인지, 최초 충전 대상인지 여부

잔액이라는 이름만 보고 같은 숫자로 취급하면 안 된다. 카드에 현재 남은 금액과 카드에 앞으로 더 충전할 수 있는 금액은 다르다. 원본 SQL에서는 이 둘을 구분하기 위해 설정 한도에서 거래 이력으로 계산한 잔액을 뺀 값을 사용한다.

계산 단계​

Plain Text
기관 가용 예치금 집계
        ↓
유효한 기관·사례·카드의 충전 신청 선정
        ↓
사례별 미처리 금액과 카드 추가 충전 가능액 계산
        ↓
카드별 누적 요청 보정
        ↓
기관별 누적 요청과 예치금 비교
        ↓
최초 충전 분리 및 최종 요청 구성

1. 가용 예치금과 카드 잔액 집계​

기관 가용 예치금은 예치금에서 유효한 충전 요청·완료 금액을 차감하고 완료된 환불을 더하는 구조다. 카드 잔액 계산에는 승인과 승인 취소 이력도 반영한다.

아래 식은 내부 상태 코드와 컬럼명을 제외하고 역할만 표현한 것이다.

Plain Text
기관 가용 예치금
  = 유효 예치금 - 계산 대상 충전 금액 + 완료 환불 금액

카드 잔액
  = 계산 대상 충전 금액 - 완료 환불 금액
    - 승인 금액 + 승인 취소 금액

카드 추가 충전 가능액
  = 설정 한도 - 카드 잔액

요청 단계의 충전과 완료 단계의 환불을 구분해 집계한다. 모든 거래 이력을 상태 구분 없이 합산하는 방식은 아니다. 신청 선정에서도 총 신청 금액과 처리 금액을 비교하고, 앞선 신청분이 아직 진행 중인 경우 다음 요청 대상으로 바로 이어지지 않도록 조건을 둔다.

2. 카드별 여러 요청을 누적해서 제한​

하나의 카드에 여러 사례가 연결될 수 있으므로 행별 한도 검사만으로는 부족했다. ROW_NUMBER()로 카드별 순서를 만들고, SUM() OVER로 그 순서의 누적 요청을 계산했다. 한도를 넘는 행에서는 LAG()로 직전 누적 금액을 읽어 남은 충전 가능액을 계산한다.

다음은 동작을 설명하기 위한 가상 금액이다. 기관 예치금 검사를 통과한다고 가정한다.

같은 카드의 처리 순서사례별 충전 후보카드 잔여 충전 가능액 100 기준 반영 금액
첫 번째7070
두 번째6030
세 번째20추가 요청 없음

누적 합과 직전 누적값으로 한도를 초과한 행의 요청 금액을 조정한 뒤, 양수인 요청만 남긴다.

3. 기관별 예치금과 누적 요청 비교​

카드 기준 보정이 끝난 요청을 기관별로 다시 누적하고, 가용 예치금에서 누적 요청을 뺀 결과로 대상 여부를 결정한다. 여러 카드가 각각 충전 가능하더라도 기관 예치금이 충분하지 않으면 모두 요청하지 않는다.

최종 조건은 잔여 예치금이 0보다 큰 경우다. 예치금과 누적 요청이 정확히 같아지는 요청은 제외한다.

4. 최초 요청 분리​

카드에 기존 유효 충전 이력이 없고 카드별 첫 행인 경우 최초 요청으로 판단한다. 최종 결과에서는 1원 요청과 나머지 금액을 분리하고, 0 이하의 요청은 제거한다. 신청 금액이 1원인 경우 나머지 0원 요청이 나가지 않도록 처리한 조건도 남아 있다.

구현 결과​

CTE는 기관 예치금, 충전 요청, 환불 요청의 역할을 나누는 데 사용했다. 윈도 함수는 카드·기관 단위 누적 계산을 행별 요청 데이터에 연결하는 수단이었다.
