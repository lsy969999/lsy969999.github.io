CPU 파티클 시뮬레이션과 Geometry Shader 빌보드

배경과 목표​

블록을 부술 때의 작은 조각, 몬스터가 사라질 때의 연기, TNT의 점화와 폭발은 게임 상태를 눈으로 전달하는 피드백이다. 이런 효과를 입자마다 GameObject로 만들면 생성·업데이트·렌더 등록을 개별적으로 관리해야 한다.

이 프로젝트에서는 CParticleManager가 종류별 입자 데이터를 벡터로 관리한다. CPU에서 수명·속도·위치·UV를 갱신하고, GPU에는 입자당 점 하나를 전달한다. Geometry Shader가 그 점을 카메라를 향한 사각형으로 펼쳐 렌더링한다.

TNT와 폭발의 게임 로직은 효과를 언제 요청할지 결정하고, 이 문서는 요청된 입자를 어떻게 유지하고 그리는지 설명한다. 구름 인스턴싱과 달리 DrawIndexedInstanced()를 사용하는 경로가 아니다.

게임 로직과 파티클 관리 분리​

GameInstance는 다음 생성 함수를 파티클 매니저에 전달한다.

API주요 입력사용하는 곳
AddParticleRenderDestruct위치·Packed Texture ID·개수·색상블록 파괴, 음식 섭취 조각
AddParticleRenderDeathSmoke위치·개수몬스터·플레이어 사망 연출
AddParticleRenderExplodeSmoke위치·개수공통 폭발 함수
AddParticleRenderTNTFusing위치·개수점화된 TNT의 윗부분

이 함수들은 즉시 Draw를 실행하는 것이 아니라 ATTRIBUTE를 만들어 종류별 배열에 추가한다. 호출한 게임 오브젝트는 생성된 각 입자의 포인터를 보관할 필요가 없다.

반대로 반환된 효과 ID로 묶음 전체를 중지하거나 위치를 계속 변경하는 기능은 이 API에 없다. 위치는 생성 당시의 월드 좌표이며, 이후에는 입자의 속도·가속도로 이동한다. TNT가 이동하더라도 이미 나온 연기가 TNT의 자식처럼 함께 이동하지는 않는다.

시뮬레이션 데이터와 렌더링 데이터​

매니저는 파티클 종류마다 두 벡터를 갖는다.

데이터담는 내용유지 기간
ATTRIBUTE위치·속도·가속도, 나이·수명, 생존 여부, 크기·색상·UV·텍스처입자의 생존 기간
VTX_POINT_PARTICLE현재 위치·크기·UV·색상·텍스처 ID·복셀 밝기 등매 Update에 다시 구성

속도와 나이처럼 CPU 계산에 필요한 값은 입자 상태에 남기고, 이번 프레임에 그릴 값만 정점 데이터로 옮긴다. Compute Shader나 GPU 버퍼 내부에서 시뮬레이션 상태를 갱신하는 방식은 아니다.

종류는 블록 파괴, 사망 연기, 폭발 연기, 횃불 테스트, TNT 점화의 다섯 가지다. 각각의 Update 함수가 직접 동작 규칙을 구현한다. 공통 구조체에 프레임 관련 멤버가 있다고 해서 모든 종류가 그 설정만으로 재생되는 범용 클립 시스템은 아니다.

실제 효과별 초기값​

다음은 GUI 테스트가 아닌 게임용 생성 함수의 값이다. 크기는 Geometry Shader가 만드는 사각형의 전체 너비·높이 기준이다.

효과수명크기이동 특성
블록 조각2초0.1×0.1위쪽 성분을 가진 무작위 방향, 속력 1~4, Y 가속도 -9.8
사망 연기4초정사각형 한 변 0.1~1.5위쪽 성분을 가진 무작위 방향, 속력 1~4, Y 가속도 -1.8
폭발 연기0.75초정사각형 한 변 0.1~2.5XYZ 무작위 방향, 속력 4~8, Y 가속도 -1.8
TNT 점화0.7초0.1×0.1XZ 속도 -0.1~0.1, Y 속도 0.8, 가속도 0

방향은 성분별 난수를 뽑고 정규화한다. 폭발 방향이 XYZ 모두 양·음으로 퍼지기는 하지만, 큐브 안에서 고른 벡터를 정규화하므로 구면 위의 균일 분포와 같지는 않다.

사망 연기도 처음에는 위로 움직이지만 Y 가속도는 음수이므로 이후에는 아래로 내려올 수 있다. 이름이 Smoke라고 해서 부력이나 유체 흐름을 계산하는 것은 아니다.

블록 텍스처를 조각으로 재사용​

블록 파괴 입자는 별도의 파편 이미지를 고르는 대신 전달받은 Texture ID를 사용한다. U·V 시작점을 각각 0.0~0.9 사이의 0.1 간격에서 고르고, UV 크기는 0.1×0.1로 설정한다. 같은 블록 이미지의 작은 구간들이 조각처럼 흩어지는 효과다.

플레이어의 파괴 처리에서는 블록의 POS_X 면 텍스처를 선택하고, 블록 기본 색상에서 구한 Tint를 전달한다. 실제로 맞힌 면마다 다른 텍스처를 고르는 경로는 아니다. 별도의 균열 표시 메시와 이 작은 파편 입자도 서로 다른 구현이다.

현재 블록 파괴 경로는 처리 중 조각 1개를 요청하고, 파괴 완료 시 일반 블록은 2개, 즉시 파괴 종류는 60개를 추가 요청한다. 실제 생성 빈도는 이 코드가 호출되는 주기에 영향을 받는다.

음식 섭취도 같은 생성 함수를 사용하되 아이템의 Packed Texture ID를 전달한다. 따라서 BLOCK_DESTRUCT라는 종류 이름보다 재사용 범위가 넓다. 같은 이동·수명 규칙을 사용하면서 이미지 출처를 바꾸는 방식이다.

CPU 이동과 수명 처리​

각 종류는 공통적으로 다음 순서로 상태를 갱신한다.

Plain Text
age += dt
velocity += acceleration × dt
position += velocity × dt
종류별 UV·크기 갱신
수명 초과 또는 비활성 → 제거
생존 → 렌더링용 정점 생성

가속도를 먼저 속도에 적용하고 그 속도로 위치를 이동시킨다. 지형 AABB, Raycast, 접촉 반사, 바닥 정지 처리는 이 경로에 없다. 조각은 화면상 파편이며 실제 물리 파편으로 바닥에 쌓이지 않는다.

수명 종료는 age > lifetime 조건이다. 정확히 같을 때는 살아 있을 수 있으므로 마지막 아틀라스 프레임의 경계값과 함께 봐야 한다. 긴 Delta Time에서 중간 프레임을 모두 재생하는 Substep은 없다.

제거 비용 줄이기: 마지막 항목과 교환​

수명이 끝난 입자는 벡터 중간에서 erase()하지 않는다. 마지막 입자와 교환한 뒤 pop_back()한다. 교환된 입자를 같은 인덱스에서 다시 처리하기 때문에 뒤에서 옮겨온 입자의 갱신을 건너뛰지 않는다.

C++
if (expired)
{
    if (i != particles.size() - 1)
        std::swap(particles[i], particles.back());
    particles.pop_back();
}
else
{
    // 현재 입자로 렌더링 정점을 구성한다.
    ++i;
}

삭제한 항목의 자리는 마지막 입자로 채운다. 뒤의 항목 전체를 이동하지 않는 대신 입자 순서는 바뀐다.

연기 아틀라스 재생​

연기와 점화는 Texture/particles.png를 사용하는 128×128 Texture Array의 Slice 0을 참조한다. 타일 하나의 크기는 8×8이므로 정규화한 UV 크기는 각 축 8/128이다.

종류사용하는 행프레임 진행
사망 연기Y = 00.5초마다 열 7 → 0
폭발 연기Y = 80/1280.05초마다 열 0 → 14
TNT 점화Y = 00.1초마다 열 7 → 0

현재 나이를 프레임 시간으로 나눠 UV를 직접 계산하므로, 프레임 지연이 발생하면 중간 타일을 건너뛰고 현재 나이에 대응하는 타일을 사용한다.

폭발의 생성 함수는 처음 UV를 15번 열로 설정하지만 활성 Update가 곧바로 나이 기반 열 번호로 덮어쓴다. 실제 재생은 초기 열 번호가 아니라 입자의 나이에 따른다. 계산 단계가 15 이상이면 열을 0으로 되돌리고, 수명 검사에서 초과한 입자를 제거한다.

TNT 점화는 8타일에 대응하는 계산이 있지만 수명이 0.7초라 마지막 타일이 충분히 표시되는지 프레임 경계에 영향을 받는다. 타일 수, 프레임 시간, 입자 수명을 하나의 계약으로 정리할 여지가 있다.

공통 Fade Out은 없다​

확인한 세 연기 경로는 나이에 따라 색상 Alpha를 0으로 보간하지 않는다. 현재 타일에 담긴 모양·Alpha가 바뀌고 수명을 넘으면 제거된다. 스르륵 사라지는 정도는 텍스처 타일의 내용에도 영향을 받는다.

따라서 LifeTime을 늘리면 자동으로 긴 Fade Out이 생기는 것은 아니다. 명시적인 페이드가 필요하면 정규화한 나이나 별도 페이드 구간에서 색상 Alpha를 계산하고, 그 Alpha가 실제 블렌딩에 쓰이는지도 함께 확인해야 한다.

점 하나를 네 정점으로 확장​

GPU 버퍼의 Topology는 POINTLIST다. CPU는 입자당 점 하나만 업로드하고, Vertex Shader는 월드 위치와 속성을 Geometry Shader에 전달한다.

Geometry Shader는 View 행렬에서 카메라 Right·Up 방향을 구한다. 사각형의 네 모서리 좌표에 크기와 2D 회전을 적용한 뒤 그 두 축으로 월드 위치를 만든다.

Plain Text
corner = (-0.5~0.5 범위의 사각형 모서리) × size
rotated = rotate2D(corner, rotation)
worldVertex = center + cameraRight × rotated.x + cameraUp × rotated.y
clipVertex = worldVertex × ViewProjection
uv = uvStart + uvCorner × uvSize

한 점에서 네 정점을 Triangle Strip으로 출력해 삼각형 두 개를 만든다. 입자의 위치는 월드 공간에 남고 사각형 방향만 카메라를 따라가므로 모든 효과가 빌보드 형태로 보인다.

셰이더에는 회전 입력이 있지만 확인한 생성·정점 구성 경로는 그 값을 별도로 채우지 않아 기본 0을 사용한다. 회전 지원 필드가 있다는 사실과 실제 무작위 회전을 적용한다는 사실을 구분했다.

텍스처 선택과 복셀 조명​

Packed Texture ID에서 배열 그룹과 Slice를 분리한다. Pixel Shader는 아이템·엔티티·블록·파티클 아틀라스에 대응하는 Texture Array를 선택해 같은 셰이더로 샘플링한다.

CPU는 살아 있는 입자마다 현재 위치를 floor()해 그 칸의 복셀 밝기를 정점에 담는다. 셰이더는 낮은 4비트를 Block Light, 높은 4비트를 Sky Light로 해석한다.

Plain Text
block = blockLightRaw / 15
sky = skyLightRaw / 15 × dayFactor
light = max(max(block, sky), 0.08)
color = texture × particleColor × (light, light, light, 1)

현재 최소 밝기는 0.08이다. 복셀을 조회하지 못한 경우 정점의 초기 밝기 0에서 이 하한이 적용된다. 파티클은 복셀 조명과 낮밤 계수를 따르지만, 이 셰이더에서 Shadow Map을 조회하지는 않는다.

텍스처 Alpha가 0.01보다 작으면 clip()으로 버린다. 이 조건은 텍스처 Alpha 기준이며 최종 particleColor.a를 곱한 뒤의 값으로 검사하는 것은 아니다.

배치 단위와 GPU 버퍼 재사용​

매 Update에서 종류별 렌더링 정점 벡터를 비우고 현재 생존 입자로 다시 채운다. Render는 블록 조각 → 사망 연기 → 폭발 연기 → 횃불 → TNT 점화 순서로 비어 있지 않은 종류를 그린다.

종류마다 같은 동적 정점 버퍼를 D3D11_MAP_WRITE_DISCARD로 갱신한 뒤 Draw(입자 수, 0)를 호출한다. 서로 다른 종류의 데이터를 합쳐 한 번에 그리지는 않으며, 최대 다섯 종류가 모두 있다면 다섯 번 업로드·Draw가 발생한다.

입자마다 Draw를 호출하는 방식보다 제출 단위를 줄였지만, Geometry Shader의 정점 확장과 픽셀 채우기 비용은 남는다. 이 방식이 인스턴스 Quad보다 항상 빠르다는 성능 비교는 수행하지 않았다.

렌더링 후에는 Geometry Shader를 null로 해제한다. 다음 오브젝트의 Vertex Shader 출력에 파티클용 Geometry Shader가 계속 연결되지 않도록 정상 종료 경로에서 상태를 정리한다.

RenderX()의 NO_OVERWRITE 기반 스트리밍은 비활성 코드다. 현재 업로드 경로는 Ring Buffer 방식이 아니다.

블렌딩과 깊이는 별도 정책​

파티클 매니저는 NONBLEND 그룹에 등록되고 DEFAULT 패스에만 참여한다. 현재 Render에서는 셰이더·샘플러·Rasterizer를 설정하지만 파티클 전용 Alpha Blend·Depth Write 정책을 명시적으로 설정하지 않는다.

따라서 연기 텍스처에 Alpha가 있다는 이유만으로 부드러운 반투명 합성이 보장되지는 않는다. 확인한 코드에서는 거리 정렬도 없고 입자 제거 시 순서도 바뀐다. 명시적 블렌딩을 추가한다면 깊이 쓰기와 렌더 순서도 함께 결정해야 한다.

Depth Texture를 읽어 지형 접촉부를 흐리게 하는 Soft Particle, 왜곡, 발광 후처리, Shadow 생성은 이 경로의 기능으로 포함하지 않았다.

최대 개수와 생성 시점​

PARTICLE_MAX_CNT = 5000은 전체 합계가 아니라 종류별 제한이다. 다섯 종류를 모두 채우면 CPU 상태는 최대 25,000개가 될 수 있다. GPU 버퍼는 한 종류씩 재사용하므로 5,000점 분량으로 생성된다.

상한에 도달한 AddParticle()은 새 입자를 넣지 않고 S_OK를 반환한다. 오래된 입자를 교체하거나 버퍼를 자동 확장하는 정책도 없다. 생성 함수들이 성공 개수를 반환하지 않으므로 호출자는 요청한 수가 조용히 누락되는지 알기 어렵다.

또한 엔진 Update 순서는 파티클 갱신이 GameObject의 PriorityUpdate·Update·LateUpdate보다 앞이다. 그 뒤 게임 오브젝트가 생성한 입자는 상태 벡터에는 들어가지만 렌더링 정점은 다음 파티클 Update에서 만들어진다. 따라서 해당 호출 경로에는 한 업데이트 지연이 있다.

TNT 점화는 초당 방출률이 아니라 각 TNT의 LateUpdate마다 1개를 요청한다. 단순히 60회/초·수명 0.7초를 가정하면 TNT 한 개당 약 42개의 점화 입자가 동시에 살아 있을 수 있지만, 실제 개수는 프레임 주기·상한·제거 경계에 따라 달라진다. 이는 성능 측정값이 아니라 부하를 추정하는 예시다.

GUI 테스트와 게임 효과의 차이​

ParticleManager GUI에는 TEST, TEST SMOKE, TEST EXPLODE, TEST TORCH, TEST FUSING 버튼이 있다. 대부분 원점에 직접 테스트 ATTRIBUTE를 만들어 넣는다.

테스트 코드와 게임용 생성 함수는 모두 같은 프리셋을 참조하는 구조가 아니다. 예를 들어 TEST SMOKE는 Y 가속도 -9.8을 넣지만 실제 사망 연기 함수는 -1.8을 사용한다. TEST EXPLODE도 위쪽 방향·속력 14로 생성해 실제 폭발의 XYZ 방향·속력 48과 다르다.

따라서 GUI의 버튼 결과만으로 실제 게임 효과의 수치가 검증되었다고 판단하면 안 된다. 테스트와 실제 생성 코드를 같은 데이터 정의로 연결하는 것이 유지보수 개선점이다.

횃불 타입은 두 타일을 번갈아 표시하면서 크기를 줄인다. GUI에서 생성해 확인할 수 있다.

구현 결과​

CPU는 생존 입자 전체의 이동·UV·수명을 갱신하고 입자마다 복셀 밝기를 조회한다. 여기에 렌더링 정점 구성과 업로드가 더해진다. GPU는 점을 Quad로 펼치고 텍스처를 샘플링하므로 화면에서 입자가 크고 겹칠수록 픽셀 처리량이 커질 수 있다.

현재 구현은 개별 입자 오브젝트 없이 효과를 관리하고, 블록·아이템 텍스처 재사용과 아틀라스 재생을 공통 렌더링으로 연결한 데 의미가 있다.
