# 인벤토리·제작·제련과 좌표 기반 보관함 관리

## 배경과 목표 {/* #해결하려던-문제 */}

블록을 캐서 아이템으로 획득하고, 슬롯 사이에서 옮기고, 재료를 조합하거나 화로에 넣어 다른 아이템을 만드는 흐름이 필요했다. 상자와 화로는 UI를 닫았다 열어도 내용이 남아야 하며, 화로의 제련은 창을 보고 있을 때만 진행되어서는 안 된다.

플레이어가 소유하는 슬롯 데이터, 커서로 들고 있는 아이템, 월드 좌표에 귀속되는 저장소를 구분했다. 제작은 패턴 매칭과 결과 수령을 분리하고, 화로는 월드 갱신에서 진행한다. 이 기능들이 [블록 설치·파괴](/projects/minecraft/dda-block-editing)의 드롭과 상호작용에 연결되어 자원 획득·가공·사용의 흐름을 구성한다.

## 아이템 값과 슬롯의 표현

`CItemObject::ItemInfo`는 일반 아이템 타입, 선택적인 `CBlock3` 값, 내구도, 수량을 가진다. `block` 값이 있으면 블록 아이템, 없으면 `eItemType`으로 일반 아이템을 구분한다.

슬롯은 `optional<ItemInfo>`로 표현한다. 빈 슬롯은 `nullopt`, 채워진 슬롯은 아이템 값과 수량을 가진다. 수량은 `uint8_t`이며 여러 경로에서 64를 스택 기준으로 사용한다. 자료형 자체가 유효한 수량 1~64를 보장하는 것은 아니므로 아이템을 만드는 쪽의 검증도 필요하다.

| 데이터 | 보관 위치 | 구성 |
| --- | --- | --- |
| Hotbar | 플레이어 | 9칸 |
| 일반 인벤토리 | 플레이어 | 27칸 |
| 방어구·보조 슬롯 | 플레이어 | 방어구 4칸, 별도 방패 슬롯 |
| 개인 제작 | 플레이어 | 입력 2×2 + 결과 1칸 |
| 작업대 제작 | 플레이어 | 입력 3×3 + 결과 1칸 |
| 상자 | ChestStorage | 월드 좌표별 27칸 |
| 화로 | FurnaceStorage | 월드 좌표별 재료·연료·결과와 진행 상태 |

작업대 입력은 작업대 좌표마다 따로 저장하지 않고 플레이어의 제작 배열을 사용한다. 반면 상자와 화로는 위치마다 다른 저장 데이터를 조회한다.

## 슬롯 UI와 실제 데이터의 연결

UI 슬롯에는 종류와 Index, 화면 위치, 표시용 `CUIItem` Handle이 있다. 플레이어는 슬롯 종류를 실제 `optional<ItemInfo>`의 주소로 대응시켜 클릭한 슬롯을 수정한다.

예를 들어 인벤토리 슬롯은 플레이어 배열을, 화로의 연료 슬롯은 현재 열린 좌표의 `storage.fuel`을 가리킨다. 이 대응을 통해 같은 플레이어 인벤토리가 개인 창·작업대·상자·화로 화면에서 공통으로 사용된다.

표시 갱신에서는 슬롯의 Handle로 `CUIItem`을 찾고 `SetItemInfo()`로 값을 전달한다. 화면용 아이템 값과 실제 저장 데이터를 각각 갱신하는 구조이며, 모든 UI가 원본 데이터의 참조만 보관하는 완전한 데이터 바인딩 시스템은 아니다.

```text
플레이어 배열 / 좌표 기반 저장소
  → 슬롯 종류·Index를 실제 데이터에 대응
  → 클릭 처리로 원본 슬롯 변경
  → 표시용 CUIItem에 값 전달
```

커서 아이템은 별도의 `CUIItem`이 값을 들고 있으며 Handle로 조회한다. 따라서 데이터가 UI와 완전히 분리되어 있다고도 할 수 없다. 커서로 이동하는 동안의 아이템 소유 상태는 UI 객체의 생성·제거와 연결되어 있다.

## 획득과 스택 이동

### 월드 드롭 획득

플레이어는 드롭 아이템 Collider와의 겹침을 확인하고, 드롭 경과 시간이 0.3초보다 클 때 획득을 시도한다. `ProcessItemGain()`이 성공하면 획득 소리를 내고 드롭 항목을 제거한다.

획득은 Hotbar를 먼저, 이후 일반 인벤토리를 순회한다. 각 배열에서는 앞에서부터 검사해 빈 슬롯이 나오면 바로 넣거나, 같은 타입의 스택이 전체 수량을 수용할 수 있으면 합친다. 모든 기존 스택을 먼저 채운 다음 빈 슬롯을 찾는 두 단계 탐색은 아니다.

한 스택에 일부만 넣고 나머지를 다음 슬롯으로 나누는 처리도 없다. 예를 들어 수량 60인 스택에 8개를 획득할 때 그 칸을 64로 채우고 4개를 넘기는 대신, 전체 8개를 넣을 다른 슬롯을 찾는다. 빈 슬롯 입력은 전달받은 값을 그대로 넣으므로 정상 범위의 입력을 전제로 한다.

### 좌클릭·우클릭 이동

일반 인벤토리의 기본 동작은 다음과 같다.

| 상황 | 처리 |
| --- | --- |
| 빈 커서로 좌클릭 | 슬롯 전체를 커서로 이동 |
| 빈 커서로 쌓을 수 있는 아이템 우클릭 | 절반을 커서로 분리 |
| 아이템을 든 채 빈 슬롯 좌클릭 | 전체 배치 |
| 아이템을 든 채 우클릭 | 가능한 경우 한 개 배치·추가 |
| 다른 타입이 있는 슬롯에 배치 | 슬롯과 커서 아이템 교환 |
| 같은 타입이 있고 합칠 수 있는 경우 | 수량 합산 |

절반 분리는 정수 나눗셈을 사용한다. 수량 5라면 커서에 2개, 원래 슬롯에 3개가 남는다. 도구·방어구 등 `IsCountableItem()`이 false인 일반 아이템은 스택 합치기와 분리에서 별도로 취급한다.

현재 일반 좌클릭 합치기는 합계가 **64 이상이면 합치지 않고 교환**한다. 합계 64를 허용하는 획득 경로와 다르며, 넘친 수량만 커서에 남기는 방식도 아니다. 사용자 경험과 규칙 일관성을 개선할 부분으로 남아 있다.

창을 닫을 때 커서에 남은 아이템은 확인한 인벤토리·화로 경로에서 월드에 드롭하고 커서 UI를 제거한다. 원래 슬롯으로 자동 반환하는 정책이 아니다. 이동 중 UI 객체 생성이 실패해도 원본 변경을 되돌리는 공통 트랜잭션은 없으므로 생성 성공·아이템 보존을 함께 검증해야 한다.

## 제작 패턴의 위치 정규화

제작법은 `CItemObject::RecipeInitialize()`에서 C++ 코드로 등록한다. `SRecipe`는 3×3 패턴과 결과 아이템을 가지며, 초기화 플래그로 중복 등록을 막는다. JSON 제작법 로더나 별도 편집기는 아니다.

현재 등록 예시로 원목 한 개에서 같은 종류의 판자 4개, 판자 두 개를 세로로 놓아 막대기 4개, 판자 네 개로 작업대를 만드는 조합이 있다. 재질별 입력은 구체적인 블록 타입으로 등록하며, 임의의 목재를 하나의 재료 태그로 처리하는 구조와는 다르다.

`GetTrimmedGrid()`는 입력에서 아이템이 있는 최소 사각형을 구하고 바깥쪽 빈 행·열을 제거한다. 제작법도 같은 방식으로 자른 뒤 비교한다.

```text
. A .      A
. A .  →   A
. . .
```

덕분에 같은 모양을 제작창의 다른 위치에 놓아도 일치시킬 수 있다. 내부의 빈칸은 남기므로 모양 정보가 사라지지 않는다. 2×2 개인 제작과 3×3 작업대 모두 같은 비교 함수를 사용하며, 개인 제작창에 들어갈 크기의 패턴은 그곳에서도 매칭할 수 있다.

`MatchTrimmedGrid()`는 가로·세로 크기, 빈칸 여부, 블록/일반 아이템 구분, 타입, 필요한 최소 수량을 비교한다. 회전·좌우 반전을 자동 탐색하거나 재료 순서를 무시하는 Shapeless 제작은 이 함수에 없다. 내구도와 블록의 부가 상태도 매칭 기준에 포함하지 않는다.

현재는 제작법 목록을 순회하며 매번 잘라 비교하고 첫 일치를 사용한다. 정규화된 제작법을 미리 캐시하거나 입력 변경 시에만 검사하도록 최적화한 구조는 아니다.

## 결과 미리보기와 제작 확정 분리

매칭되면 결과 슬롯에 제작 결과를 표시하고, 일치한 원본 제작법을 보관한다. 이 시점에는 재료를 소비하지 않는다.

사용자가 결과를 가져갈 때 다음 처리를 수행한다.

1. 결과를 커서에 생성하거나, 같은 종류의 커서 스택에 추가 가능한지 확인한다.
2. 현재 제작 입력을 다시 Trim하면서 각 입력의 원본 슬롯 주소를 함께 보관한다.
3. 제작법의 요구 수량만큼 해당 원본 슬롯에서 차감한다.
4. 수량이 0이 된 슬롯은 `nullopt`로 만든다.

Trim 후 Index가 바뀌어도 원래 어느 슬롯을 소비해야 하는지 알 수 있도록 `pair<optional<ItemInfo>, void*>`의 두 번째 값에 슬롯 주소를 전달한다. 현재 소비 코드에서는 이를 원래 슬롯 포인터로 Cast한다. 외부 데이터를 가리키는 범용 Handle이 아니라 해당 호출에서 원본 배열을 연결하는 보조 정보다.

```text
입력 배치 → 패턴 매칭 → 결과 미리보기
                         ↓ 결과 수령
                  커서 결과 + 재료 차감
```

이 구조로 결과 확인만 했는데 재료가 사라지는 일을 피한다. 다만 결과 전달과 모든 재료 차감이 하나의 성공/실패 단위로 감싸져 있지는 않다. 현재 입력·캐시된 제작법이 계속 일치한다는 전제와 UI 생성 성공에 의존하는 부분은 유지보수 시 확인해야 한다.

## 상자·화로를 월드 좌표에 귀속

`CWorldManager`가 `CChestStorage`와 `CFurnaceStorage`를 소유한다. 각 저장소는 정수 블록 좌표 `XMINT3`를 키로 하는 Map을 사용한다.

`GetStorage(location)`은 해당 데이터가 없으면 빈 데이터를 생성하고 주소를 반환한다. 따라서 단순 조회처럼 보이지만 생성 효과도 있다. `DelStorage(location)`은 해당 좌표의 데이터를 지운다.

플레이어가 상자·화로를 우클릭하면 열린 블록 좌표를 기록하고 UI에서 해당 저장소를 조회한다. 창을 닫으면 열린 좌표 상태는 해제되지만 저장 데이터 자체를 삭제하지는 않는다. 다시 열면 같은 좌표의 내용과 화로 진행 상태를 읽는다.

저장소는 청크 메시 객체와 별개이므로 청크의 렌더 데이터 수명에 직접 종속되지 않는다. 반면 좌표만으로 귀속을 구분하므로, 다른 월드에서 같은 좌표를 재사용하거나 블록을 교체할 때는 저장소 초기화 정책이 필요하다. 여기서 저장은 메모리 보관이며 디스크 직렬화·재실행 복원을 구현했다는 뜻은 아니다.

## UI를 닫아도 진행되는 제련

`CWorldManager::Update()`가 `CFurnaceStorage::Update()`를 호출하고, 저장소는 등록된 모든 화로 데이터를 순회한다. UI가 열렸는지나 해당 청크가 로드되었는지를 이 함수에서 검사하지 않는다. 월드 갱신이 계속되는 동안 창을 닫아도 제련이 진행되는 이유다.

화로 데이터는 재료·연료·결과 슬롯과 제련 진행률, 남은 연료 비율, 연료 지속 시간을 가진다. UI는 이 값을 읽어 아이콘과 진행 막대를 표시한다.

### 제련 처리 순서

1. 재료와 제련법이 유효한지 확인한다.
2. 결과 슬롯이 비었거나 같은 결과를 64개 미만으로 담고 있는지 확인한다.
3. 남은 연료가 없으면 유효한 연료 한 개를 소비한다.
4. 연료 비율을 `Delta Time / 연료 지속 시간`만큼 줄인다.
5. 제련 진행률을 `Delta Time / 10초`만큼 늘린다.
6. 완료되면 재료 한 개를 소비하고 결과 한 개를 추가한다.

현재 활성 제련법은 원목 네 종류의 숯 변환, 철·금·구리 원석의 주괴 변환, 생소고기·생닭고기·생돼지고기·생양고기의 조리다. 광석 블록 직접 제련, 모래→유리 등의 주석 처리된 분기는 현재 기능에서 제외한다.

| 연료 | 한 개의 지속 시간 |
| --- | --- |
| 지정된 원목·판자 | 15초 |
| 석탄·숯 | 80초 |
| 막대기 | 5초 |

화면 클래스 이름은 `CUIBlastFurnace`지만 열 때 검사하는 블록은 `FURNACE`이며 음식과 목재도 처리한다. 이름만 보고 원작의 용광로 전용 정책을 구현했다고 설명하지 않는다.

### 현재 제련 시간 정책의 특징

재료가 없거나 제련 불가, 결과 슬롯의 타입 불일치·가득 참 등의 조건에서는 진행률을 0으로 만들고 해당 화로의 이번 갱신을 건너뛴다. 연료 감소보다 앞에서 건너뛰므로 이 상태에서는 남은 연료도 줄어들지 않는다. 한번 불이 붙으면 입력 상태와 관계없이 계속 타는 정책과 다르다.

완료 시 진행률을 0으로 되돌리고 한 개만 생산한다. 초과 시간을 보존해 여러 개를 처리하는 반복문이 없다. 연료가 프레임 도중 소진되어도 그 프레임의 전체 Delta Time을 진행률에 더하므로 큰 Delta Time에서는 연료량과 진행량이 정확히 대응하지 않을 수 있다.

유효한 재료를 다른 유효한 재료로 교체했을 때 진행률을 반드시 초기화하는 재료 식별 상태도 별도로 없다. 이 부분은 처리 시간의 정확성이 필요한 확장 시 확인할 대상이다.

또한 현재 화로 커서 처리는 재료·연료·결과를 일반 슬롯에 대응해 이동한다. 결과 슬롯에 넣지 못하게 하거나 연료 슬롯에서 미리 종류를 제한하는 전용 정책이 충분히 분리되어 있지 않다. 제련 함수가 잘못된 조합을 거르는 것과 UI 입력 자체를 금지하는 것은 다른 책임이다.

## 보관 블록이 파괴될 때

플레이어의 블록 파괴 경로는 `DestoryBlockAfterProcess()`를 호출한다. 화로라면 재료·연료·결과를, 상자라면 27칸 내용을 확인해 각 수량을 한 개씩 월드 드롭으로 만든다. 이후 해당 좌표의 저장 데이터를 삭제한다.

```text
보관 블록 파괴
  → 내용물 드롭
  → 좌표 저장소 삭제
  → 블록 자체의 드롭 변환·생성
```

원래 블록과 드롭 아이템의 차이는 `DestoryBlockItemConverter()`에서 처리한다. 예를 들어 돌은 조약돌로, 철광석은 일반 아이템인 철 원석으로 바꾼다. 획득한 원석을 화로에서 주괴로 만드는 흐름에 연결된다.

내용물 정리는 단순히 블록을 AIR로 바꿨다고 자동으로 실행되는 것이 아니다. 다른 파괴 경로도 같은 후처리를 호출해야 한다. 대량 내용물은 수량별 드롭 생성 비용이 생기며, 드롭 실패와 저장소 삭제 사이의 복구 절차도 별도 검증 대상이다.

## 결과와 한계 {/* #구조의-장점과-남은-경계 */}

플레이어 소유 데이터와 위치에 귀속되는 데이터를 나누고, 제작 결과 확인·소비와 UI 표시·제련 진행을 분리한 것이 핵심이다. 월드 블록에서 얻은 자원이 인벤토리와 제작·화로를 거쳐 다시 사용되는 흐름을 실제 상호작용으로 연결했다.

현재는 슬롯 이동 코드가 인벤토리·작업대·화로·상자별로 반복되고, 64 상한·분리·교환 정책도 여러 위치에 들어 있다. 재사용 가능한 슬롯 연산과 입력 검증을 분리하면 화면마다 생길 수 있는 규칙 차이를 줄일 수 있다. 커서 데이터의 UI 객체 의존성과 제작 확정의 실패 복구도 개선 후보이다.

검증 자료는 다음 사례가 적합하다.

- Hotbar·인벤토리 획득 우선순위, 빈칸과 기존 스택이 함께 있을 때의 결과.
- 수량 1·5·63·64에서 분리·합치기·교환, 합계가 정확히 64인 경우.
- 같은 제작 모양을 다른 위치에 배치하고 결과를 받기 전후의 재료 수량 비교.
- 작업대 3×3과 개인 2×2에서 가능한 제작법의 차이.
- 창을 닫은 화로의 진행, 결과 슬롯 포화·연료 부족·재료 교체.
- 내용물이 있는 상자·화로 파괴, 커서 아이템을 든 채 창 닫기.
- UI 생성 실패와 드롭 실패 상황에서 아이템 수량 보존.

이번 문서화는 소스 조사이며 새 실행 측정이나 경계 사례의 검증 완료를 뜻하지 않는다. 게임 코드와 리소스는 수정하지 않았다.
