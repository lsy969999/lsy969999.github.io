# 낮밤 주기와 절차적 하늘·구름 표현

## 배경과 목표 {/* #해결하려던-문제 */}

넓은 복셀 월드를 이동할 때 배경이 고정된 이미지처럼 보이지 않으려면 카메라 방향에 맞는 하늘과 시간에 따른 변화가 필요하다. 낮과 밤의 밝기, 해와 달의 위치, 별의 가시성, 구름 색상이 서로 다른 기준으로 움직이면 장면이 어색해진다.

이 프로젝트에서는 월드의 누적 시간에서 낮 계수와 하늘 회전각을 계산한다. 하늘은 화면을 덮는 삼각형에서 시선 방향을 복원해 그리며, 구름은 노이즈로 선택한 격자 위치에 큐브 메시를 인스턴싱한다.

하늘과 구름은 같은 낮 계수를 사용하지만 구현 방식은 다르다. 하늘은 화면 공간 셰이더, 구름은 월드 공간 메시다. 대기 산란이나 볼류메트릭 구름을 구현한 것이 아니라 마인크래프트의 각진 환경 표현에 맞춘 구성이다.

## 하나의 시간에서 여러 환경 값 만들기

`CWorldManager::Update()`는 전달받은 Delta Time을 `m_fElapsedTime`에 더한다. 한 주기의 길이는 600초이며, 누적 시간으로 낮 계수와 회전각을 각각 계산한다.

```text
WorldManager의 누적 시간
  ├─ DayFactor → 하늘 색·별 밝기·구름 색·복셀 조명
  └─ SkyRotation → 해·달 방향·별 회전·그림자 카메라
```

이는 현실 시계나 날짜를 읽는 기능이 아니다. 게임이 전달하는 Delta Time의 누적으로 진행하므로 시간 배율이나 업데이트 중단 정책의 영향을 받는다.

렌더러는 이 값을 프레임 상수 버퍼의 `g_fDayFactor`, `g_matSkyRotation`, `g_matStarRotation`으로 전달한다. 각 오브젝트가 별도의 낮밤 타이머를 갖는 대신 공통 값을 참조한다.

## 낮 계수와 하늘 회전각

낮 계수는 선형 시간 비율을 삼각파 형태로 바꾼 뒤 코사인을 적용한다.

```text
phase = fmod(elapsed, 600) / 600
pingPong = 1 - abs(phase - 0.5) × 2
dayFactor = 0.5 × (1 + cos(pingPong × π))
skyAngle = phase × 2π
```

| 누적 시간 예시 | DayFactor | SkyAngle | 의미 |
| --- | --- | --- | --- |
| 0초 | 1 | 0° | 가장 밝은 낮 |
| 150초 | 0.5 | 90° | 낮에서 밤으로 전환 |
| 300초 | 0 | 180° | 가장 어두운 밤 |
| 450초 | 0.5 | 270° | 밤에서 낮으로 전환 |
| 600초 | 1 | 0° | 다음 주기 |

밝기가 끝점에서 급하게 방향을 바꾸지 않도록 코사인 곡선을 사용한다. 반면 해와 달의 기준 회전각은 시간 비율에 비례해 증가한다.

현재 시작 누적값은 -120초다. 이때 `fmod()`의 결과도 음수이므로 코드 주석과 달리 phase가 항상 0~1인 것은 아니다. 현재 수식에서는 시작 DayFactor가 약 0.655, 회전각은 -72도이며 시간이 증가하면서 밝은 낮 쪽으로 진행한다. 새로운 시간 규칙을 추가한다면 음수 시간의 정규화 정책도 명시해야 한다.

WorldManager GUI는 DayFactor를 출력하고 누적 시간을 직접 조절할 수 있게 한다. 다만 입력 라벨은 `Quat`으로 되어 있어 실제로 수정하는 값이 회전 Quaternion이 아니라 시간이라는 점을 주의해야 한다.

## 하늘은 큐브맵이 아닌 Fullscreen Triangle

`CSkybox`라는 이름을 사용하지만 현재 구현은 거대한 큐브 메시나 Cubemap을 그리지 않는다. 정점 버퍼와 Input Layout을 비우고 `Draw(3, 0)`을 호출한다.

Vertex Shader는 `SV_VertexID`로 화면 전체를 덮는 큰 삼각형의 위치를 만든다. 이 방식에서는 카메라를 따라다닐 하늘 큐브를 배치할 필요가 없다.

```hlsl
float2 uv = float2((vertexID << 1) & 2, vertexID & 2);
float4 clipPosition = float4(
    uv * float2(2.0, -2.0) + float2(-1.0, 1.0),
    1.0, 1.0);
```

깊이는 `z = w`로 두어 Far Plane에 놓는다. `DS_Skybox`는 깊이 검사를 LESS_EQUAL로 수행하고 깊이 쓰기는 끈다. 월드 렌더링 이후 그리므로 이미 가까운 지형이 기록된 픽셀을 덮지 않고 배경 영역에 하늘을 채우는 구성이다.

## 화면 픽셀에서 시선 방향 복원

하늘색과 천체 위치를 계산하려면 해당 픽셀이 월드의 어느 방향을 보는지 알아야 한다. 셰이더는 클립 위치에 역 ViewProjection을 곱한 뒤 W로 나누고 카메라 위치를 뺀다.

```text
world = clipPosition × inverse(ViewProjection)
farPosition = world.xyz / world.w
viewDirection = normalize(farPosition - cameraPosition)
```

이 방향을 사용하면 하늘을 월드의 고정된 방위와 연결하면서도, 카메라가 이동할 때 가까운 오브젝트처럼 하늘이 시차를 만드는 것을 피할 수 있다.

현재는 Vertex Shader에서 복원한 방향을 Pixel Shader로 전달하고 픽셀에서 정규화한다. Perspective 카메라를 기준으로 쓰는 경로이며, 임의의 직교 카메라에서도 같은 식으로 원하는 하늘이 나오는지까지 검증한 범용 구현으로 설명하지 않는다.

## 낮·밤 그라데이션

하늘의 세로 색 변화는 시선 방향의 Y 성분으로 만든다. `height = max(0, dir.y)`를 사용해 지평선에서 천정 방향으로 색을 보간한다.

| 기준 색 | RGB |
| --- | --- |
| 낮 지평선 | (0.6, 0.7, 0.9) |
| 낮 천정 | (0.2, 0.4, 0.8) |
| 밤 지평선 | (0.05, 0.05, 0.1) |
| 밤 천정 | (0.02, 0.02, 0.05) |

낮 하늘과 밤 하늘을 각각 만든 뒤 DayFactor로 두 결과를 보간한다. 시선이 지평선 아래로 내려가면 height가 0이므로 같은 지평선 색을 사용한다.

태양 고도에 따른 산란이나 공기 밀도를 적분하는 방식은 아니다. 현재 셰이더에는 별도의 붉은 노을 곡선, 날씨별 대기 파라미터, 고도별 대기층 계산이 없다.

## 해와 달: 회전하는 방향 공간에 텍스처 투영

렌더러는 하늘 회전각으로 X축 회전 행렬을 만든다. 셰이더는 그 전치 행렬로 시선 방향을 하늘의 로컬 공간에 돌린다. 순수 회전 행렬이므로 전치를 역회전으로 사용할 수 있다.

로컬 방향의 Y가 양수인 쪽에는 해, 음수인 반대쪽에는 달을 배치한다. XZ 성분을 Y의 크기로 나눠 평면 UV를 만들고, 각 축 절댓값이 0.05 안에 들어오는 사각 범위에서 텍스처를 읽는다.

태양은 `Texture/Env/sun.png`, 달은 `Texture/Env/Moon/full_moon.png`를 로드해 32×32 Texture Array의 0·1번 Slice로 사용한다. 달의 위상을 날짜별로 바꾸는 구조는 아니다.

태양 영역은 샘플링한 RGB로 기존 하늘색을 대체한다. 달은 RGB에 `1 - DayFactor`를 곱해 밤에 밝아지게 한다. 현재 경로는 텍스처 Alpha로 하늘과 합성하지 않으므로 텍스처 사각 영역의 RGB 자체가 중요하다.

달을 샘플링하는 동일한 조건 블록이 셰이더에 두 번 남아 있다. 두 번째가 같은 결과를 다시 대입하므로 서로 다른 두 달을 의도적으로 그리는 기능은 아니다. 정리 대상과 표현 기능을 구분했다.

## 별: 방향 격자와 해시로 생성

별은 별도 메시나 별 텍스처가 아니라 셰이더의 Hash 함수로 만든다. DayFactor가 0.5 미만일 때만 별 계산을 수행한다.

1. 시선 방향을 별의 로컬 회전 공간으로 변환한다.
2. 방향에 120을 곱하고 `floor()`로 3차원 격자 셀을 구한다.
3. 셀 좌표의 Hash가 0.98보다 큰 경우만 별 후보로 삼는다.
4. 셀 중심과의 거리가 0.3 이하이면 흰색 별 마스크를 만든다.
5. `1 - DayFactor × 2`를 곱해 밤이 깊어질수록 밝게 더한다.

격자 좌표에서 같은 해시를 얻으므로 프레임마다 새 난수를 뽑아 별 위치가 바뀌는 방식이 아니다. 0.98이라는 임계값이 화면 픽셀의 정확한 2%가 별이라는 의미도 아니다. 후보 선택 뒤 셀 중심 거리와 시선 방향 조건이 추가된다.

별 회전각은 하늘 회전각의 -0.1배다. 해·달보다 천천히 반대 방향으로 움직이지만, 원본 회전각이 한 주기마다 0으로 돌아오므로 별 회전도 매 주기 독립적으로 계속 누적되는 것은 아니다. 이 경계는 별이 보이지 않는 낮 부근에 있어 값의 불연속과 실제 보이는 깜빡임을 동일시하지는 않았다.

## 구름: 노이즈로 선택하는 월드 격자

구름은 하늘 셰이더와 별개인 `CCloud` GameObject다. 활성 카메라의 XZ를 4단위 격자로 변환하고 주변 128×128개, 총 16,384개 후보 위치를 검사한다.

선택된 위치에는 크기 4×1.5×4의 큐브를 Y = 120에 배치한다. 구름 전용 VIBuffer는 한 변 길이 1인 큐브이며, 인스턴스 행렬이 실제 크기와 위치를 만든다.

노이즈는 FastNoiseLite의 Perlin·FBm을 사용한다. CLOUD 타입 설정은 기본 Seed + 35, Frequency 0.05, Octaves 3이다. 노이즈 라이브러리 자체를 직접 구현한 것은 아니며, 출력값을 구름 배치에 사용하는 규칙을 구성했다.

```text
sampleX = gridX × 0.35 + cloudOffset × 0.005
sampleZ = gridZ × 0.35
occupied = noise(sampleX, 0, sampleZ) > 0.1
position = (gridX × 4, 120, gridZ × 4)
```

이렇게 하면 독립적인 랜덤 큐브보다 이웃 셀끼리 연결된 덩어리를 만들 수 있다. 월드 좌표에서 검사하기 때문에 카메라가 이동해도 겹치는 격자 영역은 같은 시점의 노이즈 조건을 공유한다.

단, 구름은 실제 로드된 복셀 청크에 저장되는 블록이 아니다. 카메라 주변의 임시 환경 표현이며 청크 저장·편집과 별도로 재계산한다.

## 구름이 흐르는 방식

`cloudOffset`은 매 Update에서 `2 × dt`만큼 증가한다. 그러나 이 값을 인스턴스의 Translation에 더하지는 않는다. 노이즈의 X 샘플 좌표에만 반영한다.

따라서 현재 구름은 큐브 전체가 연속적으로 X축 이동하는 것이 아니라, 시간에 따라 격자의 점유 조건이 바뀌며 덩어리가 흐르는 것처럼 보이는 방식이다. 큐브 위치는 4단위 격자에 고정되어 있고 생성·제거되는 셀이 달라진다.

`m_fCloudSpeed = 2`를 월드 이동 속도 2라고 설명하면 부정확하다. 최종 변화량에는 샘플 오프셋 배율, 격자 배율, 노이즈 Frequency, 재계산 주기가 함께 영향을 준다.

## 비동기 계산과 결과 반영

구름 배치 계산은 목표 0.2초 타이머로 요청한다. 요청 시 카메라 위치, 오프셋, 버퍼 용량, 기존 결과 크기, 오브젝트 Handle을 값으로 캡처해 Worker에 넘긴다.

Worker는 후보 격자를 검사하고 인스턴스 행렬 벡터를 반환한다. 주 스레드는 Future에 `wait_for(0)`을 사용해 준비 여부를 확인하고, 완료된 결과만 `m_InstanceData`로 교체한다. D3D 버퍼 Map과 Draw는 Render에서 수행한다.

이 분리는 CPU의 노이즈·배치 계산을 렌더링의 GPU 자원 갱신과 나누는 데 의미가 있다. 작업이 끝날 때까지 주 스레드에서 무조건 대기하는 방식은 아니다.

다만 Handle을 캡처했다고 전체 경로가 자동으로 스레드 안전해지는 것은 아니다. Worker는 오브젝트 매니저에서 Handle을 조회하고 공용 노이즈 참조도 가져온다. 매니저 조회·월드 종료·노이즈 설정 변경의 동기화 계약은 별도 점검이 필요하다. 현재 Worker는 조회한 오브젝트 포인터로 멤버를 계속 수정하지 않고 캡처한 값으로 결과를 만든다.

### 작업 중 조기 반환의 주의점

현재 코드는 0.2초 타이머가 완료된 순간 이미 유효한 Future가 있으면 LateUpdate에서 즉시 반환한다. 이 반환은 아래에 있는 결과 수거와 렌더 등록까지 건너뛴다.

렌더러가 프레임마다 등록 목록을 비우는 구조이므로, 해당 조건에서는 기존 구름 결과가 있어도 그 프레임에 렌더 등록을 놓칠 수 있다. 준비 여부를 아직 확인하지 않은 완료 Future도 `valid()`일 수 있다. 따라서 이 부분을 단순한 중복 작업 방지로만 설명하지 않고 깜빡임 재현 후보로 구분했다.

새 작업 요청을 생략하는 것과 기존 결과를 계속 그리는 것은 분리해야 한다. 이번 문서화에서는 이를 수정하지 않았다.

## GPU 인스턴싱과 색상

초기화에서는 인스턴스 20,000개 분량의 동적 정점 버퍼를 만든다. 헤더의 초기 멤버값 16,384보다 Initialize에서 대입한 20,000이 실제 할당 기준이다.

격자 순회 중 결과 개수가 용량에 도달하면 반복문을 종료하는 가드도 있다. 현재는 후보 자체가 최대 16,384개이므로 모든 셀이 선택되어도 20,000개를 넘지 않는다.

Render에서는 월드 행렬 배열을 `WRITE_DISCARD`로 업로드하고 공통 큐브 메시와 함께 `DrawIndexedInstanced()`로 그린다. 인스턴스 하나는 64바이트 행렬이며 현재 후보 상한을 모두 그릴 때 행렬 데이터만 약 1 MiB다. 이는 실제 프레임 비용의 측정값이 아니다.

구름은 DEFAULT·SHADOW 양쪽에 참여한다. 따라서 낮에 두 패스에서 Render가 호출되면 같은 행렬 배열도 각 호출에서 다시 업로드한다. 배치를 0.2초마다 계산하더라도 GPU 업로드와 Draw가 0.2초마다만 수행되는 것은 아니다.

일반 구름 셰이더는 낮에는 흰색, 밤에는 `(0.1, 0.12, 0.2)`로 보간한다. 큐브 로컬 Y가 -0.4보다 낮은 아랫면은 낮 기본 색을 0.75배로 낮춰 입체감을 준다. 실제 광원 방향과 Normal을 비교한 조명 계산은 아니다.

출력 Alpha는 0.8이지만 CCloud는 NONBLEND에 등록되며 이 Render 함수에서 Alpha Blend 상태를 명시적으로 켜지 않는다. 셰이더가 Alpha를 출력한다는 사실만으로 20% 투과되는 구름을 보장할 수는 없다.

그림자는 큐브 형상의 깊이를 기록하는 방식이다. 구름 밀도에 따른 빛 투과가 아니라는 점과 패스 구성은 [Shadow Map 문서](/projects/minecraft/shadow-map-render-passes)에서 설명한다.

## 구현 결과와 한계

이 구조는 공통 월드 시간을 하늘색·천체·별·구름색·그림자에 연결하고, 화면 기반 배경과 월드 기반 구름을 분리한 환경 표현이다. 별은 셰이더에서 생성하고 구름 배치는 Worker에서 계산한 뒤 인스턴싱으로 그린다.

반면 현재 범위는 다음과 구분해야 한다.

- 대기 산란, 날씨 전환, 달 위상, 실제 천체 좌표 계산은 아니다.
- 구름은 고정 높이의 격자 큐브이며 Ray Marching 기반 볼류메트릭이 아니다.
- 구름의 인접 큐브 사이 내부 면을 제거하는 Greedy Meshing은 없다.
- 카메라 주변 사각 후보 범위를 사용하며 확인한 구름 Render에는 인스턴스별 Frustum·Occlusion 컬링이 없다.
- 결과 교체는 이전·새 결과 간 보간 없이 벡터 단위로 수행한다.
- 활성 카메라 조회의 null 검사나 작업 예외·종료 상황의 전체 안전성을 이 경로만으로 보장하지 않는다.

개선한다면 먼저 작업 중 렌더 유지, Future 수거와 요청의 분리, 종료 시 작업 수명 계약을 정리하는 것이 우선이다. 이후 결과 변경 시에만 업로드하기, 위치 이동과 노이즈 변형을 분리하기, 격자 갱신 범위 축소나 내부 면 제거를 검토할 수 있다.

## 시연과 검증 항목

- GUI로 월드 시간을 바꾸며 낮·전환·밤의 하늘색과 구름색 비교.
- 카메라 위치 이동과 방향 회전에서 하늘의 시차·천체 방향 확인.
- 해와 달의 반대 방향 배치, 태양 텍스처 사각 경계 확인.
- 별의 위치 재현과 DayFactor 0.5 부근의 등장·소멸 확인.
- 구름을 가까이서 보며 연속 이동과 격자 점유 변화의 차이 확인.
- Worker 지연을 유도해 기존 구름 유지와 렌더 등록 누락 확인.
- 구름 계산 시간, 메인 스레드 결과 반영, 패스별 업로드·Draw 비용 분리 측정.
- 레벨 종료나 카메라 교체 중 비동기 구름 작업의 안전성 확인.

이번 작업은 소스 기반 문서화이며 실행 시연이나 성능 측정을 수행하지 않았다. 게임 코드와 리소스도 변경하지 않았다.
