# Minecraft 프로젝트 개요와 기술 문서 안내

## 개요 {/* #article-introduction */}

C++20과 DirectX 11 기반 자체 엔진으로 Minecraft의 복셀 월드와 생존 플레이를 구현한 개인 프로젝트다. 지형을 화면에 표시하는 데서 끝내지 않고, 플레이어가 블록을 변경했을 때 조명·유체·충돌·게임플레이가 함께 반응하도록 연결했다.

| 항목 | 내용 |
| --- | --- |
| 개발 기간 | 2026.04.26 – 2026.06.26 |
| 개발 인원 | 1명 · 임성윤 |
| 실행 환경 | Windows x64 |
| 주요 기술 | C++20, DirectX 11, HLSL |
| 구현 범위 | Framework, Voxel World, Rendering, Gameplay, UI/Tool |

이 문서는 전체 구조를 안내한다. 세부 알고리즘과 코드 경계는 아래 13개 기술 문서에서 설명한다. 구현 범위는 코드와 저장소 README를 기준으로 하며, 원작 리소스의 제작 기여와 게임 시스템 구현 기여는 구분한다.

## 추천 문서 {/* #먼저-읽을-핵심-문서 */}

처음에는 다음 네 문서로 계산 구조와 플레이까지 이어지는 흐름을 확인할 수 있다.

1. [비동기 청크 스트리밍](/projects/minecraft/async-chunk-streaming): 많은 블록을 언제 계산하고, 언제 GPU에 반영하는가.
2. [복셀 메시 생성과 렌더링](/projects/minecraft/voxel-meshing-rendering): 블록 배열에서 실제로 그릴 면과 정점을 어떻게 추리는가.
3. [DDA 블록 선택과 편집](/projects/minecraft/dda-block-editing): 플레이어 입력을 월드 변경과 주변 청크 갱신에 어떻게 연결하는가.
4. [하늘광·블록광 전파](/projects/minecraft/voxel-light-propagation): 설치·파괴로 달라진 공간에 빛을 어떻게 제거하고 다시 전파하는가.

렌더링에 관심이 있다면 메시 문서 다음에 [Shadow Map과 렌더 패스](/projects/minecraft/shadow-map-render-passes)를, 게임플레이에 관심이 있다면 편집 문서 다음에 [인벤토리·제작·제련](/projects/minecraft/inventory-crafting-storage)을 읽는 순서가 좋다.

## 시스템이 연결되는 방식

핵심 데이터는 청크가 소유한 블록 배열이다. 블록마다 별도의 GameObject와 Draw 호출을 만드는 대신 청크 단위 메시로 화면을 구성하고, 플레이어·몬스터·투사체는 별도 객체 로직으로 월드와 상호작용한다.

```text
카메라 주변 청크 요청
  → Worker: 지형 생성 → 초기 조명 → CPU 메시
  → Future 완료 확인 → 메인 스레드 GPU 버퍼 생성 → 렌더링

입력·폭발·유체에 의한 블록 변경
  → 편집 대기 값과 조명·유체 갱신
  → 적용 가능한 청크와 이웃 확인 → 배열 반영·재메시
  → 갱신된 GPU 버퍼로 화면 반영
```

이는 주요 책임을 요약한 흐름이며, 모든 조명·게임플레이 로직이 Worker에서 실행된다는 뜻은 아니다. 초기 청크 조명과 런타임 편집 조명은 실행 경로가 다르다. 조회는 편집 대기 값을 먼저 읽을 수 있지만 화면은 이전 버퍼를 사용할 수 있어 논리 변경과 렌더링 반영 시점도 구분된다.

## 비슷해 보이는 설명의 구분

청크·편집·조명 문서에 같은 함수가 등장하는 것은 하나의 월드 변경 흐름을 서로 다른 관점에서 보기 때문이다. 공통 API의 상세는 담당 문서를 기준으로 읽으면 된다.

| 연결 지점 | 상세 설명의 기준 |
| --- | --- |
| Worker 예약과 GPU 반영 | 01은 작업 생명주기, 05는 편집으로 작업이 다시 예약되는 조건 |
| EditShadow | 05는 저장·우선 조회·적용, 03은 전파 중 직전 밝기를 읽는 이유 |
| 조명 | 03은 복셀 밝기 데이터, 11은 깊이 기반 가림, 12는 시간에 따른 표시 계수 |
| 엔티티 | 08은 월드 위치와 충돌, 09는 그 위치에서 표시할 본 자세 |
| 폭발 | 10은 피해·월드 변경, 13은 발생한 효과의 시뮬레이션과 렌더링 |

독립적으로 읽는 데 필요한 짧은 배경 설명은 유지하고, 동일한 알고리즘을 다른 문서에서 다시 길게 설명하지 않는 방식으로 구성했다.

## Hogwarts Legacy와 공유하는 프레임워크 기반

Generation Handle과 Manager 소유권, Slot 재사용, FrameEnd 파괴는 Minecraft에도 구현되어 있다. Handle 조회 시 Index 범위·Slot 점유·Generation을 검증하고, Slot을 Reset할 때 Generation을 증가시키는 기본 원리는 두 프로젝트에서 같다.

따라서 이 원리를 Minecraft의 별도 기술 문서로 반복하지 않는다. 상세 설명은 [Hogwarts Legacy의 Generation Handle 기반 Object Manager](/projects/hogwarts-legacy/handle-object-manager)로 연결하되, 해당 문서의 후속 보강까지 Minecraft에 적용된 것으로 읽어서는 안 된다.

| 항목 | Minecraft에서 확인한 구현 | Hogwarts Legacy에서 확인한 구현 |
| --- | --- | --- |
| Handle 표현 | `size_t` Index와 `uint32_t` Generation | 두 `uint32_t` 필드와 8바이트 크기 검증 |
| 일반 파괴 처리 | FrameEnd에서 객체 트리를 역순 순회하며 PendingDestroy 검사 | 파괴 요청 Handle Queue와 현재 처리 Queue 분리 |
| 객체 등록 | Handle을 먼저 할당하고 Clone 완료 후 Slot·Layer에 저장 | Slot·Layer 등록 후 `OnRegisteredToManager()` 호출 |
| 운영 API | `AllReset()`, `DelLayer()`와 기본 Update 단계 | Layer 선택·제외 Reset, Managed Update, 단계별 Update View |

Minecraft에서 초기화 전에 Handle 값을 받는 것과 Manager를 통해 해당 객체를 조회할 수 있는 시점은 다르다. Clone 도중에는 Slot에 객체가 아직 저장되지 않는다. Hogwarts의 등록 완료 훅은 이 경계를 명시적으로 제공하는 차이다.

또한 Minecraft의 `AllReset()`과 `DelLayer()`는 내부에서 `FrameEnd()`를 직접 호출한다. 일반 Update 중 PendingDestroy 처리와 별개이므로, 모든 경로의 실제 파괴가 반드시 메인 루프 마지막에만 일어난다고 일반화하지 않는다.

이 비교는 각 저장소의 `Engine/Public/Handle.h`, `Slot.h`, `GameObjectManager.h` 및 `Engine/Private/GameObjectManager.cpp`를 기준으로 한다. 공통 기반은 여기서 짧게 설명하고, Minecraft 기술 문서는 복셀 월드처럼 프로젝트 고유의 문제에 집중한다.

## 구현 범위를 읽을 때의 기준

- 현재 월드는 `CVoxelManager3`·`CChunk3` 경로다. 이전 VoxelManager 버전이나 별도 Greedy 테스트를 현재 기능과 합쳐 설명하지 않는다.
- 메시 생성은 노출 면 컬링 기반이다. 인접 면을 병합하는 Greedy Meshing을 적용했다고 주장하지 않는다.
- 편집 기록의 메모리 보관과 청크 재생성 시 복원은 디스크 세이브·로드와 다르다.
- 비동기 작업과 상태 검사는 구현되어 있지만, 모든 공유 데이터 접근의 동시성 안전성을 입증한 것으로 설명하지 않는다.
- 비용 계산 예시와 실제 성능 측정 결과를 구분한다. FPS 향상률이나 최악 프레임 시간은 별도 측정 없이 기재하지 않는다.

## 검증 계획 {/* #시연-자료로-보강할-부분 */}

문서가 구현 설명에만 머물지 않도록 다음 장면을 영상·캡처로 보강할 수 있다. 아래는 수집할 자료이며 이미 검증을 완료했다는 목록은 아니다.

1. 카메라 이동 중 청크 생성과 Worker 상태를 함께 보여 주는 장면.
2. 청크 경계의 블록을 설치·파괴해 면과 조명이 바뀌는 장면.
3. 물·용암의 확산 및 공급원 제거, TNT에 의한 지형 변경 장면.
4. 제작·제련과 전투가 같은 월드에서 작동하는 짧은 플레이 장면.
5. 낮밤·그림자·구름과 파티클 표현을 비교할 수 있는 고정 시점 장면.

프로파일링 자료를 추가할 때는 실행 환경, 로드 범위, 카메라 이동 경로와 측정 조건도 함께 남겨야 재현 가능한 설명이 된다.

## 작성 근거와 확인 범위 {/* #소스-기준 */}

프로젝트 정보는 저장소 `README.md`, 청크 실행 경로는 `Engine/Private/GameInstance.cpp`와 `VoxelManager3.cpp`를 기준으로 확인했다. 기능별 파일과 함수는 각 기술 문서의 구현 근거에서 확인할 수 있다. Hogwarts Legacy의 후속 엔진 개선을 이 프로젝트에서 이미 구현한 것으로 소급하지 않는다.
