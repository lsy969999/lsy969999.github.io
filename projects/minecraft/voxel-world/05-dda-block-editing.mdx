# DDA 블록 선택과 설치·파괴 후 청크 갱신

## 배경과 목표 {/* #해결하려던-문제 */}

복셀 월드의 상호작용은 바라보는 블록을 찾는 것으로 끝나지 않는다. 어떤 면을 맞혔는지 알아야 그 옆에 블록을 설치할 수 있고, 파괴하면 숨겨져 있던 이웃 면과 주변 밝기를 다시 계산해야 한다. 청크 경계에서는 옆 청크의 메시에도 영향이 생긴다.

`CVoxelManager3`에서 DDA 기반 블록 선택, 편집 대기 데이터, 인접 청크 재메시 예약을 연결했다. 블록마다 GameObject나 Collider를 만들고 전부 Ray 검사하는 방식이 아니라, 월드의 격자 자료구조를 직접 조회한다.

[절차적 지형 생성](/projects/minecraft/procedural-terrain-generation)이 최초 블록 구성을 만든다면, 이 문서는 플레이 중 그 구성을 바꾸는 경로를 다룬다. [조명 전파](/projects/minecraft/voxel-light-propagation)와 [메시 생성](/projects/minecraft/voxel-meshing-rendering)의 세부 알고리즘은 별도 문서로 연결한다.

블록 편집이 주변 물·용암을 깨우고 흐름을 바꾸는 과정은 [Tick 기반 유체 확산](/projects/minecraft/fluid-tick-simulation)에서 이어서 다룬다.

파괴한 블록의 획득과 작업대·상자·화로 상호작용은 [인벤토리·제작·좌표 기반 보관함](/projects/minecraft/inventory-crafting-storage)에서 설명한다.

Ray로 대상을 고르는 판정과 몸통의 지형 충돌은 다르다. 이동용 격자 검사는 [복셀 AABB와 엔티티 이동](/projects/minecraft/voxel-entity-movement)에서 다룬다.

## 카메라 Ray와 선택 범위

플레이어의 설치·파괴는 카메라의 `GetRay()`로 방향을 얻고 최대 거리 5로 `BlockRaycast()`를 호출한다. FPS에서는 카메라 Ray의 원점을 사용하며, 다른 카메라 모드에서는 플레이어 위치에 Y=1.8을 더한 위치를 원점으로 사용한다. 방향은 카메라 Ray의 방향을 유지한다.

이는 3인칭 카메라가 뒤로 떨어져 있어도 상호작용 거리는 플레이어 부근에서 계산하려는 구성이다. 다만 화면에서 보이는 위치와 플레이어 원점에서의 차폐 관계가 언제나 일치한다는 보장은 없으므로, 벽 근처의 3인칭 선택은 별도로 확인할 사례다.

API는 정규화된 방향을 받는 계약이다. 함수 내부에서는 정규화하지 않으므로 호출자가 이를 지켜야 반환 매개변수 T를 월드 거리로 해석할 수 있다.

## DDA: Ray가 지나는 격자만 순서대로 방문

Ray는 `P(t) = Origin + Direction × t`로 표현한다. 시작 블록 좌표는 원점 각 성분에 `floor()`를 적용해 구한다.

각 축에는 다음 값을 준비한다.

| 값 | 의미 |
| --- | --- |
| Step | 방향 부호에 따른 다음 칸 이동량, +1 또는 -1 |
| tMax | 그 축의 다음 격자 경계까지 도달하는 T |
| tDelta | 같은 축으로 한 칸 더 이동할 때 증가하는 T |

방향 성분이 0인 축은 tMax·tDelta를 `FLT_MAX`로 두어 일반적인 유한 거리 순회에서 선택되지 않게 한다. 나머지 축의 tDelta는 `abs(1 / direction)`이다.

현재 칸을 검사한 뒤 tMax가 가장 작은 축으로 한 칸 이동하고, 해당 축의 tMax에 tDelta를 더한다. 현재 T가 최대 거리를 초과하면 종료한다.

```text
현재 칸 검사
  → 다음 X·Y·Z 경계 중 가장 가까운 경계 선택
  → 해당 축으로 한 칸 이동
  → 대상 발견 또는 거리 초과까지 반복
```

고정된 작은 거리만큼 Ray를 샘플링하는 방식과 달리 격자 경계를 기준으로 이동한다. 전체 청크의 모든 블록을 순회하지 않으며, 비용은 주로 Ray가 방문한 칸 수와 각 칸의 조회·AABB 검사에 따라 증가한다. 실제 실행 시간을 측정한 성능 수치는 이번 문서에 포함하지 않는다.

현재 비교는 한 번에 한 축만 선택한다. 모서리·꼭짓점에서 여러 축의 tMax가 같을 때 모든 접촉 칸을 열거하는 Supercover 구현은 아니며, 동률 처리 정책은 경계 테스트 대상이다.

## 음수 월드 좌표를 청크 좌표로 변환

월드 블록 좌표를 청크와 로컬 좌표로 나눌 때는 `FloorDiv()`를 사용한다. C++ 정수 나눗셈의 0 방향 절삭만 사용하면 음수 좌표에서 잘못된 청크를 찾을 수 있기 때문이다.

가로 32칸 청크의 예시는 다음과 같다.

| 월드 X | 청크 X | 로컬 X |
| --- | --- | --- |
| -33 | -2 | 31 |
| -32 | -1 | 0 |
| -1 | -1 | 31 |
| 0 | 0 | 0 |
| 32 | 1 | 0 |

로컬 좌표는 `world - chunk × size`로 구한다. X·Z는 32, Y는 256 크기를 사용한다. 선택 조회와 편집 기록 모두 같은 좌표 변환을 사용하는 것이 중요하다.

## 격자 후보를 블록 AABB로 다시 검사

로드된 청크의 블록 중 AIR와 `IsWater()` 분류를 제외하고 세부 교차 검사를 수행한다. 이 함수의 `IsWater()`에는 물뿐 아니라 용암의 정지·흐름·Placeholder 타입도 포함되므로 현재 선택 Ray는 용암도 통과한다. 청크를 찾지 못한 칸 역시 순회를 중단하지 않고 건너뛴다.

격자에 들어왔다고 곧바로 맞았다고 반환하지는 않는다. `GetOutlineExtents()`의 중심 Offset과 Half Extents로 월드 AABB를 만들고, Ray와 각 축 구간의 교집합을 구하는 Slab 검사를 수행한다. 작은 AABB를 빗나갔다면 다음 격자로 진행한다.

현재 크기 예외는 횃불 하나다.

| 대상 | 중심 Offset | Half Extents |
| --- | --- | --- |
| 횃불 | (0, -0.1, 0) | (0.2, 0.4, 0.2) |
| 나머지 타입 | (0, 0, 0) | (0.5, 0.5, 0.5) |

반블록·계단의 빈 공간이나 꽃 텍스처의 투명 부분까지 정확히 검사하는 것은 아니다. 현재는 이들도 기본 한 칸 AABB를 사용한다. 렌더 메시의 Triangle 검사나 Alpha 기반 픽셀 선택과 구분해야 한다.

Slab 검사는 가장 늦게 진입하는 축의 면을 Hit Face로 반환한다. 최종 결과는 DDA에서 마지막으로 넘어온 격자 면이 아니라 이 AABB 교차 면을 사용한다.

`BLOCK_RAY_RESULT`에는 월드 블록 좌표, 청크 좌표, 청크 내부 좌표, 블록 값의 복사본, Hit Face, 거리 T가 들어간다. 충돌한 오브젝트 포인터를 오래 보관하는 방식은 아니지만, 블록 값은 조회 순간의 값이므로 이후 편집 시 최신 데이터 확인은 별도 책임이다.

원점이 AABB 내부에 있으면 현재 Slab 구현은 음수인 진입 T를 반환할 수 있다. 영벡터·비정상 입력을 차단하는 별도 검증도 없다. 따라서 내부 시작 Ray를 일반적인 바깥쪽 선택과 동일하게 안전하다고 설명하지 않는다.

## 선택 결과를 플레이어 동작으로 연결

### 설치와 상호작용

우클릭은 먼저 맞힌 블록의 기능을 확인한다. 작업대·화로·상자는 관련 UI를 열고, TNT는 부싯돌과 부시를 든 경우 활성 TNT 처리로 분기한다.

일반 블록 설치는 맞힌 블록 좌표에 Hit Face 방향의 한 칸 Offset을 더한다. 예를 들어 +Y 면이면 바로 위 칸, -X 면이면 왼쪽 칸이 설치 대상이다. 선택 블록을 없애는 파괴와 달리 설치는 이 인접 좌표를 변경한다.

Hotbar의 블록 값을 `ProcessPlayerBlockSet()`에 전달하고 수량을 감소시킨다. 현재 이 경로에는 설치 성공 여부를 돌려받는 결과값이 없고, Manager 함수도 `void`다. 대상 조회 실패로 Manager가 반환해도 호출자는 성공과 구분할 수 없다. 설치 가능 공간·플레이어 겹침·아이템 소비를 하나의 검증된 트랜잭션으로 묶은 구조는 아니므로 확장 시 주의해야 한다.

### 파괴 진행과 시각 피드백

좌클릭 유지 중에는 블록 좌표와 타입으로 파괴 대상을 비교한다. 대상이 바뀌면 진행 시작 상태를 초기화하고, 동일 대상이면 시간을 누적한다.

기본 파괴 목표 시간은 1초다. 일부 돌·광물에 다이아몬드 곡괭이, 흙·잔디에 삽, 지정된 목재에 도끼를 사용하면 배율 0.1을 적용한다. 모든 블록의 경도·도구 효과를 데이터로 일반화한 체계는 아니며 코드에 지정한 조합이다. 즉시 파괴 타입은 시간 진행을 건너뛴다.

진행 시간은 균열 Frame Index 0~9로 바꾸고, Setter에서 Clamp한다. 마지막 단계 또는 즉시 파괴 조건에서 해당 칸을 AIR로 바꾼다. 파편 파티클, 재질별 소리, 드롭 아이템 변환·생성도 연결된다. 파괴 진행 시간은 현재 함수의 Static Local 값이므로 여러 플레이어 인스턴스의 독립 상태로 설계된 것은 아니다.

선택 외곽선과 균열은 같은 `GetOutlineExtents()`를 활용한다. 외곽선은 별도로 Ray를 검사하고, 해당 청크에 편집 대기 데이터나 메시·버퍼 작업이 있으면 렌더링을 건너뛴다. 편집 도중 잠시 외곽선이 보이지 않는 것은 이 조건과도 관계가 있다.

## SetBlock과 플레이어 편집 API의 책임 구분

| 함수 | 책임 |
| --- | --- |
| `BlockRaycast()` | 조회만 수행하고 선택 결과 반환 |
| `SetBlock()` | 편집 대기 값 저장, 선택적으로 편집 기록 보관 |
| `ProcessPlayerBlockSet()` | 이전 블록 조회 후 변경·조명·물/용암 갱신·소리 연결 |
| `UpdateCheckBlockEdit()` | 적용할 편집과 재메시 대상을 정리 |

`ProcessPlayerBlockSet()`은 이전 블록을 먼저 복사해 두고 AIR 변경과 배치를 분리한다. 파괴는 AIR 기록 후 주변 유체와 제거 조명을 갱신한다. 배치는 물·용암 원천의 Flag와 Tick 요청을 준비하고, 주변 유체 갱신 요청·변경 기록·설치 조명 처리를 이어간다.

조명 함수는 이전 블록과 새 상태를 비교해 빛을 제거하거나 재전파한다. 구체적인 규칙은 [런타임 조명 갱신](/projects/minecraft/voxel-light-propagation)에서 다룬다. `SetBlock()`만 직접 호출하면 이 게임플레이 후처리가 모두 자동 실행되는 것은 아니다.

## 편집 대기 데이터로 즉시 조회와 지연 반영 분리

`SetBlock()`은 바로 청크 배열을 수정하지 않고 다음 형태의 `m_EditShadow`에 값을 저장한다.

```text
청크 ID → 블록 Index → 최신 CBlock3 값
```

같은 칸을 다시 수정하면 대기 값은 마지막 값으로 덮어쓴다. 호출 이력을 모두 저장하는 이벤트 큐나 Undo 기록은 아니다.

`GetBlockByChunkCoord()`는 EditShadow를 먼저 읽고, 없으면 실제 청크 배열을 읽는다. 따라서 메시 작업을 기다리는 동안에도 조회 경로에서는 새 블록 값을 볼 수 있다. 렌더링은 아직 이전 GPU 버퍼를 사용할 수 있어 논리 상태와 화면 반영 시점은 분리된다.

`bRecord=true`이면 별도의 `m_mapEditedBlock`에도 기록한다. EditShadow는 적용 후 지우는 임시 변경이고, 편집 기록은 청크 재생성 시 다시 덮어쓸 데이터다. 기록 쓰기에는 Mutex가 있지만 EditShadow 전체에 동일한 Lock이 적용된 것은 아니므로 임의 Worker에서 자유롭게 호출해도 안전한 API라고 볼 수는 없다.

## 변경 위치에 따라 주변 청크 재메시

내부 블록을 바꾸면 자기 청크의 면 노출·AO·조명을 다시 메시로 표현해야 한다. 경계 블록은 옆 청크에서 가려졌던 면을 드러낼 수 있고, 모서리는 대각 청크의 AO 샘플에도 영향을 줄 수 있다.

현재 `UpdateCheckBlockEdit()`은 청크별 편집 Index를 복원해 X·Z가 0 또는 31인지 검사하고 방향 플래그를 모은다. 단일 편집의 기본 분기는 다음과 같다.

| 변경 위치 | 기본 재메시 후보 |
| --- | --- |
| 청크 내부 | 자기 청크 |
| X 또는 Z 한쪽 경계 | 자기 청크 + 해당 이웃 |
| XZ 모서리 | 자기 청크 + 축 방향 이웃 2개 + 대각 이웃 |

로드되지 않은 이웃은 후보에 넣지 않는다. 현재 수직 기둥 월드에 맞춘 XZ 분기이며 Y 방향 이웃까지 일반화되어 있지는 않다. 조명 전파가 다른 청크의 블록 값도 바꾸면 그 변경도 편집 데이터로 들어와 추가 재메시 대상이 될 수 있다.

자기 청크에 메시 예약이 있으면 이번 적용을 미루며, 후보 이웃이 조명 처리 중이거나 메시 예약 중일 때도 해당 편집 묶음을 보류한다. 선택한 청크 ID는 Set으로 중복을 제거해 한 검사 호출 안의 중복 예약을 줄인다.

### 여러 경계를 동시에 편집하는 경우의 한계

현재 방향 분기는 독립적인 모든 방향의 합집합이 아니라 `if / else if` 체인이다. 예를 들어 한 청크의 +X와 -X 경계를 같은 검사 전에 모두 수정하면 두 플래그가 켜져도 앞의 +X 분기만 선택될 수 있다.

또한 이웃으로 선택된 청크에 별도의 편집 대기 값이 있으면 적용 단계에서 그 값들도 함께 반영한다. 그 청크의 추가 경계 의존성까지 재귀적으로 모두 수집한다는 보장은 없다. 따라서 단일 블록 편집의 기본 범위를 전체 다중 편집에 대한 완전한 의존성 처리로 과장하지 않는다.

개선하려면 변경 블록별로 영향받는 청크 집합을 합치고, 최종 적용 묶음의 모든 편집에 대해 필요한 이웃을 검증하는 방식이 적합하다. 이번 작업에서는 문서화만 했으며 게임 코드를 수정하지 않았다.

## Worker 메시 생성에서 GPU 반영까지

대상이 확정되면 선택한 청크들의 EditShadow 값을 실제 배열에 적용하고 대기 데이터를 지운다. 청크를 찾을 수 없는 편집 대기는 정리하며, 별도 기록을 남긴 변경과 임시 변경은 구분해야 한다.

편집 재메시는 `QueueingQuadMessing(..., true)`로 큐 앞쪽에 넣어 일반적인 뒤쪽 예약보다 우선하도록 한다. 이 옵션은 실행 중인 Worker를 중단시키는 선점 기능은 아니다.

```text
플레이어 입력·블록 변경
  → EditShadow 및 필요 시 편집 기록
  → 적용 가능 상태·주변 청크 검사
  → 청크 배열 반영·재메시 예약
  → Worker에서 QuadMessing
  → Future 완료 확인
  → 메인 스레드 CreateBuffer
  → 갱신된 메시 렌더링
```

메시 작업 대기 큐는 조명·메시 처리 중인 대상을 보류하고, 제거되었거나 사라진 대상을 제외한다. Worker는 묶음 안의 청크를 순서대로 메시 처리하고 ID 목록을 반환한다. Future가 완료되면 메인 스레드에서 예약 상태를 해제하고 `CreateBuffer()`를 호출한다.

수정된 면 몇 개만 GPU 버퍼에 덧붙이는 패치 방식은 아니다. 선택한 청크 단위로 메시를 다시 만들고 버퍼를 갱신한다. 변경 횟수와 재메시 횟수를 분리할 수 있지만 대규모 변경의 비용이 사라지는 것은 아니다. 상태 검사만으로 모든 공유 데이터 접근의 동시성 안전성까지 증명되는 것도 아니다.

## 검증 계획 {/* #확인할-시연과-테스트 */}

시연에서는 선택 외곽선 → 균열 진행 → 블록 파괴 → 뒤쪽 면 노출을 연결해서 보여주고, 경계 편집은 청크 표시와 함께 확인하는 것이 좋다.

- 음수 좌표와 원점 경계에서 선택·설치 대상이 일치하는지.
- 횃불 AABB를 스쳐 지나가는 Ray, 축에 평행한 Ray, 최대 거리 근처 선택.
- 블록 내부에서 시작하는 Ray와 격자 모서리 동률 처리.
- 한쪽 경계·XZ 모서리·서로 반대쪽 경계의 동시 편집 후 이웃 면과 AO 갱신.
- 연속 설치·파괴, 조명 계산 중 편집, 편집 후 청크 언로드·재로드.
- 설치 실패 시 Hotbar 소비와 실제 배치 결과의 일치.

측정할 때는 DDA 조회 시간, 편집 대기량, 재메시 청크 수, Worker 메시 시간, 메인 스레드 버퍼 생성 시간을 나누어 확인할 수 있다. 이번 문서화에서는 새로운 런타임 측정을 수행하지 않았다.
