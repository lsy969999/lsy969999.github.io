# 비동기 청크 스트리밍과 생성 파이프라인

## 배경과 목표 {/* #해결하려던-문제 */}

Minecraft 모작에서는 카메라가 이동할 때 주변 지형이 새로 생성되고, 멀어진 청크는 제거되어야 했다. 청크를 표시하려면 블록을 채우는 것만으로 끝나지 않는다. 지형 생성, 하늘광·블록광 계산, 노출 면과 정점 생성, GPU 버퍼 준비가 필요하다.

한 청크는 `32 × 256 × 32`, 즉 262,144개 블록 칸을 가진다. 주변 청크 전체에 이 계산을 메인 스레드에서 연속 수행하면 입력·게임 로직·렌더링과 같은 프레임 시간을 사용한다. 무거운 CPU 계산을 Worker로 옮기되, 인접 청크와의 의존 관계와 제거 시점을 함께 관리하는 파이프라인을 구성했다.

이 글은 `CVoxelManager3`, `CChunk3`, `CWorkerManager`의 현재 사용 경로를 기준으로 한다. 기존 VoxelManager·VoxelManager2와 별도의 Greedy 테스트 코드는 현재 월드 경로와 구분한다. 이번 문서 작성은 소스 분석이며 실행 성능을 새로 측정한 결과는 아니다.

노출 면과 정점 데이터를 만드는 방법은 [복셀 메시 생성과 렌더링](/projects/minecraft/voxel-meshing-rendering)에서 이어서 설명한다.

전체 구현 범위와 추천 읽기 순서는 [프로젝트 개요](/projects/minecraft/overview)에서 확인할 수 있다. 이 글은 최초 생성과 작업 생명주기를 중심으로 설명하며, 플레이 중 변경이 재메시로 이어지는 조건은 [블록 편집](/projects/minecraft/dda-block-editing) 문서에서 다룬다.

## 책임 분리

| 구성 요소 | 책임 |
| --- | --- |
| `CVoxelManager3` | 범위 요청, 청크 소유, 작업 예약, Future 완료 확인, 편집·제거 조정 |
| `CChunk3` | 블록 배열, 생성·조명·메시·버퍼 상태, CPU 메시와 GPU 버퍼 |
| `CWorkerManager` | 작업 큐, 스레드 대기·실행, 반환값을 전달하는 Future |
| `CGameInstance` | 전용 Worker 접근과 Update·Render·종료 흐름 연결 |

청크를 담는 `m_mapChunks`는 좌표를 인코딩한 64비트 Key와 소유 포인터를 사용한다. 이 좌표 Key는 위치 식별자이지 객체 재생성을 구분하는 Generation Handle은 아니다.

## 카메라 주변의 최신 요청만 유지

현재 자동 스트리밍은 활성 카메라 위치를 기준으로 한다. 플레이어 자체가 아니라 카메라를 사용하므로 Fly Camera로 전환하면 스트리밍 중심도 달라질 수 있다.

X·Z 좌표를 청크 크기로 나누고 `floor`를 적용해 중심 청크를 구한다. 현재 자동 요청의 Y 중심은 0이며 수직 범위 기본값도 0이다. 좌표 자료형이 XYZ를 지원한다고 해서 여러 높이 층을 자유롭게 스트리밍하는 월드로 설명하지 않는다. 렌더링 위치 역시 현재 Y=0의 수직 열 구조에 맞춰져 있다.

Update에서 누적 시간이 약 0.05초를 넘으면 생성 요청, 약 0.07초를 넘으면 해제 요청을 갱신한다. 각각의 등록 함수는 기존 대기 요청을 비운 뒤 최신 중심을 넣는다. 빠르게 이동했을 때 이미 지나온 위치의 대기 요청을 계속 처리하지 않기 위한 구조다.

이미 실행 중인 Worker 작업을 취소하는 것은 아니다. 또한 누적 시간을 0으로 되돌리는 프레임 기반 검사이므로 정확히 고정 주기로 실행하는 타이머나 밀린 횟수를 모두 재생하는 방식도 아니다.

## 한꺼번에 전부 생성하지 않기

생성 요청을 처리할 때 XZ 원형 범위 안에서 아직 없는 청크를 찾는다. 후보를 중심과의 거리 제곱으로 정렬하고, 현재 코드는 가장 가까운 하나만 선택한다. 기본 수평 반경은 3청크다.

선택한 청크 객체와 블록 배열의 준비, Map 등록은 메인 스레드에서 수행한다. 그 뒤 `BlockFilling()`을 Worker에 넘긴다. 따라서 청크 객체 생성과 후보 탐색·정렬 비용까지 비동기로 이동한 것은 아니다.

작업 묶음 자료구조는 여러 Future를 담을 수 있지만, 현재 새 청크 선택 정책은 요청당 하나다. 여러 청크를 무제한 병렬 생성하는 구현으로 과장하지 않는다. 가까운 청크부터 점진적으로 준비하는 대신, 이동 속도가 생성 속도를 앞서면 지형 표시가 늦어질 수 있다.

## 네 단계의 실행 흐름

```text
메인: 범위 요청 → 후보 선정 → 청크 생성·등록
                           ↓
Worker: BlockFilling → 청크 좌표 반환
                           ↓ Future 완료 확인
메인: 생성 청크와 주변 청크를 조명 묶음으로 구성
                           ↓
Worker: 하늘광·블록광 계산 → 대상 좌표 집합 반환
                           ↓ Future 완료 확인
메인: 조명 완료 상태 기록 → 메시 작업 예약
                           ↓
Worker: QuadMessing → CPU 정점·인덱스 계산
                           ↓ Future 완료 확인
메인: CreateBuffer → 렌더 가능한 GPU 버퍼
```

### 1. 블록 생성

`BlockFilling()`은 노이즈와 지형 규칙으로 블록 배열을 구성한다. 생성이 끝나면 기록된 편집 데이터가 있는 칸을 덮어쓰고 완료 상태를 기록한다. 편집 기록을 읽는 부분은 별도의 Shared Mutex를 사용한다.

이 과정에서 설명하는 기록은 메모리상의 변경 데이터다. 재실행 후 월드를 복원하는 디스크 저장 기능과는 구분한다. Future의 반환값은 전체 블록 배열이 아니라 청크 좌표이며, Worker는 Manager가 소유한 청크 데이터를 직접 수정한다.

### 2. 생성 완료 묶음의 조명 계산

`UpdateCheckBlockFillingFutures()`는 한 묶음의 모든 Future가 준비됐는지 확인한다. 완료되면 새 청크와 같은 Y층의 주변 8방향 청크를 모아 중복 없는 조명 대상 집합을 만든다.

하늘광·블록광은 경계를 넘어 전달되므로 새 청크 하나만 독립적으로 계산하는 것으로 부족하다. 주변 청크를 함께 고려해 조명 Seed와 전파를 처리한다. 구체적인 광원 전파 알고리즘은 청크 스케줄링과 분리해 다룰 주제다.

조명 작업은 `m_bLighing`과 단일 `m_futLighting`으로 관리한다. 여러 조명 묶음이 동시에 공유 데이터를 수정하지 않도록 한 번에 하나를 진행하는 구조다. 조명 완료 뒤에는 대상 청크를 `DONE`으로 바꾸고 메시 작업을 예약한다.

### 3. CPU 메시 생성

메시 큐는 대상 청크가 조명 계산 또는 메시 생성 중이면 제출을 미룬다. 삭제 예정이거나 존재하지 않는 대상은 목록에서 제외한다. 조건을 통과하면 `QuadMessing()`을 Worker에서 실행한다.

현재 경로는 `NiveFaceCulling()`으로 노출 면을 구한 뒤 Solid·Alpha Test·Water별 정점과 인덱스를 만든다. 이름이 비슷한 테스트 코드가 남아 있어도 이 월드가 Greedy Meshing을 사용하는 것은 아니다.

### 4. GPU 버퍼 생성

`UpdateCheckQuadMessingEndFutures()`는 완료된 작업의 좌표 목록을 받아 메인 스레드에서 `CreateBuffer()`를 호출한다. 아직 준비되지 않은 Future를 기다리며 메인 스레드를 멈추지 않는다.

완료 확인의 핵심 형태를 단순화하면 다음과 같다.

```cpp
if (future.valid())
{
    if (future.wait_for(std::chrono::seconds(0)) == std::future_status::ready)
    {
        auto completedChunkCoords = future.get();
        // 좌표로 청크를 다시 찾아 GPU 버퍼 생성 단계로 넘긴다.
    }
}
```

리소스 클래스 이름은 `CResDynamicVIBuffer`지만 이 경로에서 지정하는 버퍼 Usage는 `D3D11_USAGE_IMMUTABLE`이다. 기존 버퍼에 부분 업데이트하는 것이 아니라 계산한 메시로 버퍼를 새로 구성한다. 비어 있는 종류의 버퍼는 제거하고, 성공적으로 업로드한 CPU 배열은 용량까지 해제한다.

세 종류의 버퍼 준비가 끝나면 Buffer 상태를 `DONE`으로 바꾸고 버전 값을 증가시킨다. Draw는 버퍼 준비 여부를 검사한다. 메인 스레드에 남는 GPU 버퍼 생성 비용은 별도로 존재하며, 비동기 메시 계산만으로 프레임 드랍이 모두 해결되는 것은 아니다.

## Future와 상태 값의 역할

청크는 블록 생성·조명·메시·버퍼 상태를 각각 `NON / ING / DONE`으로 보관한다. 모든 단계를 하나의 열거형으로 표현한 상태 머신은 아니며, 여러 상태와 큐를 Manager에서 함께 해석한다.

Future는 작업 완료와 결과 소비를 연결하고, 상태 값은 다음 작업을 예약할 수 있는지를 판단하는 데 사용한다. 상태가 Atomic이라고 해서 블록 배열·Map·정점 Vector 전체가 자동으로 스레드 안전해지는 것은 아니다.

`GetMessingQueued()`는 편집 적용을 미루는 데도 사용한다. 블록 편집은 대기 데이터에 모으고, 관련 청크의 예약·조명 상태를 확인한 뒤 재메시로 연결한다. 경계 편집은 이웃의 면과 AO에도 영향을 주므로 인접 청크까지 대상이 될 수 있다.

다만 `QueueingQuadMessing()` 자체는 이미 같은 좌표가 예약됐는지 검사해 중복을 제거하는 함수가 아니다. 예약 플래그를 기록하고 목록을 추가한다. 제출 중복 방지와 충돌 없는 동시 실행을 일반적인 작업 그래프 수준으로 보장하는 구현은 아니다.

## 생성·해제와 계산 작업 사이의 경계

새로운 범위 생성·해제 요청은 다음 네 조건이 모두 충족됐을 때 처리한다.

- 블록 생성 Future 목록이 비어 있다.
- 메시 예약 목록이 비어 있다.
- 조명 Future가 유효하지 않다.
- 실행 중인 메시 Future 목록이 비어 있다.

Worker가 청크 Map과 이웃 데이터를 참조하는 동안 청크를 추가·제거하는 일을 제한하는 보수적인 방식이다. Map을 Immutable Snapshot으로 복제해 작업마다 넘기는 구조는 아니다.

이 선택은 소유 객체의 수명 경계를 단순하게 만드는 대신 병렬성을 제한한다. 긴 조명 작업이나 재메시가 남아 있으면 다음 범위 요청도 기다린다. 청크마다 독립적인 작업 그래프를 구성해 서로 겹치지 않는 영역은 계속 생성하는 설계와는 다르다.

## 청크 제거도 두 단계로 처리

해제는 생성 반경보다 한 청크 넓은 `R + 1` 범위 밖을 대상으로 한다. 생성·해제 경계를 다르게 두어 경계 부근 이동 시 반복 생성과 제거를 줄이려는 구조다.

범위를 벗어난 청크는 먼저 `Dead`로 표시한다. 좌표 조회 API는 Dead 청크를 반환하지 않고, 남아 있는 XZ 인접 청크의 메시를 다시 예약한다. 사라진 이웃 때문에 노출되어야 하는 경계면을 갱신하기 위해서다.

실제 소유 Map의 `erase`는 계산·예약 목록이 모두 비었을 때 수행한다. 이 기준은 GameObject의 FrameEnd 파괴가 아니라 VoxelManager의 Update에서 판단하는 청크 전용 수명 관리다.

현재 해제 코드의 `iLimit`은 1이지만 중단 조건이 `delQ.size() > iLimit`이므로 한 요청에서 최대 두 개가 선택될 수 있다. 문서에서는 이를 정확한 ‘프레임당 한 개 해제’ 제한으로 표현하지 않는다.

## Worker와 엔진 종료 순서

일반 작업용 Pool과 ChunkLoader Pool을 분리했다. 작업 등록은 Mutex로 보호한 큐에 넣고 Condition Variable로 대기 중인 Worker를 깨운다. Worker는 큐에서 작업을 꺼낸 뒤 큐 잠금을 풀고 함수를 실행한다.

반환값이 필요한 작업은 `packaged_task`와 Future로 감싼다. 청크에는 `FUT_BLOCK_FILLING`, `FUT_LIGHTING`, `FUT_QUAD_MESSING` 이름을 붙여 GUI에서 실행 중인 단계와 대기 작업을 식별할 수 있게 했다.

종료 시 Worker는 대기 작업이 남아 있으면 처리한 뒤 루프를 빠져나오고 `join`된다. `CGameInstance`는 ChunkLoader를 VoxelManager보다 먼저 해제한다. 청크 데이터를 참조하는 작업이 끝나기 전에 청크 소유자를 없애지 않도록 한 순서다. 즉시 취소 방식이 아니므로 남은 작업에 따라 종료 시간이 길어질 수 있다.

## 한계와 개선 방향 {/* #현재-제약과-다시-설계한다면-바꿀-점 */}

현재 구현의 핵심은 단계 분리와 보수적인 수명 관리다. 완성된 범용 Job System이나 무정지 스트리밍을 주장하지 않는다.

- 후보 탐색·정렬·청크 객체 생성·GPU 버퍼 생성은 메인 스레드 비용으로 남는다. 시간 예산을 기준으로 분산하는 처리는 없다.
- 완료된 메시가 여러 개면 한 Update에서 버퍼를 연속 생성할 수 있다. 업로드 개수·바이트·시간 예산을 별도로 둘 수 있다.
- 실행 중 작업 취소나 요청 세대 번호를 통한 오래된 결과 폐기는 없다. 최신 대기 요청으로 교체하는 정책과 구분해야 한다.
- 실패 시 메시지를 표시하더라도 좌표를 반환하는 경로가 있으며, Future의 `get()` 예외·실패 결과·재시도 정책이 통일되어 있지 않다.
- ChunkLoader 스레드 수는 `hardware_concurrency() - 3`을 그대로 사용한다. 낮은 코어 수나 0 반환을 고려한 최소·최대 Clamp가 보강 대상이다.
- 큐와 일부 데이터의 잠금만으로 전체 공유 데이터 접근이 검증된 것은 아니다. 메시 중복 예약, 런타임 조명 변경, GUI 상태 조회까지 포함한 동시성 점검이 필요하다.

후속 설계에서는 청크별 작업 세대와 읽기 Snapshot을 도입하고, 생성·조명·메시 의존 관계를 명시해 불필요한 전역 대기를 줄이고 싶다. 동시에 메인 스레드의 버퍼 생성 예산을 두어 CPU 계산 분리 이후 남는 병목도 관리해야 한다.

## 결과와 검증 기준

월드를 한 번에 만드는 대신 가까운 청크부터 준비하고, CPU 계산 결과를 완료된 시점에만 GPU 리소스로 연결하는 흐름을 마련했다. 청크가 Map에 있다는 것과 렌더할 준비가 됐다는 것을 구분하고, 제거도 작업 종료 조건과 연결했다.

현재 문서에는 동일 환경의 동기·비동기 비교 측정값이 없으므로 FPS 개선 배수를 적지 않는다. 시연과 측정에서는 다음 항목을 함께 확인해야 한다.

1. 빠르게 이동하거나 방향을 반대로 바꿨을 때 최신 중심 근처가 먼저 채워지는지 확인한다.
2. 청크 경계에서 블록을 편집하고, 조명·메시 작업이 겹칠 때 경계면 갱신과 데이터 접근을 확인한다.
3. 생성 중 멀리 이동한 뒤 해제와 재생성이 진행되는 동안 참조 오류가 없는지 확인한다.
4. Worker 단계별 소요 시간과 메인 스레드 버퍼 생성 시간을 분리해 기록한다.
5. 하드웨어·렌더 거리·이동 경로를 고정하고 프레임 시간 분포와 미완료 작업량을 함께 비교한다.

대표 이력은 `17ec958`의 VoxelManager3 재구성, `6d653cd`의 블록 생성 비동기 처리, `43ca100`의 청크 묶음 조명 비동기 전파, `7443eee`의 경계 편집 재메시 보강이다. 설명 기준 소스는 `e38a951`이며, 후속 시연 수치와 개선 사항은 별도 근거를 확인한 뒤 추가한다.
