# 절차적 지형·바이옴과 동굴·광물·식생 생성

## 배경과 목표 {/* #해결하려던-문제 */}

청크를 필요한 위치에 생성하려면 미리 저장한 모델 없이도 해당 좌표의 블록 구성을 계산할 수 있어야 한다. 높이만 바꾸면 지형의 외형은 만들 수 있지만, 사막과 평지의 재질 차이·지하 동굴·채굴할 광물·지표면 식생까지 표현하기는 어렵다.

FastNoiseLite를 사용해 용도별 노이즈를 구성하고, `CChunk3::BlockFilling()`에서 이를 블록 배치 규칙으로 조합했다. 노이즈 알고리즘 자체를 직접 구현한 것이 아니라, 라이브러리의 값을 월드 생성에 연결하는 좌표·분포·적용 순서를 구현한 작업이다.

이 문서는 블록 데이터를 만드는 단계에 집중한다. 작업 실행 순서는 [비동기 청크 스트리밍](/projects/minecraft/async-chunk-streaming), 이후 처리는 [조명 전파](/projects/minecraft/voxel-light-propagation)와 [복셀 메시 생성](/projects/minecraft/voxel-meshing-rendering)에서 설명한다.

생성된 월드를 플레이 중 수정하는 과정은 [DDA 블록 선택과 설치·파괴 후 갱신](/projects/minecraft/dda-block-editing)에서 이어서 다룬다.

## 청크 좌표가 아닌 월드 좌표로 샘플링

현재 청크는 가로·세로 32칸, 높이 256칸인 수직 기둥이다. 로컬 X·Z를 청크 좌표와 합쳐 노이즈 입력으로 사용한다.

```cpp
// 현재 구현의 입력 좌표 관계를 단순화한 예시
float sampleX = chunkX * 32 + localX + 100000.0f;
float sampleZ = chunkZ * 32 + localZ + 100000.0f;
```

청크마다 로컬 좌표 0부터 노이즈를 반복하는 방식이 아니므로, 인접 청크는 같은 좌표계에서 이어지는 값을 읽는다. 높이·기후·식생은 XZ의 2D 샘플을, 기반암·동굴·광물은 높이 K를 포함한 3D 샘플을 사용한다.

`100000`은 샘플 영역을 이동하는 고정 Offset이다. 청크 경계를 연결하는 핵심은 Offset 자체가 아니라 월드 좌표를 쓰는 데 있다. 현재 K는 0~255이며 청크 Y를 더하는 일반적인 수직 청크 생성 구조는 아니다. 큰 좌표에서의 Float 정밀도까지 해결한 방식으로 설명하지 않는다.

## 용도별 노이즈 구성

`CVoxelManager3::Initialize()`에서 노이즈를 한 번 설정한다. 기본 시드는 `160`이며 용도마다 서로 다른 Offset을 더한다.

| 용도 | 알고리즘 | 주파수 | 시드 Offset | 추가 설정 |
| --- | --- | --- | --- | --- |
| 높이 | Perlin | 0.005 | 0 | FBm, Octave 4, Lacunarity 2, Gain 0.2 |
| 기반암 | OpenSimplex2 | 0.8 | +1 | 3D 샘플 |
| 동굴 | OpenSimplex2 | 0.04 | +2 | 3D 샘플 |
| 철 | OpenSimplex2 | 0.15 | +3 | 3D 샘플 |
| 석탄 | OpenSimplex2 | 0.12 | +4 | 3D 샘플 |
| 다이아몬드 | OpenSimplex2 | 0.22 | +5 | 3D 샘플 |
| 온도 | Perlin | 0.002 | +10 | 2D 샘플 |
| 습도 | Perlin | 0.002 | +21 | 2D 샘플 |
| 풀·꽃 배치 | Perlin | 0.22 | +31 | 2D 샘플 |
| 나무 배치 | Perlin | 0.08 | +32 | FBm, Octave 3 |

주파수는 공간에서 값이 변하는 크기를 조절한다. 높이와 기후에는 낮은 주파수를 사용하고, 광물·식생에는 더 작은 공간에서 변화하는 값을 사용한다. FBm은 여러 주파수의 노이즈를 합치는 방식이며 높이의 Gain 0.2는 뒤쪽 Octave의 영향을 줄인다.

시드를 분리하면 용도마다 다른 패턴을 사용할 수 있지만, 특정 광맥의 개수나 크기가 보장되지는 않는다. 예를 들어 다이아몬드가 반드시 1~4개씩 생성되는 군집 알고리즘은 아니다. 현재는 노이즈 임계값을 통과한 칸을 광물로 바꾼다.

`CLOUD` 설정도 존재하지만 `BlockFilling()`의 지형 배치에는 사용하지 않는다. 설정 목록과 실제로 블록을 생성하는 경로를 구분했다.

## 기후로 바이옴과 높이 공식을 선택

각 XZ 열에서 온도 T, 습도 U, 높이 노이즈 H를 읽고 아래 규칙을 적용한다. 표의 높이는 정수 변환 전 식이다.

| 바이옴 | 선택 조건 | 높이 | 해수면 이상 표면 |
| --- | --- | --- | --- |
| SNOW | T가 -0.2 미만 | 70 + H × 45 | STONE |
| DESERT | T가 0.2 초과이고 U가 -0.1 미만 | 68 + H × 15 | SAND |
| PLAINS | 나머지 | 66 + H × 25 | GRASS |

계산한 높이는 정수로 변환하고 5~250으로 제한한다. 같은 높이 노이즈라도 바이옴마다 기준 높이와 변화 폭이 다르다. 해수면은 63으로 고정했다.

현재 `SNOW`는 이름과 달리 눈 블록을 배치하지 않고 돌 표면을 사용한다. 완성된 적설 바이옴으로 소개하기보다는, 기후에 따라 지형 종류를 분기한 구조로 설명하는 것이 정확하다.

또한 바이옴 경계에서 높이 공식을 즉시 바꾼다. 노이즈 좌표는 이어져도 최종 높이가 부드럽게 연결된다는 보장은 없다. 경계를 자연스럽게 만들려면 바이옴 가중치에 따른 높이 혼합 등이 추가로 필요하다.

## 블록 배치 순서

```text
XZ 열별 기후·높이 결정
  → 기반암·돌·표층·물·공기 채우기
  → 지하 칸의 동굴 제거·광물 치환
  → 풀·꽃 배치, 나무 후보 기록
모든 열 처리 완료
  → 나무 생성
  → 해당 청크의 편집 기록 덮어쓰기
  → BlockFilling 완료 → 조명·메시 작업
```

동굴·광물은 청크 전체를 채운 뒤 별도 전체 순회를 하는 것이 아니라, 각 K 칸의 기본 타입을 정한 다음 처리한다. 나무만 별도로 모아 모든 열을 채운 뒤 생성한다.

### 기반암과 표층

K=0은 항상 기반암이다. K=1~4에서는 3D 노이즈를 0~1로 변환한 값과 `1 - K / 4`를 비교해 기반암 또는 돌을 선택한다. 높아질수록 기반암 선택 기준이 낮아지지만, 이것을 정확한 생성 확률과 동일하게 볼 수는 없다.

그 위에서는 표면 아래 5개 층보다 깊은 곳을 돌로 채우고, 표면 바로 아래 5개 층은 사막이면 모래, 나머지는 흙으로 채운다. 기반암 분기가 먼저 적용되므로 낮은 지형에서는 이 범위가 기반암과 겹칠 수 있다.

표면이 해수면보다 낮으면 사막은 모래, 나머지는 흙이다. 표면 위이면서 K가 63 이하인 공간은 정지 물로 채우고 Flag를 7로 설정한다. 나머지 위쪽 공간은 AIR로 명시적으로 초기화한다.

### 동굴을 먼저 뚫고 광물 배치

지하 후처리는 K가 4보다 크고 `height - 4`보다 작은 범위에 적용한다. 표면 가까운 층과 기반암 구간은 보호한다.

동굴 노이즈가 0.45를 넘으면 해당 블록을 AIR로 바꾸고 다음 칸으로 넘어간다. 따라서 동굴로 제거한 칸에 다시 광물을 넣지 않는다. 지표면의 높이를 만드는 2D 노이즈와 달리 3D 좌표를 사용해 지하 공간을 만든다. 통로의 연결성이나 출입구를 보장하는 별도 탐색 알고리즘은 없다.

남은 칸이 STONE일 때만 아래 순서로 광물을 검사한다.

| 우선순위 | 광물 | 높이 조건 | 노이즈 임계값 |
| --- | --- | --- | --- |
| 1 | 다이아몬드 | K ≤ 16 | 0.85 초과 |
| 2 | 철 | K ≤ 60 | 0.80 초과 |
| 3 | 석탄 | K ≤ 150 | 0.75 초과 |

앞의 조건이 성공하면 즉시 다음 칸으로 넘어가므로 중첩 조건에서는 다이아몬드 → 철 → 석탄 순서가 우선한다. 높이 조건만 만족한다고 생성되는 것은 아니며, 기본 돌·동굴 제외·노이즈 조건을 함께 통과해야 한다.

블록 Enum과 텍스처에는 딥슬레이트 및 다른 광물도 있지만, 현재 이 생성 함수에서 자동 배치하는 광물은 위 세 종류다.

## 나무를 마지막에 생성하는 이유

나무는 하나의 XZ 열을 넘어 잎을 배치한다. 지형을 채우는 도중 바로 나무를 만들면, 아직 처리하지 않은 옆 열을 나중에 초기화하면서 잎을 지울 수 있다.

이를 피하기 위해 평지의 해수면 이상 표면에서 나무 후보를 기록하고, 청크의 기본 지형과 공기 공간을 모두 채운 후 `SpawnTree()`를 호출한다.

나무 후보는 청크 XZ 가장자리 두 칸을 제외한 영역에서 나무 노이즈가 0.25를 넘을 때 선택한다. 잎의 최대 반지름이 2이므로 인접 청크에 쓰지 않고 현재 청크 안에서 생성할 수 있다. 대신 청크 경계에는 줄기 배치가 제한되는 띠가 생긴다.

나무 종류는 같은 노이즈를 `(value - 0.25) / 0.75`로 변환한 뒤 구간을 나눠 참나무·자작나무·아카시아·벚나무를 선택한다. 종류마다 독립 난수를 뽑는 방식이 아니어서 배치 밀도와 종류 선택이 같은 값에 묶여 있다.

`SpawnTree()`는 높이 4~5의 기둥과 층별 반지름 1~2의 잎을 만든다. 잎은 AIR인 칸에만 넣고 일부 모서리를 확률적으로 생략한 다음, 중심부에 줄기를 배치한다. 나무 사이의 최소 간격을 보장하는 검사는 없다.

## 풀·꽃과 월드 재현성의 경계

나무 후보가 아닌 평지의 해수면 이상 표면에서 식생 노이즈를 읽는다. 0.52 초과이면 꽃을, 그 외 0.28 초과이면 짧은 풀을 표면 한 칸 위에 배치한다. 꽃 종류는 14개 후보 중 하나를 별도 난수로 선택한다.

여기서 시드 기반 생성과 완전한 재현성은 구분해야 한다.

- 높이·바이옴·동굴·광물·나무 후보 위치는 설정된 노이즈와 좌표를 기준으로 계산한다.
- 나무 높이·잎 모서리 생략은 `random_device`로 초기화한 Thread Local 난수를 사용한다.
- 꽃 종류 역시 월드 시드와 연결되지 않은 난수 엔진을 사용한다.

따라서 같은 시드로 청크를 재생성해도 식생의 세부 형태까지 동일하다고 보장할 수 없다. Worker에 배정되는 순서도 난수 소비 순서에 영향을 줄 수 있다. 재현성이 필요하다면 월드 시드·좌표·용도 ID를 조합한 결정적 난수로 바꾸는 것이 개선 방향이다. 현재 구현에 적용했다고 주장하지 않는다.

## 생성 결과 위에 플레이어 편집 기록 적용

나무까지 만든 다음 청크 ID로 편집 기록을 조회한다. 기록은 블록별 `optional<CBlock3>` 배열이며, 값이 있는 칸만 생성 결과 위에 덮어쓴다. AIR로 파괴한 기록도 값이 있는 변경으로 적용할 수 있다.

조회와 복사는 편집 기록 Mutex의 Shared Lock 아래에서 수행한다. 마지막 적용 순서 덕분에 절차적 생성이 플레이어의 설치·파괴 결과를 다시 덮어쓰지 않는다. 이 기록은 메모리의 편집 데이터이며, 해당 코드만으로 디스크 세이브 기능을 구현했다고 볼 수는 없다.

편집되지 않은 식생까지 저장하는 구조는 아니므로 앞서 설명한 난수 재현성 문제는 별도로 남는다. 또한 `CBlock3` 전체를 복사하므로 타입뿐 아니라 부가 데이터도 함께 복원된다는 점을 조명 갱신과 함께 고려해야 한다.

## 구현 범위와 검증 자료

핵심은 하나의 노이즈를 모든 용도에 사용하는 대신, 용도별 공간 패턴과 블록 치환 순서를 조합해 청크를 생성한 것이다. 렌더링 전에 블록 데이터 생성이 완료되도록 기존 비동기 청크 처리 단계에 연결했다.

현재 규칙은 C++에 고정되어 있으며 GUI 기반 바이옴 편집기나 범용 월드 생성 Graph는 아니다. 개선 시에는 다음 항목을 분리해서 다룰 수 있다.

- 바이옴 경계의 높이 혼합과 실제 눈 표면 정책.
- 좌표 기반 식생 난수, 나무 간격, 청크 경계를 넘는 구조물 배치.
- 생성 설정·버전과 편집 기록의 호환성 관리.
- 노이즈 샘플 횟수와 청크 생성 시간 측정. 현재 K 루프는 위쪽 AIR를 포함해 256칸 전체를 처리한다.

포트폴리오 시연은 바이옴 경계, 지하 단면의 동굴·광물, 청크 경계의 나무 배치, 블록 편집 후 언로드·재로드를 우선 보여줄 수 있다. 같은 청크를 반복 생성해 기본 지형과 식생 세부 형태를 따로 비교하면 재현 범위도 확인할 수 있다. 이번 문서화에서는 실행 측정이나 개선 코드 적용을 수행하지 않았다.
