# 복셀 메시 생성과 렌더링

## 블록 데이터와 그릴 메시를 분리

복셀 월드는 블록 배열로 구성되지만, 모든 블록을 독립된 Cube 객체로 렌더링할 필요는 없다. 땅속 블록처럼 이웃에게 완전히 가려진 면은 화면에 나타나지 않는다. 블록마다 Draw를 호출하는 대신, 노출된 면을 청크 단위로 모아 메시를 구성했다.

[비동기 청크 스트리밍](/projects/minecraft/async-chunk-streaming)은 메시를 언제 계산하고 GPU에 반영하는지 설명한다. 이 문서는 `CChunk3::QuadMessing()`에서 어떤 면과 정점 데이터를 만들고, `CVoxelManager3`가 어떻게 그리는지에 집중한다.

월드 메시에는 `NiveFaceCulling()`의 노출 면 생성 방식을 사용한다. 인접 면을 병합하는 Greedy Meshing은 별도 테스트 코드로만 남아 있다.

정점에 담을 하늘광·블록광을 계산하고 변경하는 과정은 [조명 전파와 런타임 갱신](/projects/minecraft/voxel-light-propagation)에서 설명한다.

## 노출된 면만 생성

한 청크의 블록 칸을 순회하며 AIR를 건너뛰고, 일반 Cube는 여섯 방향의 이웃을 검사한다. `IsFaceExposed()`가 노출로 판단한 방향에만 `VOX_QUAD`를 추가한다.

대표 규칙은 다음과 같다. 앞서 검사한 예외 조건이 우선 적용되므로, 이웃이 AIR인지만 확인하는 것과는 결과가 다르다.

| 조건 | 처리 |
| --- | --- |
| 이웃 청크가 없거나 조회 범위 밖 | 면 생성 |
| 이웃이 횃불 또는 Alpha Test 대상 | 틈으로 보일 수 있도록 면 생성 |
| 일반 고체의 이웃이 AIR 또는 물 | 면 생성 |
| 일반 고체의 이웃이 일반 고체 | 공유 면 생략 |
| CROSS·SLAP·STAIR·TORCH·WATER 형상 | 일반 Cube 루틴 대신 전용 생성 함수로 분기 |

예를 들어 공기 중에 나란히 놓인 일반 불투명 Cube 두 개는 각각 여섯 면을 만들면 12면이지만, 서로 맞닿은 두 면을 생략하면 10면이 된다. 이는 원리를 설명하는 기하학적 예시이지 실행 성능 측정값은 아니다.

이 단계는 카메라 방향과 무관하다. 플레이어 뒤쪽이라도 외부에 노출된 면은 메시 안에 남으며, 이후 카메라 컬링에서 청크의 Draw 여부를 판단한다.

## 청크 경계와 대각선 이웃 조회

경계 블록의 이웃을 청크 내부 배열에서만 찾으면, 다른 청크와 맞닿은 면까지 불필요하게 생성된다. `GetBlockAt()`은 로컬 X·Z가 범위를 벗어났을 때 인접 청크 좌표로 바꾸어 조회한다.

메시 계산 전에 XZ 네 방향과 대각선 네 방향, 자기 자신을 포함한 목록을 구성한다. 대각선은 단순 면 노출뿐 아니라 꼭짓점의 AO 계산에 필요하다. Y가 0~255 밖이면 다른 수직 청크를 조회하지 않고 값 없음으로 처리한다.

이웃이 아직 없으면 경계면을 우선 생성한다. 이후 이웃이 로드되거나 제거되면 기존 경계의 면과 AO도 달라질 수 있으므로 재메시가 필요하다. ‘청크마다 메시를 한 번만 생성하면 끝’인 구조가 아니다.

## Vertex AO로 모서리의 가림 표현

노출 면에 동일한 밝기만 주면 블록이 맞닿은 모서리와 틈이 평평하게 보인다. 일반 Cube의 각 꼭짓점에서 두 측면과 대각선 모서리의 블록이 AO 차폐 대상인지를 검사한다.

계산은 다음 규칙이다.

```cpp
uint8_t CalculateVertexAO(bool side1, bool side2, bool corner)
{
    if (side1 && side2)
    {
        return 0;
    }

    int occluderCount = 0;
    if (side1) ++occluderCount;
    if (side2) ++occluderCount;
    if (corner) ++occluderCount;
    return static_cast<uint8_t>(3 - occluderCount);
}
```

결과는 0~3의 네 단계이며, Shader에서 각각 `0.4, 0.6, 0.8, 1.0`의 밝기 계수로 바꾼다. 두 측면이 막힌 꼭짓점은 대각선 블록 유무와 무관하게 가장 어두운 값이 된다.

메시 생성 시 블록 배치로 계산해 정점에 기록하는 AO다. 화면 깊이를 분석하는 SSAO나 광선 추적, 실시간 전역 조명과는 다르다. 주변 블록이 바뀌면 새 값을 메시로 다시 반영해야 한다.

### AO에 따라 삼각형 대각선도 선택

Quad의 네 꼭짓점 밝기가 서로 다르면 어느 대각선으로 두 삼각형을 나누는지에 따라 내부 보간이 달라진다. 한 방향만 고정하면 어두운 부분이 특정 대각선으로 치우쳐 보일 수 있다.

`QuadsToVerticies()`는 대각선 양 끝의 AO 합을 비교한다.

- `ao[0] + ao[2] < ao[1] + ao[3]`이면 1–3 대각선 사용.
- 그 외에는 0–2 대각선 사용.

정점 수를 늘리지 않고 인덱스 구성만 바꾸는 처리다. AO 값 자체를 바꾸거나 픽셀 단위로 새로운 가림을 계산하는 기능은 아니다.

## Quad에서 GPU 정점으로 변환

중간 데이터인 `VOX_QUAD`는 위치 네 개, 면 방향, 텍스처 ID, 조명, 꼭짓점별 AO·UV·Color를 가진다. 이 데이터에서 면마다 정점 4개와 인덱스 6개를 생성한다.

서로 다른 면의 위치가 같아도 정점을 전역 공유하지 않는다. 면 방향·UV·텍스처·AO가 다를 수 있기 때문이다. 인접한 동일 면을 크게 병합하는 Greedy 최적화도 이 경로에는 없다.

`VTX_VOXEL`은 Position·UV와 함께 32비트 Color, 32비트 `packedData`를 보관한다. 정점 전체가 32비트인 것이 아니라, 면 관련 속성을 하나의 정수에 모은 것이다.

| 데이터 | 비트 범위 | 용도 |
| --- | --- | --- |
| 면 방향 | 31~29 | 여섯 축 방향 법선의 인덱스 |
| Vertex AO | 28~27 | 0~3 단계 |
| Quad 안의 정점 번호 | 26~25 | 0~3 번호 |
| 텍스처 ID | 24~17 | 블록 텍스처 선택 |
| 조명 | 16~9 | Sky Light 4비트 + Block Light 4비트 |
| 미사용 | 8~0 | 현재 변환 코드에서 0 유지 |

Shader는 같은 Shift·Mask로 값을 복원한다. Color는 별도 `R8G8B8A8_UNORM` 입력으로 받아 Float 색으로 사용한다. CPU 패킹과 Shader 해석 규칙은 함께 관리해야 한다.

현재 Shader는 정점 번호로 만든 기본 UV 변수도 가지고 있지만 최종 텍스처 좌표는 정점의 `texCoord`를 사용한다. 따라서 정점 번호를 패킹했다고 UV 입력을 제거한 구조는 아니다.

## 텍스처와 조명 데이터를 한 메시에서 사용

일반 블록 텍스처는 `Texture2DArray`에서 텍스처 ID로 선택한다. 블록마다 텍스처를 교체하며 Draw하지 않고, 같은 청크 버퍼 안에서 다른 블록의 면을 그릴 수 있다. 면별 `GetTexType()`을 사용하므로 윗면과 옆면에 다른 텍스처를 지정할 수도 있다.

일반 Cube의 면 조명은 해당 면 바깥쪽 인접 칸의 값을 읽으며, 이웃이 없으면 `0xFF`를 사용한다. 한 Quad의 조명은 공통이고 AO는 꼭짓점별이다. 조명 값을 네 꼭짓점에서 각각 평균내는 Smooth Lighting과는 구분된다.

Shader의 기본 색 계산은 텍스처·블록 Tint·AO에 하늘광과 블록광의 합성 결과를 곱한다. 하늘광에는 낮밤 계수를 적용하고 블록광과 최댓값을 취한다. 일반·Alpha Test Shader에는 Shadow Map 보정도 별도로 있다. AO, Flood Fill 조명, Shadow Mapping은 서로 다른 입력이다.

물·용암은 별도 애니메이션 텍스처를 선택하는 분기도 사용한다. 모든 블록 표현이 단일 Texture Array 샘플만으로 처리되는 것은 아니다.

## 재질별 메시와 Draw 경로 분리

`QuadBuckets`는 세 목록을 보관한다. 각각을 별도의 정점·인덱스와 GPU 버퍼로 변환한다.

| 목록 | 대표 대상 | 일반 렌더 경로 |
| --- | --- | --- |
| Solid | 일반 고체, 슬랩·계단·횃불, 용암 | 일반 블록 Shader와 Back-face Culling |
| Alpha Test | 잎, 십자형 식생 등 | `clip(albedo.a - 0.5)`와 Cull None |
| Water | 물 | Alpha Blend, 깊이 기록 비활성화, Back-face Culling |

용암은 전용 표면 생성 함수를 사용하지만 결과는 현재 Solid 목록에 들어간다. 함수 인자 이름만 보고 Water 목록으로 분류하면 실제 호출 경로와 달라진다.

`RenderDefault()`는 Solid → Alpha Test → Water 순서로 그린다. 종류별 Shader를 먼저 설정하고 대상 청크를 순회해 `DrawIndexed`를 호출한다. 버퍼가 준비되고 해당 종류의 메시가 있을 때 청크마다 호출되므로, 월드 전체가 세 번의 Draw로 끝나는 구조는 아니다.

Water Shader는 물의 Alpha를 0.6으로 설정한다. 그러나 현재 청크나 물의 삼각형을 카메라 거리순으로 정렬하지 않는다. 물을 마지막에 그리는 것만으로 반투명 중첩 순서 문제가 모두 해결되지는 않는다.

## Cube가 아닌 형상

식생·계단·수면을 일반 Cube의 크기만 바꿔 표현하지 않고 형상별 생성 함수로 분리했다.

- CROSS는 교차하는 두 면으로 식생을 만들고 Alpha Test 목록에 넣는다. 이 경로의 AO는 가장 밝은 3으로 설정한다.
- SLAP은 반높이, STAIR는 높이가 다른 부분을 조합해 형상을 만든다.
- TORCH는 횃불에 맞는 위치와 크기의 면을 생성한다.
- WATER는 수위 값으로 윗면 높이를 만들고, 이웃 수위와 비교해 필요한 옆면을 생성한다.

현재 계단 방향은 `stairDir = 0`으로 고정되어 있고, 슬랩 조명에도 `240` 고정값이 남아 있다. 물의 꼭짓점별 높이를 보간하는 별도 코드는 주석 처리된 경로이며, 현재 활성 표면 생성과 구분한다.

## 서로 다른 세 종류의 컬링

노출 면 컬링은 CPU가 메시를 만들 때 이웃에 가려진 면을 생략한다. Frustum Culling은 Draw 전에 청크 전체가 카메라 영역과 겹치는지 검사한다. Rasterizer의 Back-face Culling은 실제 그릴 삼각형의 방향을 기준으로 처리한다.

현재 일반 패스는 `Coll_PlayerCamera` 그룹의 첫 Collider와 청크 Box를 비교하고, 통과한 청크 목록을 세 재질 경로에서 재사용한다. 그룹이 없으면 모든 청크를 후보에 넣는다. 활성 카메라가 무엇이든 자동으로 그 카메라의 Frustum을 사용하는 구현은 아니다.

Shadow 패스는 `Coll_ShadowCamera`로 별도 후보를 고르고 Solid·Alpha Test를 그린다. Water Draw는 이 패스에 포함되어 있지 않다. 일반 패스에서 보이지 않는 청크도 그림자 기준에서는 필요할 수 있어 두 기준을 나눴다.

## 버퍼 갱신과 비용

CPU 메시 계산은 Worker에서, GPU 버퍼 구성은 완료 확인 뒤 메인 스레드에서 수행한다. 현재 청크 버퍼는 `D3D11_USAGE_IMMUTABLE`로 새로 생성하며, 청크 내부 일부 면만 수정하는 부분 업로드는 아니다.

노출 면만 남겨도 메시를 다시 만들 때는 청크의 블록 배열을 순회한다. 편집 빈도와 인접 청크 재생성 범위에 따라 CPU 비용이 커질 수 있다. 버퍼 생성 후 CPU 배열 용량을 해제하는 선택도 메모리 회수와 다음 생성의 재할당 비용 사이에 절충이 있다.

다시 보강한다면 다음 순서로 확인할 수 있다.

1. 노출 면·정점·인덱스 수, 메시 생성 시간, GPU 버퍼 생성 시간을 각각 측정한다.
2. 특수 형상의 면 가림·방향·조명 규칙을 통일한다.
3. 물의 정렬과 깊이 정책을 중첩 장면에서 확인한다.
4. 반복 편집이 많은 영역을 더 작은 단위로 재메시할지 검토한다.
5. Greedy 병합을 도입한다면 재질뿐 아니라 방향·UV·AO·조명 호환 조건도 함께 정의한다.
