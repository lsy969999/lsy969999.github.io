물·용암의 Tick 기반 확산과 공급원 제거

배경과 목표​

블록을 파괴해 물 아래에 구멍을 만들면 물이 내려가야 하고, 공급원을 없애면 이미 퍼진 물도 줄어들어야 한다. 용암은 물보다 느리게 흐르며, 서로 만나면 고체 블록으로 바뀌는 상호작용도 필요하다.

모든 유체 블록을 매 프레임 검사하는 대신, 갱신이 필요한 위치를 큐에 넣고 물·용암별 시간 간격으로 처리했다. 격자에 저장된 유체 타입과 Level을 바꾸는 게임 규칙 기반 구현이다. 입자 유체, 압력 계산, 질량 보존을 포함한 물리 유체 Solver는 아니다.

변경 데이터 적용과 재메시는 DDA 블록 편집, 발광 갱신은 하늘광·블록광 전파, 표면 생성은 복셀 메시와 렌더링에 연결된다.

유체 타입·Level·Tick 상태​

물과 용암은 각각 정지 원천인 STILL과 흐르는 FLOW 타입을 사용한다. 현재 계산에 쓰는 값은 다음과 같다.

구분물용암
원천 타입WATER_STILLLAVA_STILL
흐름 타입WATER_FLOWLAVA_FLOW
최대 Level73
흐름 Level 읽기Flag 하위 3비트Flag 하위 2비트
목표 Tick 간격0.25초1.3초
메시 상단 높이(Level + 1) / 8(Level + 1) / 4

Level은 유속 벡터나 실제 물의 양이 아니다. 수평 전파 가능 범위와 블록 표면 높이에 사용하는 정수 단계다. Level 0도 AIR가 아니라 각각 1/8, 1/4 높이로 표시할 수 있는 마지막 흐름 단계다.

SWaterTickData·SLavaTickData에는 월드 좌표, bIsStill, Level, 상태가 들어간다. 상태는 확산을 위한 SPREAD와 공급원 상실을 확인하는 DECREASE로 나눈다.

현재 활성 Tick 함수는 이벤트에 기록된 bIsStill·Level보다 처리 시점의 실제 블록 타입·Flag를 다시 읽어 판단한다. 좌표와 상태가 처리의 핵심이며, 이미 다른 블록으로 바뀐 위치의 이벤트는 건너뛴다.

이벤트가 만들어지는 시점​

ProcessPlayerBlockSet()에서 물 원천을 배치하면 Flag 7과 SPREAD 이벤트를, 용암 원천이면 Flag 3과 SPREAD 이벤트를 준비한다. 일반 블록 설치·파괴도 주변 유체의 갱신을 요청한다.

TriggerWaterUpdateAround()와 TriggerLavaUpdateAround()는 변경 위치의 여섯 이웃을 검사한다. 해당 유체의 STILL 또는 FLOW를 찾으면 DECREASE 상태로 큐에 넣는다. 함수 이름의 Trigger는 물리 Trigger Collider의 이벤트가 아니라 이웃 격자를 깨우는 직접 호출이다.

DECREASE는 무조건 지우라는 명령이 아니다. 공급원이 남아 있는지 다시 확인하고, 여전히 공급받는 블록은 확산 경로로 이어질 수 있다. STILL 타입은 감소 분기를 건너뛰므로 주변 변화 이후에도 원천 역할을 유지한다.

최초 지형 생성에서 해수면을 WATER_STILL로 채우는 것과 Tick 등록은 별개다. BlockFilling()의 물 배치 자체에는 큐 삽입이 없으며, 월드의 모든 물을 계속 활성화해 순회하는 구조도 아니다.

한 Tick의 처리 묶음​

CVoxelManager3::Update()는 물을 먼저, 용암을 다음으로 갱신한다. 각 함수는 전달받은 Delta Time을 타이머에 누적하고 목표 시간에 도달하면 한 번 큐를 처리한다.

Plain Text
타이머 도달
  → 현재 큐 전체를 currentTicks로 이동
  → 각 위치의 최신 블록 확인
  → 감소 또는 확산 계산
  → 블록 변경은 EditShadow에 기록
  → 파생 이벤트는 다음 Tick 큐에 등록

처리 시작 시 큐를 비워 별도 목록으로 옮기므로, 같은 유체가 이번 계산 중 새로 만든 이벤트를 즉시 끝까지 따라가지는 않는다. 한 번의 호출로 전체 공간을 Flood Fill하는 대신 다음 Tick으로 확산 작업을 이어간다.

다만 블록 데이터까지 이전 Tick의 복사본으로 고정한 것은 아니다. GetBlock()은 EditShadow를 먼저 읽으므로 현재 목록의 뒤쪽 이벤트가 앞에서 바꾼 값을 볼 수 있다. 엄밀한 이중 버퍼 기반 동시 갱신과 다르며 처리 순서의 영향을 받을 수 있다.

물 처리 중 만들어진 용암 이벤트는 같은 Update에서 용암 타이머도 만료되었다면 바로 처리될 수 있다. 두 큐를 함께 동결하는 통합 시뮬레이션 Step은 아니다.

시간 간격과 처리량은 별도 문제​

타이머는 목표 시간을 넘겼을 때 Reset()으로 누적값을 0으로 만든다. 초과 시간을 보존하거나 밀린 횟수만큼 반복하는 Catch-up 루프가 없으므로, 긴 프레임에서는 실제 경과 시간에 비해 확산이 느려질 수 있다. 0.25초·1.3초는 목표 간격이지 모든 실행 조건에서 정확한 처리 주기를 보장하는 값은 아니다.

또한 현재 큐 전체를 한 번에 처리하며 개수·시간 예산이 없다. Tick 방식은 불필요한 매 프레임 계산을 줄이는 구조지만, 이벤트가 많이 쌓인 한 Tick의 부하까지 제한하지는 않는다.

낙하를 우선하는 확산 규칙​

아래가 열려 있을 때​

아래 칸이 AIR 또는 같은 종류의 FLOW이면 낙하 가능한 공간으로 본다. AIR이거나 아래 흐름의 Level이 최대보다 작으면, 아래를 최대 Level의 FLOW로 바꾸고 다음 SPREAD를 예약한다.

물은 아래에 Level 7, 용암은 Level 3을 만든다. 현재 블록을 비우거나 Level을 그만큼 빼지는 않는다. 따라서 유체량을 옮기는 질량 보존 방식이 아니라 흐름을 생성하는 규칙이다.

아래가 낙하 가능한 조건이면 그 Tick의 수평 확산은 건너뛴다. 아래가 이미 최대 Level의 FLOW라서 값 변경을 하지 않아도 이 우선순위는 유지한다.

아래로 흐를 수 없을 때​

현재 Level이 0보다 크면 수평 네 방향을 검사한다. 기본 전달 Level은 현재 Level - 1이며, AIR 또는 전달 Level보다 낮은 같은 종류의 FLOW에 확산한다.

평평한 바닥 위에서 다른 공급원이나 낙하 조건이 없다면 다음과 같은 단계가 만들어진다.

Plain Text
물   : 원천 7 → 흐름 6 → 5 → … → 0
용암 : 원천 3 → 흐름 2 → 1 → 0

추가로 목적지 바로 아래가 AIR이면 전달 Level을 현재 Level과 같게 유지한다. 가장자리에서 옆 칸으로 넘어간 뒤 낙하를 이어가기 위한 규칙이다. 현재 코드는 먼저 감소 Level로 확산 가능성을 검사하고 이후 이 보정을 하므로, 보정값을 기준으로 모든 기존 흐름을 갱신하는 것은 아니다.

자연 확산은 위로 진행하지 않는다. 위 칸은 물·용암 접촉 반응의 검사 대상으로만 포함된다. 아래 블록이 미로드되어 조회되지 않는 경우에는 아래를 생성하지 않고 이후 수평 검사로 이어질 수 있다.

공급원이 끊기면 줄어드는 과정​

FLOW에 DECREASE 이벤트가 들어오면 먼저 공급 가능성을 검사한다.

  1. 위에 같은 종류의 STILL 또는 FLOW가 있으면 공급이 있다고 본다.
  2. 그렇지 않으면 수평 이웃에서 STILL을 찾는다.
  3. 수평 FLOW가 자신의 Level보다 높아도 공급이 있다고 본다.

원천 ID나 실제 유체 경로를 추적하는 것은 아니다. 주변 타입과 Level의 관계로 공급을 판단하는 로컬 규칙이다.

공급이 없다면 Level이 0인 흐름은 AIR로 바꾸고 주변 유체를 다시 깨운다. 0보다 크면 Level을 1 낮추고 자기 위치를 다음 DECREASE로 예약한다. 이때 아래와 수평 이웃 중 기존 자신의 Level 이하인 FLOW에도 감소 확인을 전파한다. 위 방향은 이 연쇄 감소 후보에서 제외한다.

이렇게 공급원 제거 후 흐름이 여러 Tick에 걸쳐 줄어드는 연출을 구성한다. 공급이 남아 있으면 감소하지 않고 확산 처리로 이어진다. 따라서 DECREASE 이벤트를 넣었다는 사실만으로 결국 사라진다고 단정할 수 없다.

큐 중복 억제의 범위​

각 Tick은 nextTickSet과 decreasedSet을 사용한다. 전자는 다음 이벤트를 같은 좌표에 반복 예약하는 것을 줄이고, 후자는 이미 감소한 좌표를 이웃 감소 후보로 다시 넣는 것을 줄인다.

하지만 완전한 중복 제거기는 아니다.

  • Tick 시작 시 가져온 currentTicks 자체는 중복 제거하지 않는다.
  • 주변 갱신 함수와 일부 접촉 반응은 Set을 거치지 않고 큐에 직접 넣는다.
  • nextTickSet의 키는 좌표뿐이어서 SPREAD와 DECREASE를 별개 요청으로 구분하지 않는다.
  • decreasedSet은 이웃 후보 판정에 쓰이며, 현재 목록에 중복된 동일 좌표를 무조건 한 번만 처리하도록 막지는 않는다.

여러 편집·접촉이 겹치는 경우를 확인해야 하는 이유다. 개선한다면 좌표별 대기 상태 병합과 상태 우선순위를 정하고, 한 Tick에서 동일 좌표를 몇 번 계산할지 명시할 수 있다.

물·용암 접촉 시 고체 블록으로 변경​

활성 구현은 아래 칸의 반응을 먼저 검사하고, 이후 조건이 맞으면 수평·위 칸도 확인한다. 아래로 낙하하거나 반응한 경우에는 이후 방향 검사를 건너뛸 수 있고, 수평·상단 반응은 현재 Level이 0보다 클 때의 경로 안에 있다. 모든 접촉면을 항상 독립적으로 검사하는 방식은 아니다.

반응 결과는 처리하는 유체에 따라 다음과 같다.

실행 중인 Tick상대 칸고체가 되는 위치결과 판단
물용암상대 용암 칸상대가 STILL이면 흑요석, FLOW이면 조약돌
용암물상대 물 칸현재 용암이 STILL이면 흑요석, FLOW이면 조약돌

즉 ‘물이 닿으면 언제나 용암 자리만 굳는다’는 대칭 규칙은 아니다. 두 유체의 타이머와 처리 순서에 따라 변경되는 위치가 달라질 수 있다. 원작의 모든 접촉 규칙을 동일하게 재현했다고 설명하지 않는다.

고체로 바꾼 칸의 Flag를 0으로 만들고, 조명 처리와 두 유체의 주변 갱신을 요청한다. 막힌 현재 유체에도 DECREASE 이벤트를 넣는다. 앞서 설명한 것처럼 STILL 원천은 이 이벤트만으로 소멸하지 않는다.

블록 편집·조명·렌더링 연결​

논리 변경과 재메시​

유체 Tick은 대부분 SetBlock()으로 EditShadow에 변경을 남긴다. 이후 기존 블록 편집 경로가 실제 청크 배열 적용과 재메시를 처리한다. 유체 전용으로 매 프레임 메시를 별도 생성하는 것이 아니다.

플레이어가 놓은 원천은 편집 기록을 남기지만, 자연 확산의 직접 SetBlock() 호출은 기본 기록 옵션을 사용한다. 다만 조명 처리 내부에서 기록되는 변경도 있으므로, ‘모든 유체 변화가 저장된다’거나 ‘유체 관련 변화는 전혀 기록되지 않는다’고 단순화할 수 없다. 재로드 후 흐름을 복구하려면 원천·파생 흐름·대기 Tick의 보존 정책을 함께 정해야 한다.

조회할 수 없는 위치의 이벤트는 건너뛰며, 이 Tick 함수에는 미로드 위치를 따로 보관했다가 청크 로드 후 다시 깨우는 체계가 없다. 무한 월드 전체에서 유체가 계속 진행된다는 보장은 하지 않는다.

용암 발광 갱신의 확인점​

용암은 블록광 15를 내는 타입이다. 감소·AIR 전환·접촉으로 고체가 되는 곳에서 조명 후처리를 호출한다. 현재 감소 중에는 Level이 낮아져도 타입이 FLOW인 동안 발광량 자체를 Level에 비례해 줄이지 않는다.

자연 확산의 두 경로에는 좌표 일관성 문제가 보인다. 아래 또는 옆 목적지에 SetBlock()을 수행한 다음, RuntimeOnBlockPlacedLighting()에는 목적지의 이전 블록 복사본과 현재 공급 블록 좌표를 함께 넘긴다. 변경 좌표와 이전 상태의 출처가 다르므로 목적지 조명 갱신이 올바르다고 보장할 수 없다. 이번 작업에서는 발견 사항을 문서에 남겼으며 소스를 수정하지 않았다.

수위가 메시 높이로 보이는 방식​

BuildWaterMesh()는 Level을 8단계 높이로, BuildLavaMesh()는 4단계 높이로 바꾼다. 같은 유체의 옆 칸보다 높으면 그 높이 차이에 해당하는 옆면을 생성한다. 현재 활성 표면은 블록별 평평한 상단이며, 이웃 모서리 수위를 보간하는 이전 구현과 구분된다.

물은 별도의 Water 메시 목록, 용암은 Solid 목록으로 들어간다. 확산 Tick과 텍스처 애니메이션도 별개다. 현재 텍스처 Frame은 별도 누적 시간의 0.1초 단위로 계산하므로 표면 무늬가 움직이는 것과 블록이 다음 칸으로 퍼지는 것은 서로 다른 갱신이다.

용암 메시의 자신 Level 마스크는 0x03이지만 옆 칸 조회는 0x07을 사용한다. 현재 0~3 Flag만 다룰 때와 향후 다른 Flag 비트를 함께 사용할 때를 구분해 점검해야 한다.

구현 범위와 확인할 사례​

이 작업의 핵심은 원천 배치·환경 변경으로 활성 위치를 만들고, 확산과 감소를 시간차로 이어가며 기존 복셀 편집·렌더링 구조에 연결한 것이다. 물과 용암이 공통 규칙을 공유하지만 실제 코드는 별도 함수로 구현되어 있다. 범용 유체 정책 시스템으로 추상화한 상태는 아니다.

검증 자료는 다음 순서로 준비할 수 있다.

  • 평평한 바닥에서 물·용암의 확산 단계와 속도 비교.
  • 바닥 제거 시 낙하 우선 처리, 아래 흐름이 최대 Level일 때의 수평 제한.
  • 원천 제거 후 Level 감소, 여러 공급원 중 하나만 제거한 경우.
  • 물 위에 용암·용암 위에 물을 두고 반응 위치와 결과 비교.
  • 청크 경계 확산, 미로드 경계 접근, 언로드·재로드 후 복원.
  • 다수 원천과 대량 블록 편집에서 중복 이벤트·Tick 시간·재메시 청크 수 측정.
  • 용암 확산 목적지의 조명과 공급원 제거 후 잔광 확인.

개선 우선순위는 갱신 좌표 일관성, 다중 이벤트 병합, 접촉 반응 정책, 처리 예산과 미로드 복원 정책이다. 이번 문서는 현재 코드 조사 결과이며 새로운 시연·성능 측정이나 수정 완료를 주장하지 않는다.

작성 근거와 확인 범위​

VoxelManager3.cpp의 활성 UpdateWaterTick()·UpdateLavaTick(), 주변 갱신 함수와 플레이어 블록 배치, VoxelManager3.h의 Tick 데이터, Timer.h, Chunk3.cpp의 활성 물·용암 메시 생성, Block3.h의 발광 분류를 기준으로 정리했다. 같은 파일에 블록 주석으로 남은 이전 Tick 구현은 현재 동작에서 제외했다.

관련 이력은 316371d의 물 지형·전용 버퍼 도입과 1391604의 유체 관련 변경이며, 기준 체크아웃은 e38a951이다. 게임 소스와 리소스는 변경하지 않았다.
