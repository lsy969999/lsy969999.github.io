팀 공통 정기 배포와 C*erry 브랜치 이주 사례

개요​

C*erry 팀에서 매주 목요일 정기 배포를 전담했다. 이미 구축된 Kubernetes·GitLab 환경을 활용한 운영 업무였다. 이와 별개로 C*erry 개발 중 발생한 브랜치 정리 상황에서는 기존 기준점을 보존하고 새 기준점으로 master를 바꾸는 이주 계획을 작성했다.

정기 배포는 팀 공통 업무였고, 브랜치 이주는 C*erry 개발 중 진행한 별도 작업이었다.

기존 환경에서 담당한 정기 배포​

개발 브랜치와 배포 브랜치를 나누어 사용하는 환경에서 개발 결과를 운영에 반영하는 업무를 지속적으로 맡았다. 인프라 최초 구축이 아니라 기존 환경의 배포 운영 경험이다.

별도 사례: master 브랜치의 기준점 변경​

C*erry 개발 중의 일회성 상황을 다루기 위해 master 브런치 이주계획을 남겼다. 장기적인 브랜치 전략 전체를 새로 도입한 사례가 아니라, 기존 master 대신 지정한 커밋을 새 기준으로 삼으려는 작업 계획이다.

기존 기준점과 새 기준점을 별도로 보존​

이름계획에서의 역할
기존 master변경 전 기준점
target새 기준으로 삼을 커밋
master_migratetarget에서 만든 임시 브랜치
master_backup기존 master를 보존하는 백업 브랜치
새 master임시 브랜치를 최종 이름으로 전환한 기준점

기록에 남은 순서는 다음과 같다.

  1. 새 기준 커밋에서 임시 브랜치를 만든다.
  2. 기존 master는 master_backup으로 남긴다.
  3. 원격 브랜치 이름 교체를 포함해 임시 브랜치를 새 master로 전환한다.
  4. 이후 개발·배포 테스트를 진행하도록 계획한다.

이는 두 코드 흐름을 합치는 병합 작업이 아니다. 브랜치가 가리키는 기준을 교체하는 계획이므로, 기존 master에만 있던 변경이 새 기준에 자동으로 포함되는 것은 아니다. 백업 브랜치는 이전 커밋에 접근할 기준을 남기는 역할을 한다.

돌아보며: 브랜치 이름 밖의 의존성도 확인해야 한다​

브랜치 기준점을 교체할 때는 커밋 보존 외에도 다음 항목을 확인해야 한다.

  • 기존 기준과 새 기준의 차이를 비교해 유지할 변경이 빠지지 않는지 확인한다.
  • 기본·보호 브랜치 설정과 배포 파이프라인의 브랜치 참조를 확인한다.
  • 동료의 로컬 추적 브랜치와 진행 중인 병합 요청에 영향을 알린다.
  • 이전 커밋을 남기는 것과 운영 환경을 이전 상태로 복구하는 것은 별도로 검증한다.

정기 배포를 맡으면서 팀의 변경 사항을 운영 환경에 반영했다. 브랜치 기준점을 교체할 때는 이전 상태를 보존하고 변경 순서를 계획으로 남겼다.
