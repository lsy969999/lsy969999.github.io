# C\*erry Run 가입 스파이크와 PostgreSQL 인덱스 개선

## 개요 {/* #article-introduction */}

C\*erry의 C\*erry Run 이벤트 개시 후 가입 요청이 급증하면서 DB 부하와 응답 지연이 발생했다. 원인을 살펴보니 사용자 조회에 필요한 인덱스가 없거나 비교 조건에 맞지 않아 풀스캔을 하는 문제가 있었다. 조회별 인덱스를 추가하고, 일반 컬럼 인덱스로 해결되지 않은 대소문자 무시 검색에는 표현식 인덱스를 적용했다.

2023년 7월, C\*erry Run 이벤트 개시로 가입자가 급증하면서 사용자 조회에 부하가 집중됐다. 당시 C\*erry World 개발과 함께 대응한 C\*erry의 운영 문제였다.

## 현상: 요청 집중과 DB 지연 {/* #1-현상-요청-집중과-db-지연 */}

업무 노트에는 트래픽이 몰리는 이벤트에서 DB CPU 사용량이 높아지고 애플리케이션 트랜잭션이 지연되다가 타임아웃이 발생했다는 기록이 있다. 7월 4일 자료의 RDS 조회 화면에도 사용자 식별값과 이메일 조건의 쿼리가 높은 부하 항목으로 나타난다.

RDS 화면의 해당 쿼리들은 `Avg latency (ms)/call`이 약 83,779~96,885ms로 표시됐다.

[![RDS에서 높은 부하와 호출당 평균 지연이 관측된 세 쿼리](/img/work-evidence/query-load-observation.png)](/img/work-evidence/query-load-observation.png)

*2023.07.04 RDS 관측 화면. SQL 원문은 가리고 부하·호출 빈도·지연 수치는 남겼다.*

부하가 큰 조회를 찾고, 실행 계획에서 데이터 접근 방식을 확인했다.

## 쿼리 조건과 인덱스의 불일치 {/* #2-쿼리-조건과-인덱스의-불일치 */}

대상에는 사용자 식별값 조회와 이메일·닉네임의 대소문자 무시 비교가 있었다. 일반 컬럼 인덱스를 추가한 뒤에도 `LOWER(컬럼)`으로 비교하는 조회는 원하는 실행계획으로 바뀌지 않았다.

다음은 실제 테이블·컬럼·사용자 값을 제거한 설명용 예시다.

```sql title="조회 형태를 재구성한 예시"
SELECT COUNT(*)
FROM example_member
WHERE lower(display_name) = lower(:search_name);

CREATE INDEX example_member_lower_name_idx
ON example_member (lower(display_name));
```

핵심은 컬럼 이름이 같다는 것만으로 충분하지 않았다는 점이다. 비교 대상인 `lower(display_name)`의 결과에 맞는 인덱스를 마련했다. PostgreSQL의 표현식 인덱스 문서도 `lower(컬럼)`을 비교하는 조회와 그 표현식에 대한 인덱스를 예로 든다. 인덱스 유지에는 쓰기 비용이 있으므로 조회 개선만으로 무조건 추가하는 구조는 아니다. [PostgreSQL — Indexes on Expressions](https://www.postgresql.org/docs/current/indexes-expressional.html).

이 사례를 “함수를 쓰면 언제나 모든 인덱스가 무효가 된다”는 규칙으로 일반화하지 않는다. 당시 쿼리와 인덱스 조합에서 관측한 문제와 수정이다.

## 7월 4일: 일반 인덱스 적용 후 남은 조회 재확인 {/* #3-7월-4일-일반-인덱스-적용-후-남은-조회-재확인 */}

사용자 식별값과 이메일 조회에 인덱스를 추가했다. 이메일을 소문자로 비교하는 조건에는 순차 스캔이 남아 있어, 소문자 변환 표현식에도 인덱스를 추가했다.

```text
높은 부하의 사용자 조회 확인
          ↓
조회 컬럼의 일반 인덱스 추가
          ↓
LOWER 조건의 실행계획 재확인
          ↓
표현식에 맞는 인덱스 추가
          ↓
Bitmap Index Scan 사용 확인
```

인덱스 생성 명령이 성공했다고 작업을 끝내지 않고, 대상 조회가 실제로 변경된 인덱스를 사용하는지 다시 확인했다. 남아 있는 캡처에서는 이메일 표현식 조건에 Bitmap Index Scan과 Bitmap Heap Scan을 사용하는 계획을 볼 수 있다.

## 7월 5일: 닉네임 조회에도 같은 원인 확인 {/* #4-7월-5일-닉네임-조회에도-같은-원인-확인 */}

다음 날에는 닉네임 조회에서도 같은 문제를 발견했다. 닉네임 컬럼에 인덱스가 있었지만 실제 조건은 `LOWER(닉네임)`이었다. 표현식에 맞춘 인덱스를 추가한 뒤 실행계획을 비교했다.

| 비교 항목 | 수정 전 캡처 | 수정 후 캡처 |
| --- | --- | --- |
| 계획의 주요 형태 | Aggregate·Gather 아래 순차 스캔 | Aggregate 아래 Bitmap Heap Scan·Bitmap Index Scan |
| 선택된 노드 | Seq Scan | Bitmap Index Scan |
| 선택 노드의 Actual Total Time | 114.808ms | 0.066ms |
| 선택 노드의 Actual Loops | 3 | 1 |

이 표는 캡처를 그대로 읽은 관측 정보이며 성능 향상률 계산표가 아니다. 수정 전에는 순차 스캔 노드, 수정 후에는 비트맵 인덱스 탐색 노드를 선택했고, 수정 후의 힙 접근과 집계 전체 시간이 같은 칸에 들어 있지 않다. 두 숫자를 나눠 전체 쿼리가 몇 배 빨라졌다고 계산할 수 없다.

`EXPLAIN`의 cost는 실행 시간 자체가 아니며, `EXPLAIN ANALYZE`의 실제 시간과 반복 횟수는 노드 기준으로 해석해야 한다. 이 구분은 PostgreSQL 공식 설명과도 일치한다. [PostgreSQL — Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html).

## 인덱스 적용 결과 {/* #5-결과로-남길-수-있는-것 */}

조회 조건을 분석하고, 일반 인덱스로 해결되지 않은 조건에 표현식 인덱스를 적용했다. 변경 후에는 순차 스캔 대신 비트맵 인덱스 접근을 사용하는 것을 확인했다.

당시 작업 후 DB CPU 사용량이 80~99%에서 10~20%로 낮아진 것을 업무 노트에 기록했다.

## 가입자 집중 시 남긴 AWS 대기 부하 화면 {/* #6-가입자-집중-시-남긴-aws-대기-부하-화면 */}

8월 5일에도 가입자가 몰리면서 AWS의 대기 부하를 확인했다. 아래 화면은 7월 인덱스 작업과 별개 시점의 기록이다.

[![가입자 집중 시 AWS의 평균 활성 세션 그래프와 빨간 Lock:tuple 대기 부하, 상위 SQL 목록](/img/work-evidence/aws-lock-wait-observation.png)](/img/work-evidence/aws-lock-wait-observation.png)

*2023.08.05 AWS 관측 화면. SQL과 내부 테이블·컬럼 이름은 가렸다.*

이 화면의 세로축은 CPU 사용률이 아니라 **평균 활성 세션(AAS)**이다. 빨간 영역은 범례의 `Lock:tuple`이며, 잠금 획득을 기다리는 부하다. AWS 공식 설명에서도 이 이벤트는 같은 튜플에 대한 충돌하는 잠금이 해제되기를 기다리는 상황으로 설명한다. [AWS — Lock:tuple](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/apg-waits.locktuple.html).

캡처에서 확인한 항목은 다음과 같다.

- `Lock:tuple`, `Lock:transactionid`, `Timeout:VacuumDelay` 등의 대기가 표시됐다.
- 10:24 UTC의 총 DB 로드는 3.63, 최대 vCPU 수는 2였다.
- 상위 SQL 첫 항목의 대기 부하는 3.61로 표시됐다.

가입자가 몰릴 때 느려진 조회와 함께 대기 종류, 부하가 높은 SQL을 확인했다.

## 추가 인덱스가 항상 개선은 아니었다 {/* #7-추가-인덱스가-항상-개선은-아니었다 */}

별도의 요구사항에 대응해 인덱스를 추가했다가 기존 조회의 실행계획이 달라지고 성능이 저하된 적도 있었다. 이때는 추가한 인덱스를 다시 제거했다.

이 경험을 통해 인덱스 존재 여부만 보는 것이 아니라, 자주 실행되는 조회와 변경 이후의 계획을 함께 점검해야 한다는 관점을 갖게 됐다. 복합 인덱스의 순서와 표현식 조건도 같은 맥락에서 확인했다.
