# 팀 공통 정기 배포와 C\*erry 브랜치 이주 사례

## 개요 {/* #article-introduction */}

C\*erry 팀에서 매주 목요일 정기 배포를 전담했다. 이미 구축된 Kubernetes·GitLab 환경을 활용한 운영 업무였다. 이와 별개로 C\*erry 개발 중 발생한 브랜치 정리 상황에서는 기존 기준점을 보존하고 새 기준점으로 `master`를 바꾸는 이주 계획을 작성했다.

정기 배포는 특정 제품만의 업무가 아닌 팀 공통 업무다. 중복 서술을 피하기 위해 이 문서에 모았으며, 브랜치 이주 사례만 C\*erry 개발에 해당한다.

## 기존 환경에서 담당한 정기 배포

개발 브랜치와 배포 브랜치를 나누어 사용하는 환경에서 개발 결과를 운영에 반영하는 업무를 지속적으로 맡았다. 인프라 최초 구축이 아니라 기존 환경의 배포 운영 경험이다.

| 구분 | 담당 범위와 기록 |
| --- | --- |
| 배포 주기 | 매주 목요일 정기 배포 전담 |
| 협업 환경 | 개발 브랜치와 배포 브랜치를 분리한 기존 환경 |
| 사용 환경 | 이미 구성된 Kubernetes·GitLab |
| 별도 사례 | C\*erry 개발 중 master 브랜치 이주 계획 작성 |
| 포함하지 않는 주장 | CI/CD 최초 구축, 무중단 배포 설계, 배포 자동화율·장애율 개선 수치 |

정기 배포와 다른 운영 문서의 주간 Pod 재시작은 같은 작업이라고 단정하지 않는다. 주기가 같다는 사실만으로 실행 목적이나 절차까지 동일했다고 볼 수는 없다.

## 별도 사례: master 브랜치의 기준점 변경

C\*erry 개발 중의 일회성 상황을 다루기 위해 `master 브런치 이주계획`을 남겼다. 장기적인 브랜치 전략 전체를 새로 도입한 사례가 아니라, 기존 `master` 대신 지정한 커밋을 새 기준으로 삼으려는 작업 계획이다.

이주를 필요로 했던 구체적인 발단은 남아 있는 자료만으로 확정하기 어렵다. 잘못된 병합, 이력 손실 등의 원인을 임의로 덧붙이지 않는다.

### 기존 기준점과 새 기준점을 별도로 보존

| 이름 | 계획에서의 역할 |
| --- | --- |
| 기존 master | 변경 전 기준점 |
| target | 새 기준으로 삼을 커밋 |
| master_migrate | target에서 만든 임시 브랜치 |
| master_backup | 기존 master를 보존하는 백업 브랜치 |
| 새 master | 임시 브랜치를 최종 이름으로 전환한 기준점 |

기록에 남은 순서는 다음과 같다.

1. 새 기준 커밋에서 임시 브랜치를 만든다.
2. 기존 `master`는 `master_backup`으로 남긴다.
3. 원격 브랜치 이름 교체를 포함해 임시 브랜치를 새 `master`로 전환한다.
4. 이후 개발·배포 테스트를 진행하도록 계획한다.

이는 두 코드 흐름을 합치는 병합 작업이 아니다. 브랜치가 가리키는 기준을 교체하는 계획이므로, 기존 `master`에만 있던 변경이 새 기준에 자동으로 포함되는 것은 아니다. 백업 브랜치는 이전 커밋에 접근할 기준을 남기는 역할을 한다.

원본에는 명령 순서까지 있지만 이 문서에는 운영 저장소에서 그대로 실행할 수 있는 삭제 명령을 싣지 않았다. 계획 기록과 실제 작업 완료·검증 결과도 구분한다. 남아 있는 자료만으로 이주 성공이나 복구 시간을 수치로 주장하지 않는다.

## 돌아보며: 브랜치 이름 밖의 의존성도 확인해야 한다

이 사례를 현재 관점에서 검토하면, 커밋 보존 외에도 다음 확인이 필요하다. 아래 항목은 당시 모두 수행했다는 실적이 아니라 이주 계획을 보완할 점이다.

- 기존 기준과 새 기준의 차이를 비교해 유지할 변경이 빠지지 않는지 확인한다.
- 기본·보호 브랜치 설정과 배포 파이프라인의 브랜치 참조를 확인한다.
- 동료의 로컬 추적 브랜치와 진행 중인 병합 요청에 영향을 알린다.
- 이전 커밋을 남기는 것과 운영 환경을 이전 상태로 복구하는 것은 별도로 검증한다.

이 문서에서 보여 주려는 기여는 팀 공통 배포 업무의 담당 경험과, 브랜치 정리 시 변경 전후 기준을 분리해 절차로 남긴 경험이다. 대규모 인프라 전환이나 새로운 Git 전략 수립으로 과장하지 않는다.

## 관련 운영 대응

정기 배포 외에 [Argo CD 외부 노출 관련 보안 사고 대응](/projects/cherry/argocd-security-response) 기록도 남아 있다. 반복되는 Pod 종료를 로그로 추적하고 내부망 접근 제한과 버전 업그레이드로 대응한 사례다. 배포 환경을 처음 구축한 경험이나 정기 배포 절차의 일부로 합치지 않고 별도 문서로 구분했다.

## 작성 근거와 확인 범위 {/* #작성-근거 */}

당시 업무 노트의 `운영배포 전담`과 `master 브런치 이주계획`, 담당자 회고를 바탕으로 작성했다. 정기 배포는 팀 공통, 브랜치 이주는 C\*erry 개발 중의 사례라는 구분을 반영했다. 내부 저장소 주소와 커밋 식별자는 공개하지 않았다.
