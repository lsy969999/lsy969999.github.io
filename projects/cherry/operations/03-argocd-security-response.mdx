# Argo CD 외부 노출 관련 보안 사고 대응

## 개요 {/* #article-introduction */}

서비스 Pod가 반복적으로 종료되는 현상을 조사하다 외부 접근과 관련된 종료 흔적을 확인했다. 대응 과정에서 외부에 공개돼 있던 Argo CD의 접근을 내부망으로 변경하고 버전을 업그레이드했다. 업무 노트에는 내부망 전환 후 같은 공격이 더 들어오지 않았다는 관측을 남겼으며, 버전 업그레이드도 함께 수행했다는 내용은 후속 회고로 보완했다.

이 사례는 노션의 「argo 해킹 이슈」에 남긴 대응 경험이다. 원문은 제품명을 `argo`로 적었고, 회고에서 Argo CD를 지칭한 것으로 확인했다. 팀 운영 사례를 모아 둔 C\*erry의 운영·성능 개선 그룹에 배치했으며, 특정 제품만의 인프라였거나 특정 재직 구간에 발생했다고 단정하지 않는다.

## 반복 종료에서 외부 접근 흔적으로

처음 드러난 증상은 서비스 Pod가 계속 종료되는 것이었다. 업무 기록에는 `stderr` 로그를 확인한 결과 외부 IP에서 발생한 `kill pod` 관련 로그를 확인했다고 적혀 있다. 이를 바탕으로 애플리케이션 내부 오류만이 아니라 외부에서 운영 자원을 제어하는 경로를 살폈다.

원본 로그가 현재 증빙에 포함돼 있지는 않다. 따라서 이 표현을 Kubernetes 감사 로그의 특정 이벤트나 API 호출로 바꿔 쓰지 않는다. 확인 가능한 것은 당시 로그를 근거로 외부 공격으로 판단하고 대응했다는 기록이다.

## 대응: 내부망 전환과 버전 업그레이드

당시 Argo는 구버전이었고 외부에서 접근할 수 있는 상태였다. 공개 접근을 내부망으로 제한했으며 버전 업그레이드도 진행했다. 두 조치는 같은 역할이 아니다. 내부망 전환은 외부에서 접근할 수 있는 범위를 줄이는 조치이고, 보안 수정이 포함된 버전으로의 업그레이드는 취약한 구현을 수정하는 대응이다.

| 단계 | 업무 노트·회고에 남은 내용 |
| --- | --- |
| 증상 | 서비스 Pod가 반복적으로 종료됨 |
| 조사 | 로그에서 외부 IP와 관련된 Pod 종료 흔적 확인 |
| 당시 판단 | 외부에 공개된 구버전 Argo를 통한 공격으로 판단 |
| 접근 제한 | Argo CD 접근을 public에서 내부망으로 변경 |
| 버전 변경 | 버전 업그레이드도 수행했다고 후속 회고에서 확인 |
| 이후 관측 | 변경 후 공격이 더 들어오지 않았다고 기록 |

변경 전후의 정확한 버전과 적용 순서는 현재 자료에 남아 있지 않다. 자격정보 교체·권한 재설정까지 수행했다고 추가하지 않으며, 내부망 전환을 보안 그룹·Ingress·VPN 중 어떤 설정으로 구현했는지도 확인되지 않아 구체적인 구성도를 재현하지 않았다.

## 회고상 추정되는 취약점: CVE-2022-29165

후속 회고에서는 당시 대응한 문제가 조작된 JWT를 이용하는 `CVE-2022-29165`였던 것으로 기억했다. 정확한 사건 원인이 확정된 것으로 바꾸기보다, 공식 공지와 부합하는지 확인할 수 있는 취약점 후보로 남긴다.

Argo CD의 공식 보안 공지는 이 취약점이 **익명 접근이 활성화된 경우** 조작된 JWT를 통해 인증되지 않은 요청자가 사용자나 관리자 권한을 사칭할 수 있는 문제라고 설명한다. 기본 설치에서는 익명 접근이 비활성화돼 있으므로, 외부 공개 상태였다는 사실만으로 이 취약점의 악용 조건이 충족됐다고 볼 수는 없다. [Argo CD 공식 보안 공지](https://github.com/argoproj/argo-cd/security/advisories/GHSA-r642-gv9p-2wjj)

공지는 당시 패치 버전으로 `2.1.15`, `2.2.9`, `2.3.4`를 안내하며, 빠른 업그레이드가 어렵다면 익명 접근 비활성화를 권고했다. 이는 당시 공지의 내용이지 현재 사용할 버전의 추천이나 실제 운영에 적용한 버전의 기록이 아니다. [당시 패치·완화 안내](https://github.com/argoproj/argo-cd/security/advisories/GHSA-r642-gv9p-2wjj#patches)

내부망 전환은 익명 접근 설정을 끄는 것과도 다른 조치다. 실제로 수행한 대응은 내부망 전환과 버전 업그레이드이며, 당시 익명 접근의 활성 여부나 해당 설정을 변경했는지는 현재 기록으로 확인되지 않는다. 공격 요청·설정·버전 이력이 없어 CVE의 특정은 회고상 추정으로 유지한다.

## 결과와 확인 범위

노트에는 내부망으로 변경한 뒤 공격이 더 들어오지 않게 됐다는 관측이 남아 있다. 관측 기간과 종료 횟수의 전후 집계는 없으므로, 무재발 기간이나 공격 차단율을 숫자로 제시하지 않는다.

내부망 전환과 버전 업그레이드를 수행했다는 회고와, 그 조치의 효과를 완전히 검증했다는 주장은 구분한다. 정확한 버전·최초 침투 경로, 계정 탈취나 데이터 유출 여부는 현재 기록으로 확인되지 않는다. 이후 같은 공격이 관측되지 않았다는 사실만으로 기존 침해 흔적까지 모두 제거됐다고 판단하지 않는다.

## 이 경험에서 남은 관점

이 사례의 핵심은 Pod를 다시 띄우는 데서 멈추지 않고, 반복 종료의 원인을 로그와 운영 도구의 접근 경계까지 넓혀 조사했다는 점이다. 애플리케이션 코드 외부의 관리 경로가 서비스 운영에 영향을 줄 수 있다는 점을 경험했다.

현재 문서화에서는 증상, 당시 판단, 실제 조치와 이후 관측을 나누었다. 보안 제품 개발이나 전체 사고 포렌식을 수행한 성과로 확대하지 않고, 운영 중 이상 징후를 추적해 접근 제한과 버전 업그레이드로 대응한 경험으로 정리한다.

[팀 공통 정기 배포와 브랜치 관리](/projects/cherry/release-branch-management)는 같은 운영 업무 묶음의 별도 사례다. 정기 배포, Pod 재시작, 이번 보안 대응을 하나의 작업으로 합치지 않는다.

## 별도 배경: 팀의 Log4j 이슈 대응 경험

재직 중 Log4j 보안 이슈로 팀에서 JDK와 Log4j 버전을 긴급하게 올렸던 경험도 있다. 다만 **해당 업그레이드를 직접 수행한 것은 아니다.** 이 내용은 당시 운영 환경에서 보안 이슈에 대응하는 과정을 경험한 배경이며, 나의 패치·마이그레이션 구현 실적으로 포함하지 않는다.

정확한 Log4j CVE, 변경 전후 버전과 JDK 업그레이드를 병행한 세부 이유는 현재 회고만으로 특정하지 않는다. Apache는 Log4j 보안 문제를 개별 취약점별로 안내하고 있으므로, 이 기억을 특정 CVE로 단정하거나 JDK 업그레이드만으로 해결된 사례라고 설명하지 않는다. [Apache Logging Services 보안 공지](https://logging.apache.org/security.html)

Argo CD 사건과 같은 시기에 발생했다거나 하나의 공격으로 이어진 사건이라는 의미도 아니다. 직접 대응한 Argo CD 경험과 동료가 수행한 Log4j·JDK 업그레이드를 분리해 기록한다.

## 작성 근거와 확인 범위 {/* #작성-근거와-공개-범위 */}

당시 노션 업무 기록의 「argo 해킹 이슈」 항목과 후속 회고를 기준으로 작성했다. 노트에는 반복 종료·로그 확인·구버전 공개 접근·내부망 전환과 이후 관측이 남아 있고, 회고로 버전 업그레이드 및 CVE 후보를 보완했다. 공식 보안 공지는 취약점의 조건을 설명하는 출처이지 당시 사건에서 해당 CVE가 악용됐음을 증명하는 자료는 아니다.

Log4j·JDK 업그레이드 내용은 직접 작업하지 않았다는 범위를 포함해 회고로 추가했다. 두 사건의 정확한 날짜와 설정 변경 이력은 확인되지 않았다.

내부 서비스·Pod 이름, IP·호스트·계정 정보와 운영 설정은 공개하지 않는다. 확인한 해당 항목은 텍스트 메모이며, 실제 공격 로그나 Argo CD 화면 캡처를 확보한 것으로 소개하지 않는다. 증빙처럼 보이는 화면을 새로 만들거나 다른 사건의 이미지를 붙이지 않았다.
