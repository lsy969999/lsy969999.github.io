사용자·관리자 기능과 제휴·시즌 이벤트

개요​

기존 기부 플랫폼에서 기능을 추가하는 작업은 화면 한 장을 만드는 것만으로 끝나지 않았다. 사용자에게 보여 줄 정보와 관리자가 수정할 데이터, 기존 페이지 흐름을 함께 고려해야 했다. 반복되는 관리자 구성은 공통화하고, 제휴·행사 화면은 각 요구사항에 맞춰 구현했다.

운영자와 요구사항을 확인하는 과정에서는 Excel로 정리할 수 있는 내용을 문서화했다. 구현뿐 아니라 반복되는 업무 협의 방식을 개선하는 작업도 함께 수행했다.

관리자 화면의 반복 구조​

업무 기록에는 Thymeleaf와 thymeleaf-layout 기반으로 검색 조건과 데이터 테이블을 공통화한 내용이 남아 있다. 관리자 기능은 목록을 검색하고 결과를 확인하는 형태가 반복되므로, 각 화면을 완전히 독립적으로 만드는 대신 공통 구성을 활용했다.

구성역할
페이지별 검색 조건해당 업무에서 필요한 조회 기준 입력
공통 레이아웃여러 관리자 화면에서 반복되는 화면 구성 재사용
데이터 테이블검색 결과 표시와 관리 작업의 진입점
페이지별 처리업무마다 다른 입력·조회 조건을 적용

공통화의 범위는 관리 화면에서 반복되는 구성이다. 범용 관리자 프레임워크나 자동 CRUD 생성기를 개발한 것으로 소개하지 않는다. 당시 기록에는 이 작업의 개발 시간 단축률이나 코드 감소량은 남아 있지 않다.

소울: 외부 회사 연계 후원 페이지​

기록의 「소울 메인 페이지 개발」은 외부 회사에서 연계된 후원 페이지를 개발한 작업이다. 별도 서비스 전체의 소유권을 맡은 것이 아니라 C*erry의 제휴 후원 기능으로 참여했다.

이 작업은 기존 기부 플랫폼 안에서 외부 요구사항을 사용자 화면으로 연결한 사례다. 공개 자료에는 확인되지 않은 결제 방식, 제휴사의 내부 시스템 구성이나 성과 수치를 추가하지 않는다. 외부 회사와의 연계 범위와 페이지 구현을 중심으로 설명한다.

C*erry Run: 시즌별 챌린지 이벤트​

C*erry Run은 C*erry에서 시즌별로 진행한 챌린지 이벤트다. 업무 기록의 표현은 「C*erry Run 인수인계」다. 따라서 이벤트 전체의 최초 설계·개발과 이후 인수인계받은 업무를 구분하는 것이 중요하다.

인수인계와 유지보수 경험은 새 기능을 만드는 경험과 다르다. 기존 동작과 운영 의도를 이해하고, 시즌별 요구사항을 다룰 수 있도록 맥락을 이어받는 역할이다. 다만 시즌별로 수정한 기능과 담당 범위의 상세 이력이 충분하지 않아, 이 문서에서는 구현하지 않았거나 확인되지 않은 순위·보상·집계 기능을 열거하지 않는다.

후속 운영에서는 이벤트 개시 후 가입 요청이 급증하면서 발생한 DB 스파이크를 분석했다. 사용자 조회의 풀스캔을 확인하고 일반·표현식 인덱스를 적용한 내용은 C*erry Run 가입 스파이크 대응에 별도로 정리했다. 시즌 이벤트 기능을 처음부터 모두 개발한 기여와, 운영 중 병목을 찾아 개선한 기여를 구분한다.

캠페인별 기능 개발과 외부 서비스 연동​

업무 노트에는 행사 이름과 담당 작업이 구체적으로 남아 있다. 기존 문서에서 ‘행사 페이지·외부 활동 서비스 연계’로 묶었던 내용을 아래와 같이 구분한다.

작업기록에 남은 담당 내용
C*erry 캠페인캠페인 상세 페이지 개발
C*erry 스니커즈 데이행사 페이지 개발
Strava외부 활동 서비스 연동
재고관리재고관리 기능 개발
댄스 챌린지기능 개발과 Safari WebView 성능 문제 조사

Strava 연동과 재고관리는 행사 페이지 작업 부근에 함께 기록돼 있지만, 특정 행사와의 정확한 연결 관계까지는 확인되지 않는다. 각각의 담당 업무로 소개하며, Strava의 인증 방식·활동 집계·자동 보상이나 재고 예약·동시성 제어처럼 기록에 없는 기능을 포함하지 않는다.

공통 관리자 화면과 개별 행사 화면의 차이​

관리자 화면은 검색 조건과 데이터 테이블처럼 반복되는 구성을 공통화했다. 반면 이벤트 페이지는 요구조건마다 페이지를 개발했다고 기록했다. 모든 행사 화면을 하나의 공통 틀로 처리한 것이 아니라, 공통으로 사용할 수 있는 관리자 구성과 행사별로 구현할 화면을 구분해 작업했다.

이는 위의 관리자 공통화와 모순되는 설명이 아니다. 재사용한 범위가 관리 화면의 반복 구조였고, 행사마다 달라지는 사용자 화면은 개별 요구사항을 다뤘다는 뜻이다. 범용 이벤트 생성기나 캠페인 저작 도구를 구축한 경험으로 확대하지 않는다.

운영자 요구사항의 Excel 문서화​

요구사항이 생길 때마다 운영자와 미팅하는 부담이 있었다. 이를 개선하기 위해 Excel 문서로 정리할 수 있는 내용은 문서화했다. 기능을 구현하는 것에 더해 요구사항을 전달하고 확인하는 과정도 정리한 것이다.

당시 노트에는 이 작업을 업무 효율 향상으로 기록했다. 다만 모든 미팅을 없앴다는 의미는 아니다. 대화가 필요한 협의와 문서로 남길 수 있는 내용을 구분한 경험으로 설명한다.

현재 자료에는 실제 Excel 양식과 항목, 작성·검토 절차가 남아 있지 않다. 따라서 확인되지 않은 승인 단계나 변경 이력 관리 체계를 만들었다고 적지 않으며, 회의 횟수·처리 시간의 감소율도 제시하지 않는다. 확인 가능한 기여는 반복되는 요구사항 협의에서 문서화 가능한 부분을 찾아 업무 방식에 반영했다는 점이다.

팀 안에서 기술을 연구하고 공유한 다른 경험으로는 사내 연구 프로젝트와 기술 지식 공유가 있다. 운영자 요구사항 정리와 Flutter·Firebase 앱 연구는 목적이 다른 활동이다.

다른 캠페인 작업과 개발 중 피드백​

댄스 챌린지 개발 중에는 Safari WebView에서 느려지는 현상을 디버깅하며 CSS blur 관련 성능 문제를 조사했다. 이 내용은 iOS WebView 성능·문법 호환성 분석에 모았다. 같은 문서의 C*erry World 메인 페이지 문법 오류와는 발생 서비스와 증상이 다른 사례다.

초기 개발 당시 동기 AJAX를 사용해 UI가 멈추는 문제를 겪고 비동기 처리에 대한 피드백을 받은 기록도 있다. 이 경험은 요청 처리 결과를 기다리는 동안 화면이 어떻게 동작하는지까지 고려하게 된 계기다. 이후의 Native–JS 비동기 브리지는 다른 플랫폼 경계에서 호출 흐름을 정리한 사례다.

구현 결과​

이 작업 묶음에서는 관리자 화면의 반복 구조를 공통화하고, 제휴·행사별 요구사항을 구현하거나 인수인계했다. 운영자와의 협의 중 문서화할 수 있는 요구사항은 Excel로 정리했다. 기존 서비스의 기능 개발, 유지보수와 업무 전달 방식 개선을 함께 수행한 경험이다.

작성 근거와 확인 범위​

업무 노트의 관리자 페이지 공통화, 소울 메인 페이지, C*erry Run 인수인계, 캠페인 상세·스니커즈 데이·Strava·재고관리·댄스 챌린지 및 Excel 문서화 항목을 사용했다. 소울과 C*erry Run의 서비스 성격은 담당자 회고로 보완했다. 원본에는 없는 세부 기능과 수치 성과는 추가하지 않았다. 원본 Excel과 해당 행사 화면 이미지는 현재 확인 자료에 없어 임의로 재현해 증빙으로 첨부하지 않았다.
