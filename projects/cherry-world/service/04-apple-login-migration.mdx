# Apple 로그인 마이그레이션과 장애 대응

## 개요 {/* #article-introduction */}

개발자 계정 이전 이후 Apple 비공개 이메일 사용자가 기존 계정으로 인식되지 않는 문제가 발생했다. 변경 전후 식별정보를 매핑하고 LDAP와 RDB의 데이터를 갱신하는 작업을 진행했으며, 처리 중 발견한 SQL 오류와 계정 중복 문제를 분리해 대응했다.

이 사례는 C\*erry World 담당 업무에 해당한다. 원본 자료에 「C\*erry앱」이라는 이름이 사용돼 있지만, 프로젝트 구분은 실제 담당 범위를 확인해 반영했다. 2023년 1월의 장애·이전 기록이며 최신 Apple API 사용 가이드는 아니다.

## 장애의 시작과 초기 판단

당시 서비스는 이메일을 사용자 판단에 활용했다. 앱을 이전해도 동일 이메일이 전달될 것으로 판단했으나, 비공개 이메일 사용자의 식별정보가 달라져 기존 로그인 대신 신규 가입으로 이어지는 문제가 발생했다.

이전 전에 이 차이를 충분히 반영하지 못했다는 점이 출발점이다. 처음부터 모든 예외를 검증한 성공적인 무중단 이전으로 설명하지 않는다.

## 이전 대상을 어디서 찾을 것인가 {/* #1-이전-대상을-어디서-찾을-것인가 */}

처음에는 RDB를 기준으로 대상을 구했으나 사용할 수 없는 데이터가 포함되어 LDAP에서 대상을 조회하는 방식으로 바꿨다. 두 저장소의 역할 차이도 확인했다. 소셜 가입 시도만으로 LDAP에는 정보가 남을 수 있지만, 서비스 가입 완료까지 진행돼야 RDB에도 데이터가 존재했다.

따라서 LDAP에 대상이 있다는 사실만으로 RDB의 대응 행까지 반드시 있다고 가정할 수 없었다. 조회 기준과 실제 갱신 대상의 차이를 분리해야 했다.

## 변경 전후 식별정보 매핑 {/* #2-변경-전후-식별정보-매핑 */}

[![이전 전후 Apple Developer의 Services IDs 설정을 비교한 당시 기록](/img/work-evidence/apple-service-id-migration.png)](/img/work-evidence/apple-service-id-migration.png)

*2023년 1월 마이그레이션 이슈 기록의 설정 비교 화면.* 당시 표시해 둔 메뉴·화살표는 유지하고 회사명·Team ID·서비스 이름·식별자 값은 가렸다. 자격정보와 설정의 전후 맥락을 보여 주는 자료이며, 사용자별 매핑 성공 여부는 아래 결과 파일 집계와 구분한다.

이전 API로 기존 식별자를 중간 이전 식별자에 연결한 다음, 새 계정 기준 식별정보를 얻는 흐름을 구성했다. 이전 양쪽 계정의 자격정보를 구분해 사용해야 했고, 비공개 이메일 사용자와 공개 이메일 사용자의 응답 차이를 고려했다.

```text
기존 사용자 식별자
       ↓ 이전 측 요청
중간 이전 식별자
       ↓ 이전받는 측 요청
새 사용자 식별자 / 해당되는 경우 새 비공개 이메일
       ↓
매핑 이력과 처리 상태 기록
```

키와 토큰의 실제 값, 발급 스크립트 원문은 공개하지 않는다. 원본에는 키 확보와 서명 준비 과정의 시행착오도 기록돼 있으며, 데이터 변경 전에 API 사용 조건을 이해하는 데 시간이 필요했다.

### 남아 있는 결과 파일의 집계

| 항목 | 건수 | 해석 |
| --- | ---: | --- |
| 조회 대상 | 1,987 | 원본 대상 파일의 행 수 |
| 매핑 결과 Y | 1,981 | 매핑 결과 파일의 처리 상태 |
| 매핑 결과 N | 6 | 같은 파일에 실패 상태로 남은 대상 |

이 숫자는 매핑 결과 파일을 집계한 것이다. `Y`를 LDAP·RDB 최종 변경 완료나 사용자별 로그인 성공으로 바꿔 읽으면 안 된다. 실패 6건의 최종 복구 결과는 현재 자료에서 확인되지 않는다.

## LDAP와 RDB 갱신 {/* #3-ldap와-rdb-갱신 */}

매핑 이력을 기준으로 LDAP의 사용자 식별정보와 RDB의 사용자·이메일 정보를 갱신하는 배치를 작성했다. 문서에는 HTTP 요청으로 비동기 작업을 시작하고, 처리 중 실패가 발생하면 중단하는 형태가 기록돼 있다.

중요한 차이는 롤백 범위였다. 당시 구현 기록상 RDB 작업의 예외 롤백과 LDAP 변경은 하나의 원자적 작업이 아니었다. 재실행 시 이미 변경된 데이터가 있을 수 있으므로, 단순히 전체 작업을 다시 실행하는 것만으로 일관성을 보장할 수 없었다.

이미 변경 전후 이메일이 같은 대상에 대한 건너뛰기 조건과 개별 대상 재처리 기록이 남아 있다. 이를 완성된 범용 분산 트랜잭션 또는 자동 보상 처리 체계로 확대해 설명하지 않는다.

## 처리 중 발견한 두 가지 오류 {/* #4-처리-중-발견한-두-가지-오류 */}

### 조건부 UPDATE의 빈 SET

공개 이메일이고 사용자 ID도 변경 조건에 해당하지 않는 대상에서, 변경할 컬럼이 없는 UPDATE가 만들어져 SQL 오류가 발생했다. 정상적인 변경 대상만 예상하고 조건부 SQL을 구성하면 아무 필드도 변경하지 않는 입력이 빠질 수 있다는 사례다.

기록에는 소스를 수정해 다시 QA에 배포한 후 작업을 이어간 과정이 있다. 첫 번째 실패 로그에서도 PostgreSQL 예외가 확인된다. 수정 구문의 전문까지 남아 있지는 않으므로 상세 구현을 재현한 코드로 제시하지 않는다.

### 계정 복구 경로를 통한 식별정보 중복

로그인 화면은 차단했지만 계정 복구 화면의 Apple 로그인 진입점은 남아 있었다. 이 경로에서 새 식별정보가 LDAP에 먼저 등록돼, 이전 작업 중 중복 오류가 발생했다.

해당 사용자를 분리하고 잘못 생성된 계정을 정리한 뒤 개별적으로 다시 처리한 기록이 남아 있다. 변경 중 쓰기를 막으려면 기본 로그인 화면뿐 아니라 동일한 식별정보를 생성하는 우회 경로도 찾아야 한다는 점을 보여준다.

## 여러 차례 실행한 이유 {/* #5-여러-차례-실행한-이유 */}

자료는 첫 대상 확인, 전체 처리 중 SQL 오류, 수정 후 중복 오류, 문제 대상 제외 처리, 해당 대상 개별 처리의 다섯 차례 실행으로 정리돼 있다. 첨부에도 다섯 작업 로그가 남아 있다.

이는 다섯 번 모두 동일한 전체 배치를 성공시켰다는 뜻이 아니다. 검증·중단·재처리의 목적이 서로 달랐다. 서비스 재개 기록은 확인되지만, 모든 대상의 로그인 성공을 일괄 확인한 시험 결과는 별도로 남아 있지 않다.

## 회고

이 작업에서 배운 핵심은 API 호출 자체보다 식별정보의 의미와 변경 경로를 확인하는 일이었다. 외부 서비스의 식별자를 내부 사용자 키처럼 사용하면 계정 소속 변경의 영향이 로그인과 가입 흐름으로 이어질 수 있었다.

또한 실패 후 재실행을 준비하려면 대상별 진행 상태, 서로 다른 저장소의 반영 상태, 쓰기가 발생하는 모든 진입점을 함께 고려해야 한다. 이 내용은 실제로 놓친 조건과 대응 기록에서 얻은 교훈이지, 처음부터 모두 방어한 구현 목록이 아니다.

## 작성 근거와 확인 범위 {/* #작성-근거와-공개-범위 */}

「애플 로그인 마이그레이션 이슈, 2023.01.11–01.19」 문서와 대상·매핑 결과 파일, 5개 작업 로그를 확인해 작성했다. 대상 수와 Y/N 집계는 파일에서 확인했으며, 사용자 이메일·식별자·계정 비밀번호·토큰·키와 원본 로그는 공개 문서에 포함하지 않았다. 새로 운영 API를 호출하거나 마이그레이션을 실행한 것은 아니다.
