# 광고 공통 계층 설계와 SDK·오퍼월 연계

## 개요 {/* #article-introduction */}

C\*erry World에서 iOS 개발을 전담하며 Android·iOS 광고 연계 작업을 수행했다. 여러 광고 SDK를 연결하는 것에 더해, 웹에서 사용할 진입점과 사업자별 구현을 분리하는 광고 공통 계층을 설계했다. 이 문서는 그 설계와 별도 오퍼월 보상 연계를 나누어 설명한다.

## 담당 범위

업무 기록에는 Coupang 배너, AdMob, AppLovin, TNK, Exelbid와 광고 호출부의 공통화, GreenP 오퍼월 검토·연계가 남아 있다. 모든 사업자의 기능을 두 운영체제에서 동일하게 구현했다는 뜻은 아니며, 개별 SDK의 플랫폼별 적용 범위는 구분해야 한다.

웹에서 호출하는 기능과 네이티브 SDK의 구현을 연결하고, Android 관련 작업에서는 인턴 개발자에게 내용을 전달한 기록도 있다. 플랫폼 전체를 혼자 개발했다는 설명 대신 담당 구현과 협업을 구분한다.

## 광고 앱·웹 추상화 계층 설계

노션의 「광고 앱 웹 추상화 레이어 설계(고도화)」 기록과 함께 PlantText 링크에 PlantUML 클래스 설계 원문을 남겼다. 단순히 어떤 광고 SDK를 사용했는지만 적은 자료가 아니라, 호출 진입점·광고 유형·사업자별 구현·콜백 사이의 관계를 정의한 설계다.

원문에서는 `appJsInterface`가 전면 광고와 배너 광고의 Commander를 각각 참조한다. 각 광고는 공통 인터페이스를 구현하고, 광고 측의 `delegate` 관계는 Commander로 연결된다.

[![광고 공통 계층의 원본 PlantUML 설계도 — 웹 진입점, 전면·배너 Commander, 사업자별 광고 구현 및 콜백 관계](/img/work-evidence/ad-common-layer-design.png)](/img/work-evidence/ad-common-layer-design.png)

*당시 작성한 PlantUML 원문을 로컬에서 렌더링한 설계도. 이미지를 클릭하면 크게 볼 수 있다.*

회사명이 포함된 패키지 표기만 `C*erry Ad`로 가리고 클래스명과 관계는 유지했다. 설계에서 `Native` 광고를 전면 광고 그룹 아래에 배치한 것도 원문 기준이다. 현재 SDK의 광고 분류나 지원 기능을 비교한 표로 해석하지 않는다.

### 웹 진입점과 사업자 구현을 나눈 이유

| 계층 | 설계에 나타난 역할 |
| --- | --- |
| `appJsInterface` | 웹에서 연결할 광고 진입점, 전면·배너 Commander 참조 |
| Commander 인터페이스·구현체 | 전면 광고와 배너 광고를 각각 다루는 공통 제어 계층 |
| `FullScreenAd`·`BannerAd` | 사업자별 광고 클래스가 구현하는 공통 계약 |
| AdMob·TNK·AppLovin 클래스 | 광고 사업자·유형에 따라 나뉜 구체 구현 |

이 구조의 설계 의도는 웹 호출부가 모든 사업자 SDK의 구체 구현을 직접 다루지 않도록 경계를 두는 것이다. 공통 요청을 받는 계층과 실제 광고를 다루는 구현체를 분리해, 사업자별 차이가 호출부 전체로 번지는 범위를 줄이려 했다.

원문에는 Commander와 광고 인터페이스 사이에 `1`·`N` 관계가 표시돼 있다. 여러 광고 구현을 다루는 설계라는 점은 확인할 수 있지만, 이를 동시에 N개를 재생하는 정책이나 특정 우선순위·워터폴·실패 시 대체 광고 선택 알고리즘으로 확대하지 않는다. 어떤 구현체를 선택하고 언제 로딩하는지는 이 클래스도만으로 확정되지 않는다.

### 광고 로딩과 이벤트 콜백의 분리

콜백도 하나의 사업자 클래스에만 종속시키지 않고 별도 인터페이스로 정의했다.

- `AdLoadCallbackDelegate`: 광고 로딩 관련 콜백 계약.
- `AdEvnetCallbackDelegate`: 광고 이벤트 관련 콜백 계약. 이름의 철자는 원문 그대로다.
- `AdCallbackDelegate`: 위 두 계약을 함께 상속하는 인터페이스.

전면·배너 Commander는 공통 `AdCallbackDelegate`를 상속한다. 광고 측에서 Commander를 `delegate`로 참조하는 관계와 함께 보면, 사업자별 광고 결과를 공통 제어 계층으로 모으려는 설계로 읽을 수 있다.

다만 클래스도에는 개별 이벤트 메서드·반환값·실패 처리 순서가 나와 있지 않다. 광고 닫힘·보상 확정·타임아웃의 정확한 계약이나 콜백 수명 관리까지 완성된 것으로 주장하지 않는다.

### Native–JS 브리지와의 관계

[Native–JS 비동기 브리지](/projects/cherry-world/native-js-bridge)는 웹과 네이티브 사이에서 요청·응답을 어떻게 연결할지 다룬다. 광고 계층은 그 경계에서 제공할 광고 기능을 전면·배너·사업자별 구현으로 어떻게 나눌지 다룬다. 서로 관련된 설계이지만 같은 기능은 아니다.

현재 근거로 확인할 수 있는 것은 광고 공통 계층의 설계와 SDK 연계 업무다. 모든 사업자 구현체가 두 운영체제에서 동일하게 완성됐거나, 모든 광고 호출을 이 구조로 전환 완료했다고 단정하지 않는다. 특히 본문 앞의 전체 SDK 목록과 이 PlantUML에 등장하는 구현체 목록은 일치하지 않으므로 구분한다.

<details>

아래는 원문에서 패키지 경로를 생략하고 핵심 관계만 남긴 PlantUML 발췌다. 실행 가능한 광고 라이브러리 코드가 아니라 설계 근거다.

```text title="PlantUML 설계 발췌 — 패키지 경로 생략"
interface AdLoadCallbackDelegate
interface AdEvnetCallbackDelegate
interface AdCallbackDelegate extends AdLoadCallbackDelegate, AdEvnetCallbackDelegate

interface FullScreenAdCommander extends AdCallbackDelegate
class FullScreenAdCommanderImpl implements FullScreenAdCommander
interface FullScreenAd
class AdmobInterstitial implements FullScreenAd

interface BannerAdCommander extends AdCallbackDelegate
class BannerAdCommanderImpl implements BannerAdCommander
interface BannerAd
class AdmobBannerAd implements BannerAd
```

## 오퍼월은 광고 열기와 보상 처리가 분리된다

GreenP 자료에는 웹·앱에서 오퍼월을 여는 진입점과 외부 서버에서 내부 서버로 전달되는 보상 결과의 흐름이 정리돼 있다.

```text
Web → Native 광고 진입점 → 오퍼월 참여
                              │
                        외부 사업자 서버
                              │ 보상 콜백
                              ↓
                     서비스 서버 → 보상 처리
```

광고 화면을 열었다는 사실만으로 서버 보상을 지급하는 구조로 설명하지 않는다. 웹·네이티브의 기능 호출과 서버 측 보상 결과 처리를 각각 구분하는 것이 중요하다.

[![오퍼월 검토 자료에 남아 있는 테스트 캠페인 목록](/img/work-evidence/offerwall-test-campaigns.png)](/img/work-evidence/offerwall-test-campaigns.png)

*「그린피 검토」에 첨부한 시험 화면 일부.* 실제 자료의 테스트 캠페인 목록만 잘라 냈다. 오퍼월 연동을 확인하던 화면이며, 외부 사업자가 제공하는 화면 디자인·캐릭터를 직접 제작했다는 의미는 아니다.

## 외부 결과를 내부 데이터로 연결

검토 자료에는 내부 사용자 연결값, 광고 제공자 종류, 보상 금액과 추가 데이터처럼 보상 처리에 필요한 항목이 정리돼 있다. 필요한 서버 API와 저장 구조를 함께 검토했다는 점이 남아 있다.

[![광고 보상 콜백에 필요한 파라미터 이름과 의미를 검토한 설정 화면](/img/work-evidence/offerwall-postback-parameters.png)](/img/work-evidence/offerwall-postback-parameters.png)

*같은 자료의 Postback 파라미터 검토 화면.* 사용자 연결값, 보상 금액, 전환 식별값과 중복 참여 항목을 확인할 수 있다. 내부 콜백 URL은 가리고 서버 IP·완성 URL 영역은 제외했다. 보이는 `{app_uid}` 등의 표기는 실제 사용자 값이 아닌 템플릿이다.

업무 노트에는 외부 사업자에 파라미터를 확인하고 해당 값을 저장한 뒤 유니크 인덱스를 추가한 기록이 있다. 이는 동일 식별값의 중복 처리를 제한하는 맥락으로 설명할 수 있다. 그러나 유니크 인덱스만으로 요청의 발신자를 검증하거나 보상 금액의 진위를 증명할 수 있는 것은 아니다.

따라서 이 문서에서는 중복 처리 관련 작업과 인증·서명 검증을 같은 기능으로 취급하지 않는다. 서명 검증의 정확한 구현과 트랜잭션 단위, 재시도 정책은 현재 자료만으로 확정하지 않는다.

## WebView 캐시 설정 점검

Android 데이터 사용량 제보를 받아 캐시 모드와 생성 시 캐시 삭제 로직을 수정한 작업은 [WebView 캐시 정책 개선](/projects/cherry-world/webview-cache-policy)으로 분리했다. 광고 SDK만의 문제가 아니라 웹 리소스 로딩 전반에 관한 사례이며, 별도 문서에서 변경 내용과 당시 비교 표를 설명한다.

## 결과와 확인 범위 {/* #결과와-범위 */}

이 경험에서는 웹 진입점과 사업자별 광고 구현을 분리하는 공통 계층을 설계하고, 실제 SDK 연계 업무와 오퍼월의 외부 보상 결과 연결을 수행했다. 공통 계층의 클래스 설계, 각 SDK의 적용 범위, 서버 측 보상 처리는 서로 다른 기여로 구분한다.

수익 증가율, 광고 성공률이나 부정 보상 완전 차단 같은 수치는 확인 자료가 없어 기재하지 않는다. 코드와 시험 결과가 없는 보안 기능을 구현 성과로 확대하지 않는다.

## 작성 근거와 확인 범위 {/* #작성-근거 */}

업무 노트의 광고 연계·추상화 계층 고도화·Android 협업 항목, 연결된 PlantText의 PlantUML 원문과 「그린피 검토」 자료를 참고했다. PlantUML은 URL에 포함된 내용을 로컬에서 복원하고 회사명 표기를 가린 뒤 이미지로 렌더링했다. 이미지에는 소스 메타데이터를 포함하지 않았으며, 사내 설계 원문을 외부 서비스로 다시 전송하지 않았다. 별도 TypeScript Playground 예제 링크의 코드 내용은 이번 설명의 검증 근거에 포함하지 않았다.

자료에 포함된 사용자 식별값, 광고 식별자, 콜백 URL과 검증값은 공개하지 않았다. 설계에 나타난 클래스 관계와 실제 전환 완료 여부, 오퍼월 자료의 필요 API·테이블 검토와 적용 기록의 범위를 구분했다.
