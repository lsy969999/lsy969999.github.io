# 연휴 운영 중 MyBatis 쿼리 파싱 오류 추적

## 개요 {/* #article-introduction */}

2023년 10월 1일, C\*erry World의 추석 연휴 모니터링 중 쿼리 파싱 오류를 발견했다. MyBatis에서 작성한 쿼리와 DB에서 실행된 SQL의 공백·줄바꿈 처리를 비교하며 원인을 추적했다.

## 확인한 현상과 로그

[![2023년 10월 1일 PostgreSQL 문법 오류와 트랜잭션 중단 로그 — 내부 식별정보와 SQL은 가림](/img/work-evidence/mybatis-holiday-sql-errors.png)](/img/work-evidence/mybatis-holiday-sql-errors.png)

*연휴 모니터링 때 남긴 원본 로그 일부.* 날짜와 오류 메시지는 유지하고 서버 주소·DB명·사용자명·프로세스 식별정보와 SQL 원문은 가렸다. 원래 캡처의 빨간 표시도 그대로 남겼다. 이미지를 클릭하면 크게 볼 수 있다.

캡처에는 닫는 괄호 근처의 `syntax error`와 이어지는 `current transaction is aborted` 메시지가 보인다. 단순히 조회가 느렸던 사례가 아니라, DB가 SQL을 해석하지 못한 오류를 확인하던 기록이다. 이는 AWS의 높은 대기 부하나 7월 인덱스 개선과 별개의 운영 사례다.

## 매퍼와 실제 실행 SQL의 차이를 추적

이 작업의 초점은 매퍼 편집 화면에서 보이는 공백·줄바꿈과 DB에서 해석하는 SQL을 구분하는 것이었다. 코드에 띄어쓰기가 있다는 사실만으로 실행되는 SQL이 올바르다고 판단하지 않고, DB 오류 위치와 실제 문장을 함께 살펴야 했던 상황이다.

PostgreSQL은 공백·탭·줄바꿈을 토큰 구분자로 허용한다. 줄바꿈 자체보다 최종 SQL이 어떤 문자열로 조합됐는지를 확인해야 한다. [PostgreSQL — Lexical Structure](https://www.postgresql.org/docs/16/sql-syntax-lexical.html)

## 분석 결과 {/* #담당-작업과-남은-검증 */}

연휴 모니터링에서 발견한 오류를 로그와 대조하며 MyBatis 쿼리와 DB 실행 SQL의 차이를 추적했다.

비슷한 문제를 추적할 때는 매퍼 원문뿐 아니라 최종 SQL과 바인딩 파라미터를 함께 확보해야 한다. 수정 전후 재현 결과까지 남기면 문자열 조합 문제와 DB 실행 문제를 나누어 확인하기 쉽다.
