# 대용량 배치로 드러난 스레드 풀 누적 분석

## 개요 {/* #article-introduction */}

기존 블록체인 연계 서비스에는 타이머 요청마다 스레드 풀을 만들고 종료하지 않는 문제가 있었다. 매주 Pod를 내렸다 올리는 운영 중에는 OOM이 드러나지 않았지만, C\*erry World에서 대용량 배치가 돌기 시작하면서 문제가 눈에 띄었다. 로그와 덤프를 추적해 타이머별 실행 자원의 생성·종료 구조를 분석했다.

분석 대상은 이전부터 사용하던 타이머 로직이다. 정기 Pod 재시작과 부하 증가의 관계는 담당자 회고를, 오류 유형과 로직 분석은 당시 캡처·노트를 기준으로 정리했다.

## 정기 재시작이 가리고 있던 누적 문제 {/* #1-정기-재시작이-가리고-있던-누적-문제 */}

당시 노트에는 장애 시점의 서비스 종료와 Kubernetes 재기동도 기록돼 있다. 매주 수행한 정기 재시작과 장애 발생 후 재기동은 서로 다른 사건이다. 정기 재시작을 모두 장애로 계산하거나, 재시작이 없었다면 정확히 며칠 뒤 실패했을 것이라는 수치를 만들지 않는다.

```text
기존 운영: 자원 누적 → 주간 Pod 재시작 → 누적 상태 초기화

C\*erry World 배치 도입: 많은 타이머 작업 → 누적 문제가 드러남
                                      ↓
                           로그·덤프·타이머 로직 분석
```

문제의 발견 계기는 부하 증가였지만, 분석 대상은 기존 타이머 로직의 수명 관리였다. 정기 재시작은 남은 자원을 초기화할 수 있어도 생성·종료 구조 자체를 수정하지는 않았다.

초기 대응으로 메모리 할당을 약 500MB에서 2GB로 늘렸다. 기록상 기존과 비슷한 부하에서는 이전과 같은 종료 현상이 줄었다. 다만 이 값이 어떤 Kubernetes 설정 필드였는지까지 남아 있지 않으므로 request·limit·JVM heap 값을 임의로 같은 의미로 취급하지 않는다.

## 메모리가 남아 보이는데 왜 실패했는가 {/* #2-메모리가-남아-보이는데-왜-실패했는가 */}

증설 이후에도 오류가 발생했고, 2023년 9월 1일 캡처에서 다음 메시지가 확인된다.

[![2023년 9월 1일 native thread 생성 실패가 반복된 실제 오류 로그](/img/work-evidence/native-thread-error-log.png)](/img/work-evidence/native-thread-error-log.png)

*당시 노션 업무 기록에 직접 첨부했던 오류 화면.* 날짜와 `unable to create native thread` 메시지는 그대로 두고 사내 서비스 이름·로거·접속 스레드 정보만 가렸다.

```text
java.lang.OutOfMemoryError:
unable to create native thread:
possibly out of memory or process/resource limits reached
```

이 메시지는 Java 객체를 더 할당하지 못한다는 일반적인 표현으로 뭉뚱그릴 것이 아니라, 새 네이티브 스레드 생성이 실패했다는 정보로 읽었다. 노트에는 메모리 여유가 있어 보인다는 관측과 함께 스레드 개수의 한계에 도달했을 가능성을 의심한 과정이 남아 있다.

다만 이 로그 하나로 OS의 정확한 제한값이나 컨테이너 설정이 원인이라고 확정하지 않는다. 당시 메모리 사용 그래프가 어떤 영역을 보여줬는지도 확인되지 않는다. `OOMKilled` 종료 원인까지 이 메시지로 증명되는 것도 아니다.

## 덤프와 요청 처리 로직을 연결 {/* #3-덤프와-요청-처리-로직을-연결 */}

서비스가 멈추는 시점의 덤프를 확인해 스레드가 많이 쌓여 있다는 점을 관측했다. 인수인계받은 타이머 로직은 요청마다 스레드 1개짜리 풀을 새로 만들고, 타이머 작업이 끝난 뒤에도 풀을 종료하지 않는 구조였다. 당시 노트의 요청별 풀 생성·정리 누락 기록과 담당자 회고가 이 원인에 대응한다.

[![단일 스레드 스케줄러 생성 코드와 덤프의 DelayedWorkQueue 대기 스택을 연결해 분석한 원본 화면](/img/work-evidence/native-thread-executor-dump.png)](/img/work-evidence/native-thread-executor-dump.png)

*노션에 보관한 당시 분석 이미지.* 왼쪽의 `newSingleThreadScheduledExecutor`와 오른쪽 덤프의 `ScheduledThreadPoolExecutor$DelayedWorkQueue.take`, `pool-…-thread-1` 항목을 연결해 살펴본 흔적이다. 서비스 수정 코드가 아니라 JDK 코드와 덤프를 비교한 분석 자료다.

[![덤프 목록에 Total 156 of 2703 entries와 2547 more가 표시된 원본 캡처](/img/work-evidence/native-thread-dump-count.png)](/img/work-evidence/native-thread-dump-count.png)

*같은 업무 기록의 덤프 집계 부분.* 화면에는 `156 of 2,703 entries; 2,547 more`가 표시돼 있다. 이는 해당 시점 목록의 집계이지 누수 스레드가 정확히 2,703개라는 판정이나 수정 전후 비교 수치가 아니다. 다른 서비스의 집계와 비교한 영역은 제외했다.

아래는 그 기록의 수명 관계를 설명하는 도식이다. 실제 수정 코드의 재현은 아니다.

```text
요청 A → 풀 A 생성 → 지연 작업 A → 작업 종료 / 풀 종료 누락
요청 B → 풀 B 생성 → 지연 작업 B → 작업 종료 / 풀 종료 누락
요청 C → 풀 C 생성 → 지연 작업 C → 작업 종료 / 풀 종료 누락
                                  ↓
                         남은 실행 자원 누적
                                  ↓
                     새 스레드 생성 실패와 연결해 분석
```

스레드 풀이라는 이름을 사용해도 요청마다 풀을 새로 생성하면 재사용의 이점을 얻지 못한다. 하나의 작업이 끝나는 시점과 그 작업을 실행한 풀의 수명이 끝나는 시점을 구분해야 했다.

## 확인된 관측과 원인 판단의 구분 {/* #4-확인된-관측과-원인-판단의-구분 */}

| 항목 | 확인 수준 |
| --- | --- |
| 매주 Pod를 내렸다 올렸고 당시에는 OOM이 드러나지 않음 | 담당자 회고로 확인 |
| C\*erry World 대용량 배치를 계기로 문제 분석 | 담당자 회고로 확인 |
| 네이티브 스레드 생성 실패 | 실제 오류 캡처에서 확인 |
| 덤프에서 스레드가 많이 보임 | 원본 캡처에 2,703 entries가 표시됨. 누수 개수·OS 전체 스레드 수와 동일시하지 않음 |
| 요청마다 풀을 생성하고 종료하지 않음 | 당시 로직 분석 메모에 기록 |
| 메모리 증설 후 일시적으로 증상 완화 | 당시 관측 기록 |
| 최종 수정 코드와 장시간 재검증 | 현재 자료만으로 확인되지 않음 |

따라서 기여는 증상 완화 후에도 원인 분석을 이어가고, 덤프 관측과 자원 생성·종료 흐름을 연결했다는 데 둔다. 수정 diff와 검증 결과가 없는 상태에서 장기간 재발 0건이나 메모리 누수 완전 제거를 성과로 쓰지 않는다.

## 자원의 소유자와 종료 시점 {/* #5-자원의-소유자와-종료-시점 */}

이 문제를 다시 설계한다면 먼저 Executor를 누가 소유하고 언제 종료하는지 정해야 한다. 서비스가 공유하는 풀을 요청 하나가 끝났다고 종료하는 것도 잘못이며, 요청별로 만든 풀을 아무도 종료하지 않는 것도 수명 문제다.

`ExecutorService.shutdown()`은 새 작업을 받지 않도록 하고 이미 제출된 작업의 처리를 이어가지만, 호출 자체가 모든 작업 종료를 기다리는 것은 아니다. 완료 대기와 종료 요청을 구분해야 한다. 이는 Java 8 공식 API에 명시된 동작이다. 당시 사용한 JDK 버전이나 최종 수정 방법을 Java 8로 단정하는 근거는 아니다. [Oracle — ExecutorService](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ExecutorService.html).

## 현재 시점에서의 보강 방향

다음은 당시 적용 완료 목록이 아니라 원인 기록을 바탕으로 한 후속 설계·검증 방향이다.

- 풀을 요청마다 만드는지, 서비스 수명 동안 공유할 수 있는지 검토한다.
- 지연 작업의 취소와 서버 종료 시 대기·정리 정책을 정한다.
- 요청이 많을 때 작업 큐가 무한히 쌓이지 않도록 용량과 거부 정책을 검토한다.
- 정상 완료뿐 아니라 예외·취소·재시도 경로에서도 자원이 남는지 확인한다.
- 부하를 반복하고 요청을 중단한 뒤 스레드 수와 대기 작업 수가 안정되는지 관측한다.

정확한 API 이름을 바꾸는 것보다, 생성 주체와 소유권·종료 책임을 명확히 하는 일이 우선이다. 현재 자료에는 공유 풀 전환인지 종료 처리 보강인지 확정할 수정 코드가 없어 하나를 실제 적용안으로 선택해 쓰지 않는다.

## 회고

주간 재시작 아래에서는 드러나지 않던 문제가 새로운 배치 부하에서 나타났다. 처음에는 서비스 종료와 메모리 사용량에 집중해 자원을 늘렸지만, 실패가 남자 로그의 구체적인 실패 대상과 덤프를 확인했다. 같은 `OutOfMemoryError` 이름을 보더라도 어떤 자원을 생성하지 못했는지에 따라 확인해야 할 로직이 달랐다.

운영 환경이 프로세스를 다시 띄워 주는 것과 코드의 자원 수명이 올바른 것은 별개였다. 이 경험은 이후 객체·스레드·비동기 작업의 소유자와 정리 시점을 함께 생각하는 데 연결되는 사례다. 블록체인 합의나 프로토콜 자체의 구현 경험과는 구분한다.

## 작성 근거와 확인 범위 {/* #작성-근거와-공개-범위 */}

당시 업무 노트의 블록체인 서비스 재시작, 메모리 증설, 2023.09.01 오류 캡처, 덤프와 요청별 스레드 풀 분석 기록을 기준으로 작성했다. 주간 Pod 재시작, C\*erry World 대용량 배치라는 발견 계기, 요청마다 스레드 1개짜리 풀을 만드는 타이머 구조는 담당자 회고로 보완했다. 현재 덤프 파일을 재분석하거나 운영 부하를 재현한 것은 아니다.

사내 서비스 주소·패키지명·원본 덤프 파일·계정 정보는 공개하지 않는다. 첨부 이미지는 당시 노션 본문에서 확보한 원본의 검수 사본이다. JDK 실행기와 덤프 대기 스택은 확인되지만, 서비스의 최종 수정 코드·스레드 수의 전후 추이·무재발 기간은 증빙이 없어 추가하지 않았다.
