대용량 배치로 드러난 스레드 풀 누적 분석

개요​

기존 블록체인 연계 서비스에는 타이머 요청마다 스레드 풀을 만들고 종료하지 않는 문제가 있었다. 매주 Pod를 내렸다 올리는 운영 중에는 OOM이 드러나지 않았지만, C*erry World에서 대용량 배치가 돌기 시작하면서 문제가 눈에 띄었다. 로그와 덤프를 추적해 타이머별 실행 자원의 생성·종료 구조를 분석했다.

정기 재시작이 가리고 있던 누적 문제​

매주 수행하던 정기 재시작과 별개로, 장애가 발생했을 때도 서비스가 종료되고 Kubernetes에서 재기동되는 현상이 있었다.

Plain Text
기존 운영: 자원 누적 → 주간 Pod 재시작 → 누적 상태 초기화

C\*erry World 배치 도입: 많은 타이머 작업 → 누적 문제가 드러남
                                      ↓
                           로그·덤프·타이머 로직 분석

문제의 발견 계기는 부하 증가였지만, 분석 대상은 기존 타이머 로직의 수명 관리였다. 정기 재시작은 남은 자원을 초기화할 수 있어도 생성·종료 구조 자체를 수정하지는 않았다.

초기 대응으로 메모리 할당을 약 500MB에서 2GB로 늘렸다. 기존과 비슷한 부하에서는 이전과 같은 종료 현상이 줄었다.

메모리가 남아 보이는데 왜 실패했는가​

증설 이후에도 오류가 발생했고, 2023년 9월 1일 캡처에서 다음 메시지가 확인된다.

당시 노션 업무 기록에 직접 첨부했던 오류 화면. 날짜와 unable to create native thread 메시지는 그대로 두고 사내 서비스 이름·로거·접속 스레드 정보만 가렸다.

Plain Text
java.lang.OutOfMemoryError:
unable to create native thread:
possibly out of memory or process/resource limits reached

이 메시지는 Java 객체를 더 할당하지 못한다는 일반적인 표현으로 뭉뚱그릴 것이 아니라, 새 네이티브 스레드 생성이 실패했다는 정보로 읽었다. 노트에는 메모리 여유가 있어 보인다는 관측과 함께 스레드 개수의 한계에 도달했을 가능성을 의심한 과정이 남아 있다.

덤프와 요청 처리 로직을 연결​

서비스가 멈추는 시점의 덤프에서 스레드가 많이 쌓인 것을 확인했다. 기존 타이머 로직은 요청마다 스레드 1개짜리 풀을 만들고, 작업이 끝난 뒤에도 풀을 종료하지 않고 있었다.

노션에 보관한 당시 분석 이미지. 왼쪽의 newSingleThreadScheduledExecutor와 오른쪽 덤프의 ScheduledThreadPoolExecutor$DelayedWorkQueue.take, pool-…-thread-1 항목을 연결해 살펴본 흔적이다. 서비스 수정 코드가 아니라 JDK 코드와 덤프를 비교한 분석 자료다.

스레드 덤프의 집계 화면. 목록에 156 of 2,703 entries; 2,547 more가 표시돼 있다.

타이머 생성과 스레드 풀의 수명 관계는 다음과 같다.

Plain Text
요청 A → 풀 A 생성 → 지연 작업 A → 작업 종료 / 풀 종료 누락
요청 B → 풀 B 생성 → 지연 작업 B → 작업 종료 / 풀 종료 누락
요청 C → 풀 C 생성 → 지연 작업 C → 작업 종료 / 풀 종료 누락
                                  ↓
                         남은 실행 자원 누적
                                  ↓
                     새 스레드 생성 실패와 연결해 분석

스레드 풀이라는 이름을 사용해도 요청마다 풀을 새로 생성하면 재사용의 이점을 얻지 못한다. 하나의 작업이 끝나는 시점과 그 작업을 실행한 풀의 수명이 끝나는 시점을 구분해야 했다.

메모리 증설로 증상이 잠시 줄어든 뒤에도 분석을 이어가, 덤프의 스레드 누적과 요청별 풀 생성·종료 누락을 연결했다.

자원의 소유자와 종료 시점​

ExecutorService.shutdown()은 새 작업을 받지 않도록 하고 이미 제출된 작업의 처리를 이어가지만, 호출 자체가 모든 작업 종료를 기다리는 것은 아니다. 완료 대기와 종료 요청을 구분해야 한다. Oracle — ExecutorService.

회고​

주간 재시작 아래에서는 드러나지 않던 문제가 새로운 배치 부하에서 나타났다. 처음에는 서비스 종료와 메모리 사용량에 집중해 자원을 늘렸지만, 실패가 남자 로그의 구체적인 실패 대상과 덤프를 확인했다. 같은 OutOfMemoryError 이름을 보더라도 어떤 자원을 생성하지 못했는지에 따라 확인해야 할 로직이 달랐다.

운영 환경이 프로세스를 다시 띄워 주는 것과 코드의 자원 수명이 올바른 것은 별개였다. 이 경험은 이후 객체·스레드·비동기 작업의 소유자와 정리 시점을 함께 생각하는 데 연결되는 사례다.
