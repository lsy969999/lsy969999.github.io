# Rapier 기반 공 혼합·포착·배출과 추첨 단계 제어

## 물리 시뮬레이션과 제어된 운반을 조합하기

추첨 장치에서는 공이 서로 부딪히며 섞여야 하지만, 선택된 공을 들어 올려 배출하는 과정까지 충돌에만 맡기면 진행 완료 시점을 다루기 어렵다. Lucky Ball은 공의 혼합·낙하·배출에는 물리를 사용하고, 포착한 공은 잠시 고정한 뒤 Tween으로 운반하는 방식을 구성했다.

핵심은 물리 라이브러리 자체의 구현이 아니라 **공의 물리 상태를 추첨 단계에 맞게 바꾸고, 센서 결과와 장치 동작 완료를 다음 단계에 연결한 것**이다. 현재 코드는 Rapier를 사용하며, 초기 장치 구현 이후 Rapier 연결과 Bevy 업그레이드가 진행된 이력도 구분했다.

## glTF 노드에 물리 역할 부착

Game 진입 시 `test_new_setup()`이 `luckyball.glb`의 Scene을 생성한다. `new_setup_added()`는 새로 추가된 이름 있는 노드를 조회해 장치 이름별로 Component와 Collider를 부착한다. 기존 `spawn_setup()`이 아니라 현재 등록된 이 경로를 기준으로 분석했다.

| 장치 역할 | 현재 물리 구성 |
| --- | --- |
| 공 케이스·풀·배출 가이드 | Fixed 강체와 메시 기반 TriMesh |
| `BallMixer2` | KinematicVelocityBased 강체, TriMesh, Y축 각속도 |
| `BallDrawStick`·출구 덮개 | Fixed 강체와 TriMesh, Transform Tween으로 이동 |
| `poolFrontCollider` | Fixed 강체와 ConvexHull, 표시용 자식 메시 제거 |
| `poolPumpCollider` | Fixed 강체·ConvexHull Sensor·충돌 엔티티 목록 |
| `BallDrawStickIn` | 역할 마커를 붙여 별도 Tween 대상으로 사용 |

모델의 공 노드는 장치 Scene에서 제거한다. 공은 규칙에 따라 별도로 생성해야 하기 때문이다. 충돌 전용 모델은 Collider를 만든 뒤 자식 메시를 제거해 물리 형태와 표시 여부를 나눈다.

이 방식은 glTF의 노드 이름·첫 번째 자식 메시·재질 구성에 의존한다. 자식 조회와 Collider 생성에 `unwrap()`을 사용하므로 임의의 모델을 자동 분석하는 범용 장치 로더는 아니다. 모델을 교체할 때 이름·계층·콜라이더 생성 가능 여부를 함께 확인해야 한다.

## 규칙에 맞는 공 생성과 초기 배치 섞기

`er_ball_spawn()`은 기존 `Ball` 엔티티를 제거한 뒤, `rule_given_ball`에 포함된 번호에 해당하는 glTF 노드의 메시와 재질을 수집한다. 번호는 `Ball(u8)`에 보관하며, 각 노드의 첫 번째 primitive를 사용한다.

셔플 요청이면 전체 공 노드에서 모은 초기 Transform 목록 중 하나를 무작위로 뽑아 제거하면서 배정한다. 동일한 초기 위치를 중복 사용하지 않도록 목록에서 소비하는 방식이다. 번호별 메시·재질은 유지하고 배치 위치를 바꾸는 것이며, 추첨 결과를 미리 번호 난수로 결정하는 처리는 아니다.

생성 시 공의 주요 설정은 다음과 같다.

- 처음에는 `RigidBody::Fixed`, 추첨 시작 시 Dynamic으로 전환한다.
- `Collider::ball(1.0)`과 Transform의 균일 스케일 `0.069`를 조합한다. 최종 스케일은 glTF의 기존 스케일 대신 이 값으로 지정한다.
- 마찰은 0.6, 반발 계수는 0.9, 선형·각 감쇠는 각각 0.8이다.
- 초기 중력 배율은 0.5이며 충돌 이벤트를 활성화한다.

이 수치들은 현재 모델과 장치에 맞춘 설정이다. 크기·시간 간격이 달라져도 같은 조작감이나 충돌 안정성을 보장하는 보편값으로 설명하지 않는다.

## 투입과 혼합

추첨 시작 이벤트는 선택 번호와 센서 플래그를 초기화하고, 출구 덮개 열기와 공의 Dynamic 전환을 요청한다. 덮개는 500ms Tween으로 이동한다. 열림 완료 후 풀 내부 공 수 감지를 켜고, 센서 안의 `Ball` 개수가 0이 되면 덮개를 닫는다.

여기서 세는 것은 월드 전체에 남은 공 수가 아니라 **풀 센서 영역과 겹친 공 수**다. 공이 장치 밖으로 잘못 빠져나간 경우까지 정상 투입과 구분하는 검사는 아니다.

펌프 센서 영역의 공에는 실행 중 +X 방향 impulse를 넣고, 중력 배율을 기본값으로 바꾸며 속도를 0으로 설정한다. 단 한 번의 진입 콜백이 아니라 `CollidingEntities`를 매 Update에서 확인하는 방식이다. 따라서 이 보조 처리의 효과는 업데이트 주기와 체류 시간에 영향을 받을 수 있다.

믹서는 Y축 각속도로 움직인다. 직접 작성한 `MyAngularVelocityYLens`가 현재 `Velocity.angvel.y`에서 목표값까지 보간하며, `component_animator_system::<Velocity>`를 Tween 시스템 집합에 등록했다. 추첨 중 빠른 혼합 목표는 18, 포착 대기·종료 시 느린 목표는 1이고 전환 시간은 1.6초다. 각도를 매번 덮어쓰기보다 키네마틱 강체의 각속도를 조절하는 경로다.

## 센서에 들어온 공을 한 개 포착

스틱 내리기가 완료되면 혼합 속도를 낮추고 `is_catching`을 켠다. `ball_catch()`는 실행·포착 플래그가 켜진 동안 포착 센서의 충돌 목록에서 `Ball`을 찾는다.

공을 찾으면 다음을 처리하고 즉시 반환한다.

1. 포착 플래그를 꺼 추가 선택을 막는다.
2. 공을 Fixed로 바꾸고 선형·각속도를 0으로 만든다.
3. `Catched`, `Picked` 마커를 부착한다.
4. 현재 위치에서 포착 기준점까지 150ms Tween을 적용한다.
5. 공 번호를 `picked_ball` 목록에 추가한다.

동시에 여러 공이 들어와도 이 호출에서 선택하는 것은 첫 번째로 찾은 한 개다. 충돌 목록의 순서를 균등한 무작위 추첨 알고리즘으로 해석해서는 안 된다. 초기 배치 셔플과 물리 혼합을 사용하지만, 결과의 통계적 균등성이나 같은 시드의 재현성을 검증한 시스템은 아니다.

`picked_ball`에는 배출 후가 아니라 포착 시 번호가 추가된다. 또한 포착 쿼리는 `Picked`를 제외하지 않으므로 재진입에 대한 중복 방지는 장치 동선에 의존하는 부분이 남아 있다.

## 고정한 공 운반 후 물리 배출

포착 Tween의 완료 ID는 `tcb_to_step_convert()`에서 `STEP_BALL_CATCH_DONE`으로 변환한다. 이후 외부 스틱·내부 스틱·포착된 공에 각각 Tween을 적용해 2초 동안 상승시킨다. 이 운반은 부모 부착이나 물리 조인트가 아니라 각 Transform을 같은 진행에 맞춰 움직이는 방식이다.

외부 스틱 상승 완료 후 내부 스틱과 공을 300ms 동안 조금 더 올린다. 내부 상승 완료가 배출을 시작하는 기준이다. 공에서는 `Catched`를 제거하고 반발 계수를 0으로 낮춘 뒤 Dynamic으로 전환하며, -Z 방향으로 작은 impulse를 준다.

믹서와 달리 스틱·덮개는 Fixed 상태의 Transform을 Tween으로 갱신한다. 따라서 모든 이동 장치를 속도 기반 키네마틱 또는 조인트 모터로 제어했다고 설명하지 않는다. 높은 이동 속도나 다른 모델 크기에서 충돌 반응을 보강하려면 이 이동 방식부터 검토할 수 있다.

## 배출 완료와 결과 공 고정

배출 센서는 활성화된 동안 영역 안에 `Ball`이 하나도 없으면 완료 이벤트를 보낸다. 특정 포착 공이 센서에 들어왔다가 나갔다는 이력을 추적하는 방식은 아니다. 센서가 처음부터 비어 있으면 완료될 수 있으므로, 지연된 충돌 목록 갱신이나 장치 위치 변경 시 확인할 경계다.

완료 후 내부 스틱을 내리고, 선택한 번호 수가 목표보다 적으면 외부 스틱을 다시 내리며 혼합을 빠르게 한다. 목표 개수에 도달했다면 실행 플래그를 끄고 `GameEndEvent`를 보낸다. 결과 화면은 이 이벤트를 받아 전환한다.

배출 가이드 끝과 충돌한 공에는 `PickedStatic`과 Fixed를 붙여 결과 위치에서 계속 움직이지 않도록 한다. 고정된 공에 닿은 다른 공도 고정하려는 시스템이 별도로 있다. 다만 첫 고정 공을 만드는 경로에서는 `CollidingEntities`를 추가하지 않고 후속 시스템은 이를 요구하므로, 고정이 연쇄적으로 전파되는 경로가 완성됐다고 단정하지 않는다.

## 공이 잡히지 않으면 재혼합

포착 대기를 시작할 때 `RemixerTimer`를 생성한다. 단순히 매번 새 공을 강제로 선택하는 대신 믹서 속도를 조절해 공 배치가 다시 변하도록 구성했다.

| 타이머 완료 | 다음 요청 |
| --- | --- |
| 3초 대기 | 믹서 목표 속도 18, 2초 타이머 생성 |
| 이후 2초 | 믹서 목표 속도 1, 2초 판정 대기 타이머 생성 |
| 이후 2초 | 느린 목표 유지, 다시 3초 대기 타이머 생성 |

속도 요청마다 1.6초 Tween이 적용되므로 표의 대기 시간을 일정 속도로 회전한 시간과 동일하게 보면 안 된다. 각 타이머는 앱 delta를 누적하며, 포착 완료나 새 추첨 시작 시 남은 재혼합 타이머 엔티티들을 제거한다.

`RemixerJudgeTimer`라는 이름이지만 자체적으로 센서 성공 여부를 검사하지는 않는다. 성공 판정은 포착 시스템이 하고, 이 타이머는 재혼합 반복을 이어준다. 최대 재시도 횟수나 전체 실패 제한 시간은 없어 장치·센서 설정이 잘못되면 계속 기다릴 수 있다.

## 이벤트 연결에서 주의할 경계

단계 전환은 `GameStepFinishEvent`의 숫자 ID를 해석해 다음 시작 이벤트를 보내는 방식이다. Tween·센서 완료를 공통 경로로 모았지만, 현재 단계를 하나의 enum으로 보관해 모든 이벤트의 유효성을 검증하는 구조는 아니다.

이벤트에는 실행 회차 ID가 없고 Tween 완료 변환도 완료 대상 엔티티를 단계 검증에 사용하지 않는다. 이전 실행의 지연된 완료 이벤트, 같은 ID의 중복 이벤트, 재혼합 타이머와 포착 완료의 경합은 후속 검증 대상으로 남는다. 등록 튜플 순서만으로 이 모든 시스템이 의도한 순서에 실행된다고 가정하지 않는다.

보강 우선순위는 센서·노드 준비 검증, 현재 단계와 실행 회차 검증, 특정 공의 배출 이력 확인, 중복 선택 차단, 제한 시간·실패 복구다. 현재 문서는 구현 분석이며 이 항목을 코드에 적용한 것은 아니다.
