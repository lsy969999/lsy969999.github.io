# 플랫폼별 빌드·패키징과 Web 배포

## 공통 소스 이후에 달라지는 산출물

게임 로직을 공통 Rust crate로 묶어도 실행 파일 구성과 리소스 배치는 플랫폼마다 다르다. Lucky Ball은 Android·iOS·Web crate와 빌드 스크립트를 두어 공통 앱을 각 플랫폼에서 사용할 산출물로 변환했다.

| 대상 | Rust 산출물 | 다음 단계 |
| --- | --- | --- |
| Android | ARM64 cdylib와 C++ 공유 런타임 | Android Studio 프로젝트의 jniLibs·assets로 복사 |
| iOS | 기기·시뮬레이터 target별 staticlib | Xcode 앱에서 링크하고 리소스를 번들에 포함 |
| Web | WASM 모듈과 JavaScript 바인딩 | HTML·에셋과 함께 GitHub Pages 게시 |

현재 저장소에서 자동 게시 워크플로로 확인되는 것은 Web이다. Android·iOS 빌드 구성이 있다는 사실과 모바일 서명·스토어 업로드까지 CI에서 자동화됐다는 주장은 구분한다.

## 공통 빌드 프로파일과 feature

루트 Cargo 설정은 개발 코드에 `opt-level = 1`, 의존성에 `opt-level = 3`을 적용한다. release는 크기 중심 최적화 `z`, LTO, codegen unit 1개, panic abort, debug symbol 제거와 strip을 지정한다. 실행 성능이나 실제 바이너리 감소율을 새로 측정한 결과가 아니라 현재 설정이다.

공통 crate의 기본 feature에는 inspector가 있지만 각 플랫폼 crate는 `default-features = false`로 이를 참조한다. Web은 추가 feature로 `webgl2`·`webgpu`를 나누어 해당 Bevy 렌더 기능에 연결한다.

`Cargo.lock`은 저장소에서 추적한다. 다만 스크립트의 Cargo 호출은 `--locked`를 사용하지 않고, Rust 도구체인은 워크플로에서 고정하지 않는다. winit 패치와 일부 의존성에는 Git branch 참조도 있다. lockfile이 있다는 사실과 모든 도구·의존성 해석이 변하지 않는 재현 빌드는 별개다.

## Android: cargo-ndk에서 Gradle 프로젝트로

`android/build_android.sh`의 활성 명령은 다음과 같다.

```sh
cargo ndk -t arm64-v8a -o ./jniLibs build --release
```

다른 ABI를 함께 빌드하는 명령은 주석 처리돼 있어 현재 스크립트는 ARM64 한 종류를 대상으로 한다. 작업 디렉터리를 `android/`로 가정하며, 빌드 후 루트의 assets와 생성된 jniLibs를 `android_studio/app/src/main`으로 복사한다.

`android/build.rs`는 Android target일 때 `c++_shared` 링크를 지정한다. cargo-ndk가 제공하는 sysroot·출력 경로 환경변수를 사용해 `libc++_shared.so`도 ABI별 출력 폴더에 복사한다. Rust의 공유 라이브러리만 만들고 끝내지 않고 필요한 런타임 파일도 패키징 경로로 보내는 구성이다.

앱은 NativeActivity 기반이며 manifest의 `android.app.lib_name`은 `android`다. Gradle 프로젝트가 복사된 네이티브 라이브러리와 에셋을 앱 구성에 사용한다. 다만 이 shell 스크립트는 Gradle의 APK·AAB 생성이나 서명·배포 명령까지 실행하지 않는다.

### Release 난독화와 JNI 이름 계약

Android release는 minify를 켠다. Rust JNI 코드는 문자열 이름으로 MainActivity 메서드를 호출하므로, 클래스·메서드 이름을 보존하는 규칙이 필요하다.

프로젝트의 ProGuard 설정은 MainActivity의 public 멤버와 RustBinding의 static 메서드를 보존하도록 작성돼 있다. 앞선 FFI 문서의 메서드 시그니처 계약이 패키징 단계에서도 유지되도록 연결한 부분이다. 실제 release 기기 실행을 새로 검증한 결과는 아니다.

## iOS: Xcode 설정에 맞춘 Rust target 선택

`ios/build.ios.sh`는 `aarch64-apple-ios`의 release 정적 라이브러리를 만드는 간단한 수동 경로다. Xcode에는 별도로 `cargo_ios` legacy target이 있으며 `build_rust_deps.sh`를 호출한다.

이 스크립트는 Xcode의 CONFIGURATION·ARCHS·시뮬레이터 구분 정보를 읽는다.

| 실행 환경 | Rust target |
| --- | --- |
| ARM64 iOS 기기 | `aarch64-apple-ios` |
| Apple Silicon 시뮬레이터 | `aarch64-apple-ios-sim` |
| Intel 시뮬레이터 | `x86_64-apple-ios` |

Debug 이외에는 `--release`를 붙이며, 선택된 아키텍처마다 `cargo rustc --crate-type staticlib --lib`를 호출한다. 호스트에서 실행하는 빌드 도구의 라이브러리 경로와 Homebrew 도구 경로도 보완한다.

Xcode는 target별 라이브러리 검색 경로와 `-lios` 링크 옵션을 가진다. Objective-C `main.m`이 `main_rs()`를 호출하는 진입점도 마련돼 있다. 에셋은 프로젝트의 폴더 리소스 참조를 통해 포함하며, Rust 코드와 별개로 번들에 모델·폰트·이미지가 들어가야 한다.

### 빌드 설정과 링크 경로의 불일치

현재 스크립트는 Debug이면 debug 산출물을 만들지만, Xcode의 Debug·Release 라이브러리 검색 경로는 모두 target 하위 `release`를 가리킨다. Debug 빌드를 해도 해당 라이브러리를 찾지 못하거나 기존 release 산출물을 참조할 가능성이 있는 구성이다.

따라서 기기·시뮬레이터·Debug·Release를 분기하는 스크립트를 작성한 성과와, 모든 조합의 링크가 검증됐다는 것은 구분한다. XCFramework 생성이나 archive·서명·스토어 업로드를 이 스크립트가 자동화한 것도 아니다.

## Web: 컴파일·바인딩·최적화

WebGL2·WebGPU 스크립트는 같은 순서로 처리하며 feature와 출력 디렉터리가 다르다.

```text
cargo build --target wasm32-unknown-unknown --release
  → wasm-bindgen --target web
  → 생성 JavaScript의 fetch 호출 변경
  → wasm-opt -Oz
  → wasm_webgl2 또는 wasm_webgpu 출력
```

Cargo가 만든 `web.wasm`을 wasm-bindgen이 웹에서 import할 JavaScript와 WASM 파일로 변환한다. 이후 Binaryen의 wasm-opt로 최적화하고 원래 바인딩이 참조할 파일명으로 교체한다.

이는 Rust 소스 전체를 JavaScript로 변환하는 방식이 아니다. 게임 본체는 WASM으로 실행하고 JavaScript 바인딩과 HTML이 로딩·브라우저 API 연결을 담당한다.

## 다운로드 진행률을 표시하는 연결

스크립트는 생성된 JavaScript의 기본 fetch 호출을 `bevyProgressiveFetch()` 호출로 치환한다. HTML의 함수는 Response body를 TransformStream으로 통과시키며 받은 바이트 수를 누적해 progress 요소를 갱신한다.

이 진행률은 WASM 다운로드를 표시하는 용도다. WASM 컴파일·초기화와 glTF·폰트·이미지 로딩까지 합친 앱 전체 준비율은 아니다. 앱 안의 로딩 UI와 다른 단계로 이해해야 한다.

현재 총량은 HTML에 `16,244,146`바이트로 고정돼 있다. 이는 현재 산출물 크기를 실측해 이 문서에서 보증한 수치가 아니라 코드에 들어 있는 기준값이다. 바이너리 크기가 달라지면 진행률이 실제와 어긋날 수 있다.

생성 코드 수정도 정해진 문자열에 의존한다. wasm-bindgen 출력 형태가 바뀌었을 때 치환 성공 여부를 별도로 검사하지 않는다. fetch 실패는 로그를 남기지만 이후 Response 사용을 중단하는 복구 흐름도 부족하다. 파일 크기 전달과 생성 코드 의존성을 보강할 경계다.

## 두 렌더 빌드와 실제 실행 선택

현재 워크플로는 WebGL2와 WebGPU를 모두 빌드한다. 하지만 `web/index.html`에서 `navigator.gpu`를 검사해 선택하는 분기는 주석 처리돼 있고, 활성 코드는 `./wasm_webgl2/web.js`만 import한다.

따라서 두 종류의 산출물을 만드는 경로가 있다는 것과 현재 페이지가 자동으로 WebGPU를 선택하거나 fallback한다는 것은 다르다. 확인한 실행 구성은 WebGL2 고정이다.

## GitHub Actions와 Pages 게시

워크플로는 `master` push에 반응하고 Ubuntu runner에서 실행한다. Binaryen의 지정 버전과 wasm-bindgen-cli 0.2.99를 준비한 뒤 WASM target을 추가하고 두 Web 빌드 스크립트를 순서대로 실행한다.

이후 공통 assets를 `web/`으로 복사하고 `peaceiris/actions-gh-pages`에 `publish_dir: ./web`을 넘긴다. 전용 배포 폴더로 필요한 파일만 모으는 방식이 아니라 web 디렉터리 전체를 게시하도록 설정돼 있다. 따라서 HTML·산출물·에셋 외의 파일도 게시 대상에 포함될 수 있는 구성이다.

이번 작업에서는 저장소 설정만 확인했다. 실제 Pages 게시 이력·현재 접속 가능 여부·브라우저별 실행 결과를 새로 검증하거나 push·배포를 실행하지 않았다.

## 빌드 실패와 오래된 산출물의 경계

iOS의 Xcode용 스크립트는 실패 시 중단하도록 설정하지만, Android·Web의 짧은 빌드 스크립트는 같은 실패 중단 정책이 명시돼 있지 않다. 중간 Cargo·바인딩 생성이 실패해도 뒤의 복사나 출력 명령으로 이어질 여지가 있다. 기존 산출물이 남아 있으면 이번 빌드 결과와 혼동할 수 있다.

Android의 재귀 복사는 삭제된 파일을 대상에서 정리하는 동기화가 아니다. Web도 출력 디렉터리 정리 명령이 주석 처리돼 있다. 또한 Web은 sed에 대해서는 macOS·Linux를 분기하지만 마지막 크기 출력은 macOS 형태의 `stat -f %z`라 Ubuntu 워크플로와의 일관성을 점검해야 한다.

후속 보강은 실패 즉시 중단, configuration과 링크 경로 일치, 필요한 파일만 담는 배포 디렉터리, 오래된 산출물 정리, 도구 버전과 lockfile 고정, 빌드 후 smoke test로 나눌 수 있다. 이번 문서 작성에서는 관련 스크립트나 프로젝트 설정을 변경하지 않았다.
