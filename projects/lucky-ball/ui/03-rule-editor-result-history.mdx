# 추첨 규칙 편집과 결과 저장·목록 UI

## 추첨 장치를 사용 가능한 앱으로 연결하기

물리 장치가 공을 뽑는 것에 더해, 사용자가 대상 번호와 추첨 개수를 고르고 결과를 보관할 수 있도록 UI를 구성했다. 메뉴에서 게임의 물리 엔티티를 직접 조작하기보다, 규칙을 `GameConfig`에 반영하고 공 생성·추첨 실행 이벤트를 보내는 방식이다.

화면에 표시할 상태와 저장 데이터는 `UiConfig`에 둔다. 사용자 지정 규칙과 저장 번호 목록을 앱 초기화 때 읽어, 메뉴를 다시 생성해도 이전 설정을 사용할 수 있도록 했다. 플랫폼별 저장소 호출은 공통 `kv_get`·`kv_set` 뒤에 두며, 여기서는 UI와 데이터의 연결을 중심으로 설명한다.

## RootNode 아래의 메뉴 교체

`setup_main_ui()`가 전체 화면 크기의 `RootNode`를 만들고 메인 메뉴를 붙인다. 규칙 선택·사용자 지정·게임·결과·저장 목록으로 이동할 때 기존 자식 엔티티들을 제거하고 해당 화면의 UI 트리를 다시 생성한다.

메뉴마다 별도의 Bevy State를 추가한 구조는 아니다. 큰 앱 상태는 Game으로 유지하면서 UI 루트의 자식을 교체한다. 페이지 전환도 전체 화면이 아니라 `NumbersContentNode` 아래의 목록 항목을 다시 만드는 방식으로 처리한다.

버튼의 `Pointer<Click>` observer는 클릭 엔티티를 담은 이벤트를 보내고, 등록된 시스템이 이를 읽는다. 일반 버튼과 삭제 버튼의 색상 반응은 각각 `BtnInteract`, `BtnIndianRedInteract` 마커를 대상으로 `Changed<Interaction>`을 검사해 처리한다. 표시 반응과 기능 실행을 나눈 구성이다.

## 프리셋과 실제 게임 설정

| 메뉴 프리셋 | 투입 대상 | 추첨 개수 |
| --- | --- | ---: |
| 6/45 | 1~45번 공 | 6 |
| 5/69 | 1~69번 공 | 5 |
| 1/26 | 1~26번 공 | 1 |

각 프리셋 처리기는 `rule_given_ball`, `rule_taken_ball`을 설정하고 `BallSpawnEvent(false)`를 보낸 뒤 게임 메뉴로 전환한다. 규칙 선택이 곧 추첨 시작은 아니다. 게임 메뉴에서 실행 버튼을 누르면 별도의 `GameRunEvent`가 나간다.

셔플 버튼은 `BallSpawnEvent(true)`를 보내 초기 공 배치를 다시 구성한다. 실행 버튼을 누른 뒤에는 실행·셔플 버튼을 숨겨 진행 중 재조작을 UI에서 제한한다. 이것이 외부 이벤트나 디버그 호출까지 차단하는 규칙 검증을 의미하지는 않는다.

## 사용자 규칙의 편집 상태와 저장 상태

사용자 지정 화면은 1~70번 공의 포함 여부와 추첨 개수를 편집한다. `CustomRuleBall(u8, bool)`은 번호와 선택 여부를, `CustomRuleFireCnt(u8)`는 추첨 개수를 보관하는 UI Component다.

메뉴에 들어오면 `SavedCustomRule`에서 초기값을 읽는다. 공을 클릭하면 Component의 bool을 바꾸고 배경색과 체크 표시를 갱신한다. 동시에 `UiConfig.saved_custom_rule`에도 반영해 JSON으로 저장한다. 개수 조절도 변경할 때마다 같은 저장 경로를 호출한다.

따라서 별도의 저장 버튼으로 확정하는 편집기가 아니라 **변경 즉시 저장하는 설정 화면**이다. 되돌아가기를 취소 동작으로 해석하면 안 된다. 이후 다시 사용자 지정 화면을 열면 바꾼 설정을 읽는다.

개수 감소는 1 초과일 때, 증가는 20 미만일 때 허용한다. 사용자 지정 적용 버튼은 선택된 공의 Component를 모아 `GameConfig`에 옮기고 공 생성 이벤트를 보낸다. 저장용 규칙과 실행 중 게임 설정은 이 시점에 연결된다.

### 현재 규칙 검증 범위

선택 공 수와 추첨 개수의 관계 검증은 비활성화돼 있다. 공 선택 처리의 조건에 `true || ...`가 있고, 개수 증가 처리도 선택 수 대신 최대 20만 검사한다. 적용 처리에서도 다시 검증하지 않는다.

선택한 공이 0개이거나 추첨 개수가 선택 수보다 큰 규칙을 UI에서 만들 수 있다. 물리 추첨은 목표 개수에 도달해야 종료하므로, 완료할 수 없는 설정이 계속 대기하는 상황으로 이어질 수 있다. 공 선택 범위·개수의 상하한·선택 수 이상 추첨 금지를 실행 진입점에서도 검사할 필요가 있다.

## 두 가지 저장 모델

| 저장 키 | 모델 | 용도 |
| --- | --- | --- |
| `saved_custom_rule` | `SavedCustomRule { load, fire }` | 공별 선택 여부와 추첨 개수 복원 |
| `saved_ball_numbers` | `Vec<BallNumber>` | 사용자가 보관한 추첨 결과 목록 |

두 모델 모두 serde로 JSON 직렬화·역직렬화한다. 사용자 규칙을 읽지 못하면 70개 공 전체 선택·5개 추첨으로 초기화하고, 기록 목록을 읽지 못하면 빈 배열을 저장한다.

기본값을 마련해 초기 실행을 처리하지만, 현재는 저장값 부재와 잘못된 JSON을 모두 파싱 실패로 취급한다. 손상된 데이터를 별도 보관하거나 사용자에게 복구 여부를 묻는 경로는 아니다. 유효한 JSON이라도 공 배열 길이·번호 범위까지 검사하지 않아, 70개와 번호 순서를 전제하는 UI 인덱싱과 계약이 맞아야 한다.

## 결과는 사용자가 저장할 때 기록

게임 종료 이벤트를 받으면 `picked_ball`을 결과 화면에 표시한다. 이 화면에서는 포착 순서의 목록을 그대로 보여준다. 자동으로 영구 기록에 추가하지는 않는다.

저장 버튼을 누르면 다음 데이터를 생성한다.

```rust
pub struct BallNumber {
    pub id: String,
    pub numbers: Vec<u8>,
    pub game_type: String,
    pub time: i64,
}
```

`id`는 새 UUID, `numbers`는 선택 번호 복사본, `game_type`은 `추첨 개수/대상 개수` 문자열이다. `time`은 저장 처리 시 `AppFfi::get_current_epoch_time()`으로 얻는다. 따라서 추첨 종료 순간을 별도로 보관한 시각이 아니라 **저장 버튼을 처리한 시각**이다.

벡터에 항목을 추가하고 전체 목록을 직렬화한 뒤 저장 버튼을 숨긴다. 이것은 UI에서 반복 클릭을 줄이는 처리이며, 같은 결과의 중복 이벤트를 저장 계층에서 거부하는 방식은 아니다. 기록에는 사용자 규칙의 전체 대상 번호 집합이 없으므로 저장 항목만으로 당시 사용자 규칙을 완전히 복원할 수도 없다.

결과 화면의 재시도 함수와 이벤트 선언은 남아 있지만, 현재 재시도 버튼 생성과 시스템 등록은 주석 처리돼 있다. 활성 경로는 저장과 규칙 선택으로 돌아가기다.

## 최신순 정렬과 5개 단위 페이지

저장 목록에 들어갈 때 전체 벡터를 복사한 뒤 `time` 내림차순으로 정렬한다. 기록의 원본 저장 순서를 바꾸는 대신 표시용 목록을 만든다. 이전·다음 페이지 처리에서도 복사·정렬 후 필요한 범위를 선택한다.

`paginate_with_total()`은 0 기반 페이지와 페이지 크기를 받아 해당 slice와 총 페이지 수를 반환한다. 현재 호출 크기는 5이며 마지막 페이지에는 남은 항목만 표시한다. `NumbersPagination.now`는 페이지 인덱스이고, 이름이 `last`인 필드는 마지막 인덱스가 아니라 총 페이지 수다.

각 항목은 날짜·규칙·번호 목록·삭제 버튼을 가진다. 저장된 번호의 복사본만 오름차순 정렬해 10개까지 첫 줄에, 초과분은 다음 줄에 표시한다. 결과 화면의 포착 순서와 목록의 정렬 순서가 다르며, 표시 정렬이 저장 번호 배열 자체를 바꾸지는 않는다.

날짜는 저장한 epoch 값에 플랫폼이 제공한 현재 시간대 offset을 적용해 문자열로 만든다. 기록에 시간대 자체를 저장하지 않으므로 기기 시간대가 달라지면 표시 시간도 달라질 수 있다.

## ID로 삭제하고 페이지 다시 계산

삭제 이벤트는 클릭 엔티티에서 부모를 따라가며 `NumbersItem`을 찾아 UUID를 얻는다. `delete_item()`은 같은 ID가 아닌 항목만 남기는 `retain`으로 목록을 갱신하고 전체 JSON을 다시 저장한다. 화면상의 줄 번호나 정렬 위치로 저장 항목을 지우지 않는 방식이다.

그다음 목록을 다시 정렬하고 총 페이지 수를 계산해 현재 페이지를 조정한다. 끝 페이지의 마지막 항목을 삭제했을 때 앞 페이지로 이동하려는 처리다.

다만 모든 기록을 삭제하면 총 페이지 수가 0인데 `pagination.now = total_size - 1`을 수행할 수 있다. `usize`의 0에서 1을 빼는 연산이므로 빌드의 overflow 검사 설정에 따라 panic 또는 래핑 문제가 생긴다. 이후 표시 문자열을 최소 1로 만드는 처리만으로 앞선 계산을 보호하지는 못한다.

초기 빈 목록은 화면에 1/1로 표시하지만 내부 총 페이지는 0이고, 이전·다음 클릭 처리에서는 이 표시 보정이 일관되게 적용되지 않는다. 빈 목록 상태와 일반 페이지 계산을 분리해 보강할 경계다.

## 저장 실패와 데이터 규모의 경계

저장·삭제는 전체 목록을 매번 JSON으로 직렬화하고, 사용자 규칙도 클릭마다 저장한다. 소량의 로컬 설정·기록을 단순하게 관리하는 구조이며, 대량 기록의 부분 갱신이나 목록 가상화는 아니다. 페이지마다 전체 복사·정렬과 UI 재생성이 있으므로 기록 수가 커질 때의 비용은 별도로 측정해야 한다.

또한 공통 `kv_set`은 성공·실패 결과를 반환하지 않는다. UI가 저장 성공을 확인한 뒤 버튼을 숨기는 계약은 아니며, 직렬화 오류 분기는 빈 문자열을 만들어 저장을 이어간다. 저장 오류 전달, 손상 원본 보존, 스키마 버전, 마지막 항목 삭제 경계는 후속 보강 항목이다.
