AssetManager 도입과 리소스 관리 책임 분리

배경과 목표​

기존 CTexture는 파일 경로와 개수를 받아 DirectX 텍스처를 만들고, 텍스처 배열을 보관하며, 렌더링 시 사용할 인덱스를 선택하는 역할까지 맡았다. 텍스처 이외의 리소스를 추가하면서 파일 로드와 사용 객체의 책임을 구분할 공통 관리 지점이 필요했다.

CAsset과 CAssetMgr를 도입해 리소스 등록·로딩·조회·해제를 모았다. CTexture는 리소스 그룹의 키를 보관하고 필요한 프레임을 바인딩하는 컴포넌트로 변경했다. 폰트 등 다른 리소스도 같은 관리 경로에 연결하고, 등록 상태를 확인하는 ImGui 화면을 추가했다.

이 문서는 공통 리소스 관리 구조를 다룬다. 씬 전환 스레드의 실행 순서, FMOD 재생 기능, Spine의 정점 변환은 별도 범위다. 팀원이 추가한 JSON·모델 로더 전체를 본인이 구현한 것으로 포함하지 않는다.

기존 구조에서 달라진 부분​

7594f76 커밋의 CTexture 변경 전후를 비교하면 책임 이동이 드러난다.

구분도입 전도입 후
컴포넌트 초기화텍스처 종류·파일 패턴·개수로 파일 로드Asset 그룹 키 저장
실제 리소스 보관CTexture의 텍스처 포인터 배열CAssetTexture·CAssetCubeTexture
컴포넌트 Clone배열 복사 후 각 텍스처 AddRef()그룹 키 복사
렌더링컴포넌트 배열에서 인덱스로 선택Manager에서 그룹을 찾아 인덱스로 선택
해제 책임컴포넌트가 보관한 텍스처 참조 해제Manager가 Asset 해제 경로 관리

기존 Clone도 텍스처 포인터를 공유하고 참조 수를 늘리는 방식이었다. 따라서 변경 전에는 모든 Clone이 이미지 파일을 다시 읽거나 GPU 텍스처를 복제했다고 설명하면 안 된다. 이번 변경의 핵심은 중복 복사 제거라는 성능 주장보다 파일 리소스의 관리 책임을 컴포넌트에서 분리한 것이다.

공통 Asset 계약​

CAsset은 경로와 로드 상태를 보관하고, 파생 클래스에 Load()와 Unload() 구현을 요구한다. 생성 직후 상태는 UNLOAD다. 문자열 인자는 std::wstring_view로 받지만 경로는 std::wstring에 복사하므로 전달한 임시 문자열의 수명에 의존하지 않는다.

텍스처 Asset에서는 다음 순서로 상태를 갱신한다.

Plain Text
Create(path) → UNLOAD
Load()       → LOADING → LOADED 또는 LOADFAIL
Unload()     → 실제 텍스처 해제 → UNLOAD

CAssetTexture::Load()는 D3DXCreateTextureFromFileEx()로 텍스처와 이미지 정보를 얻는다. 실패하면 경로를 포함한 메시지를 띄우고 LOADFAIL로 바꾼다. 성공하면 LOADED로 바꾸고, Unload()에서는 텍스처 참조를 해제한다. CubeTexture도 같은 상태 계약으로 DirectX 큐브 텍스처 생성·해제를 감싼다.

Manager가 직접 모든 상태를 전환하는 것은 아니다. 실제 로드 결과와 상태 갱신은 파생 Asset의 책임이다. LOADING 상태가 있다는 이유만으로 Manager 자체가 비동기 로딩을 제공하는 것도 아니다.

키 하나에 여러 리소스를 묶는 등록 구조​

저장 구조는 map<const std::wstring, vector<CAsset*>>다. 키는 리소스 그룹을 식별하고, 벡터는 그 그룹에 등록한 Asset을 보관한다. API의 svLayerTag라는 이름은 여기서는 GameObject 레이어가 아니라 Asset 그룹 키를 뜻한다.

AddAsset()은 null 포인터를 거부한다. 새 키이면 벡터를 만들고, 이미 있는 키이면 기존 벡터 뒤에 추가한다. 같은 키를 사용해 여러 장의 프레임 텍스처를 묶을 수 있다. 실제 등록 코드에도 Tex_Blood에 인덱스별 텍스처를 추가한 뒤 전체 로드를 요청하는 사례가 있다.

다만 같은 키를 다시 등록한다고 기존 리소스를 교체하지는 않는다. 같은 파일 경로인지 비교하거나 동일한 Asset 포인터인지 검사하지도 않는다. 파일 경로 단위 중복 제거 캐시나 자동 리로드 시스템과는 구분해야 한다.

등록과 로딩 시점 분리​

CAssetTexture::Create()는 경로를 가진 객체만 생성한다. 파일 읽기와 DirectX 리소스 생성은 Load()에서 수행한다. 호출자는 여러 Asset을 먼저 등록하고 이후 필요한 그룹만 또는 전체를 로드할 수 있다.

  • LoadAsset(key)는 해당 그룹을 순회한다.
  • LoadAsset()은 등록된 모든 그룹에 대해 같은 처리를 수행한다.
  • 각 Asset이 UNLOAD인 경우에만 Load()를 호출한다.

동일 Asset이 이미 LOADED라면 Manager를 통해 다시 로드를 요청해도 건너뛴다. 이는 등록된 객체의 상태를 기준으로 한 중복 로드 방지다. 같은 경로로 새 Asset을 등록한 경우까지 막는 것은 아니다.

LOADFAIL도 UNLOAD가 아니므로 단순히 LoadAsset()을 다시 호출하는 것만으로 자동 재시도하지 않는다. 또한 Manager의 반환형은 void이고 개별 Load()의 HRESULT를 집계하지 않는다. 모든 리소스의 성공 여부를 하나의 결과로 보장하는 로딩 작업 시스템은 아니다.

사용하는 쪽은 키와 인덱스로 접근​

CTexture의 초기화와 복사 생성자는 m_sAssetLayer 문자열을 설정·복사한다. Set_Texture(iIndex)는 Manager에서 그룹을 찾고, 해당 Asset이 일반 텍스처인지 CubeTexture인지 dynamic_cast로 확인한 뒤 DirectX의 텍스처 슬롯 0에 연결한다.

여러 게임 객체가 같은 그룹 키를 사용하면 같은 Asset 리소스를 참조할 수 있다. 개별 컴포넌트는 파일 경로를 다시 구성하거나 리소스를 직접 소유할 필요가 없다. 대신 키·인덱스·타입이 올바르고 사용 시점에 로드되어 있다는 전제가 필요하다.

단일 Asset에는 Get_AssetFirst<T>(key)를 사용한다. 키가 없으면 nullptr를 반환하고, 키가 있으면 첫 번째 원소를 dynamic_cast<T*>로 변환한다. 그룹 전체에서 T에 맞는 Asset을 탐색하는 함수는 아니며 로드 상태도 검사하지 않는다.

현재 조회 구현은 std::map의 find()가 아니라 find_if()와 문자열 비교로 전체 키를 순회한다. 따라서 해시 기반 조회나 로그 시간 조회로 설명할 수 없다. 렌더 중 반복 조회 비용을 줄이려면 검색 구현 개선이나 수명을 고려한 참조 캐싱을 별도로 검토해야 한다.

폰트와 다른 리소스의 연결​

본인 커밋 3005bcf에서는 폰트 출력을 CAssetDefaultFont로 옮겼다. 이 Asset이 DirectX Font와 Sprite를 구성하고 Render_Font()를 제공한다. UI는 폰트 키로 Asset을 조회해 텍스트를 출력한다.

파일 경로를 받는 폰트 생성 경로에서는 AddFontResourceEx(..., FR_PRIVATE, ...)로 폰트를 등록하고, 등록된 폰트 이름·크기·굵기로 DirectX Font를 생성한다. 파일 없이 설치된 폰트 이름을 사용하는 경로도 있다. 텍스처의 포인터 Getter뿐 아니라 타입에 맞는 사용 API를 Asset이 제공하는 사례다.

Spine도 공통 Asset 경로에 들어가지만 개체별 재생 상태까지 Manager가 관리하지는 않는다. 공유 리소스와 개별 재생 컴포넌트의 구분은 Spine 통합 문서에서 다룬다. JSON 등 팀원의 리소스 타입은 이 구조를 사용하는 확장 사례로만 구분한다.

소유권과 해제 순서​

AddAsset()은 받은 포인터를 저장하며 별도의 AddRef()를 호출하지 않는다. 반면 DelAsset(key)는 그룹의 Asset마다 Safe_Release()를 호출하고 그룹을 지운다. Manager 전체 해제도 모든 그룹에 대해 같은 처리를 한다.

따라서 정상적인 사용 계약은 생성한 Asset의 해제 책임을 Manager에 맡기고, 조회 결과를 빌려 사용하는 방식이다. 반환 포인터가 참조 수를 자동으로 늘려 주는 것은 아니다. 같은 포인터를 여러 번 등록하거나 등록 후 호출자가 임의로 해제하는 사용법도 별도의 방어가 없다.

CTexture는 키만 가지므로 컴포넌트가 살아 있다고 Asset의 수명이 자동으로 연장되지 않는다. 사용 중인 그룹을 삭제하면 이후 조회가 실패하며, Asset이나 그 내부 포인터를 별도로 보관한 소비자는 무효 포인터를 가질 수 있다. 소비자를 정리한 다음 해당 리소스를 해제하도록 수명 순서를 맞춰야 한다.

공통 Free() 계약을 만들었다고 모든 리소스 해제가 완벽히 검증된 것은 아니다. 예를 들어 현재 CAssetDefaultFont::Unload()에는 Font·Sprite 참조 해제 코드가 주석 처리되어 있다. 공통 관리 경로의 존재와 각 파생 Asset의 실제 해제 완결성은 구분해서 점검해야 한다.

ImGui로 등록 상태 확인​

ASSET_MGR 창은 키별 Asset 개수를 트리 라벨에 보여 주고, 펼치면 각 Asset의 상태 문자열과 경로를 출력한다. 등록 누락인지, 경로 오류로 실패했는지, 로드를 아직 요청하지 않았는지 확인할 단서를 제공한다.

이 GUI는 현재 목록·경로·상태를 확인하는 조회 화면이다. 메모리 사용량이나 로딩 시간을 측정하지 않으며, 버튼으로 재로드하거나 Asset을 편집하는 리소스 에디터까지 구현한 것은 아니다.

결과와 한계​

리소스 생성과 게임 객체에서의 사용을 분리하고, 서로 다른 리소스 타입에 등록·로드·조회·해제의 공통 경로를 마련했다. 개별 UI·물고기·컴포넌트 코드는 키를 통해 사용할 리소스를 선택하고, Manager 화면에서 등록 상태를 확인할 수 있게 했다.

현재 구현에는 다음 개선 여지가 있다.

  • 그룹 조회는 선형 검색이다. 키 개수와 실제 조회 빈도를 측정한 뒤 자료구조에 맞는 검색을 적용할 수 있다.
  • Get_AssetFirst()는 빈 벡터를 검사하지 않고, CTexture::Set_Texture()도 그룹 존재·인덱스 범위를 검증하지 않는다. 이전 컴포넌트에 있던 범위 검사가 새 구조에서는 빠진 점도 보강 대상이다.
  • 내부 map과 vector를 수정 가능한 포인터로 공개한다. 호출자가 내용을 변경하면 등록·해제 규칙을 우회할 수 있다.
  • 실패 결과 집계·재시도·부분 로드 실패 정리 정책이 공통화되어 있지 않다. 각 파생 Asset의 실패 경로도 별도 검증이 필요하다.
  • 상태 값과 컨테이너 접근에 동기화가 없다. 등록과 로드가 분리되어 있다는 이유만으로 여러 스레드에서 안전한 Manager라고 볼 수 없다.

이 변경에 따른 메모리 절감량·로딩 시간·FPS 개선을 측정한 자료는 없다. 성과는 관리 책임과 사용 경로를 분리한 설계 변경으로 설명한다.

시연·검증 자료​

  1. 등록 직후 UNLOAD인 텍스처 그룹이 로드 후 LOADED로 바뀌는 화면.
  2. 하나의 키에 여러 프레임을 등록하고 인덱스를 바꾸어 출력하는 장면.
  3. 같은 그룹 키를 사용하는 여러 컴포넌트가 하나의 Asset 그룹을 참조하는 코드·GUI 비교.
  4. 잘못된 경로에서 LOADFAIL과 파일 경로를 확인하고, 재시도 정책의 현재 동작 점검.
  5. 소비자를 정리한 뒤 그룹을 삭제하는 정상 수명과, 누락된 키·빈 그룹·범위 초과의 경계 테스트.

이번 문서는 현재 소스와 Git 변경 이력을 분석해 작성했다. 위 항목은 제출용 검증 자료로 확보할 대상이며, 이번 작성 중 게임 실행·누수 검사·성능 측정을 완료했다는 뜻은 아니다.
