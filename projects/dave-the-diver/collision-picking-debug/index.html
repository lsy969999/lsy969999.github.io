충돌체 관리·마우스 피킹·디버그 렌더링

배경과 목표​

물고기의 감지 범위, 아이템 접촉, 회전하는 스마트폰 아이콘 선택에 공통으로 사용할 충돌체가 필요했다. 화면에 보이는 객체와 실제 검사 영역이 일치하는지 확인할 디버그 출력도 필요했다.

CCollider로 도형 변환·교차 검사·태그·연결 포인터를 묶고, CColliderMgr에서 현재 프레임의 충돌체를 문자열 그룹별로 조회하도록 구성했다. 마우스 위치를 월드 Ray로 바꾸는 헬퍼와 Ray 교차 거리 반환을 UI 피킹에 연결하고, 충돌 상태는 도형 색상으로 확인하도록 했다.

교차 판정에는 DirectXCollision.h의 Bounding 볼륨을 사용했다. 이를 엔진 인터페이스에 연결하고, 충돌 그룹 관리·좌표 변환·피킹·디버그 렌더링을 구현했다.

공통 충돌체와 도형별 데이터​

CCollider는 충돌체 종류, 문자열 태그, 원래 색·충돌 색, 사용자 연결 포인터와 디버그 버퍼 정보를 가진다. 도형별 클래스가 실제 Bounding 데이터를 보관한다.

엔진 클래스사용하는 Bounding 데이터용도
CAABBBoundingBox월드 축에 정렬된 박스 검사
COBBBoundingOrientedBox방향을 가진 박스 검사
CBoundingSphereBoundingSphere중심·반지름 기반 검사
CBoundingFrustumBoundingFrustum투영 행렬로 만든 절두체 검사

공통 API에는 충돌체끼리의 Intersect(), Ray와의 Intersect(), 행렬 또는 크기·회전·이동을 받는 Transform()이 있다. 내부에서는 종류 값으로 분기해 대응하는 DirectX Bounding 함수에 전달한다.

종류 값과 실제 파생 타입이 일치한다는 전제로 static_cast를 사용한다. 도형을 추가하려면 관련 분기도 확장해야 하며, 등록만으로 모든 조합이 자동 지원되는 구조는 아니다.

등록은 보관, 판정은 호출자의 책임​

CColliderMgr의 저장 구조는 map<const std::wstring, list<CCollider*>>다. AddColliderGroup(key, collider)로 현재 프레임에 검사할 객체를 넣고, Get_Colliders(key)로 원하는 그룹을 조회한다.

Manager가 모든 충돌체 쌍을 자동 검사하지는 않는다. 예를 들어 물고기 관리 코드는 플레이어 그룹과 물고기 감지·피격 그룹을 가져와 검사하고, 스마트폰 아이콘은 자신의 OBB에 직접 Ray 검사를 요청한다.

실제 프레임 흐름은 다음과 같다.

Plain Text
게임 객체 Update
  → 소유한 충돌체를 그룹에 등록
  → 객체의 행렬로 충돌 도형 갱신
게임 로직·UI
  → 필요한 그룹 또는 자기 충돌체에 Intersect 호출
디버그 렌더
  → 등록된 충돌체와 검사 결과 색상 출력
프레임 끝
  → 등록 목록 비우기

물고기 콜라이더와 스마트폰 앱에서는 등록 후 Transform을 적용하는 순서를 사용한다. 따라서 등록만으로 최신 도형이 되는 것은 아니며, 실제 검사 전에 변환 갱신까지 완료되어야 한다.

문자열 그룹은 후보를 나누는 기준이지 충돌 레이어 비트마스크나 Simulation Collision Matrix가 아니다. Enter·Stay·Exit 이벤트 추적, 접촉 해결, 밀어내기, 반발력 계산도 Manager가 제공하지 않는다.

프레임별 등록 목록과 소유권​

Clear_ColliderGroup()은 그룹 목록과 맵을 비우지만 충돌체를 해제하지 않는다. 충돌체의 생성·해제 책임은 소유한 게임 객체에 있고, Manager는 검사·디버그 출력에 필요한 포인터를 잠시 보관한다.

현재 통합 코드에서는 CMainApp::EndOfFrame_MainApp()에서 목록을 비운 뒤 씬의 프레임 끝 정리를 수행한다. 같은 충돌체를 다음 프레임에도 사용하려면 다시 등록해야 한다. 등록 목록을 영구적인 충돌체 저장소로 사용하지 않는 방식이다.

그룹은 find_if()로 조회하고, 해당 그룹에 등록된 도형을 충돌 검사 후보로 사용한다.

충돌 도형의 변환​

박스는 초기 Extents, OBB는 초기 방향, 구는 초기 반지름, Frustum은 기준 투영 행렬을 보관한다. Transform(matrix)는 이 기준값으로 임시 Bounding 볼륨을 구성하고 현재 행렬을 적용해 검사 데이터를 갱신한다. 이미 변환된 크기에 매 프레임 스케일을 누적하려는 구조는 아니다.

AABB는 회전된 물체의 방향을 그대로 유지하는 OBB와 다르다. 회전 행렬을 적용하더라도 결과는 월드 축에 정렬된 경계 박스다. 회전하는 스마트폰 아이콘은 OBB를 사용해 렌더링에 사용한 행렬과 같은 기준으로 선택 영역을 갱신했다.

현재 재구성 경로에서는 박스·구의 초기 중심을 기준 데이터로 다시 복사하지 않는다. 원점 중심 도형을 객체 행렬로 이동하는 사용과, 도형 내부에 별도 중심 오프셋을 넣는 사용은 구분해야 한다.

검사 결과와 게임 객체 연결​

충돌체끼리의 Intersect()는 교차하면 true를 반환하고 두 충돌체를 충돌 색으로 바꾼다. Ray 검사에서는 맞은 충돌체의 색을 바꾸고 거리도 반환한다. 법선·접촉점 목록·관통 깊이를 함께 반환하는 접촉 데이터 API는 아니다.

태그는 해당 충돌체의 역할을 구분하고, void* 연결 포인터는 대응하는 게임 객체를 찾는 데 사용한다. 물고기의 감지·피격 영역에서 같은 물고기를 가리키거나, UI의 OBB에서 선택할 아이콘을 찾는 식이다.

이 포인터는 타입과 수명을 보장하지 않는다. 태그를 확인하고 올바른 객체 타입으로 해석하는 책임은 호출자에게 있다. 핸들 기반 안전 조회나 충돌체 자체의 객체 소유 기능과는 다르다.

게임플레이 적용은 물고기 행동·포획 문서, 아이콘 선택은 스마트폰 UI 문서에 정리했다. 팀원들이 이 API로 구현한 플레이어 전투·상자 로직까지 본인 기여로 합치지 않는다.

마우스 좌표를 월드 Ray로 변환​

CHelper::GetMousePointRay()는 운영체제의 커서 위치를 클라이언트 좌표로 바꾼 뒤 Viewport 크기를 사용해 X·Y를 정규화한다. Y 방향을 뒤집고 Z를 0으로 설정한 점에 역 Projection을 적용해 뷰 공간의 점을 얻는다.

뷰 공간 원점에서 그 점을 향하는 방향을 만들고, 역 View로 Ray 원점과 방향을 월드 공간으로 옮긴다. 점은 TransformCoord, 방향은 TransformNormal로 처리해 방향에 카메라의 이동 성분이 섞이지 않도록 했다.

이 헬퍼는 카메라 원점에서 출발하는 원근 투영용 Ray를 구성한다. 직교 투영에서도 같은 원점으로 발사하면 올바른 피킹이 되지 않으며, 현재 디바이스에 설정된 View·Projection과 Viewport에 의존한다. 여러 Viewport의 원점 보정이나 별도 UI 좌표계까지 일반화한 함수는 아니다.

Ray 교차 거리와 잘못된 방향 방어​

CCollider::Intersect(rayPos, rayDir, outDistance)는 방향 길이가 0.00001보다 작으면 false를 반환한다. 유효한 방향은 정규화해 Bounding 볼륨의 Ray 검사에 전달한다. 정규화는 입력 포인터가 가리키는 방향 값 자체를 수정한다.

방향 벡터의 길이를 검사하도록 보강했다. 길이가 없는 방향을 정상적인 단위 방향으로 간주하지 않도록 한 수정이다. 성공 시 거리로 맞은 위치를 계산하거나 여러 후보 중 가까운 것을 선택할 수 있지만, 현재 API가 모든 후보를 모아 가장 가까운 객체까지 골라 주지는 않는다. 실패한 경우의 거리 값을 유효한 결과로 사용해서도 안 된다.

스마트폰 앱은 자체 OBB의 교차 여부를 이용해 선택·실행을 분기한다. 이 사용처가 거리별로 모든 아이콘을 정렬해 하나만 선택하는 구현은 아니므로, 겹친 UI의 우선순위 정책은 별도 문제다.

충돌 상태를 화면에서 확인​

그룹 등록 시 현재 색을 원래 색으로 초기화하고, 그 프레임의 검사에서 교차한 도형을 충돌 색으로 바꾼다. 기본 도형은 일반 상태를 초록색, 교차 상태를 빨간색으로 설정한다. 이 색은 실제로 호출한 검사 결과를 보여 주는 것이며, 그리지 않은 모든 상대와의 충돌을 자동 계산한 결과는 아니다.

Manager의 렌더 토글은 디버그 출력만 제어한다. 끈다고 게임 코드의 등록·변환·Intersect 호출이 중단되는 것은 아니다. 같은 프레임에 다시 등록하면 색도 초기화되므로 검사와 등록 순서가 화면 결과에 영향을 줄 수 있다.

AABB·OBB·Frustum은 최초 Render에서 버퍼를 준비하고 이후 현재 도형의 모서리 좌표를 정점 버퍼에 기록한다. 박스는 8개 정점·12개 삼각형을 와이어프레임으로 그린다. 단순히 12개 외곽선만 그리는 Line List 방식과는 다르다.

깊이 검사를 끄고 월드 변환이 반영된 정점을 그려 검사 영역을 확인하도록 했다. 출력 후에는 Fill·Cull·Depth 등을 정해진 기본 상태로 돌린다. 이전의 모든 렌더 상태를 저장했다가 그대로 복구하는 범용 디버그 렌더 패스는 아니다.

디버그 버퍼 공통화의 범위​

박스·Frustum의 버퍼 생성을 CDynamicBuffer로 공통화했다. 공통 함수가 Usage·Pool·FVF·정점/인덱스 크기 등을 받아 버퍼를 만들고, 도형별 코드가 자신의 인덱스와 정점을 채운다. 갱신에는 D3DLOCK_DISCARD를 사용한다.

이는 코드 재사용이며 여러 충돌체가 하나의 GPU 버퍼를 공유하거나 한 번의 Draw로 배치 렌더링한다는 의미가 아니다. 도형별 버퍼와 Draw가 남아 있다. 구의 디버그 출력은 D3DXCreateSphere()로 만든 별도 Mesh를 중심·반지름에 맞춰 그리는 경로다.

구현 결과​

여러 게임플레이·UI에서 같은 도형 인터페이스와 좌표 변환·시각화 경로를 사용하도록 연결했다. 물리 시뮬레이션, 연속 충돌 검사와 충돌 이벤트 상태 관리는 지원하지 않는다.
