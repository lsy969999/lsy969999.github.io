컴포넌트 부착·조회 API와 소유자 연결

반복적인 부착 코드를 공통화​

게임 객체는 Prototype에서 컴포넌트를 복제하고, 원하는 타입으로 캐스팅한 뒤 객체의 컴포넌트 맵에 등록하는 구조였다. Buffer·Texture·Transform마다 같은 준비 코드를 반복했다.

기존 Prototype 패턴 자체를 새로 설계한 작업은 아니다. 본인 보강 범위는 이 반복을 AddComponent<T, ID>()로 묶고, 타입을 지정하는 조회 API와 컴포넌트에서 소유 객체로 접근하는 연결을 추가한 것이다.

기존 코드는 다음과 같은 형태였다. 아래 예시는 당시 Buffer 부착 코드를 간추린 것이다.

C++
CComponent* pComponent = m_pBufferCom =
    dynamic_cast<CRcTex*>(
        CProtoMgr::GetInstance()->Clone_Prototype(L"Proto_RcTex"));
if (pComponent == nullptr)
    return E_FAIL;

m_mapComponent[ID_STATIC].insert({L"Com_Buffer", pComponent});

공통화 후 파생 객체에서는 타입·갱신 그룹·Prototype 이름·객체 내부 이름을 지정한다.

C++
const HRESULT result = AddComponent<Engine::CRcTex, ID_STATIC>(
    L"Proto_RcTex", L"Com_Buffer", &m_pBufferCom);
if (FAILED(result))
    return E_FAIL;

Proto_RcTex는 복제할 원본을 찾는 이름이고, Com_Buffer는 해당 객체 안에서 조회할 이름이다. 마지막 출력 인자는 선택 사항이며, 등록한 컴포넌트와 같은 포인터를 돌려준다. 별도의 소유권이나 참조 카운트를 추가하는 반환은 아니다.

부착과 조회의 실제 동작​

AddComponent()는 protected 함수로 파생 객체의 초기화 코드에서 사용한다. 내부 순서는 Prototype 복제 → dynamic_cast → 출력 포인터 설정 → 소유자 연결 → 맵 등록이다. 복제 또는 타입 변환 결과가 null이면 E_FAIL을 반환한다.

GetComponent()는 public 함수다. 지정한 그룹에서 이름으로 찾고, dynamic_cast 결과를 반환한다. 이름이 없거나 타입이 다르면 null이므로 호출자가 검사해야 한다.

C++
auto* pTransform = GetComponent<Engine::CTransform, ID_DYNAMIC>(
    L"Com_Transform");
if (pTransform == nullptr)
    return E_FAIL;

템플릿은 호출부의 타입 표기와 반복 코드를 정리한다. 실제 타입 검증은 RTTI를 사용하는 dynamic_cast이므로, 컴파일 시점에 모든 조합을 검증하거나 캐스팅 비용을 제거한 구조는 아니다.

ID_STATIC과 ID_DYNAMIC은 기본 컴포넌트 갱신 루프의 참여 여부를 구분한다. 기본 Update·LateUpdate는 Dynamic 그룹을 순회한다. Static이라는 이름이 컴포넌트의 불변성이나 인스턴스 공유를 뜻하지는 않으며, 두 그룹 모두 부착 시 Prototype을 복제한다.

소유자 연결과 수명​

컴포넌트에 m_pGameObject와 Get_GameObject()·Set_GameObject()를 추가했다. 부착 시 Set_GameObject(this)를 호출해 컴포넌트가 자신을 사용하는 객체에 접근할 수 있게 했다.

복사 생성자에서는 원본의 소유자 주소를 복사하지 않고 null로 초기화한다. 새 복제본은 부착 대상이 결정된 뒤 해당 객체와 연결된다.

객체의 Free()에서는 등록된 모든 컴포넌트의 소유자 포인터를 먼저 null로 만든 뒤 컴포넌트를 해제하고 맵을 비운다. 컴포넌트 정리 중 소유 객체를 계속 참조하는 경로를 끊기 위한 순서다.

이 연결은 raw pointer이며 소유 객체의 수명을 연장하지 않는다. 조회·출력 포인터 역시 객체가 관리하는 컴포넌트에 대한 접근 수단이므로, 외부에서 장기간 보관하거나 임의로 해제해도 안전하다는 의미는 아니다.

결과와 한계​

호출부가 직접 수행하던 복제·캐스팅·등록을 한곳으로 모으고, 부착 시 소유자 연결이 함께 이루어지도록 정리했다. 작은 API 보강이지만 객체별 준비 코드의 중복을 줄이고 사용 방식을 통일하는 역할을 했다.

현재 구현에는 다음 경계 처리가 남아 있다.

  • 중복 이름: 맵의 insert() 성공 여부를 확인하지 않는다. 기존 컴포넌트가 있으면 새 복제본이 등록되지 않아도 성공을 반환하고, 출력 포인터는 새 복제본을 가리킬 수 있다. 새 복제본 해제도 필요하다.
  • 타입 불일치: 복제에는 성공했지만 dynamic_cast가 실패하면 원래 복제 포인터를 잃는다. 원본 포인터를 따로 보관하고 실패 시 해제하는 처리가 필요하다.
  • 실패 시 출력: 실패 경로에서 출력 포인터를 null로 초기화하지 않는다. 호출자는 성공 여부를 확인해야 한다.

따라서 완성된 런타임 컴포넌트 편집 시스템보다는, 기존 생성 흐름을 정리한 공통 API로 설명한다. 의존성 자동 해결이나 예외 상황까지 포함한 등록 트랜잭션을 구현한 것으로 확대하지 않는다.

작성 근거와 확인 범위​

본인 커밋 7a5845f에서 AddComponent()와 소유자 연결·복사 초기화·해제 전 연결 해제를 추가하고, 당시 Client/Code/CPlayer.cpp의 부착 코드를 교체했다. 8cfa596에서는 타입 지정 조회 함수 GetComponent()를 추가했다.

현재 구현은 Engine/Header/CGameObject.h, Engine/Code/CGameObject.cpp, Engine/Header/CComponent.h, Engine/Code/CComponent.cpp에서 확인했다. 기존 Prototype 관리 구조와 팀원 개별 게임플레이 구현은 본인 API 보강과 구분했다.

문서는 소스와 커밋 비교를 근거로 작성했다. 제출용 검증 자료로는 정상 부착·조회, 없는 Prototype, 잘못된 타입, 중복 이름, 복제본의 소유자 연결·해제 순서 확인이 적합하다. 이번 문서 작성 중 게임을 실행해 해당 경계 테스트를 완료한 것은 아니다.
