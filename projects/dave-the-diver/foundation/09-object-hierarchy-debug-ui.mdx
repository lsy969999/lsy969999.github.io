# 부모·자식 계층 기반 업데이트와 오브젝트 디버그 GUI

## 배경과 목표 {/* #해결하려던-문제 */}

UI 패널과 이미지, 물고기와 충돌 영역처럼 서로 연결된 객체는 부모의 변경 결과를 자식이 사용하는 경우가 많았다. 레이어에 넣은 순서만으로 업데이트하면 이 관계를 명시하기 어렵고, 부모를 제거할 때 함께 정리할 대상도 따로 관리해야 한다.

`CGameObject`에 부모 포인터와 자식 목록을 추가하고, 씬에서 계층 관계를 기준으로 업데이트 순서를 구성했다. 같은 관계를 하위 객체의 제거 표시에 재사용하고, ImGui에서 실제 저장 목록과 부모·자식 구조를 각각 확인할 수 있도록 했다.

본인 구현은 계층 연결·순회와 디버그 GUI다. 실제 제거를 프레임 끝의 `CScene::EndOfFrame()`으로 옮긴 작업은 팀원 커밋 `246d167`이며, 현재 동작을 설명할 때도 구분한다. 또한 아래의 순회 방식은 설계 의도와 호출 경로를 설명하는 것으로, 현재 헬퍼의 수명 관련 결함까지 해결되었다는 의미는 아니다.

## 보관 구조와 계층 관계를 분리

레이어는 태그별 `list<CGameObject*>`를 보관한다. `Add_GameObject()`는 같은 태그가 있으면 목록 뒤에 추가하므로, 하나의 이름으로 여러 객체를 등록할 수 있다. 레이어의 `Free()`는 등록된 객체를 순회하며 해제한다.

부모·자식 관계는 이 저장 구조와 별개다.

| 구성 | 역할 |
| --- | --- |
| 씬의 레이어 맵 | 레이어와 그 안의 객체를 찾는 진입점 |
| 레이어의 태그별 객체 목록 | 객체 등록·조회와 해제 대상 보관 |
| 객체의 부모 포인터 | 상위 객체 참조, 루트 여부 판별 |
| 객체의 자식 목록 | 하위 순회와 일괄 처리 대상 연결 |

`Set_Parent()`는 레이어를 옮기거나 객체의 참조 수를 늘리지 않는다. 부모가 자식을 독점 소유하는 스마트 포인터 트리가 아니라, 레이어에 등록된 객체 사이의 관계를 원시 포인터로 표현한 구조다.

실제 UI 구성에서도 패널과 이미지를 각각 레이어에 넣은 뒤 이미지의 부모를 패널로 설정한다. 부모 연결만 하고 레이어 등록을 생략하면 계층 순회에서는 도달하더라도 레이어 기반 정리 대상에서는 빠질 수 있으므로 등록 책임을 별도로 지켜야 한다.

## 부모 변경과 연결 해제

`Set_Parent(newParent)`는 기존 부모가 있으면 그 부모의 자식 목록에서 자신을 제거한다. 이후 새 부모 포인터를 저장하고 새 부모의 자식 목록에 자신을 추가한다. nullptr를 전달하면 이전 부모 목록에서 자신을 빼고 부모 포인터를 비운다.

양쪽 연결을 함께 바꾸기 때문에 정상적인 재연결에서는 이전 부모의 자식 목록에 잔여 포인터가 남지 않도록 했다. 같은 부모를 다시 지정하는 경우도 제거 후 재추가하므로 형제 목록의 순서가 달라질 수 있다.

복사 생성자는 원본의 부모 관계를 복사하지 않고 부모 포인터를 nullptr로 시작한다. 복제된 객체가 원본 계층에 자동으로 연결되는 것을 피하고, 생성하는 쪽에서 관계를 다시 설정하도록 한 것이다.

현재 함수는 자기 자신이나 자신의 자손을 부모로 지정하는 것을 거부하지 않는다. API가 트리의 유효성까지 보장하는 것은 아니며 순환 연결 검증은 추가로 필요하다.

## 부모부터 업데이트하기

`CScene::Update_Scene()`은 모든 레이어와 태그별 목록을 순회해 부모가 없는 객체를 모은다. 각 루트에서 `TreeLevelTraversal()`로 계층 목록을 만든 뒤 그 순서대로 Update를 호출하는 구조다.

순회 의도는 큐를 사용하는 너비 우선 탐색이다. 예를 들어 하나의 트리가 다음과 같으면 실행 목록은 `Panel → Image → Button → Label` 순서가 된다.

```text
Panel
├─ Image
└─ Button
   └─ Label
```

루트를 모두 합친 하나의 전역 깊이 순서가 아니라, 루트 하나의 하위 트리를 처리한 다음 다음 루트로 넘어간다. 따라서 서로 다른 트리 사이의 의존성까지 정렬하는 일반적인 위상 정렬 시스템은 아니다.

Update 중 `Get_Dead()`가 true인 객체는 건너뛰고, 반환값이 `OBJ_DEAD`이면 해당 객체에 제거 표시를 한다. LateUpdate에서도 루트와 계층 목록을 새로 구성해 살아 있는 객체만 호출한다.

계층 목록은 해당 루트의 객체 Update를 시작하기 전에 만든다. 자식 리스트를 순회하면서 곧바로 Update하는 방식과 달리 현재 목록을 확보한 뒤 실행하지만, 모든 루트의 관계 변경을 안전하게 일괄 적용하는 스냅샷 시스템은 아니다. Update 중 부모를 바꾸면 이미 확보한 목록과 이후 루트·LateUpdate에서 얻는 관계가 달라질 수 있다.

## 업데이트 계층과 Transform 상속은 다르다

`Set_Parent()` 자체는 위치·회전·크기를 계산하지 않는다. 공통 `CTransform`도 부모 행렬을 자동으로 곱하지 않는다. 계층을 연결하면 부모의 Update를 먼저 처리할 수 있지만, 실제로 어떤 값을 따라갈지는 자식 클래스가 정한다.

예를 들어 [획득 팝업 이미지](/projects/dave-the-diver/item-interaction-feedback)는 부모 위치에 고정 오프셋을 더한다. [스마트폰 아이콘](/projects/dave-the-diver/phone-app-navigation)은 부모의 기준 벡터를 정규화한 행렬을 사용해 크기 영향을 조정한다. [물고기 콜라이더](/projects/dave-the-diver/fish-behavior-capture)는 부모 위치와 선택적인 회전을 읽는다.

이처럼 계층은 서로 다른 추종 로직이 같은 부모 관계를 사용할 수 있는 기반이다. 자동 월드 행렬 전파·Dirty Flag·KeepWorld 재부모화까지 제공하는 Transform Scene Graph는 아니다. 부모 우선 호출만으로 모든 월드 행렬의 최신 상태를 보장하지도 않으므로, 각 클래스가 Transform 값을 변경하고 계산하는 시점도 맞춰야 한다.

## 제거 표시와 실제 수명 종료

`Set_Dead()`는 자기 자신의 플래그만 바꾼다. `Set_DeadCascade()`는 자기 자신을 루트로 하위 순회를 수행해 자손에게도 같은 표시를 한다. 팝업과 이미지처럼 함께 사라져야 할 객체 묶음에서 사용한다.

표시하는 순간 객체를 삭제하지는 않는다. 현재 통합 코드에서는 팀원이 추가한 `CScene::EndOfFrame()`이 레이어 목록을 순회하며 Dead 객체를 `Safe_Release()`하고 목록에서 제거한다. 본인의 계층·제거 표시 구현과 팀원의 삭제 시점 변경을 하나의 개인 성과로 합치지 않는다.

`CGameObject::Free()`는 자신을 부모의 자식 목록에서 제거하고, 남아 있는 자식의 부모 포인터를 nullptr로 바꾼다. 자식 객체를 그 자리에서 직접 해제하지는 않는다. 따라서 부모에게만 `Set_Dead()`를 호출하면 자식은 함께 죽는 것이 아니라 부모가 해제된 뒤 분리되어 남을 수 있다. 함께 제거하려면 Cascade 표시를 사용해야 한다.

단일 객체가 `OBJ_DEAD`를 반환하는 경로도 자동 Cascade가 아니다. 또한 부모만 Dead 상태여도 순회 목록에는 살아 있는 자식이 포함될 수 있어, Dead 부모를 기준으로 전체 하위 트리 업데이트를 중단하는 정책과 구분해야 한다.

## RAW와 TREE로 같은 객체를 다르게 보기

`CManagement::Update_ImGui()`에 두 가지 보기를 마련했다.

`RAW`는 레이어 → 객체 태그 → 등록된 객체 순서로 보여 준다. 태그별 목록의 크기를 라벨에 표시하므로 같은 이름으로 몇 개가 등록되어 있는지 확인할 수 있다. 객체의 실제 보관 위치를 확인하는 용도다.

`TREE`는 모든 등록 객체의 포인터에 `태그_인덱스` 라벨을 만들고 루트를 찾는다. 이후 재귀적으로 `Childs`를 펼쳐 부모·자식 관계를 보여 준다. 트리 노드는 객체 포인터를 ImGui ID로 사용하므로 표시 이름이 같더라도 해당 노드를 구분할 수 있다. 라벨의 인덱스는 목록 순서이며 영속적인 객체 식별자는 아니다.

게임 업데이트는 큐 기반 레벨 순회를 의도한 반면 GUI는 재귀적으로 계층을 펼친다. 따라서 화면의 트리 나열 순서 자체를 그대로 프레임 실행 순서로 해석하면 안 된다.

## 객체에서 컴포넌트 GUI로 연결

각 객체의 `Update_ImGui()`는 컴포넌트를 STATIC·DYNAMIC 그룹으로 나누어 보여 주고, 컴포넌트 이름을 펼치면 해당 컴포넌트의 `Update_ImGui()`를 호출한다. 기본 객체 화면에서는 ViewZ도 조절한다.

`CTransform`은 위치·회전·크기를 `DragFloat3`로 노출한다. 상위 GUI가 모든 컴포넌트의 속성을 직접 알 필요 없이, 각 컴포넌트가 자신의 편집 항목을 구현하는 방식이다. 타입 메타데이터로 자동 생성하는 Reflection Inspector를 구현한 것은 아니다.

이 GUI는 런타임 상태 확인·수치 편집에 사용한다. 부모를 드래그해 재연결하거나, 편집 내용을 파일에 저장하고 Undo하는 씬 에디터까지 제공하지는 않는다. RAW 보기에서는 객체별 ID 범위를 따로 두지 않고 동일한 위젯을 연속 호출하므로, 같은 그룹의 여러 객체를 펼칠 때 ImGui ID 충돌도 점검 대상이다.

## 한계와 개선 방향 {/* #코드-검토에서-확인한-보강점 */}

가장 우선적으로 구분할 문제는 `TreeLevelTraversal()`의 큐 원소 수명이다. 현재 코드는 `auto& node = q.front()`로 큐 내부 원소를 참조하고, `q.pop()`으로 그 원소를 제거한 뒤 콜백과 자식 접근에 node를 사용한다. 포인터가 가리키는 GameObject가 살아 있더라도, 큐에서 제거된 포인터 원소에 대한 참조는 더 이상 유효하지 않다.

후속 수정에서는 front의 포인터 값을 복사해 보관한 뒤 pop해야 한다. 현재는 null인 front에서 pop하지 않는 경로도 있어 무한 반복 가능성이 있다. 이는 이번 문서 작성에서 발견한 코드 문제이며, 게임 코드를 고치거나 실행 검증을 완료한 것으로 표시하지 않는다.

그 외의 개선 대상은 다음과 같다.

- 자기 부모·순환 연결을 막는 검증과 순회 중 관계 변경 정책이 없다. 순환 구조는 루트를 찾지 못해 누락되거나 순회가 끝나지 않는 원인이 될 수 있다.
- Update와 LateUpdate마다 전체 객체에서 루트를 찾고 계층 벡터를 다시 만든다. 구조 변경 시에만 캐시를 재구성하는 최적화는 적용되어 있지 않다.
- `Get_Children()`이 수정 가능한 목록 포인터를 반환한다. 호출자가 직접 편집하면 양방향 연결 규칙을 우회할 수 있다.
- 레이어 중복 등록과 원시 포인터 수명에 대한 방어가 부족하다. 계층 연결이 핸들 유효성이나 소유권을 대신 보장하지 않는다.

구현의 성과는 UI·게임플레이 객체의 관계를 공통 구조로 표현하고, 부모 우선 호출과 일괄 제거 표시·디버그 확인에 재사용한 점이다. 순회 비용이나 성능 개선 수치를 측정하지 않았으며, 결함을 해결한 완성형 객체 관리자라고 설명하지 않는다.

## 시연·검증 자료

1. 부모와 자식의 Update 로그를 비교해 한 트리 안의 호출 순서 확인.
2. 부모 위치 변경 후 이미지·아이콘·콜라이더가 각자 구현한 방식으로 따라가는 장면.
3. Set_Dead와 Set_DeadCascade를 비교해 자식이 남거나 함께 제거 표시되는 차이 확인.
4. RAW의 등록 목록과 TREE의 계층을 나란히 확인하고 Transform 수치 편집.
5. 재부모화·연결 해제·순환 입력·순회 헬퍼의 참조 수명을 별도 경계 테스트로 확인.

이번 문서는 현재 소스와 Git 이력 분석으로 작성했다. 위 항목은 제출용으로 확보할 시연·검증 자료이며, 이번 작성 중 게임 실행이나 메모리 오류 검사를 수행했다는 뜻은 아니다.
