# 씬 전환 예약과 로딩 화면 구성

## 배경과 목표 {/* #해결하려던-문제 */}

로고·선박·잠수·초밥집 사이를 이동할 때 기존 씬의 실행을 마치고 다음 씬을 준비해야 했다. 씬 내부의 Update나 콜백에서 현재 씬을 즉시 해제하면 아직 진행 중인 프레임의 객체 접근과 충돌할 수 있다. 리소스를 준비하는 동안 보여 줄 화면과, 준비가 끝났을 때 넘어가는 연출도 필요했다.

씬 교체 요청과 실제 교체를 분리하고, 중간에 `CTransition` 씬을 거치도록 구성했다. Transition은 로딩 화면을 갱신하면서 별도 스레드에서 목적지의 리소스 준비 함수를 실행하고, 페이드와 준비 완료 조건을 함께 확인한 뒤 다음 씬을 요청한다.

본인 구현 범위는 교체 예약과 적용 시점, Transition의 실행 흐름, 로딩 화면 구성과 페이드 연결이다. `CTransition.cpp`에는 팀원들의 맵·플레이어·보스 리소스 등록도 들어 있으므로 파일 전체를 본인 작업으로 간주하지 않는다. 이 문서에서는 완성된 범용 비동기 로더가 아니라 실제 구현된 흐름과 남은 한계를 설명한다.

## 즉시 교체에서 프레임 끝 적용으로

`4224720` 커밋 이전의 `CManagement::Set_Scene()`은 함수 안에서 기존 씬을 해제하고 새 씬을 적용했다. 변경 후에는 null 여부를 확인하고 `m_pTmpChangeScene`에 다음 씬 포인터를 저장하는 것으로 역할을 줄였다.

실제 적용은 `LastFrame_Set_Scene()`으로 옮겼다. 메인 루프의 순서는 다음과 같다.

```text
Update → LateUpdate → Render → EndOfFrame_MainApp
                                ├─ 충돌 그룹 비우기
                                ├─ 현재 씬 EndOfFrame
                                └─ 예약이 있으면 LastFrame_Set_Scene
```

Update·LateUpdate 중 전환 요청이 생겨도 현재 씬은 해당 프레임의 렌더까지 마친다. 그 뒤 `Is_ScheneChanged()`로 예약 포인터가 있는지 확인하고 씬을 교체한다. 이는 현재 프레임의 실행 중간에 씬을 제거하지 않기 위한 적용 시점 분리다.

다만 모든 교체가 반드시 프레임 끝을 거치는 것은 아니다. 프로그램 초기화에서는 첫 Transition을 예약한 뒤 `LastFrame_Set_Scene()`을 직접 호출한다. 아직 실행 중인 이전 게임 프레임이 없는 초기 진입 경로와 런타임 전환 경로를 구분해야 한다.

## 전환 훅의 실제 호출 대상

`LastFrame_Set_Scene()`은 예약된 새 씬의 `Before_SceneChange()`를 호출하고, 기존 씬을 해제한 뒤 새 씬을 현재 씬으로 지정한다. 이후 그 새 씬에 `After_SceneChange()`를 호출하고 예약 포인터를 비운다.

이름만 보면 이전 씬의 Before와 다음 씬의 After를 연결한 것처럼 보이지만, 현재 코드는 두 훅 모두 새 씬을 대상으로 한다. 반환 자료형에 레이어 포인터 맵이 있다는 이유로 이전 씬의 객체를 다음 씬에 자동 이관하는 완성된 기능이라고 설명하지 않는다.

`CTransition`은 `m_reserveTransfer`를 반환하고 다시 저장하는 구현을 갖고 있다. 여기서는 훅 호출 지점이 존재한다는 사실까지만 다루며, 영속 객체 이관 기능과는 구분한다.

## 중간 씬을 거치는 화면 흐름

일반 런타임 전환은 `FadedTransition(src, dst)`로 시작한다. 현재 씬의 첫 번째 사용 가능한 레이어에 Fade Out 객체를 넣고, 그 완료 콜백에서 Transition을 생성해 `Set_Scene()`으로 예약한다.

```text
현재 씬 Fade Out
  → Transition 생성·교체 예약
  → 프레임 끝 Transition 적용
  → Transition Fade In + 목적지 리소스 준비
  → 두 완료 조건 충족
  → Transition Fade Out
  → 목적지 씬 생성·Fade In 추가·교체 예약
  → 프레임 끝 목적지 씬 적용
```

목적지 씬 객체의 `Create()`는 로딩 스레드가 아니라 Transition의 페이드 완료 콜백에서 호출한다. 따라서 리소스 준비 일부를 분리했어도, 목적지 씬의 객체 생성·초기화 비용까지 모두 백그라운드에서 처리하는 구조는 아니다.

## 스레드는 첫 Update에서 시작

`a11f4c0` 커밋에서는 스레드 생성 위치를 `Ready_Scene()`에서 첫 `Update_Scene()`으로 옮겼다. `m_bLoadingStart`가 false일 때 Critical Section을 초기화하고 `_beginthreadex()`로 `Thread_Main(this)`를 실행한다. 이후 Update에서는 다시 시작하지 않는다.

이 배치에서는 Transition 객체를 만들고 환경 레이어를 준비하는 시점과, 현재 씬으로 적용된 뒤 로딩을 시작하는 시점이 구분된다. 단, 첫 Update에서 시작하므로 로딩 화면이 반드시 한 번 렌더된 다음에 스레드가 시작되는 것은 아니다.

스레드는 출발·도착 씬 ID 조합에 따라 `Transition_INIT_TO_LOGO()`, `Transition_SHIP_TO_DIVE()` 등의 준비 함수를 호출한다. 함수 안에서는 Asset과 Prototype 등록·로딩 등을 수행한다. 등록된 리소스를 관리하는 방법은 [AssetManager 문서](/projects/dave-the-diver/asset-manager)에 별도로 정리했다.

호출 가능한 모든 씬 조합을 자동으로 처리하지는 않는다. Thread_Main의 조건 분기에 명시한 조합을 지원하는 구조다. 실행 작업을 여러 워커에 배분하는 Job System이나 로딩 작업 그래프를 구현한 것은 아니다.

## 로딩 완료와 화면 연출 완료를 함께 확인

Transition의 Update는 `m_bFadeEnd && m_bFinish`를 확인한다.

| 조건 | 의미 |
| --- | --- |
| `m_bFadeEnd` | Transition 화면을 드러내는 Fade In 완료 |
| `m_bFinish` | 목적지 준비 함수에서 설정한 완료 표시 |

초기 시작인 `SCENE_INIT`에서는 진입 Fade In을 생략하고 `m_bFadeEnd`를 true로 둔다. 그 외에는 Fade In의 완료 콜백이 값을 변경한다.

리소스 준비가 빨라도 진입 페이드가 끝나기 전에는 퇴장 연출을 시작하지 않는다. 반대로 페이드가 먼저 끝났다면 준비 완료를 기다린다. 두 조건을 만족하면 `m_bFadeEnd`를 다시 false로 내려 매 Update마다 퇴장 페이드를 추가하지 않도록 한다.

여기서 `m_bFinish`는 작업 스레드 핸들이 종료 상태라는 뜻도, 모든 리소스의 성공을 집계한 결과라는 뜻도 아니다. 준비 함수가 완료 표시를 설정한 시점을 의미한다. 실제 스레드 종료 대기는 Transition 해제 경로에서 별도로 수행한다.

## 재방문 시 등록을 건너뛰는 정책

목적지별 `s_LogoAssetLoaded`, `s_ShipAssetLoaded` 등의 정적 플래그로 최초 준비 여부를 구분한다. 이미 준비한 목적지라면 등록 함수를 다시 호출하지 않고 완료 표시를 설정하는 경로가 있다.

씬 재방문마다 리소스를 모두 새로 등록하지 않으려는 정책이지만, 현재 플래그는 준비 함수를 호출하기 전에 true가 된다. 함수가 실패한 경우까지 성공 상태를 보장하는 플래그는 아니다. 실패·재시도·리소스 삭제 후 재진입을 포함하려면 실제 준비 결과와 상태를 연결해야 한다.

씬을 교체한다고 Asset이 자동으로 전부 해제되는 것도 아니다. 씬 객체의 수명과 전역 AssetManager에 남아 있는 리소스의 수명은 별개다.

## 로딩 화면과 페이드 구성

`CTransitionBG`, `CTransitionImg`, `CTransitionTxt`, `CTransitionFace`, `CTransitionFade`를 환경 레이어에 조합했다. 목적지가 선박·잠수·초밥집인지에 따라 이미지와 제목을 선택하고, 로딩 중에는 얼굴 아이콘을 반복적으로 움직인다.

얼굴 아이콘 세 개는 시작 지연을 0.1·0.2·0.3초로 다르게 둔다. 각 아이콘은 Tween으로 위로 이동하고 돌아온 뒤 잠시 유지하는 움직임을 반복한다. 이는 로딩 중 화면이 살아 있다는 표시이며, 실제 완료율이나 남은 작업 수를 나타내는 진행률은 아니다.

페이드는 700ms 동안 검은 텍스처의 알파를 선형으로 바꾼다. Fade In은 1에서 0, Fade Out은 0에서 1로 진행한다. Update에서 알파를 계산하고 LateUpdate에서 완료 콜백을 호출한 뒤 제거를 요청한다.

`947cb45` 커밋에서는 페이드 렌더에 직교 투영을 적용했다. 기존 View·Projection을 저장하고 화면 기준 행렬로 페이드를 그린 다음 복구한다. 현재 씬 카메라에 따라 페이드 평면이 다르게 보이지 않도록 한 변경이다. 텍스처 단계와 렌더 상태 일부는 지정한 기본값으로 되돌리므로 모든 그래픽 상태를 원래 값 그대로 복원하는 범용 상태 가드는 아니다.

최종 소스에 있는 무작위 팁 문구·선택 로직은 팀원 커밋 `2607b91`에서 추가되었다. 본인 작업인 텍스트 출력 객체·배치와 구분한다. 팀원이 조절한 배경 이동 속도도 본인 성과로 합치지 않는다.

## 스레드 수명과 현재 한계

`CTransition::Free()`에는 스레드 종료를 기다리는 `WaitForSingleObject(..., INFINITE)`, 핸들 닫기, Critical Section 제거가 있다. 하지만 현재 순서는 `CScene::Free()`로 씬 내용을 정리한 뒤 스레드를 기다리는 방식이다. 일반 완료 경로뿐 아니라 로딩 중 종료에서도 안전하려면 작업이 접근하는 객체와 리소스의 수명을 확인하고 정리 순서를 보강해야 한다.

완료 통신과 실패 처리에도 다음 한계가 있다.

- `m_bFinish`는 일반 bool이고, 작업 스레드의 쓰기와 메인 스레드의 읽기에 공통 동기화가 없다. 작업 스레드 내부의 Critical Section만으로 메인 스레드 접근까지 보호되지는 않는다. 안전한 완료 신호 전달 방식이 필요하다.
- 준비 함수의 HRESULT를 Thread_Main에서 검사하지 않는다. 실패 시 완료 표시가 설정되지 않거나, 하위 로드 실패를 놓친 채 완료로 진행할 여지가 있다. 실패 결과·오류 화면·재시도 정책을 별도로 구성해야 한다.
- 스레드 생성 성공 여부를 검사하지 않는다. 첫 Update 전 생성 실패·중도 해제에서는 핸들과 Critical Section 초기화 여부를 구분한 정리도 필요하다.
- 예약은 큐가 아니라 포인터 하나다. 한 프레임에 여러 `Set_Scene()` 요청이 오면 기존 예약을 덮어쓰므로 거부·취소·해제 정책이 필요하다.
- 페이드 추가는 대상 씬에 레이어가 있다는 전제를 갖는다. 레이어가 없거나 목적지 씬 생성에 실패했을 때 전환을 복구하는 일반화된 처리는 부족하다.

따라서 성과는 **교체 적용 시점 분리와 로딩 화면·준비 작업·페이드 완료의 연결**이다. 데이터 경쟁과 실패 처리를 모두 해결한 비동기 로더나 무중단 스트리밍 시스템으로 설명하지 않는다.

## 시연·검증 자료

1. 로고 → 선박 → 잠수 → 선박 전환의 전체 화면 흐름.
2. Set_Scene 호출과 LastFrame_Set_Scene 호출을 디버거로 비교해 실제 교체 시점 확인.
3. 준비가 빠를 때와 느릴 때, 진입 페이드와 준비 완료를 모두 기다리는지 확인.
4. 최초 방문과 재방문에서 목적지 준비 함수 호출 여부 비교.
5. 잘못된 리소스 경로, 로딩 중 종료, 연속 전환 요청을 경계 테스트로 확인.

이번 문서는 현재 코드와 Git 변경 이력으로 작성했다. 위 항목은 제출용으로 확보할 검증 자료이며, 이번 작성 중 게임 실행·스레드 진단·로딩 시간 측정을 새로 완료했다는 의미는 아니다.
