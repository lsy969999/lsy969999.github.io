# 플레이어 동작·전투와 사운드 연동

## 행동의 시작과 결과를 소리로 구분하기

사슬을 발사한 순간과 지형에 부착한 순간, 적을 붙잡은 순간과 처형한 순간을 각각 다른 소리로 구분했다. 이동·공격 코드가 실제로 수행되는 지점에 사운드를 연결하고, 배경음과 반복 효과음은 씬의 시작·종료와 함께 관리했다.

중심은 오디오 엔진 자체의 구현이 아니라 게임 행동과 FMOD 재생 경로의 연결이다. 저장소에는 FMOD 2.02.19의 헤더·라이브러리가 포함되어 있다. `d7bb149`에서 `CSoundMgr`를 프로젝트에 추가했고, 이후 플레이어 동작과 전투 효과음 연결, 채널 지정 반복 재생 오버로드를 보강했다. 이 이력만으로 일반적인 FMOD 래퍼 패턴까지 독자적인 신규 설계라고 주장하지 않는다.

## 초기 로드와 파일 이름 기반 재생

`CMainGame::Initialize()`에서 사운드 매니저를 초기화한다. 매니저는 FMOD 시스템을 생성하고 `FMOD_System_Init(..., 32, ...)`를 호출한 뒤 `../Sound/*.*`를 순회한다. `FMOD_System_CreateSound()`가 성공한 항목을 파일 이름과 사운드 객체로 보관한다.

게임플레이 코드는 전체 경로 대신 `SFX_SNB_Shoot.wav` 같은 파일 이름을 전달한다. 재생할 때 파일을 매번 다시 읽는 방식이 아니라, 이미 생성한 사운드 객체를 찾아 사용한다. 하위 폴더를 재귀 탐색하거나 파일 변경을 감지해 핫리로드하는 기능은 없다.

현재 저장 컨테이너는 `map<TCHAR*, FMOD_SOUND*>`이며, 조회는 `find_if`와 `lstrcmp`로 문자열 내용을 비교한다. 따라서 파일 이름 해시나 문자열 키의 로그 시간 검색이 아니라 선형 탐색이다. 이름을 찾지 못하면 로그 없이 반환하므로, 잘못된 키를 전달했을 때 원인을 알기 어렵다는 한계가 있다.

## 행동별 논리 채널

`CHANNELID`는 `m_pChannelArr`에서 재생 채널 포인터를 보관할 슬롯을 나타낸다. BGM, 사슬 발사, 부착, 발걸음, 점프, 천장 이동, 몬스터 사격·폭발 등을 나눠 필요한 종류의 소리를 지정해 정지하거나 볼륨을 바꿀 수 있도록 했다.

이 enum은 FMOD의 버스나 ChannelGroup을 정의한 것이 아니다. 객체 인스턴스마다 발급하는 재생 ID도 아니다. 같은 종류의 적들이 같은 enum 값을 사용하면 하나의 슬롯을 공유한다.

| 호출 방식 | 코드에서 요청하는 동작 |
| --- | --- |
| `PlaySound(key, channel, volume)` | 지정 슬롯의 상태를 검사한 뒤 효과음 재생 시도 |
| `StopSound(channel)` | 해당 슬롯이 가리키는 채널 정지 |
| `PlayBGM(key, volume)` | 기본 BGM 슬롯에서 루프 모드 재생 |
| `PlayBGM(key, channel, volume)` | 지정한 슬롯에서 루프 모드 재생 |
| `SetChannelVolume(channel, volume)` | 해당 채널의 볼륨 변경 |
| `StopAll()` | 배열의 모든 슬롯에 정지 호출 |

볼륨 설정은 즉시 적용한다. 페이드·크로스페이드·거리 감쇠·3D 위치 연동을 구현한 구조는 아니다. 또한 논리 슬롯의 수와 FMOD 초기화에서 지정한 동시 재생 설정 32는 다른 개념이다.

## 플레이어의 재생 시점

| 행동 | 연결한 시점 | 대표 채널 |
| --- | --- | --- |
| 사슬 발사 | 사슬 객체를 생성·등록한 뒤 | `SOUND_HOOK_SHOOT` |
| 지형 부착 | 사슬 길이·진자 기준점을 설정하는 경로 | `SOUND_GRAB` |
| 적 제압 | `Grabbed()` 호출과 끌어당김 상태 연결 | `SOUND_SFX_EXCGRAB` |
| 처형 | 대상 `Excuted()` 호출과 플레이어 반동 대시 연결 | `SOUND_SFX_EXC` |
| 일반 점프 | 점프 가능 분기에서 `JumpRoutine()` 호출 후 | `SOUND_SFX_JUMP` |
| 피격 | 재피격 제한을 통과해 피격 상태로 들어간 경우 | `SOUND_SFX_DAMAGED` |
| 벽 이동·부착 | 해당 벽 동작 분기 | 벽 부착·등반 전용 채널 |

여러 경로에서 `StopSound()` 후 `PlaySound()`를 호출한다. 같은 동작의 이전 소리를 끊고 새 행동에 맞춰 재생을 요청하려는 사용 방식이다. 예를 들어 사슬 발사 볼륨은 0.5, 부착·제압·처형은 1.0으로 지정한다. 실제 음량의 체감 차이는 원본 파일에도 영향을 받으므로 숫자만으로 믹싱 품질을 평가하지 않는다.

발사와 부착을 별도 채널로 나눠 한쪽을 정지시키는 호출이 다른 동작의 채널까지 직접 건드리지 않게 했다. 다만 재생 성공·중복 방지를 보장하는 매니저 조건에는 아래에서 설명하는 보강점이 있다.

## 반복 동작: 발걸음과 천장 이동

발걸음은 애니메이션 프레임 이벤트가 아니다. 일반 이동 분기에서 A·D를 누르고 있고 `!m_bJump`이면 300ms 간격의 `CTimeMgr::Delay()` 안에서 기존 발걸음을 정지하고 다시 재생한다. 키 입력이 끝나면 이 반복 호출이 멈추지만 이미 시작한 짧은 소리를 반드시 즉시 끊는 방식은 아니다. 입력 시작 시 Interval을 등록하려던 코드는 주석 처리되어 있다.

천장 이동은 다른 방식이다. A·D 이동 분기에서 `PlaySound()`를 매 Update 호출하며, 천장 영역의 좌우 끝을 벗어나는 경로에서는 명시적으로 `StopSound()`를 호출한다. 일정 간격 재생으로 바꾸려던 Delay 코드는 주석 상태다.

천장 이동음은 `PlayBGM()`으로 설정한 루프 채널이 아니다. 반복 재생 요청과 재생 상태 검사에 의존한다. 키를 놓았을 때의 분기는 팔의 정지 애니메이션을 설정하지만 같은 위치에서 사운드를 정지시키지는 않는다. 따라서 시작·유지·종료가 통합된 이동음 컨트롤러로 소개하지 않는다.

행동 코드와 소리의 관계는 [플레이어 액션 문서](/projects/sanabi/player-actions-animation) 및 [사슬·처형 문서](/projects/sanabi/grapple-execution-bomb)의 흐름에 대응한다.

## 몬스터·보스 공격과 연출 연결

몬스터의 등장, 총알 생성, 워리어의 공격 준비, 감시 드론의 촬영 시작, 폭발 객체 생성 시점에 효과음을 배치했다. 예를 들어 트루퍼는 각 탄환을 생성할 때 사격음을 요청하고, 워리어는 공격 준비 상태에 들어갈 때 베기 효과음을 요청한다. 모든 소리가 실제 명중 순간이나 애니메이션의 특정 프레임에 연결된 것은 아니다.

보스 격파 연출은 `CObjBossFirebirdEndSprite::Initialize()`에서 300·1400·2700ms 뒤에 서로 다른 파괴음을 예약한다. `SOUND_SFX_BOSS_DESTROY1/2/3`으로 슬롯을 나눠 단계별 소리를 구분했다. 이는 프레임 번호가 아니라 연출 시작 이후의 타이머 기준이다.

동종 몬스터는 사격·등장·폭발 채널을 공유한다. 여러 적이 연달아 `StopSound → PlaySound`를 호출하면 앞선 적의 같은 종류 소리가 끊길 수 있다. 개별 발음의 동시 재생과 우선순위·최대 개수 제어를 제공하는 구조는 아니다. 이 특성은 [일반 몬스터 문서](/projects/sanabi/enemy-ai-animation)의 동시 전투 시연과 함께 점검할 부분이다.

## 씬 BGM과 보스 반복음의 분리

| 씬 | 기본 BGM | 종료 처리 |
| --- | --- | --- |
| 튜토리얼 | `BGM_PRLG1_ForestDaughter01.wav` | `SOUND_BGM` 정지 |
| 몬스터 전투 | `BGM_Chap2_Main_Intro.wav` | `SOUND_BGM` 정지 |
| 화조 보스 | `BGM_Chap4_Main_Intro.wav` | BGM과 보스 반복음 모두 정지 |
| 엔딩 | `BGM_Event_MariTheme.wav` | `SOUND_BGM` 정지 |

보스 씬은 기본 BGM 외에 `SFX_Chap4_Firebird_Loop.wav`를 `SOUND_BGM_FIREBIRD_LOOP`에서 반복 재생한다. 이를 위해 채널을 지정할 수 있는 `PlayBGM()` 오버로드를 추가했다. 음악과 기계 반복음을 서로 다른 슬롯에 보관하고 씬 해제에서 각각 정지한다.

파일 이름에 Intro가 있어도 이 함수는 `FMOD_LOOP_NORMAL`을 설정한다. 인트로 종료 후 별도의 루프 곡으로 넘기는 음악 시퀀서나 자동 구간 전환은 구현되어 있지 않다. 또한 BGM 재생 함수 자체는 기존 슬롯의 소리를 먼저 정지하지 않으므로, 정상적인 씬 종료 호출과 반복 재생 요청 여부를 함께 관리해야 한다.

## 재생 상태 검사에서 확인한 한계

현재 `PlaySound()`는 다음 조건을 사용한다.

```cpp
FMOD_BOOL bPlay = FALSE;
if (FMOD_Channel_IsPlaying(m_pChannelArr[eID], &bPlay))
{
    FMOD_System_PlaySound(m_pSystem, iter->second, 0, FALSE,
        &m_pChannelArr[eID]);
}
```

저장소의 `fmod.h`에서 이 함수의 반환형은 `FMOD_RESULT`이고, 실제 재생 여부는 출력 인자 `bPlay`로 전달된다. `fmod_common.h`의 성공 값 `FMOD_OK`는 0이다. 즉 현재 조건은 재생 중인지 확인하는 것이 아니라 **호출이 오류 코드를 반환했는지**를 분기한다. `bPlay`는 읽지 않는다.

따라서 “재생 중이면 무시하고, 끝나면 다시 재생한다”는 정책이 명시적으로 구현됐다고 볼 수 없다. `StopSound()` 후 호출하는 경로도 이 오류 코드 의존을 올바른 상태 검사로 바꿔 주지는 않는다. 반환 코드와 재생 여부를 분리해 검사하고, 잘못된 채널·재생 완료·강제 정지·채널 회수에 대한 정책을 정하는 것이 우선 보강점이다.

그 밖에 확인한 경계는 다음과 같다.

- 생성자에서 채널 포인터 배열을 초기화하지 않는다. 초기 정지·재생 상태 조회가 유효한 포인터를 받는다고 가정할 수 없다.
- FMOD 시스템 Update는 로드·재생·볼륨 변경 함수에 들어 있고, 메인 루프에서 독립적으로 호출하는 경로는 없다. 주기적 갱신 책임을 분리할 필요가 있다.
- 종료 함수는 사운드들을 해제한 뒤 `System_Release` 다음에 `System_Close`를 호출한다. 시스템 수명과 종료 순서를 재검토해야 하며 안전한 종료를 검증한 코드로 소개하지 않는다.
- 채널 범위와 FMOD 호출 결과를 대체로 검사하지 않는다. 누락 파일·재생 실패·동시 재생 한계의 진단 정보가 부족하다.
- 보스 파괴음의 예약 ID를 보관·취소하지 않는다. 씬이 일찍 끝나도 예약된 소리가 나올 수 있어 씬 수명과 연동할 필요가 있다.

## 구현 범위와 시연 계획

이 작업의 성과는 이동·사슬·제압·전투·씬 전환에 구체적인 재생 시점을 연결하고, 행동별 채널 및 보스 반복음 분리를 마련한 것이다. 오디오 믹싱 엔진이나 안전한 범용 재생 관리자 전체를 완성했다고 설명하지 않는다. 특히 재생 상태 검사 문제는 후속 수정 대상이며, 이번 문서 작성에서 게임 코드를 고치지는 않았다.

| 본인 커밋 | 확인한 작업 |
| --- | --- |
| `d7bb149` | 프로젝트에 FMOD 사운드 매니저 추가 |
| `74f8ddc` | 사슬·이동 효과음과 튜토리얼 BGM 연동 |
| `91ed2a3` | 전투용 채널 확장과 채널 지정 반복 재생 API 추가 |

주요 근거는 `Start/CSoundMgr.cpp`·`.h`, `Define.h`, `CMainGame.cpp`, `CObjPlayer2.cpp`, 각 몬스터의 행동 코드, `CObjBossFirebirdEndSprite.cpp`, `CSceneTutorial.cpp`, `CSceneMonster.cpp`, `CSceneBoss.cpp`, `CSceneEnding.cpp`다. FMOD 함수 시그니처와 결과 enum은 저장소에 포함된 헤더로 확인했다.

시연은 사슬 발사와 부착, 이동과 점프, 제압과 처형, 보스 음악과 반복음의 동시 재생·씬 종료 순서가 적합하다. 같은 동작 연속 수행, 여러 몬스터의 동시 사격, 이동 중 입력 해제, 재생 완료 후 재시작, 씬 조기 종료는 별도 검증 대상으로 둔다. 이번 문서는 소스와 Git 분석 결과이며 청취 테스트·믹싱 평가·종료 안정성 검증을 새로 수행한 결과는 아니다.
