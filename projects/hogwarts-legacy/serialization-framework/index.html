포맷 독립 직렬화와 안전한 파일 저장

배경과 목표​

레벨 배치, 애니메이션, 사운드, 시네마틱처럼 구조가 다른 데이터를 각 시스템이 직접 JSON으로 읽고 쓰면 타입 지원과 오류 처리가 중복된다. 실행용 Binary가 필요해졌을 때 데이터 구조마다 저장 코드를 다시 작성해야 하는 문제도 생긴다.

저장 실패 중 원본 파일이 잘리거나, 역직렬화 도중 일부 필드만 갱신되어 런타임 객체가 반쯤 변경되는 상황도 방지해야 했다.

포맷과 데이터 정의의 분리​

데이터 타입은 ISerializable만 구현한다.

C++
class ISerializable
{
public:
    virtual void Serialize(ISerializer& serializer) const = 0;
    virtual void Deserialize(IDeserializer& deserializer) = 0;
};

실제 포맷은 공통 Interface 뒤로 분리했다.

Plain Text
게임 데이터와 ISerializable
            ↓
ISerializer / IDeserializer
      ┌─────┴─────┐
      ↓           ↓
 JSON 구현     Binary 구현

게임 데이터는 자신이 JSON으로 저장되는지 Binary로 저장되는지 알 필요가 없다. 같은 Serialize() 구현을 두 Writer가 사용한다.

지원 타입​

공통 Interface에 엔진에서 반복 사용하는 타입을 모았다.

  • 정수, 실수, Boolean, String
  • Enum의 Underlying Type 변환
  • DirectX 기반 _float2, _float3, _float4, _float4x4
  • StringID
  • 중첩된 ISerializable
  • pair, optional
  • 반복자 범위와 일반 Container
  • vector, C 배열, std::array
  • map, unordered_map

Container는 요소의 포인터 여부와 직렬화 가능 타입 여부를 Template에서 분기한다. Map Key가 String이나 StringID인 경우 포맷에서 사용할 문자열 Key로 변환한다.

반복되는 필드명과 값을 한 번에 전달하는 Helper도 제공해 데이터 클래스의 Boilerplate를 줄였다.

JSON과 Binary의 역할​

JSON은 사람이 직접 확인하거나 Editor가 수정하는 원본 데이터에 적합하다. Binary는 실행 시 파싱 비용을 줄이고 형식을 고정하는 용도로 사용한다.

Binary 파일 앞에는 고정 Header를 기록한다.

C++
struct HEADER
{
    uint32_t iMagic;
    uint16_t iVersion;
    uint16_t iFlags;
    uint64_t iPayloadSize;
};

읽을 때 Magic, Version, Flags, Payload Size와 실제 파일 크기를 검증한다. 역직렬화가 끝난 후 읽지 않은 Byte가 남으면 TRAILING_DATA 오류로 처리해 Writer와 Reader의 형식 불일치를 조기에 찾는다.

손상되거나 비정상적으로 큰 입력으로 메모리가 과도하게 할당되지 않도록 제한도 둔다.

  • Payload 최대 512 MiB
  • 문자열 최대 16 MiB
  • Container 최대 1,000,000개

원본 파일을 보호하는 저장 절차​

Serializer가 대상 파일에 바로 쓰지 않고 같은 위치의 임시 파일을 만든다.

Plain Text
대상 경로 검증
   ↓
Temporary Path 생성
   ↓
임시 파일에 전체 데이터 저장
   ↓
저장 성공 확인
   ↓
임시 파일을 최종 경로로 Commit

중간 단계가 실패하면 Temporary File을 제거하고 기존 파일은 유지한다. 디렉터리가 없으면 먼저 생성하고, Commit 단계의 실패도 별도 오류로 반환한다.

이는 Editor 저장 도중 예외나 디스크 오류가 발생했을 때 정상 파일이 빈 파일이나 부분 데이터로 교체되는 것을 막는다.

런타임 객체를 보호하는 Load 절차​

Deserialization도 출력 객체를 즉시 수정하지 않는다. 먼저 임시 객체에 전체 데이터를 읽고 검증이 끝난 뒤 최종 객체로 Move 또는 Copy한다.

Plain Text
Deserializer 생성
   ↓
Temporary Object에 Read
   ↓
형식과 잔여 데이터 검증
   ↓
성공할 때만 outValue 교체

필드 하나를 읽다가 실패하더라도 호출자가 사용 중인 기존 설정은 유지된다. 단, 이 방식을 사용하려면 대상 타입이 기본 생성 가능하고 Move 또는 Copy 대입 가능해야 한다.

상세 오류 결과​

기존 호출부를 위한 HRESULT API와 진단을 위한 Detailed API를 함께 제공한다.

C++
struct SERIALIZE_RESULT
{
    HRESULT hResult;
    SERIALIZE_ERROR eError;
    std::string sPath;
    std::string sMessage;
};

오류는 다음 단계로 구분한다.

  • 잘못된 경로
  • Serializer 또는 Deserializer 생성 실패
  • 대상 경로 준비 실패
  • 데이터 변환 실패
  • 임시 파일 기록 실패
  • 최종 파일 Commit 실패
  • 원본 파일 Header 검증 실패
  • 역직렬화 실패
  • 읽지 않은 Binary 데이터

Editor는 단순히 E_FAIL만 받지 않고 실패 단계와 파일 경로를 사용자에게 표시할 수 있다.

검증과 실제 적용​

ImGui의 Serializer Regression Test에서 지원 타입을 묶은 Test Case를 JSON과 Binary로 저장한 뒤 다시 읽어 원본과 비교한다. Container, Optional, 수학 타입과 중첩 객체처럼 Template 분기가 많은 영역을 한 번에 확인할 수 있다.

실제 프로젝트에서는 다음 데이터에 공통 API를 사용한다.

  • Cinematic Asset과 Editor 저장
  • Ambient Sound 배치
  • Animation 관련 데이터
  • NvCloth Collision Rig와 설정
  • NPC·Map Placement
  • Level별 게임 데이터

시스템 연결​

CGameInstance는 JSON/Binary와 일반/Detailed 호출을 façade로 제공한다. 데이터 시스템은 구체 Serializer를 직접 생성하지 않고 동일한 진입점을 사용한다.

StringID가 직렬화 타입으로 포함되어 Resource, Prototype, Effect처럼 Hash Tag를 사용하는 데이터도 Debug 문자열 기반으로 저장하고 다시 복원할 수 있다.

구현 결과​

게임 데이터가 저장 포맷에 직접 의존하지 않게 되었고, JSON과 Binary가 같은 타입 지원과 오류 정책을 공유하게 됐다. 임시 파일 Commit과 임시 객체 Load를 통해 실패가 기존 파일과 런타임 상태를 훼손하지 않도록 만들었으며, Detailed Result로 Editor에서 문제 지점을 추적할 수 있게 했다.
