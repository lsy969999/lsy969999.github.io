# Resource Manager와 경로 기반 캐시

## 배경과 목표 {/* #문제 */}

Shader, Texture, Model, Sound, JSON, Animation처럼 성격이 다른 리소스를 각 시스템이 직접 생성하면 동일 파일을 중복 로드하기 쉽다. 레벨 로딩이 Worker Thread에서 수행되기 시작하면서, 등록과 조회가 동시에 일어날 때 Container의 안전성도 보장해야 했다.

리소스의 소유권, 논리 태그 조회, 실제 파일 경로 캐시를 `CResourceManager` 한곳에서 관리하도록 구성했다.

## 논리 태그 Registry

주 저장소는 `GroupTag → ResourceTag → Resource 배열`의 2단계 구조다. Group에는 Permanent Shader, Level Resource 같은 수명 범위를 표현하고 Resource Tag에는 실제 사용 이름을 둔다.

```cpp title="ResourceManager.h"
using Resources =
    std::unordered_map<StringID, std::vector<SPtr<CResource>>>;

std::unordered_map<StringID, Resources> m_Resources;
```

태그는 64-bit `StringID`를 사용하고 실제 객체는 `shared_ptr<CResource>`로 보관한다. 같은 Tag에 배열을 둔 이유는 Texture Sequence처럼 하나의 논리 이름 아래 여러 리소스가 들어가는 경우를 지원하기 위해서다.

```cpp
auto shader = game.GetResourceFirst<CResVertexShader>(
    TAG_RES_GRP_PERMANENT_SHADER,
    "VS_TestModelAnim");
```

Typed API는 자체 Derived Type의 `StaticType`과 `Engine::Cast<T>`를 사용한다. 호출자는 기반 포인터를 직접 변환하지 않고, 존재하지 않거나 타입이 다르면 `nullptr`로 처리한다.

## 논리 태그와 실제 경로의 분리

서로 다른 Tag가 같은 파일을 참조할 수 있기 때문에 Tag Registry만으로는 중복 로드를 막을 수 없다. 이를 위해 정규화한 파일 경로를 Key로 사용하는 보조 Lookup을 만들었다.

```cpp
std::unordered_map<
    std::string,
    std::vector<WPtr<CResource>>
> m_PathLookup;
```

`std::filesystem::path::lexically_normal()`과 `generic_string()`으로 경로 표현을 통일하고, `GetOrCreateResourceByPath<T>`에서 살아 있는 동일 타입 리소스를 먼저 찾는다. 없을 때만 전달받은 Factory Lambda를 호출한다.

```text
요청 경로 정규화
        ↓
PathLookup에서 만료된 weak_ptr 제거
        ↓
동일 경로 + 동일 타입 발견 ──▶ 기존 shared_ptr 반환
        │
        └─ 없음 ──▶ 생성 함수 호출 → weak_ptr 캐시 등록
```

Path Lookup은 `weak_ptr`만 보관하므로 캐시 자체가 리소스 수명을 불필요하게 연장하지 않는다. 실제 소유권은 Tag Registry나 사용하는 객체의 `shared_ptr`에 남는다.

## 동시 접근 제어

Resource Manager는 `std::shared_mutex`로 접근을 구분한다.

- 조회와 Snapshot 생성: `shared_lock`
- 등록, 삭제, 경로 이동, Cache 정리: `unique_lock`

외부에는 내부 Vector나 Map의 참조 대신 `shared_ptr` 또는 Container 복사본을 반환한다. 함수가 Lock을 해제한 뒤 다른 Thread가 Registry를 수정하더라도 호출자가 Manager 내부 Iterator를 계속 들고 있지 않게 하기 위한 선택이다.

ImGui Resource View도 Lock을 잡은 채 UI를 그리지 않는다. 먼저 Registry Snapshot을 만든 뒤 Lock을 해제하고 정렬·검색·렌더링을 수행한다. UI에서 삭제 버튼을 눌렀을 때도 현재 순회 중인 Container를 바로 수정하지 않고 삭제 목록을 모아 순회가 끝난 후 처리한다.

## Animation과 Shader 보강

Animation Clip은 파일명을 전역 식별자로 사용하는 별도 `weak_ptr` 캐시를 두어 동일 Animation을 한 번만 로드한다. 생성된 Animation은 일반 Path Lookup에도 함께 등록해 경로 기준 진단이 가능하다.

Debug 환경에서는 `CShaderWatcher`가 HLSL 변경을 감지한다. 짧은 시간에 같은 파일 이벤트가 연속으로 들어오는 상황을 모아 처리한 뒤, 해당 경로를 참조하는 Shader Resource만 다시 빌드한다. ImGui에서는 전체 Shader를 수동으로 Rebuild하는 기능도 제공한다.

파일 감시부터 D3D Shader 교체까지의 실행 경로와 실패 정책은 [Shader Hot Reload 파이프라인](/projects/hogwarts-legacy/shader-hot-reload)에서 별도로 다룬다.

## 종료 순서 방어

엔진 종료 중 Lua Watcher나 다른 시스템이 늦게 Resource API를 호출하면 이미 해제 중인 Registry에 다시 항목이 들어갈 수 있다. `Release()` 시작 시 `m_bIsShutdown`을 먼저 설정하고 이후 등록과 Cache 변경을 거부하도록 했다.

```cpp
void CResourceManager::Release()
{
    ResourceMap resourcesToRelease;
    PathMap pathsToRelease;
    std::unique_lock lock{m_Mutex};

    m_bIsShutdown = true;
    resourcesToRelease.swap(m_Resources);
    pathsToRelease.swap(m_PathLookup);
}
```

저장소를 지역 변수와 교환해 Manager를 즉시 빈 상태로 만들고, Lock이 풀린 뒤 지역 변수의 `shared_ptr`가 소멸하게 했다. 리소스 소멸자가 다시 Manager에 접근하더라도 잠금 재진입과 Container 순회 충돌을 피할 수 있다.

## 진단 기능

Resource Manager GUI에서는 다음 정보를 확인할 수 있다.

- Group·Resource별 등록 개수
- 정규화된 경로별 살아 있는 Resource
- Group, Resource, Path 검색
- Process Working Set·Private Memory
- 개별 Resource의 Debug GUI
- Shader 전체 Rebuild

## 한계와 개선 방향 {/* #트레이드오프와-개선점 */}

`GetOrCreateResourceByPath`는 중복 생성을 확실히 막기 위해 생성 과정까지 Exclusive Lock 안에서 수행한다. 안전성은 높지만 파일 로드가 길면 다른 Resource 조회를 잠시 막을 수 있다. 프로젝트 규모에서는 단순하고 확실한 방식을 선택했지만, 더 큰 규모에서는 Loading 상태를 나타내는 Entry와 Future를 등록한 뒤 실제 I/O를 Lock 밖에서 수행하는 비동기 Cache로 발전시킬 수 있다.

Animation Cache가 파일명만 전역 Key로 사용하므로 서로 다른 폴더에 같은 파일명이 존재하면 충돌할 수 있다. 이 부분도 전체 정규화 경로나 Asset GUID를 기준으로 바꾸는 것이 다음 개선점이다.
