# 안전한 Level 전환과 Runtime 수명주기

## 배경과 목표 {/* #문제 */}

Level 전환은 다음 맵을 읽는 작업만으로 끝나지 않는다. 이전 Level의 GameObject, Effect, Particle, Light, Sound, Navigation Data와 Prototype을 안전하게 종료한 뒤 다음 Level의 자원을 준비해야 한다.

이 과정에서 수명 경계가 어긋나면 오류가 즉시 드러나지 않는다.

- Update 순회 중 객체를 제거해 비소유 Pointer View가 무효화됨
- Effect Instance가 참조하는 Particle·Light·Sound를 남긴 채 Preset이나 Resource를 제거함
- 종료 Callback이 이미 파괴된 GameObject의 `this`를 다시 사용함
- Worker의 Load·Unload가 끝나기 전에 실제 Level을 교체함
- Debug Client가 Release Engine DLL을 불러 STL 객체의 ABI가 달라짐

그래서 Level 전환을 하나의 함수가 아니라 **전환 상태, Frame 경계, Manager별 소유권, Binary 경계**가 연결된 수명주기로 설계했다.

## 전환 상태를 명시한 Loading Level

Loading Level은 이전 Level과 다음 Level 사이에서 전환 상태를 소유한다.

```cpp
enum class PHASE
{
    READY,
    UNLOADING,
    LOADING,
    COMPLETE,
    FAILED
};
```

각 단계의 책임은 다음과 같다.

| 단계 | 책임 |
| --- | --- |
| `READY` | 이전 Level의 Unload 시작 |
| `UNLOADING` | Unload Future 완료 확인 |
| `LOADING` | 다음 Level의 Load Future 완료 확인 |
| `COMPLETE` | 다음 Level 생성과 교체 예약 허용 |
| `FAILED` | 전환 중단과 오류 표시 |

`UNLOADING`과 `LOADING`에서는 `future.wait_for(0s)`로 완료 여부만 확인한다. 준비되지 않은 Future를 `get()`으로 기다려 Main Thread와 Loading UI를 멈추지 않는다. Future가 Ready일 때만 결과를 꺼내고, 실패하면 다음 단계로 진행하지 않는다.

```text
현재 Level
   │ ChangeLevel 요청
   ▼
Loading Level
   │ READY
   ├─ 이전 Effect·Map Runtime State 정리
   │
   ├─ UNLOADING ── Worker에서 Prototype·Resource 제거
   │
   ├─ LOADING ──── Worker에서 다음 Resource 준비
   │
   └─ COMPLETE
         │ Loading Level의 FrameEnd에서 교체 예약
         ▼
다음 FrameStart에서 실제 Level 초기화·교체
```

전환이 끝나기 전에는 `IsLevelChangeLocked()`가 새로운 Level 변경 요청을 막는다. 연속 입력으로 서로 다른 Load·Unload Future가 겹치는 상황을 상태 자체로 제한한다.

## 실제 Level 교체는 FrameStart에서

다음 Level의 Resource Load가 끝나면 Loading Level의 `FrameEnd()`가 새 Level 객체를 만들고 `ChangeLevel()`에 전달한다. 이 호출은 현재 Level을 즉시 파괴하지 않고 `m_pLevelBeforeLevelChange`에 예약한다.

실제 교체는 다음 `LevelManager::FrameStart()`에서 수행한다.

1. 남아 있는 Time Scale 요청과 Map Texture Cache를 정리한다.
2. 현재 Loading Level을 해제한다.
3. Deferred Initialization을 사용하는 다음 Level의 `Initialize()`를 호출한다.
4. 초기화에 성공한 Level만 현재 Level로 이동한다.
5. 새 Level의 `FrameStart()`를 시작한다.

Update 또는 Render 도중 현재 Level 포인터를 교체하지 않으므로, 한 프레임 안에서 서로 다른 Level의 로직이 섞이지 않는다. 다음 Level 초기화가 실패하면 Pending Level을 제거하고 오류를 표시하며, 초기화에 실패한 객체를 Current Level로 공개하지 않는다.

## Layer Reset도 즉시 파괴하지 않는다

Loading Level 초기화 시 기존 GameObject는 Layer 조건으로 제거를 예약한다.

```cpp
GameObjectAllResetExceptLayers({
    "00_ENGINE_CINEMATIC_CAMERA"
});
```

전환 Fade를 유지해야 하는 Cinematic Camera는 제외하고 나머지 기존 객체를 대상으로 삼는다. 이 호출은 객체를 바로 삭제하지 않는다.

```text
Layer 조건으로 대상 Slot 표시
        ↓
GameObject에 PendingDestroy 설정
        ↓
남은 Update Dispatch에서 실행 차단
        ↓
GameObjectManager::FrameEnd
        ↓
Slot 해제 · Generation 증가 · Layer Handle 정리
```

Reset 요청 시점에 존재한 객체만 표시하므로, 그 뒤 Loading Level이 생성하는 Fly Camera와 UI Camera가 이전 Level의 Reset에 휘말리지 않는다. 실제 파괴는 Update 순회가 끝난 FrameEnd로 통일해 단계별 Pointer View와 Iterator의 안정성을 유지한다.

Batch Reset을 처리할 때는 Pending Layer 집합을 `move`로 떼어 낸다. 소멸 과정에서 새 Reset 요청이 들어와도 현재 처리 묶음과 섞이지 않고 다음 FrameEnd의 요청으로 남는다. 반면 객체 소멸자가 다른 객체의 Destroy를 요청하면 Pending Queue를 Wave 단위로 다시 비워 같은 FrameEnd 안에서 연쇄 파괴를 마친다.

## Resource보다 먼저 Runtime Effect를 종료

Effect Instance는 단순한 이름이 아니라 실행 중인 하위 객체를 함께 추적한다.

```text
Effect Instance
├─ Particle Owner IDs
├─ Effect Light Handles
├─ Sound IDs
├─ Preset Pointer
└─ Finished Callback
```

따라서 Level Loader는 Map Prototype과 Resource를 Worker에서 제거하기 전에 Main Thread에서 다음 Runtime State를 먼저 정리한다.

- 실행 중인 Effect 전체 중지
- Map Chunk와 Dynamic Light 정리
- Navigation Mesh Runtime Data 정리
- 이후 Worker에서 해당 Level의 Prototype과 Resource 제거

`StopEffect()`는 Particle Owner를 비우고, Effect Light를 반환하고, Effect가 시작한 Sound를 멈춘 뒤 Instance를 제거한다. Preset Reload도 같은 이유로 실행 중인 Instance를 먼저 중지하고 Preset Map을 비운다. Instance가 Preset Entry의 Pointer를 보관하므로 순서를 반대로 하면 다음 Update에서 무효 Pointer를 역참조할 수 있다.

## 재진입 가능한 Effect 전체 정리

`ClearAllRunningEffect()`가 Instance Map을 직접 순회하면서 `StopEffect()`를 호출하면, Stop 과정에서 같은 Map의 원소가 지워져 Iterator가 무효화된다. 종료 Callback이 다른 Effect를 정지하거나 시작한다면 재진입까지 발생할 수 있다.

현재 구현은 먼저 Effect ID Snapshot을 만든 뒤 Snapshot을 순회한다.

```cpp
std::vector<EFFECT_INSTANCE_ID> effectIds;
effectIds.reserve(m_Instances.size());

for (const auto& effect : m_Instances)
    effectIds.push_back(effect.first);

for (EFFECT_INSTANCE_ID effectId : effectIds)
    StopEffect(effectId);
```

각 `StopEffect()`도 Callback을 지역 변수로 이동하고 Instance를 Map에서 먼저 지운 뒤 Callback을 호출한다. Callback 안에서 같은 Effect ID를 조회하면 이미 종료된 상태를 관찰하며, Callback이 Manager에 재진입해도 현재 원소의 Reference를 다시 사용하지 않는다.

## 비동기 Callback에는 Pointer 대신 Handle

Effect 종료 Callback은 Effect보다 먼저 GameObject가 파괴되는 경우를 고려해야 한다. 장기 Callback에 `this`를 Capture하면 Level 전환 후에도 해제된 주소를 호출할 수 있다.

```cpp
const CHandle ownerHandle = GetHandle();

PlayEffect(name, world, {},
    [ownerHandle](EFFECT_INSTANCE_ID id, EFFECT_FINISH_REASON reason)
    {
        auto* owner = CGameInstance::Get()
            .GetGameObjectByHandleT<CEffectOwner>(ownerHandle);
        if (owner == nullptr)
            return;

        owner->OnEffectFinished(id, reason);
    });
```

Callback 시점에 Slot과 Generation을 다시 확인하므로, 소유 객체가 사라졌거나 같은 Slot이 다른 객체에 재사용됐다면 `nullptr`로 종료된다. 같은 프레임 안의 임시 Pointer와 프레임을 넘는 보관 참조를 구분하고, 후자에 Handle을 적용했다.

## Engine 종료도 의존 관계를 따라 정리

프로그램 종료 시에는 GameObject Manager를 바로 해제하지 않는다. 먼저 Pool Manager를 종료하고, 모든 GameObject에 Reset을 요청한 뒤 `FrameEnd()`를 직접 호출해 실제 소멸을 완료한다. GameObject의 `Free()`가 Component와 Physics 객체를 반환할 수 있으므로 관련 Manager가 살아 있을 때 객체 수명주기를 끝내기 위한 순서다.

Sound Manager도 FMOD System을 먼저 해제하지 않는다.

1. Master Bus의 재생을 중지한다.
2. Playing Sound Map을 비운다.
3. 사용자 Bus를 해제한다.
4. FMOD System의 User Data를 끊는다.
5. System을 Close·Release한다.
6. 완료 Callback Queue를 비운다.

핵심은 컨테이너의 원소가 참조하는 외부 시스템을 그 컨테이너보다 먼저 없애지 않는 것이다. Manager를 단순히 선언의 역순으로 지우기보다 `Free()`에서 접근하는 의존성을 기준으로 종료 순서를 결정했다.

## Debug·Release DLL 혼용은 시작 단계에서 차단

수명주기 크래시처럼 보이지만 실제로는 Binary 조합이 원인인 경우도 있었다. Debug Client와 Release Engine DLL처럼 C++ Runtime과 STL ABI가 다른 모듈을 혼용하면, 한 모듈이 만든 `string`, `shared_ptr`, Container를 다른 모듈이 해제하는 시점에 내부 메모리가 손상될 수 있다. 오류는 원인이 발생한 시작 시점이 아니라 Sound Map이나 Effect Map을 비우는 종료 시점에 나타날 수 있다.

이를 늦은 메모리 손상으로 관찰하지 않도록 Engine DLL이 64-bit Build Signature를 C ABI로 노출한다.

```text
63                         32 31                          0
+---------------------------+-----------------------------+
|        ABI Version        |     Build Configuration     |
+---------------------------+-----------------------------+
```

Client와 Map Editor는 `wWinMain()`의 시작에서 자신이 기대하는 Signature와 실제 로드된 Engine DLL의 값을 비교한다. 다르면 두 Configuration과 ABI Version을 Message Box에 표시하고 `RaiseFailFastException()`으로 즉시 중단한다.

Signature 조회는 STL 객체를 넘기지 않는 `extern "C"` 함수로 만들었다. 호환성을 검사하는 함수 자체가 C++ Name Mangling이나 STL ABI 차이의 영향을 받지 않게 하기 위해서다.

이 검사는 Debug·Release 구성과 명시한 Engine ABI Version의 불일치를 잡는다. 모든 Third-party DLL 버전이나 Compiler Option 차이를 자동 검증하는 것은 아니므로, 공개 ABI가 바뀌면 Version을 올리고 배포물도 Configuration별로 분리해야 한다.

## 장애를 분리해서 판단한 기준

Level 전환 중 Effect Container에서 발생한 접근 위반과 프로그램 종료 시 Sound 객체 소멸에서 발생한 메모리 손상은 증상이 비슷해도 같은 원인으로 단정하지 않았다.

- Effect 전체 정리는 Erase 중 순회와 Callback 재진입에 안전하도록 Snapshot 방식으로 변경했다.
- Effect가 보유한 하위 Runtime 객체는 Level Resource보다 먼저 정리했다.
- 장기 Callback은 Handle 재조회로 소유 객체의 수명을 검증했다.
- 서로 다른 Build의 DLL 혼용은 시작 시 Signature 검사로 별도 차단했다.

크래시가 사라졌다는 결과만으로 하나의 원인을 확정하는 대신, 서로 다른 수명 경계마다 재현 가능한 불변식을 두었다.

## 한계와 개선 방향 {/* #남은-한계 */}

현재 Loading Level은 Level별 Loader와 생성 분기를 `switch`로 직접 관리한다. Level이 계속 늘어난다면 Loader Factory나 Registry로 전환해 분기 누락을 줄일 수 있다.

또한 `ClearAllRunningEffect()`는 Level 소유권과 관계없이 모든 실행 Effect를 정리한다. Level을 넘어 유지해야 하는 UI Effect나 전역 Effect가 늘어난다면 Effect Instance에 Scope 또는 Owner Level을 부여해 선택적으로 종료할 필요가 있다.

Future는 Load·Unload 완료 여부만 표현한다. Worker에서 실제로 호출하는 Resource API의 Thread Safety까지 보장하지는 않으므로, GPU 객체와 Main Thread 전용 Runtime State는 Loader 시작 전 동기 구간에 두고 Worker에는 Thread-safe한 Resource 작업만 배치해야 한다.

## 구현 결과 {/* #결과 */}

Level 전환을 비동기 작업 하나가 아니라 Frame 경계를 가진 상태 머신으로 정리했다. GameObject는 PendingDestroy와 FrameEnd, Effect는 하위 Runtime 객체 정리 후 Callback, Level은 Future 완료 후 다음 FrameStart, Binary는 애플리케이션 시작 시 Signature 검사라는 각자의 종료 지점을 갖는다.

그 결과 늦게 나타나는 Dangling Pointer와 ABI 손상을 같은 크래시로 취급하지 않고, 수명 경계별로 조기에 실패하거나 안전하게 무시할 수 있는 구조를 마련했다.
