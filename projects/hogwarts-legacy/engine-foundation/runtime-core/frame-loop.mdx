# Frame Loop와 Fixed Update 구조

## 배경과 목표 {/* #설계-목표 */}

게임 루프에는 서로 다른 시간 특성을 가진 시스템이 함께 들어간다.

- 입력과 게임 로직은 화면 Frame을 기준으로 갱신한다.
- PhysX와 NvCloth는 일정한 Step 간격이 필요하다.
- Hit Stop과 Slow Motion은 게임 시간만 느려져야 한다.
- 객체 파괴와 Level 교체는 현재 순회가 끝난 뒤 처리해야 한다.
- 렌더링과 디버그 UI는 모든 Simulation 결과가 반영된 후 실행해야 한다.

이를 `CBaseApp`의 실행 주기와 `CGameInstance`의 Manager Dispatch로 나누고, 한 Frame의 책임을 명확한 단계로 구성했다.

## 전체 실행 순서

```text
TimeProvider에서 실제 경과시간 측정
        ↓
60Hz Update Cadence 도달 여부 확인
        ↓
BeginFrameTime
        ↓
FrameStart
  ├─ Input 갱신
  ├─ Level FrameStart
  ├─ GameObject Update View 재구축
  ├─ Collider FrameStart
  └─ GameObject PriorityUpdate
        ↓
FixedUpdate × 0..N
  ├─ CCT 상호작용 준비
  ├─ GameObject FixedUpdate
  ├─ PhysX Simulation
  └─ NvCloth Simulation
        ↓
Update
  ├─ Effect·Particle·GameObject
  ├─ Camera·LateUpdate·Level
  ├─ Light·Renderer·Map
  └─ Sound Listener와 FMOD
        ↓
Render
  ├─ Renderer Draw
  ├─ ImGui
  └─ Present
        ↓
FrameEnd
  ├─ GameObject 지연 파괴
  ├─ Object Pool 반환 처리
  ├─ Level·Event 지연 처리
  └─ Renderer·Collider·Debug 임시 상태 정리
```

## 실제 경과시간과 실행 주기 분리

Update 실행 주기는 60Hz로 제한하지만 `TimeProvider`가 측정한 실제 경과시간은 Loop 호출마다 누적한다. Update가 실행되는 순간 누적값 전체를 이번 Frame의 Raw Delta로 사용하고, 실행 주기를 계산하는 Timer의 나머지는 다음 Cadence 판정에만 남긴다.

```cpp
const float measuredDelta = game.UpdateTimeProvider();
m_UpdateTimer.AppendCurrTime(measuredDelta);
m_fPendingUpdateElapsed += measuredDelta;

if (m_UpdateTimer.Get_JustFinished())
{
    const float rawDelta = m_fPendingUpdateElapsed;
    m_fPendingUpdateElapsed = 0.f;

    const float delta = std::min(rawDelta, 0.125f);
    game.BeginFrameTime(delta);
    // Frame 실행
}
```

이전에는 누적한 실제 시간 전체를 Delta로 소비한 뒤 Cadence Timer의 나머지를 다음 Frame Delta에 다시 포함해 시간이 중복 가산될 수 있었다. 실제 경과시간용 `m_fPendingUpdateElapsed`를 분리해 Update 주기의 나머지와 게임 Delta가 서로 다른 책임을 갖게 했다.

비정상적으로 큰 정지 시간이 한 Frame에 들어오면 Animation과 물리가 폭발적으로 따라잡으려 할 수 있으므로 Gameplay Delta는 최대 0.125초로 제한한다. 이는 멈춘 시간을 완전히 재현하는 것보다 게임 상태의 안정성을 우선한 선택이다.

## Fixed Update Accumulator

Fixed Timer의 목표 간격도 1/60초다. 누적시간이 Fixed Step 이상이면 같은 크기의 Delta로 Simulation을 반복한다.

```cpp
while (fixedCurrentTime >= fixedGoalTime)
{
    FixedUpdate(fixedGoalTime);
    fixedCurrentTime -= fixedGoalTime;
}
```

Frame Drop이 심할 때 밀린 물리를 무제한으로 실행하면 Fixed Update가 다음 Frame을 다시 늦추는 Spiral of Death가 발생한다. 한 Frame의 최대 실행 횟수를 기본 8회로 제한하고, 초과한 전체 Step은 버린 뒤 `fmod`로 1 Step 미만의 나머지만 유지한다.

ImGui에서 최대 실행 횟수를 1회로 제한하는 진단 옵션도 제공한다. 물리 정확도보다 Frame 비용을 우선했을 때의 동작과 Simulation 병목을 비교하기 위한 기능이다.

## Scaled Time과 Unscaled Time

`CTimeManager`는 실제 Frame Delta에서 두 값을 만든다.

```text
Unscaled Delta = 실제 게임 Frame 경과시간
Scaled Delta   = Unscaled Delta × 현재 Time Scale
```

Time Scale 요청은 StringID Tag로 관리하고 `BLEND_IN → HOLD → BLEND_OUT` 단계를 거친다. 여러 요청이 겹치면 가장 작은 Scale을 사용하며, 해제 요청이 누락되더라도 복구할 수 있도록 최대 Unscaled 지속시간과 Safety Blend Out을 설정할 수 있다.

요청 중첩과 해제 규칙, 고대마법 투척에 적용한 사례는 [시간 배율 요청 관리](/projects/hogwarts-legacy/time-scale-requests)에서 자세히 설명한다.

GameObject는 `TIME_DOMAIN::SCALED` 또는 `UNSCALED`를 선택한다. GameObject Manager가 Update 직전에 각 객체에 맞는 Delta를 전달하므로, Slow Motion 중에도 UI나 반드시 진행돼야 하는 제어 로직은 Unscaled Time을 사용할 수 있다.

```cpp
const float objectDelta =
    object->GetTimeDomain() == TIME_DOMAIN::UNSCALED
        ? unscaledDelta
        : scaledDelta;
```

Effect, Particle, Camera, Level 같은 게임 연출은 주로 Scaled Delta를 사용하고, Lua Hot Reload, Shader Watcher, Editor, Renderer 관리처럼 게임 속도와 독립적인 기능은 Unscaled Delta를 사용한다.

## 물리 Simulation 순서

Fixed Update에서는 먼저 GameObject가 이동 의도와 Kinematic Target을 갱신하고 그 다음 PhysX를 Step한다.

```text
PrepareCCTInteractions
        ↓
GameObject::FixedUpdate
        ↓
PhysX::simulate / fetchResults
        ↓
Rigid Body·CCT 결과 동기화와 Callback
        ↓
NvCloth::StepSimulation
```

Time Scale이 0이면 Scaled GameObject에는 0 Delta가 전달되지만 Unscaled GameObject는 Fixed Update를 계속 수행할 수 있다. 이후 PhysX와 NvCloth Step은 건너뛰어 Pause 중 Simulation이 진행되지 않게 한다.

물리 결과가 확정된 뒤 NvCloth를 실행하므로 Ragdoll이나 캐릭터 충돌체의 최신 위치를 망토 Simulation에 반영할 수 있다.

## Priority, Update, LateUpdate 분리

GameObject의 일반 Frame 갱신은 세 단계로 나눴다.

- `PriorityUpdate`: 입력 처리 직후, 다른 일반 객체보다 먼저 필요한 상태 갱신
- `Update`: 게임 로직과 상태 전개
- `LateUpdate`: 일반 이동이 끝난 뒤 Camera, 추적 객체, 후처리 Transform 동기화

모든 GameObject가 네 종류의 Update 함수를 빈 상태로 호출하지 않도록 참여할 Loop를 Bit Mask로 선언한다. 객체 구성이 바뀔 때만 단계별 Pointer View를 재구축하고, 각 Hot Loop는 해당 단계에 참여하는 객체만 순회한다.

## FrameEnd를 둔 이유

Update 도중 GameObject, Event Listener, Render Queue를 즉시 제거하면 현재 순회 중인 Container와 비소유 Pointer가 무효화될 수 있다. 변경 요청은 Pending 상태로 기록하고 FrameEnd에서 일괄 반영한다.

- GameObject Slot Reset과 Generation 증가
- Object Pool 반환과 비활성화
- Level 전환 및 Event Queue 정리
- Render Group, Instance Frame Data 초기화
- Collider와 Debug Line의 Frame 임시 데이터 제거

이 규칙 덕분에 각 Manager가 “언제 실제 삭제가 일어나는가”를 제각각 판단하지 않고 Frame 경계를 공통 안전 지점으로 사용할 수 있다.

## Render와 보간 값

Fixed Timer와 별개로 Update Cadence의 남은 비율을 계산해 `Render(interpolation)`에 전달할 수 있는 Hook을 마련했다. 다만 현재 Base Render 경로는 이 값을 객체 Transform 보간에 직접 사용하지 않는다. 향후 Simulation 이전·현재 상태를 보관한다면 Fixed Update 사이의 화면 움직임을 보간하는 데 사용할 수 있다.

## 한계와 개선 방향 {/* #트레이드오프 */}

현재 구조는 긴 Stall 이후 밀린 시간을 의도적으로 버린다. 따라서 실제 시간과 Simulation 시간이 잠시 어긋날 수 있지만, 한 Frame에서 수십 번 물리를 실행해 응답 불가능 상태에 빠지는 것을 방지한다.

또한 Update와 Render가 같은 60Hz Cadence 안에서 실행되므로 고주사율 화면에서 Render만 더 자주 수행하는 구조는 아니다. 다음 단계에서는 Simulation Tick과 Render Frequency를 완전히 분리하고, 준비해 둔 보간 인자를 실제 Transform에 적용하는 방향으로 확장할 수 있다.
