GameObject와 Prototype 생명주기

배경과 목표​

게임에 등장하는 객체는 생성 방법만 같다고 끝나지 않는다. Component를 구성하고, 고유 Handle을 받아 Layer에 등록되며, 정해진 Update 단계에 참여한 뒤 안전한 시점에 제거되어야 한다.

초기 구조에서는 이 단계들의 경계가 명확하지 않았다. 특히 Initialize() 안에서 자기 Handle로 Manager를 조회하면 아직 Slot과 Layer 등록이 끝나지 않아 nullptr이 반환될 수 있었다. 객체 생성과 등록, 사용 가능한 시점을 하나의 생명주기로 정리할 필요가 있었다.

생성·소멸 경로를 제한한 스마트 포인터​

객체를 스마트 포인터로 보관하더라도 생성자와 소멸자가 공개돼 있으면 외부에서 new·delete로 수명을 따로 관리할 수 있다. 이를 막기 위해 구체 클래스의 생성자·소멸자를 private으로 두고, 상속이 필요한 기반 클래스에서는 protected로 제한했다. 생성은 정적 Create()나 Prototype의 Clone()을 거치고, 반환된 스마트 포인터가 소유권을 갖도록 했다.

생성자 접근 제한이 임의 생성을 막는 장치라면, 커스텀 삭제자는 소멸자를 공개하지 않고도 스마트 포인터가 객체를 정리할 수 있게 하는 장치다. 일반 삭제자가 직접 delete하는 대신, 엔진 전용 삭제자가 CEngineBase::Free()를 호출하도록 연결했다.

다음은 Engine_Base.h에서 수명 관리 부분만 추린 코드다.

C++
class CEngineBase
{
    friend struct tagEngineBaseDeleter;

protected:
    CEngineBase() = default;
    virtual ~CEngineBase() {}
    virtual void Free() { delete this; }
};

struct tagEngineBaseDeleter
{
    void operator()(CEngineBase* base) const
    {
        if (base)
            base->Free();
    }
};

using ENGINE_BASE_DELETER = tagEngineBaseDeleter;

template <typename T>
using UPtr = std::unique_ptr<T, ENGINE_BASE_DELETER>;

삭제자만 friend로 지정해 비공개 Free()에 접근하게 했다. 호출은 기반 포인터로 하지만 Free()가 가상 함수이므로 파생 클래스의 정리 코드가 먼저 실행된다. 이후 부모 Free()를 거쳐 delete this에 도달하고, 가상 소멸자로 파생 객체와 멤버가 소멸한다. 외부 호출자는 Free()나 소멸자를 직접 호출할 필요 없이 소유권을 이전하거나 스마트 포인터를 reset()한다.

CSoundManager::Create()처럼 초기화가 필요한 객체는 먼저 UPtr로 감싼 뒤 Initialize()를 실행한다. 초기화 실패로 반환해도 지역 스마트 포인터가 같은 정리 경로를 호출한다.

C++
UPtr<CSoundManager> CSoundManager::Create()
{
    auto instance = UPtr<CSoundManager>(new CSoundManager{});
    if (FAILED(instance->Initialize()))
        return nullptr;

    return instance;
}

생성자가 비공개이므로 std::make_unique를 클래스 밖에서 호출하지 않고, 접근 권한이 있는 정적 멤버 함수 안에서 생성한다. Create() 내부라도 make_unique 자체가 생성자에 접근할 권한을 얻는 것은 아니다. 이 경로에서는 기본 삭제자가 아닌 엔진 삭제자도 필요하다.

공유 소유에는 SPtr<T>를 사용한다. 이 별칭 자체는 std::shared_ptr<T>이므로, ToSPtr()에서 ENGINE_BASE_DELETER를 함께 등록한다. 마지막 공유 소유자가 해제될 때 같은 Free() 경로가 실행된다. WPtr는 객체를 관찰할 뿐 수명을 연장하지 않는다.

이 방식에서 주의할 점은 파생 클래스가 Free()를 재정의하면 자원 정리 후 부모의 Free()를 반드시 호출해야 한다는 것이다. 이를 빠뜨리면 최종 delete this에 도달하지 않아 객체가 누수된다. 부모 호출 뒤에는 객체가 이미 제거됐으므로 멤버에 접근해서도 안 된다.

커스텀 삭제자는 최종 해제 방법을 통일하고, GameObject Manager는 해제 시점을 FrameEnd로 정한다. 스마트 포인터를 사용하더라도 Update 순회 중 객체를 임의로 제거하지 않도록 두 책임을 구분했다.

Prototype과 Instance 분리​

공통 설정을 가진 원본 객체는 CPrototypeManager에 Group과 Tag 조합으로 등록한다. 실제 GameObject나 Component가 필요할 때 원본의 Clone()을 호출해 Instance를 만든다.

Plain Text
Prototype 등록
   ↓
Group + Tag 조회
   ↓
Clone(pArg)
   ↓
Instance Initialize

Prototype Registry는 shared_mutex로 보호한다. 조회 중에는 shared_lock, 추가·삭제에는 unique_lock을 사용한다. Clone 과정 전체에서 Lock을 유지하지 않고, Registry 안에서는 Prototype의 shared_ptr만 확보한 뒤 Lock 밖에서 실제 복제를 수행한다.

C++
SPtr<CPrototype> prototype;
{
    std::shared_lock lock{m_PrototypeMutex};
    prototype = FindPrototype(groupTag, prototypeTag);
}

return prototype ? prototype->Clone(pArg) : nullptr;

이렇게 하면 복제 과정에서 다른 Prototype이나 Resource를 다시 조회하더라도 같은 Mutex에 재진입하지 않는다. 실제로 Prototype Lock을 두 번 획득하던 경로를 이 방식으로 수정했다.

GameObject 생성 순서​

GameObject Manager는 Instance 생성 전에 Handle Slot을 먼저 확보한다. 생성 인자에 Handle을 넣은 뒤 Prototype을 복제하고, 성공한 객체를 Slot과 Layer에 등록한다.

Plain Text
Handle Slot 확보
   ↓
GAMEOBJECT_DESC에 Handle 전달
   ↓
Prototype Clone과 Initialize
   ↓
Object Slot 소유권 이전
   ↓
Layer에 Handle 등록
   ↓
OnRegisteredToManager 호출

Clone이나 Initialize가 실패하면 선점한 Slot을 초기화하고 Free Slot 목록으로 되돌린다. 성공했을 때만 객체 소유권을 CSlot로 이동한다.

객체 외부에는 포인터 대신 Generation Handle을 돌려준다. 따라서 Slot이 재사용되더라도 이전 Handle이 새로운 객체를 가리키는 것을 막을 수 있다.

등록 완료 Hook​

Initialize()가 실행될 때 객체는 아직 Manager의 Slot과 Layer에 등록되지 않았다. Lua Script처럼 생성 직후 자기 Handle로 Context를 구성하거나, 다른 객체가 자신을 조회해야 하는 기능은 이 시점에 실행할 수 없다.

이를 위해 다음 Hook을 추가했다.

C++
virtual void OnRegisteredToManager() {}

Manager가 Slot과 Layer 등록을 모두 마친 직후 한 번 호출한다. 이 시점부터 다음 동작이 안전하다.

  • 자기 Handle을 통한 Manager 재조회
  • 같은 Layer의 다른 객체 검색
  • Lua Context에 Owner Handle 전달
  • Manager 등록을 전제로 하는 Controller 연결

이 Hook은 Lua 전용 기능이 아니라 모든 GameObject가 사용할 수 있는 생명주기 경계다.

Component 소유와 조회​

GameObject는 Component를 unique_ptr로 소유한다. 순회에 적합한 Vector와 Tag 조회용 Hash Map을 함께 사용한다.

C++
std::vector<std::pair<StringID, UPtr<CComponent>>> m_Components;
std::unordered_map<StringID, size_t> m_ComponentsLookup;

Component 추가 시 Vector Index를 Lookup에 기록하고, 조회할 때는 StringID로 Index를 찾은 뒤 자체 Runtime Type Cast를 적용한다. Component 제거는 마지막 원소와 교환하는 방식으로 Vector의 중간 이동을 줄이고, 이동된 원소의 Lookup Index만 갱신한다.

Transform과 기본 Collider 역시 같은 Prototype 복제 경로로 생성된다. 각 Component는 자신을 소유한 GameObject 포인터를 Descriptor로 전달받는다.

Update 참여 정책​

모든 객체가 네 개의 Managed Update를 전부 사용할 필요는 없다. Prototype에서 GAMEOBJECT_UPDATE_LOOP 비트 마스크를 설정해 참여 단계를 정적으로 분류한다.

  • PRIORITY
  • FIXED
  • UPDATE
  • LATE
  • ALL 또는 NONE

Manager는 이 분류로 단계별 View를 만들고, 매 프레임 전체 객체를 순회하며 빈 함수를 호출하는 비용을 줄인다.

런타임에는 SetManagedUpdateEnabled()를 Master Switch로 사용한다. Pool에 반환된 객체처럼 Manager에는 남아 있어야 하지만 게임 로직 실행은 멈춰야 하는 객체를 위해 마련했다. 활성 상태가 바뀌면 파생 클래스가 OnManagedUpdateEnabled()와 OnManagedUpdateDisabled()에서 Physics나 부가 상태를 함께 전환할 수 있다.

지연 파괴​

Update 도중 객체를 즉시 제거하면 현재 순회 중인 Container와 외부 참조가 무효화될 수 있다. SetPendingDestroy()는 실제 메모리를 바로 해제하지 않고 Handle을 Manager의 제거 Queue에 넣는다.

Plain Text
게임 로직에서 파괴 요청
   ↓
Pending Handle Queue
   ↓
FrameEnd에서 Layer 분리
   ↓
Slot Reset과 Generation 증가
   ↓
Free Slot 반환

파괴 요청은 수집되기 전까지 취소할 수 있지만, Layer에서 논리적으로 분리된 이후에는 확정 파괴로 처리한다. 같은 요청이 여러 번 Queue에 쌓이지 않도록 상태 변화가 있을 때만 등록한다.

시스템 연결​

이 생명주기는 독립된 기능이 아니라 다른 Foundation 시스템의 접점이다.

  • StringID: Prototype·Component·Layer Tag
  • Derived Type: Component와 Prototype의 Typed Cast
  • Generation Handle: 외부 객체 참조와 유효성 검사
  • Frame Loop: 단계별 Update와 FrameEnd 파괴
  • Object Pool: Manager 소유권을 유지한 활성·비활성 전환
  • Lua: 등록 완료 후 Owner Context 구성

구현 결과​

Prototype 복제, Component 구성, Manager 등록, Update 참여, 파괴가 하나의 순서로 연결됐다. 객체가 언제부터 조회 가능한지와 언제 실제로 제거되는지가 명확해졌고, Handle Manager·Pool·Lua 같은 후속 시스템이 같은 생명주기 위에서 동작할 수 있게 됐다.
