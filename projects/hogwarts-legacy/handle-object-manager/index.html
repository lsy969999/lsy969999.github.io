Generation Handle 기반 Object Manager

배경과 목표​

GameObject를 Raw Pointer로 외부에 전달하면 조회 직후에는 빠르고 편하다. 하지만 레벨 전환, 전투 중 파괴, 비동기 Callback처럼 객체의 수명보다 참조가 오래 남는 순간 Dangling Pointer가 된다. 주소만으로는 그 메모리가 해제됐는지, 같은 주소에 다른 객체가 생성됐는지 판별할 수 없다.

이 문제를 Manager 소유권과 외부 참조로 분리해 해결했다.

  • Manager는 unique_ptr<GameObject>의 유일한 소유자다.
  • 외부 시스템은 장기 참조가 필요하면 CHandle을 저장한다.
  • 사용할 때마다 Manager가 Handle을 검증해 현재 객체를 반환한다.

Handle 구조​

CHandle은 32-bit Slot Index와 32-bit Generation으로 구성한 8-byte 값이다.

Handle.h
class CHandle
{
public:
    constexpr uint32_t GetIndex() const;
    constexpr uint32_t GetGeneration() const;

private:
    uint32_t m_iIndex{ INVALID_INDEX };
    uint32_t m_iGeneration{ INVALID_GENERATION };
};

static_assert(sizeof(CHandle) == sizeof(uint64_t));

Index는 m_Objects의 Slot을 찾고, Generation은 그 Slot이 Handle 발급 당시와 같은 생명주기인지 확인한다.

Plain Text
Handle { index: 12, generation: 3 }
                    │
                    ▼
m_Objects[12] { generation: 3, object: Player }
                    │
                    └─ 일치: Player 반환

m_Objects[12] { generation: 4, object: NewMonster }
                    │
                    └─ 불일치: nullptr 반환

객체가 파괴되면 Slot의 소유 포인터를 Reset하고 Generation을 증가시킨다. 이후 같은 Slot을 재사용하더라도 이전 Handle은 새로운 객체를 가리킬 수 없다.

조회와 Typed Lookup​

Manager는 범위, 점유 상태, Generation을 순서대로 검사한다.

C++
const CGameObject* GetGameObjectByHandle(CHandle handle) const
{
    if (handle.index >= slots.size())
        return nullptr;
    if (!slots[handle.index].IsOccupied())
        return nullptr;
    if (slots[handle.index].Generation() != handle.generation)
        return nullptr;

    return slots[handle.index].Get();
}

GetGameObjectByHandleT<T>는 여기에 자체 Engine::Cast<T>를 연결한다. Handle은 유효하지만 기대 타입이 아닌 경우에도 nullptr을 반환하므로, 수명과 타입을 한 번에 검증할 수 있다.

즉시 삭제 대신 FrameEnd 지연 파괴​

Update 도중 컨테이너에서 객체를 즉시 제거하면 현재 순회 Iterator와 다른 객체가 가진 Pointer가 동시에 무효화될 수 있다. 그래서 삭제 요청은 PendingDestroy와 Handle Queue에 기록하고, 모든 Update 단계가 끝난 FrameEnd에서만 실제 해제를 수행한다.

Plain Text
Update에서 Destroy 요청
        ↓
PendingDestroy 설정 + Handle Queue 등록
        ↓
남은 Update에서 Pending 객체 호출 차단
        ↓
FrameEnd에서 Slot Reset + Generation 증가
        ↓
영향받은 Layer의 Handle 안정 압축

파괴 처리 중 소멸자가 또 다른 객체를 파괴할 수 있으므로 Pending Queue와 Processing Queue도 분리했다. 현재 순회 중인 메모리를 건드리지 않고 다음 처리 묶음으로 넘긴다.

Layer와 Update 경로 최적화​

Layer는 GameObject Pointer가 아니라 Handle 배열을 보관한다. Slot Index를 기준으로 객체의 Layer 위치를 병렬 저장해, 삭제할 때 모든 Layer를 다시 검색하지 않고 영향받은 Layer만 압축한다.

또한 GameObject가 참여할 Update 단계는 Mask로 선언하고, 객체 구성이 바뀔 때만 단계별 Pointer View를 재구성한다.

  • PriorityUpdate
  • FixedUpdate
  • Update
  • LateUpdate

일반 프레임의 Hot Loop에서는 전체 객체의 Mask를 반복 검사하지 않는다. Pointer View는 비소유이므로 객체가 실제 파괴된 다음 FrameStart 전에 반드시 재구축한다는 불변식을 함께 유지한다.

운영 기능​

실제 레벨 전환과 Pooling 준비 과정에서 다음 기능도 같은 생명주기 규칙 위에 추가했다.

  • 지정 Layer만 Reset
  • 지정 Layer를 제외하고 Reset
  • Update 참여를 끄고 켜는 Managed Update
  • 이전 계층 API 호출부를 보존하는 Cascade 명칭의 호환 API
  • 빈 Slot, 점유 Slot, 무효 Handle을 확인하는 ImGui Debug View
  • FrameEnd에서 무효 Layer Handle 정리

적용 사례​

  • Effect 종료 Callback은 this 대신 Handle을 Capture하고, Callback 시점에 다시 조회한다.
  • PhysX Actor User Data도 GameObject 생포인터 대신 Handle로 소유 객체를 식별한다.
  • Query 결과에는 즉시 사용 Pointer와 보관 가능한 Handle을 함께 제공한다.
  • Object Pool은 객체를 Manager 밖으로 꺼내지 않고 Managed Update와 활성 상태를 전환한다.

결과와 한계​

외부 참조가 객체 파괴 이후 조용히 다른 메모리를 사용하는 대신, 조회 시점에 명확히 nullptr로 실패하게 됐다. 동시에 지연 파괴, Layer Reset, Pooling이 하나의 생명주기 규칙을 공유하게 됐다.

Generation도 유한한 32-bit 값이므로 같은 Slot이 2^32회 재사용되면 순환할 수 있다. 실사용 범위에서는 충분히 크지만 이론적으로 영구 고유 ID는 아니다. 또한 같은 프레임 안에서만 사용하는 지역 Pointer까지 무조건 Handle로 바꾸기보다, “수명을 넘어 저장되는 참조”에 Handle을 적용하는 기준이 중요하다.
