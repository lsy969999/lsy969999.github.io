Magic Square Step — 다수의 물리 발판을 패턴으로 제어하기

배경과 목표​

찰스 룩우드 구간에서는 작은 사각 발판들이 순차적으로 솟아올라 길과 계단을 만들고, 여러 발판에 걸쳐 파동이 전달되는 장면이 필요했다. 화면에 보이는 장식이 아니라 플레이어와 물리 객체가 실제로 올라설 수 있는 발판이므로, 모델 이동과 Collider 이동을 함께 처리해야 했다.

발판마다 구간 전체의 연출을 하드코딩하는 대신, 배치 정보와 패턴 진행을 관리하는 Controller를 만들고 개별 발판에는 이동과 물리 상태만 맡겼다. 이후 줄 단위 이벤트 콜백과 객체 풀을 연결해 사운드 확장과 반복 구간의 재사용을 지원했다.

배치·패턴·개별 이동의 책임 분리​

구성책임
Level / Trigger구간별 Group 등록, 생성 요청, 패턴 설정, 후속 게임 로직
CMyMagicSquareStepController배치 좌표 생성, Group 상태, 생성 대기열, 패턴 시간, 이벤트 전달
CMyMagicSquareStep목표점 이동, Bounce, Kinematic Target, 렌더 등록, 풀 활성·비활성 처리
GameObject Pool Manager재사용 가능한 발판 확보·대여·반환

Group은 StringID로 구분하고, 실제 발판은 포인터를 장기 보관하지 않고 CHandle로 참조한다. Controller는 발판의 구체적인 모델 렌더링을 수행하지 않으며, 발판은 자신이 전체 경로의 몇 번째 줄인지 몰라도 이동할 수 있다.

배치 등록과 실제 생성을 분리​

RegistRectGroup은 시작 위치, X·Z 개수와 간격으로 격자 좌표를 만든다. RegistFilledCircleGroup은 원 주변의 격자를 검사해 반지름 안에 들어가는 점만 남긴다. 원 둘레에만 배치하는 Ring이 아니라 내부를 채우는 방식이다.

각 좌표에는 World 위치 외에도 격자 Index, 정규화된 X·Z, 중심에서의 거리 등을 저장한다. 같은 배치를 X 방향으로 채우거나 중심에서 바깥쪽으로 펼칠 때 좌표를 다시 만드는 대신 이 정보를 사용한다.

현재 레벨에는 10×59, 8×35, 8×34 사각 Group과 반지름 14의 원형 Group이 등록되어 있다. Level 초기화에서는 Group 배치 정보를 등록하고, 실제 구간 진입 시 Trigger가 SpawnGroup을 요청한다.

Plain Text
REGISTERED: 배치 정보만 준비
    ↓ SpawnGroup
SPAWNING: 대기열에서 발판을 확보·배치
    ↓ 목표 개수 확보
READY: 패턴 실행 가능
    ↓ 패턴 시작
PATTERN_RUNNING
    ↓ 개별 이동 또는 파동 종료 확인
PATTERN_COMPLETE

생성이나 실행 중 발판을 확보하지 못하면 FAILED로 전환한다. 등록 성공, 생성 요청 성공, 실제 패턴 완료가 서로 다른 상태라는 점이 중요하다.

프레임당 생성 요청 예산​

SpawnGroup은 모든 발판을 즉시 생성하지 않고 Group ID와 배치 정보를 대기열에 넣는다. Controller의 Update는 기본적으로 프레임당 최대 50개 항목을 처리한다. 이 예산은 여러 Group이 공유한다.

현재 SpawnOne은 Clone을 직접 호출하는 대신 Pool에서 발판을 Acquire하고, 반환된 Handle을 Group에 저장한다. 모든 발판을 확보한 뒤 READY가 된다. Rise 설정은 SPAWNING 중에도 예약할 수 있지만 실제 상승은 READY 이후 PriorityUpdate에서 시작한다.

이는 구간 배치를 여러 프레임으로 나누는 장치다. 뒤에서 설명하는 초기 Pool Prewarm까지 50개씩 분할하는 구조는 아니므로, 초기화 비용과 플레이 중 배치 비용을 구분해야 한다.

Rise: 생성 순서와 최종 높이를 독립적으로 설정​

Rise는 발판마다 이동을 시작할 시간을 계산하고, 시간이 된 발판에 한 번만 목표점을 전달한다.

  • Fill Mode: X·Z 방향 또는 중심 거리 기준 RADIAL
  • Direction: 정방향 또는 역방향
  • Height Axis: 최종 높이를 X 또는 Z 위치에 따라 보간
  • Timing: 줄 간격, 줄 내부 발판 간격, 시간 곡선, Jitter
  • Movement: 상승 속도, 목표 높이, Bounce 높이와 안착 속도

채워지는 방향과 높아지는 방향을 분리했기 때문에, Z 방향으로 발판을 등장시키면서 X 방향의 높이 차이로 계단을 만들 수도 있다. 모든 발판이 같은 높이에 도착하게 하려면 시작·끝 목표 Y를 같게 지정한다.

직선 배치에서는 주축 Index로 줄 시작 시간을 계산하고, 보조축 Index에 거듭제곱 곡선과 Jitter를 적용한다. 방사형은 중심 거리와 방향으로 시작 순서를 정한다. Jitter는 격자 Index 해시에서 만들므로 매 프레임 새로운 난수를 뽑아 출발 시간이 흔들리는 방식이 아니다.

Bounce는 물리 반발이 아니라 제어된 두 단계 이동​

개별 발판은 먼저 최종 목표보다 Bounce Height만큼 높은 위치로 올라간 뒤, 별도의 Settle Speed로 최종 높이에 안착한다.

Plain Text
BOUNCE_RISE → BOUNCE_SETTLE → IDLE

이는 힘이나 반발 계수로 튀어 오르는 Dynamic Simulation이 아니라, 연출을 위해 지정한 두 목표점 사이를 Kinematic으로 이동하는 방식이다. Bounce가 없으면 MOVE 이후 IDLE로 끝난다.

Controller는 이동 명령을 모두 보냈다는 이유만으로 완료하지 않는다. 모든 발판에 명령을 전달했고, 각 발판이 실제로 IDLE에 도달했는지 확인한 뒤 COMPLETED 이벤트와 PATTERN_COMPLETE 상태를 만든다.

Wave: 줄마다 지연된 반 주기 Sine​

Wave 시작 시 각 발판의 현재 위치를 기준 위치로 저장한다. FixedUpdate에서 줄 Index에 따른 지연을 빼고, 해당 줄의 진행 시간에 따라 Y Offset을 계산한다.

Plain Text
LocalTime = PatternElapsed - LineIndex × LineInterval
Ratio = LocalTime / WaveDuration
OffsetY = sin(π × Ratio) × Amplitude

유효한 시간 구간 밖에서는 Offset을 0으로 만든다. 양수 Amplitude라면 올라갔다가 기준 위치로 돌아오는 하나의 봉우리가 줄마다 순차적으로 전달된다. 마지막 줄의 지연과 WaveDuration을 합친 시간이 지나면 패턴을 완료한다.

Rise는 PriorityUpdate에서 출발 명령을 배분하고 개별 발판이 FixedUpdate에서 이동한다. Wave는 Controller의 FixedUpdate에서 위치를 직접 계산해 발판에 전달한다. 두 패턴의 시간 처리가 모두 같은 Update 함수에 들어 있는 것은 아니다.

모델과 Collider에 같은 Kinematic 목표 전달​

발판은 Kinematic RigidBody와 Box Collider를 가진다. Box의 Half Extents와 Local Offset은 모델에 맞춘 공통 상수이고, Geometry·Material 리소스는 Prototype에서 준비해 Clone이 공유한다. Actor와 Shape 자체는 발판별로 존재한다.

이동 시 남은 거리와 Speed × DeltaTime 중 작은 값을 적용해 목표를 지나치지 않도록 한다. 계산한 다음 위치를 Transform에 반영하고 같은 위치·회전을 SetKinematicTarget에 전달한다. Wave도 SetKinematicPosition 내부에서 같은 방식으로 Target을 갱신한다.

Collision Layer는 MOVING_PLATFORM이다. 현재 Simulation Mask에는 World Dynamic, Player·Enemy·NPC Body, Debris가 들어 있다. 발판끼리의 충돌을 위해 MOVING_PLATFORM을 서로 포함시키지는 않는다. Query Mask는 All이지만 실제 조회 여부는 호출 측 필터와 엔진 필터 정책까지 함께 결정한다.

이 구조는 발판의 이동과 충돌 형상을 제공하는 부분이다. CCT의 탑승·이동 플랫폼 처리를 이 Controller가 별도의 플레이어 이동 코드로 대신하는 것은 아니다. 또한 여러 발판을 하나의 Actor에 Shape SubIndex로 합친 방식도 아니다.

줄 단위 이벤트로 사운드·후속 동작 연결​

패턴 Descriptor는 fnEventCallback을 받는다. 콜백에는 Group ID, 패턴 종류, 이벤트 종류, 위치, 줄 Index와 대표 발판 Handle을 전달한다.

이벤트의미
STARTED패턴 실행 시작
LINE_ISSUED해당 줄의 첫 이동 명령 또는 Wave 시작
COMPLETED패턴 완료
FAILED실행 과정에서 실패

줄 Index를 Set에 기록해 같은 줄의 모든 발판이 사운드를 중복 호출하지 않도록 했다. RADIAL에서는 중심 거리 구간을 줄 Index로 사용한다. LINE_ISSUED의 위치와 Handle은 그 줄에서 이벤트를 발생시킨 대표 발판이지 줄 중앙을 별도로 계산한 값은 아니다.

현재 Spawn Trigger의 활용 예에서는 일부 줄만 골라 지연 사운드를 예약한다. 예약 함수는 Handle로 발판을 다시 조회해 그때의 위치에서 3D 사운드를 재생한다. 패턴 Controller 안에 모든 사운드 파일과 재생 정책을 고정하지 않고 외부 구간 로직에서 선택할 수 있도록 한 것이다.

순회 중 콜백을 바로 호출하지 않는 이유​

콜백 안에서 Group을 삭제하거나 다음 패턴을 요청하면 Controller가 순회 중인 컨테이너가 바뀔 수 있다. 그래서 패턴 계산 중에는 콜백과 데이터의 복사본을 대기열에 넣고, 순회가 끝난 뒤 별도 Dispatch 단계에서 실행한다.

Dispatch는 대기열을 로컬로 이동시킨 뒤 처리한다. 콜백 실행 중 새로 들어온 이벤트는 다음 처리로 남으며, 이미 삭제된 Group의 이벤트는 건너뛴다. 다만 Group ID를 즉시 삭제·재등록한 경우를 구분하는 세대 값까지 있는 구조는 아니다.

풀 재사용과 Physics 비활성화​

Controller는 공통 Pool Manager에 발판 생성 함수를 등록한다. 현재 기본 정책은 Prewarm 1,024개, 부족할 때 50개씩 증가, 최대 2,048개다. Pool 등록 시 Prewarm은 동기적으로 실행된다. 이 수치는 모든 Group의 발판을 항상 동시에 켜 둔다는 의미는 아니다.

Acquire에서는 Physics Pose와 Transform을 새 배치 위치로 맞추고 이동 목표·속도·Bounce·State를 초기화한다. 활성화 Hook에서는 Collider의 Simulation과 Query를 다시 켠다.

반환할 때는 Managed Update만 끄지 않는다. Update가 멈춰도 PhysX Scene의 Shape는 남기 때문이다. 비활성화 Hook에서 Simulation·Query를 모두 끄고, Release Hook에서는 이동 상태를 초기화한 뒤 발판을 맵 밖의 대기 위치로 옮긴다.

Group 삭제는 발판을 Pool에 반환하고 해당 Group의 남은 생성 요청도 제거한다. Pool 반환이 실패하면 유효한 객체를 PendingDestroy하는 경로를 사용한다. Controller가 해제될 때는 자신이 등록한 Pool을 해제한다.

따라서 반복 구간에서는 동일 발판의 GameObject·Component·Actor를 재사용할 수 있다. 대신 비활성 발판도 메모리와 Physics 객체를 보유하며, Pool 한도에 도달하면 Acquire 실패와 Group FAILED 처리가 필요하다.

렌더링 연결과 조정 도구​

각 발판은 팀의 Static Model Instancing 경로에 현재 World Matrix를 등록한다. 기존 Instancing 시스템을 사용한 것이며 이 작업에서 배치 렌더러 전체를 새로 구현한 것은 아니다. 현재 발판은 별도 Shadow 등록을 제거한 상태이고, 일반 Render 함수는 그리지 않으므로 Instancing이 꺼졌을 때의 대체 렌더 경로는 없다.

Controller GUI에서는 생성 Queue 길이·예산·Group 수와 Rise·Wave 설정을 확인하고 패턴을 시험할 수 있다. 개별 발판 GUI에는 이동 목표를 조정하는 기능을 두었다. 구간 트리거를 매번 밟지 않고 높이·출발 간격·Bounce·Wave를 조정하기 위한 도구다.

결과와 한계​

사각·원형 배치 데이터를 공통 패턴 시스템으로 제어하고, 실제 Collider가 따라오는 발판으로 연결했다. 생성 완료와 이동 완료를 분리했으며, 줄 단위 콜백으로 외부 사운드 로직을 연결했다. Pool 반환 시에는 Update와 Physics 참여 상태를 함께 정리했다.

현재 구조의 한계도 명확하다.

  • 발판마다 GameObject·Actor·Shape가 남는다. Pool은 반복 생성 비용을 줄이지만 활성 발판의 갱신·Physics 비용을 없애지는 않는다.
  • 초기 Prewarm과 Pool 확장 비용은 별도다. 그룹의 프레임별 배치 예산만으로 초기화 정지를 해결했다고 볼 수 없다.
  • 패턴 실행 중 발판 Handle을 잃으면 FAILED로 전환하지만, 이미 발급한 모든 이동 명령을 취소·롤백하지는 않는다. 재시도·삭제 정책은 호출 측에서 정해야 한다.
  • 그룹 배치는 현재 World XZ 격자 기준이다. 임의 회전 Anchor나 비균일 스케일의 배치·Collider 재생성까지 일반화한 도구는 아니다.
  • Pool 반환은 GameObject 파괴와 다르므로 Handle이 계속 유효할 수 있다. 장시간 지연한 콜백은 객체 존재 여부 외에도 현재 Group 소속·대여 상태가 맞는지 확인할 필요가 있다.

시연에는 사각 길 생성, 중심에서 퍼지는 원형 발판, 높이 차이가 있는 계단, Wave, Group 삭제 후 재사용을 포함할 수 있다. 정량 성능 비교는 현재 소스 확인만으로 주장하지 않고 실제 활성 발판 수·생성 비용·프레임 시간을 측정해 보완할 항목으로 남긴다.

작성 근거와 확인 범위​

핵심 구현은 MyMagicSquareStepController.cpp/.h, MyMagicSquareStep.cpp/.h에 있다. 레벨 배치는 CLevelCharlesRookwood::SpawnMyMagicStepController, 외부 연출 연결 예는 TriggerCRW_SpawnStep 계열에서 확인할 수 있다.

기여 이력은 5c38ee60의 Magic Step 초안, 1f530b6c의 패턴 콜백, 8a5f26a5의 발판 풀링·Shadow 등록 제거 커밋으로 추적할 수 있다. 이후 팀의 Instancing 경로 수정과 구간별 연출 변경은 기반 시스템 및 협업 결과로 구분한다.
