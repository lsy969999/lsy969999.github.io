# 주문 이펙트 구현 — 콘프링고·봄바르다·아바다 케다브라

## 목표와 담당 범위

콘프링고·봄바르다·아바다 케다브라의 이펙트 작업을 하나의 문서로 정리했다. 지팡이에 빛이 모이는 순간부터 발사, 비행 또는 Beam 연결, 충돌·잔류까지 하나의 동작으로 보여야 했다. 파티클을 단독으로 재생하는 것만으로는 부족했다. 캐스팅은 움직이는 지팡이를 따라야 하고, 떨어져 나온 불꽃은 공간에 남아야 하며, 발사 연출이 끝나도 충돌 위치의 잔향은 유지되어야 했다.

팀원이 구축한 Particle·Effect 시스템과 플레이어 Animation·State 구조를 기반으로 세 주문의 연출 데이터를 구성하고, 캐스팅 추적·투사체 이동과 충돌·사운드 및 조명 연결을 구현했다. 아바다 케다브라는 기존 Beam에 전기 다발 모드와 양 끝 테이퍼를 추가했다. 공통으로 필요한 Particle Fade, Trail의 조기 제거 제어, Loop 종료와 Queue 재사용도 보강했다.

초기에는 Player 클래스의 비대화를 줄이기 위해 주문별 Controller로 로직을 분리했다. 이후에는 스킬 State의 Enter·Update·LateUpdate·Exit와 연출 수명주기를 일치시키도록 Controller 로직을 State로 이관했다. 아래 설명은 이관 이후의 소스와 이후 팀 변경이 합쳐진 현재 구조를 기준으로 한다.

## 주문별 표현과 공통 처리

| 주문 | 주요 표현 | 게임 로직과 연결하는 방식 |
| --- | --- | --- |
| 콘프링고 | 지팡이 화염, 떨어지는 불꽃, 화염 투사체와 폭발 | 거리 기반 입자 배치, 곡선 Bullet과 Sphere Sweep |
| 봄바르다 | 전기 Cast Trail, 발사 섬광, 폭발·연기·비산 입자 | Trail 포인트 갱신, 곡선 Bullet과 Sphere Sweep |
| 아바다 케다브라 | 녹색 Cast, 전기 다발 Beam, Impact Arc와 잔류 | 시작점·목표점으로 Beam 생성, 타깃 판정과 지연 Impact |

세 주문 모두 JSON으로 표현을 구성하고 State가 실행 시점을 관리하지만, 이동·충돌 방식까지 같지는 않다. 아래 투사체 절은 콘프링고·봄바르다에 해당하며, 아바다 케다브라는 별도의 Beam 절에서 다룬다. 공통 엔진 확장은 후반부에 모았다.

## 콘프링고·봄바르다: 네 단계로 나누되 수명은 따로 관리

| 단계 | 역할 | 위치와 수명의 기준 |
| --- | --- | --- |
| Cast | 지팡이 끝의 화염·불꽃 또는 전기 궤적 | 스킬 State와 Weapon Socket |
| Muzzle | 발사 순간의 연기·섬광 | 발사 시점의 위치·방향 |
| Projectile | 이동하는 주문 본체와 비행음 | Bullet GameObject |
| Impact | 폭발·비산 입자·충돌음·점조명 | 충돌 위치에 생성되는 독립 연출 |

```text
Skill State
  ├─ Animation Cue → Cast 시작 / Muzzle 재생
  └─ 발사 시점의 시작점·목표점 → Bullet 생성
                                   ├─ FixedUpdate: 경로 이동 + Sphere Sweep
                                   ├─ Effect 위치·비행음 갱신
                                   └─ 충돌: 비행 종료 → 독립 Impact → 지연 파괴
```

Cast가 끝나도 이미 발사한 Bullet은 계속 진행할 수 있다. Bullet이 제거되어도 Impact와 충돌음의 잔향은 끝까지 재생되어야 한다. 이처럼 함께 시작한 연출이라도 종료 조건이 다르므로 하나의 객체 수명에 모두 묶지 않았다.

## Animation Ratio를 한 번만 소비하는 Cue

현재 두 State는 정규화된 Animation Ratio가 임계값을 넘는지를 확인한다. 특정 값과의 동등 비교 대신 `>=` 비교를 사용하고, 실행 여부를 Boolean으로 보관해 같은 Cue가 매 프레임 반복되지 않도록 한다.

| Cue | Confringo | Bombarda |
| --- | --- | --- |
| Cast 시작 | 0.08 | 0.08 |
| 투사체 발사 | 0.28 | 0.28 |
| Recovery 전환 | 0.32 | 0.38 |
| 종료 판단 | 0.45 또는 Animation 종료 | 0.52 또는 Animation 종료 |

프레임 사이에 Ratio가 임계값을 건너뛰어도 Cue를 실행할 수 있다. 이 값은 현재 Animation에 맞춘 조정값이지 모든 주문에 적용하는 규칙은 아니다. 봄바르다는 발사하면서 Cast를 중지하고, 콘프링고의 Cast는 현재 State의 Exit까지 유지하는 차이도 있다.

강제 상태 전환에 대비해 Exit와 Free에서도 Cast를 정리한다. 정상적인 Animation 종료만 정리 경로로 삼으면 피격·취소 등으로 State를 빠져나갈 때 연출이 남을 수 있기 때문이다.

## 붙어 있는 화염과 떨어지는 불꽃을 분리

콘프링고의 Cast는 Flame과 Sparks Queue를 분리했다.

Flame은 처음에 한 번 생성하고 Particle Owner ID를 보관한다. 이후 LateUpdate에서 이전·현재 지팡이 위치의 차이만큼 해당 Owner의 파티클을 이동시킨다. 매 프레임 새 화염을 생성하는 방식에서 발생하던 깜빡임을 줄이고 지팡이 끝에 붙어 있는 빛으로 표현하기 위한 선택이다.

Sparks는 반대로 생성 순간의 World 위치에 남긴다. 지팡이를 따라 기존 불꽃까지 이동시키지 않고, 새로운 위치에 입자를 추가하면서 각 입자가 자기 수명을 소비하도록 한다. Cast 종료 시 Flame은 제거하지만 이미 방출한 Sparks는 자연스럽게 사라진다.

### 빠른 동작에서 비어 보이는 궤적

시간 간격으로 현재 위치에만 입자를 생성하면 지팡이가 빨리 움직일수록 생성 지점 사이가 벌어진다. 생성 횟수만 늘리는 대신 이전 위치들을 저장하고 그 사이에도 입자를 배치했다.

콘프링고는 네 개의 제어점으로 Catmull–Rom 곡선의 가운데 구간을 평가한다. 현재 설정은 0.05초 간격으로 제어점을 갱신하고, 12개 샘플로 구간 길이를 추정한 뒤 약 0.08 간격을 목표로 Queue 생성 횟수를 정한다. 한 번의 처리에서는 최대 16회로 제한한다.

이 방식은 직선으로 이어 붙인 흔적의 각짐을 완화한다. 다만 정확한 호 길이 재매개화는 아니므로 배치 간격이 완전히 균일하지는 않으며, 네 번째 제어점이 필요한 만큼 한 샘플 뒤의 구간을 그린다. 극단적인 이동에서는 생성 상한 때문에 밀도가 떨어질 수 있다.

### 봄바르다의 전기 궤적은 다른 표현

봄바르다는 `Bombarda_Cast_Energy_Trail`에 지팡이 주변의 두 점을 전달하는 별도 Trail 경로를 사용한다. 입자를 띄엄띄엄 배치하는 방식과 달리 폭을 가진 연속 궤적을 만들기 위한 표현이다.

봄바르다는 Update에서도 CastEnd Queue를 생성한다.

## 시작점·목표점으로 만드는 흔들리는 투사체

발사 시 Weapon Socket 위치를 시작점으로 사용하고, 타깃이 있으면 HurtBox 위치를 목표점으로 캡처한다. 타깃이 없으면 플레이어 전방의 일정 거리로 목표점을 정한다. 목표는 발사 시 확정되며 비행 도중 다시 추적하지 않는다.

단순 직선 이동 대신 전진 방향에 수직인 Right·Up 기저를 만들고 두 Sine 파형을 더해 경로를 생성했다. 중심 구간에서 흔들리고 양 끝에서는 원래 위치로 돌아오도록 진폭에 `sin(πt)`를 곱한다.

```text
기준 위치 = Lerp(Start, End, t)
경로 위치 = 기준 위치 + Right 방향 파형 + Up 방향 파형
파형 진폭 = 설정 진폭 × sin(πt)
```

랜덤 위상으로 발사마다 흔들림을 달리하고 첫 점과 마지막 점은 지정한 위치로 고정한다. 현재 기본값은 경로를 64개 선분으로 나누는 것이다. FixedUpdate에서는 `Speed × DeltaTime`만큼의 이동 거리를 소비하며, 선분 하나를 끝내면 남은 거리를 다음 선분에서 이어서 소비한다.

따라서 속도는 경로의 정규화된 진행률이 아니라 실제로 이동하는 선분 길이를 기준으로 한다. 기본 속도는 콘프링고 90, 봄바르다 110이며 모두 조정 가능한 설정값이다.

## 별도 RigidBody 없이 Sphere Sweep으로 충돌 검사

두 Bullet은 자체 RigidBody·Collider를 만들지 않고, 이번 FixedUpdate에서 이동할 구간에 Sphere Sweep을 수행한다. 끝 위치의 Overlap만 확인하면 빠른 이동 중 지나친 얇은 물체를 놓칠 수 있기 때문이다.

한 Tick에서 여러 경로 선분을 통과하면 각각 Sweep한다. 시작점에서 최종 도착점으로 한 번만 검사하면 곡선 안쪽을 가로지르는 다른 경로를 검사하게 되므로, 시각적 이동과 충돌 검사가 같은 선분을 사용하도록 했다.

Query는 World Static·World Dynamic·Enemy Body·Enemy HurtBox를 대상으로 하고, 발사자 Handle은 제외한다. Trigger는 검사하지 않는다. 충돌 상대는 Query에 참여할 Shape가 있어야 하며, Bullet 자체에 물리 Actor가 없다는 뜻이지 상대 Collider까지 필요 없다는 뜻은 아니다.

첫 충돌 이후에는 비행을 종료한다. 충돌 대상의 `CSkillTarget`에 스킬 판정을 전달하는 게임 로직과, 접촉점에서 폭발을 출력하는 연출 로직을 구분했다. 현재 이 Sweep 경로는 첫 충돌 대상의 판정이며, 폭발이 크게 보인다는 이유만으로 같은 크기의 광역 판정이 생기는 것은 아니다.

### 구체 중심과 접촉점을 구분

Sphere Sweep의 이동 거리는 구체 중심을 어디까지 이동시킬지를 결정하고, Hit Position은 실제 접촉 위치를 나타낸다. Bullet의 마지막 이동·잔상에는 구체 중심을, Impact에는 접촉점을 사용한다.

Impact 방향은 Hit Normal을 기준으로 구성한다. 유효한 Normal을 얻지 못하면 진행 방향의 반대쪽을 사용하고, 기준 Up과 평행해지는 경우에는 다른 축으로 기저를 만든다. 콘프링고 Impact 데이터에는 추가 Local Offset도 있으므로 최종 파티클 위치는 접촉점과 완전히 같지는 않다.

## 비행 잔상은 이동 거리 누적 방식

Projectile의 잔상 입자는 본체 Effect와 별개다. 이동한 선분을 따라 일정 거리마다 Trail Queue를 생성하고, 생성 간격에 못 미친 나머지 거리를 다음 선분·Tick으로 넘긴다.

빠른 프레임과 느린 프레임에서도 같은 이동 거리에 비슷한 수의 잔상이 생기도록 하는 방식이다. 콘프링고의 지팡이 Cast에 사용하는 Catmull–Rom 배치와는 별도 알고리즘이며, 두 Bullet 모두 이미 계산한 이동 선분 위에 입자를 놓는다.

현재 기본 간격은 콘프링고 0.32, 봄바르다 0.18이다. 간격을 줄이면 궤적은 촘촘해지지만 생성량과 Overdraw가 증가한다.

## 아바다 케다브라: 이동 궤적 대신 두 지점을 잇는 Beam

아바다 케다브라는 앞선 두 주문의 Bullet을 복제하지 않고 기존 `CBeam_CPU`를 확장했다. Trail이 지나온 위치의 이력을 연결하는 표현이라면, Beam은 지정한 시작점과 끝점 사이의 형상을 만드는 표현이다. 이 코드에서 Beam의 굴곡 자체를 물리적으로 시뮬레이션하지는 않는다.

현재 State는 Cast를 지팡이 행렬로 갱신하고 별도의 Cast Energy Trail을 남긴다. 발사 단계에서는 지팡이 위치와 목표 위치를 구해 `AvadaKedavra_Beam`의 재생 인자로 전달한다. 목표는 몬스터 HurtBox, 일반 스킬 타깃 위치, 객체 위치 순으로 확인하며, 타깃이 없으면 전방 30 지점을 사용한다.

콘프링고·봄바르다와 달리 이 State의 Release 경로에는 이동 Bullet이나 Sphere Sweep이 없다. 발사 시 선택된 `CSkillTarget`에 판정을 전달하고, Impact는 0.05초의 지연 타이머로 출력한다. 따라서 “Beam 선두가 실제 충돌한 순간 Impact를 재생한다”거나 “전기 선분 전체가 충돌 판정이다”라고 설명해서는 안 된다.

### 시각적 끝점과 판정 대상을 분리

현재 `CalculateVisualTargetPosition`은 목표에서 지팡이 쪽으로 끝점을 당긴다. 이동량은 최대 4이며, 가까운 대상에서는 목표 거리의 절반을 넘지 않게 제한한다. Beam과 Impact가 대상 몸 안에 묻히지 않도록 조정하는 시각적 위치이며, 실제 타깃 객체를 바꾸는 처리는 아니다.

발사한 Beam의 시작점·끝점은 Release에서 캡처한다. Cast처럼 매 프레임 지팡이를 따라 행렬을 갱신하는 경로와 구분된다. Beam Manager에 위치 변경 API가 있다고 해서 현재 스킬이 지속적으로 목표를 추적하는 것은 아니다.

### 기존 굴곡 생성기를 재사용한 전기 다발

기존 Beam은 JAGGED와 SINE 형상을 지원했다. JAGGED는 시작점과 끝점을 고정하고, 선분의 중점을 두 수직 방향으로 무작위 변위시킨 뒤 재귀적으로 세분화하는 방식이다. 깊어질수록 진폭에 Damping을 곱한다. 이 굴곡 생성 알고리즘 전체를 새로 작성한 것이 아니라, 이를 재사용하는 `ELECTRIC_BUNDLE = 2` 모드를 추가했다.

전기 다발 모드에서 바꾼 부분은 다음과 같다.

- 기존 거리 비례 진폭 대신 JSON의 `fDisplacementAmplitude`를 사용한다.
- `flickerTimeInverval` 주기마다 굴곡을 다시 생성한다.
- 기존 Beam의 `STRAIGHTEN` 단계를 건너뛰고 Hold·Fade 중에도 굴곡을 유지한다.
- `fSpawnDelay`만큼 경과시간을 음수에서 시작해, 시간차를 둔 Beam 생성을 지원한다.

여기서 다발은 하나의 Beam 인스턴스가 자동으로 여러 갈래로 분기한다는 뜻이 아니다. 확인한 `LSY_AvadaKedavra_Beam_Queue.json`은 GeometryType 2인 Beam 명령 20개를 겹친 구성이다. 비교적 굵고 진폭이 작은 중심 Beam과, 가늘고 진폭·깜빡임 주기·지연이 다른 주변 Beam을 함께 재생한다.

기존 JAGGED·SINE의 진폭 규칙은 유지하고 새 모드만 분기했다. 다른 스킬의 Beam 모양까지 동시에 바꾸지 않기 위한 변경 범위였다.

### 양 끝의 폭과 알파를 줄이는 테이퍼

일정한 폭의 띠는 시작점과 선두가 평평하게 잘린 것처럼 보인다. 이를 완화하기 위해 `StartTaperRatio`와 `EndTaperRatio`를 추가하고, 끝부분에 가까울수록 폭과 알파를 함께 줄였다.

```text
시작 테이퍼 = Smoothstep(0, StartTaperRatio, 구간 진행률)
선두 테이퍼 = Smoothstep(0, EndTaperRatio, 현재 선두 뒤쪽의 정규화 거리)
끝점 계수   = 시작 테이퍼 × 선두 테이퍼
최종 반폭   = 기본 반폭 × 끝점 계수
최종 알파   = 기존 색 알파 × 시간 Fade × 꼬리 알파 × 끝점 계수
```

End Taper의 기준은 항상 최종 목표점이 아니라 성장 중인 현재 선두다. 단위도 초나 월드 거리가 아닌 정규화된 경로 구간이다. Ratio가 0이면 해당 테이퍼 계수를 1로 사용해 기존 표현을 유지한다.

설정은 Beam 파라미터와 인스턴스에 전달하고, Particle Manager의 GUI·JSON 저장·로드 경로에도 연결했다. 새 옵션이 없는 기존 데이터는 기본값 0으로 읽는다.

### Beam 수명은 JSON 값 그대로만 결정되지 않는다

전기 다발도 기존 Grow·Hold·Fade 수명 계산을 공유한다. 현재 `AddBeam`은 시작점과 끝점 거리에서 `거리 / 100`으로 Grow 시간을 계산하고, JSON의 단계 간 시간 차이를 더해 이후 단계와 전체 수명을 구성한다.

Flicker는 굴곡 재생성 주기이지 파티클을 새로 생성하는 주기가 아니다. 현재 Update는 타이머가 만료되면 한 번 갱신하므로 큰 Delta에서 놓친 모든 Flicker 횟수를 반복해서 따라잡는 방식도 아니다.

### Impact Arc와 잔류는 별도 연출

Impact 위치에서는 `AvadaKedavra_Impact`, `AvadaKedavra_Residue`와 12개의 Arc를 별도로 재생한다. Arc는 중심에서 서로 다른 오프셋을 끝점으로 삼고, Early·Mid·Late Effect 프리셋으로 시간차를 준다. 확인한 JSON의 명령 지연은 각각 0, 0.18, 0.38초다.

이는 State가 매 프레임 무작위 방향의 전기를 계속 생성하는 방식이 아니다. 현재 오프셋 배열은 고정되어 있고, 각 Beam 내부의 굴곡이 무작위로 갱신된다. 게임 로직의 타깃 판정과 이 주변 Arc들의 시각적 확산은 별개다.

Cast와 Beam의 Effect ID는 따로 보관하고 Stop 전에 무효화한다. State Exit·Free에서는 둘을 정리하고 미실행 Impact 예약도 취소한다. 이미 재생한 Impact·Residue는 별도 Effect 수명으로 진행한다. 현재 Cast와 Beam의 종료 콜백에는 `this` 캡처가 있으므로 State 수명과 명시적인 종료 처리에 의존한다.

현재 통합 코드에는 Beam 재생 중 망토에 외부 바람을 갱신하고 종료 시 제거하는 연결도 있다. 이는 Beam 형상 계산과 분리된 연출 연동이다. 얼굴 Animation·Morph와 Cinematic 코드도 함께 존재하지만, 해당 시스템 전체를 이 이펙트 작업의 단독 구현 범위에 포함하지 않는다.

## 공통 엔진 확장: Particle Fade와 Trail 제거를 구분

### CPU 파티클의 수명 기반 Fade

입자의 위치·형상만 맞춰도 수명이 끝나는 순간 알파가 그대로면 갑자기 사라져 보인다. `BEHAVIOR_FADEOUT`과 `BEHAVIOR_FADEOUT_LATE`를 추가해 최초 알파를 기준으로 시간에 따라 감소시키도록 했다.

| 옵션 | 감소 방식 | 수명 1초일 때 |
| --- | --- | --- |
| FadeOut | 정규화 수명 전체에서 최초 알파부터 0까지 선형 감소 | 생성 직후부터 1초까지 감소 |
| FadeOutLate | 수명의 58%까지 최초 알파 유지, 나머지 구간에서 Smoothstep 감소 | 0.58초까지 유지, 이후 0.42초 동안 감소 |

현재 남은 알파에 매 프레임 계수를 곱하는 방식이 아니라 `fStartAlpha`와 정규화된 경과시간으로 계산한다. 두 플래그를 함께 켜면 Late 분기가 우선한다. 이 비율은 현재 CPU 구현의 상수이며 GUI에서 임의의 Fade 시작 비율을 지정하는 기능은 아니다.

이 처리는 특정 Pattern 전용이 아니다. Standard든 Pattern이든 CPU 파티클 생성 데이터에 해당 Behavior가 전달되면 같은 처리 경로를 사용한다. 다만 이를 GPU·Mesh·Beam·Trail을 포함한 모든 종류의 공통 Fade API라고 일반화하지는 않는다.

### Trail은 포인트를 너무 일찍 지우지 않도록

봄바르다 Cast Trail은 포인트 수명에 따른 알파 감소가 끝나기 전에 Idle Retract가 오래된 포인트를 먼저 제거해, 꼬리가 툭툭 끊기는 문제가 있었다. 셰이더 알파만 조정해도 CPU에서 이미 제거한 형상은 복원할 수 없다.

`bIdleRetractEnabled`를 추가해 기존 기본값 true는 유지하고, 비활성화한 Trail은 Idle 시간에 의한 조기 제거를 건너뛰도록 했다. 포인트는 `fMaxDuration`에 도달할 때 정상 제거되므로 무한히 남는 옵션이 아니다. 현재 CPU는 포인트 나이에서 남은 수명 계수를 계산해 정점 알파에 반영한다.

`bShrinkWidth`는 별도 옵션이다. 켜면 같은 수명 계수로 폭도 줄어든다. 알파가 사라지는 시간, 폭의 감소, 실제 포인트 제거 시점을 구분해서 조절해야 한다. 이 보강은 Trail 시스템 전체를 새로 작성한 것이 아니라 기존 제거 정책을 선택 가능하게 만든 작업이다.

### Cone을 순간 방출에서 연속 분사로 확장

머즐의 원뿔 연기와 불꽃을 한 번에 내보내는 대신 짧은 시간 동안 이어서 발사할 수 있도록 Cone 파라미터에 시작 지연과 입자별 간격을 추가했다. 생성 시 각 입자의 지연을 `fSpawnDelay + 입자 인덱스 × fSpawnInterval`로 계산한다.

Loop와는 다르다. 한 명령 안의 유한한 입자를 시간차로 내보내는 방식이며, 개수·간격을 크게 설정하면 마지막 입자가 나타나는 시점도 뒤로 밀린다. Effect의 수명 계산과 Owner 정리 역시 이런 대기 항목을 고려해야 한다.

## JSON은 표현을, C++은 실행 시점과 소유권을 담당

| 데이터 | 담당 내용 |
| --- | --- |
| ParticleData | 텍스처·셰이더·파티클 종류·최대 개수 등 리소스 설정 |
| ParticleQueue | Standard·Pattern별 수명·크기·색·속도·지연 등 생성 명령 |
| Effect | Queue·Light·Sound 명령을 묶는 연출 프리셋 |
| Skill State / Bullet | 재생 시점·위치·충돌 처리·중지 조건 |

GUI에서 먼저 단독 재생하고, 이후 JSON 수치를 조정하면서 실제 지팡이와 Bullet에 연결해 확인했다. 콘프링고는 화염과 불꽃, 봄바르다는 섬광·전기·연기·비산 입자를 조합하되 색·수명·생성 지연을 따로 조정했다.

아바다 케다브라는 Cast·Release·Beam·Impact·Residue와 Arc 프리셋으로 나눴다. 확인한 `AvadaKedavra_Beam.json`은 Particle Queue 명령만 포함한다. 세 주문의 모든 Effect가 Particle·Light·Sound를 전부 포함한다고 가정하지 않고, 실제 JSON 명령과 State의 별도 사운드 호출을 함께 확인한다.

현재 비행 Effect 이름은 `Confringo_Projectile`, `Bombarda_Projectile`이며 Particle과 Light 명령을 포함한다. 충돌 Effect는 콘프링고가 `Confringo_Impact`를 사용한다. 봄바르다는 이후 합쳐진 코드의 기본값이 `BombardaImapact`이므로, 초기 제작한 `Bombarda_Impact.json`만 수정해서는 현재 기본 충돌 연출이 바뀌지 않는다. 파일의 존재와 실제 참조를 구분해야 하는 사례다.

발사 연기도 Queue 고유의 축을 확인해야 한다. 콘프링고 Muzzle은 해당 데이터의 방향 규칙에 맞춰 Bullet의 초기 진행 방향을 반전한 기저를 사용한다. 모든 Queue에 같은 회전값을 일괄 적용하는 방식이 아니라, 생성 패턴의 로컬 축과 실제 발사 방향을 맞춘 것이다.

## 종료 후 다시 나타나는 Loop 파티클 처리

비행 Effect를 멈췄는데도 입자가 남거나 다시 나타나는 문제는 화면에 보이는 입자만 지워서는 해결되지 않았다. Effect가 생성한 Particle Owner를 기준으로 다음 세 상태를 함께 정리하도록 보강했다.

1. 이미 생성되어 살아 있는 파티클
2. SpawnDelay를 기다리는 생성 예약
3. 이후 재생성할 Loop Request

`StopEffect`는 인스턴스에 기록된 Owner들을 `ClearByOwner`로 정리하고, 연결된 Light와 Sound도 중지한다. Particle Manager는 활성 입자뿐 아니라 Owner의 대기 생성 항목과 Loop Request까지 제거한다.

Loop를 발견하면 수명 계산 중 즉시 반환하던 경로도 수정했다. 무한 수명 여부만 기록하고 실제 Spawn과 Owner 등록까지 진행해야, Effect ID만 생기고 파티클은 생성되지 않는 상태를 피할 수 있다. 유한 수명 계산에는 생성 지연·입자별 생성 간격·입자 수명을 반영한다.

Bullet에서는 Effect ID를 먼저 무효화한 뒤 Stop을 호출한다. Stop에서 종료 콜백이 실행될 수 있기 때문이다. 비행 Effect의 콜백은 Bullet Handle로 객체를 다시 조회하고 현재 Effect ID와 일치할 때만 값을 정리한다. 다만 봄바르다 State의 Cast 콜백은 현재 `this`를 캡처하므로, 모든 콜백이 Handle 기반인 것은 아니며 State의 Exit·Free 정리 규칙에 의존한다.

## 객체보다 오래 남는 소리와 빛

영창은 Voice 채널의 2D 사운드로, Muzzle과 비행음은 위치를 가진 3D 사운드로 연결했다. Bullet의 비행음은 Component Slot으로 관리해 위치를 갱신하고 충돌·시간 초과·Free에서 중지한다.

Impact Main·Tail과 봄바르다의 Low 레이어는 Sound Manager의 독립적인 3D One-shot으로 재생한다. Bullet이 PendingDestroy되어도 폭발음과 잔향을 끊지 않기 위해서다. 충돌 Effect도 Bullet에 붙이지 않고 별도 위치에서 재생한다.

비행 Effect는 GameObject Manager 등록 후의 `OnRegisteredToManager`에서 시작한다. 초기화 도중 아직 조회할 수 없는 Handle을 종료 콜백에 넘기는 문제를 피하고, 관리 가능한 객체가 된 뒤 외부 연출을 시작하는 경계로 사용했다.

## 반복 재생 비용과 시각적 문제를 구분

Effect 실행 시 Queue를 매번 파일에서 파싱하는 대신 Particle Manager의 `FindCachedCommandQueue`로 이미 파싱한 명령을 찾도록 했다. 콘프링고 Cast도 Queue를 재사용한다. 봄바르다 Cast의 일부 데이터는 첫 준비 때 파싱해 보관한다. 캐시에서 찾지 못하면 생성하지 않으므로 사전 로드와 이름 일치가 필요하다.

이 변경은 반복 파일 읽기·파싱 비용을 줄이는 것이지, 파티클 생성·갱신·반투명 Overdraw까지 없애는 최적화는 아니다. 실제 튜닝에서도 다음 문제를 구분했다.

- 궤적이 비는 문제: 시간 기준 방출과 이동 거리를 확인하고 중간 지점을 보충한다.
- 밝은 화염이 흰색·분홍색으로 보이는 문제: Additive 중첩, 텍스처, 색과 Emissive를 함께 조정한다.
- 연기가 전기 표현을 가리는 문제: 크기·알파·공간 배치와 생성 지연을 조정한다.
- 잔상이 오래 남는 문제: 생성 중지, 입자·Trail 수명, 실제 제거 시점을 따로 확인한다.

콘프링고·봄바르다는 Animation Cue, 지팡이 Cast, 곡선 Bullet, Sphere Sweep, Impact·사운드·조명까지 연결했다. 아바다 케다브라는 기존 Beam의 굴곡 생성기를 재사용하면서 전기 다발·양 끝 테이퍼·시간차 Arc를 더했다. 핵심은 개별 연출의 화려함보다 위치를 결정하는 주체와 종료 책임을 단계별로 나눈 것이다. 거리 기반 배치로 빈 궤적을 보완하고, Owner 단위 정리로 중지 후 지연·Loop 생성이 남지 않도록 했다.

Bullet은 발사 시 정한 목표까지 곡선 경로를 선분으로 나누어 이동한다. 아바다 케다브라의 Beam은 시전자와 타깃을 잇는 시각적 형상으로 사용한다.
