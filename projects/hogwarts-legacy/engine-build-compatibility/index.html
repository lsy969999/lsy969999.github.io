종료 크래시 조사에서 DLL 빌드 구성 조기 검증까지

문제: 게임은 실행되지만 종료할 때 크래시​

Release 실행을 종료하는 과정에서 CSoundManager::Free가 재생 중인 사운드 목록을 비우다가 접근 위반이 발생했다. 당시 보고된 스택을 핵심 경로로 정리하면 다음과 같다.

Plain Text
CGameInstance::Release_Engine
  → CSoundManager::Free
  → 재생 목록 clear
  → SPlayingSound 소멸자
  → shared_ptr<char[]> 소멸 / 참조 카운트 감소
  → 접근 위반

디버거에서는 sBusID.owned_str._Rep가 0x6D8000006D74로 표시되었다. 사운드 버스 ID는 StringID이며, 문자열을 소유하는 구성에서는 내부에 shared_ptr<char[]>를 가진다. 따라서 사운드 목록의 요소를 지우는 과정에서 버스 ID의 문자열 소유권도 정리된다.

확인한 사실과 남아 있는 가설​

당시 확인 내용은 다음과 같이 구분했다.

종료 중 사운드 목록의 공유 포인터를 정리하는 지점에서 접근 위반이 발생했다. 전체 재빌드 후에는 같은 오류가 재현되지 않아 Client와 Engine의 빌드 구성을 확인할 장치를 추가했다.

유효하지 않은 내부 포인터는 객체 상태가 정상적으로 해석되지 않는다는 단서다. 이전의 잘못된 쓰기, 수명 종료 후 접근, 중복 해제, 서로 다른 레이아웃 해석 등 여러 원인이 가능하다. 특정 주소 값 하나가 Debug/Release 혼용을 증명하지는 않는다.

사운드의 정상적인 소유권과 종료 처리는 사운드 수명 관리에서 별도로 설명한다.

DLL이 다르면 왜 문제가 될 수 있는가​

DLL 파일이 다르다는 사실 자체가 메모리 손상을 의미하지는 않는다. 문제는 경계를 넘는 데이터에 대해 양쪽 바이너리가 같은 약속을 따르는지다. 이 약속에는 객체 레이아웃, 함수 호출 방식, 메모리 소유권과 해제 규칙 등이 포함되며 이를 ABI 관점에서 확인해야 한다.

예를 들어 한쪽은 구조체의 특정 위치를 포인터로 읽는데 다른 쪽은 그 위치를 다른 멤버로 해석하면, 정상적으로 저장한 값도 잘못된 포인터처럼 읽힐 수 있다. 프로젝트의 StringID 역시 조건부 컴파일로 문자열 관련 멤버의 포함 여부가 달라질 수 있으므로 공개 타입의 구성 일치가 중요하다.

표준 라이브러리 설정도 점검 대상이다. MSVC의 _ITERATOR_DEBUG_LEVEL 기본값은 Debug에서 2, Release에서 0으로 다르다. Debug/Release를 단지 최적화 유무로만 취급하지 않고, 경계에서 사용하는 타입과 빌드 설정을 함께 확인해야 한다. Microsoft의 설정 설명

또 다른 위험은 메모리를 할당한 CRT와 해제하는 CRT가 다른 경우다. DLL 경계에서 메모리 소유권을 넘길 때는 사용하는 런타임과 해제 주체도 맞춰야 한다. 단순히 DLL을 사용한다는 이유로 문제가 생기는 것은 아니다. Microsoft의 CRT 경계 오류 설명

대응: 초기화 전에 빌드 서명 비교​

Engine DLL이 자신이 컴파일된 구성을 반환하도록 하고, 실행 파일은 자신의 컴파일 시점 기대값과 비교하도록 만들었다. 서명에는 두 값만 담는다.

Plain Text
64비트 Build Signature
상위 32비트: ENGINE_ABI_VERSION
하위 32비트: DEBUG(1) 또는 RELEASE(2)

여기서 서명은 암호학적 서명이나 DLL 파일 해시가 아니다. 구성과 버전을 묶은 식별값이다. 현재 ABI 버전은 1이며, 공개 ABI에 영향을 주는 변경이 생기면 개발자가 직접 올리는 방식이다.

실제 조합 함수는 다음과 같다.

Engine_BuildConfig.h
constexpr std::uint64_t MakeEngineBuildSignature(
    std::uint32_t iABIVersion,
    ENGINE_BUILD_CONFIGURATION eConfiguration) noexcept
{
    return (static_cast<std::uint64_t>(iABIVersion) << 32) |
        static_cast<std::uint32_t>(eConfiguration);
}

CURRENT_BUILD_CONFIGURATION은 각 모듈을 컴파일할 때 _DEBUG 유무로 결정한다. 따라서 DLL이 반환하는 값은 Engine의 구성이고, Client의 EXPECTED_ENGINE_BUILD_SIGNATURE는 Client가 사용한 헤더와 구성에 따른 값이다.

DLL 쪽 값을 실행 파일의 기대값으로 대신 사용하면 자기 자신과 비교하는 검사가 된다. 기대값은 호출자에, 실제값을 반환하는 구현은 Engine DLL에 두는 구분이 중요했다.

검증 함수는 왜 C ABI로 노출했는가​

불일치 여부를 확인하는 함수부터 복잡한 C++ 객체를 넘기면, 검증에 앞서 동일한 경계 문제에 의존하게 된다. 그래서 인자는 없고 고정 폭 정수만 반환하는 함수로 만들었다.

Engine_BuildConfig.cpp
extern "C" ENGINE_DLL std::uint64_t Engine_GetBuildSignature() noexcept
{
    return Engine::EXPECTED_ENGINE_BUILD_SIGNATURE;
}

ENGINE_DLL은 Engine에서는 export, 호출하는 쪽에서는 import로 확장된다. extern "C"로 C 언어 연결을 지정하고, std::string이나 컨테이너·스마트 포인터를 반환하지 않는다. 이 호출에는 DLL 경계를 넘는 동적 메모리 소유권 이전도 없다.

이는 검사 인터페이스의 의존성을 줄인 선택이지, extern "C"가 모든 ABI 문제를 해결한다는 뜻은 아니다. 플랫폼과 호출 규약 등 기본 조건은 여전히 맞아야 한다.

호출 시점과 실패 처리​

Client와 MapEditor 모두 wWinMain의 첫 문장에서 ValidateEngineBuildCompatibility를 호출한다. 창 생성과 CMainApp::Create보다 먼저 실행되므로, 일반적인 엔진 초기화와 Manager 생성에 진입하기 전에 비교할 수 있다. SampleClient에는 적용하지 않았다.

비교가 일치하면 그대로 진행한다. 불일치하면 MessageBoxW에 Client와 Engine 각각의 구성·ABI 버전, 동일 구성으로 다시 빌드하라는 안내를 표시한 뒤 RaiseFailFastException을 호출한다.

일반 오류처럼 복구해 계속 실행하는 대신, 호환성 전제가 깨진 프로세스를 종료하도록 선택했다. 이 함수는 예외 처리기를 우회하는 Fail Fast 경로이므로 정상적인 스택 해제와 종료 루틴을 수행하는 용도로 사용하지 않는다. Microsoft의 Fail Fast 설명

DLL 로드 이후, 애플리케이션 초기화에 들어가기 전에 빌드 구성을 비교한다.

검출 범위와 한계​

상황현재 동작 또는 한계
Debug Client와 Release Engine서명 불일치로 중단한다.
같은 구성이지만 ABI 버전이 다름서명 불일치로 중단한다.
같은 구성·같은 ABI 버전의 오래된 DLL통과한다. 파일 버전이나 커밋을 비교하지 않는다.
공개 타입이 바뀌었지만 ABI 버전을 올리지 않음자동 검출하지 못한다.
CRT 옵션·타입 구성 매크로만 달라짐현재 서명에 해당 값이 없으므로 직접 검출하지 못한다.
검증 함수 export가 없는 오래된 DLL일반 import 기준으로 로더 단계에서 실패할 수 있어 자체 메시지까지 도달하지 못한다.
정상 구성에서 발생한 잘못된 메모리 쓰기이 검증의 대상이 아니다.

결과와 담당 범위​

기존에는 빌드 조합이 맞는지 애플리케이션에서 확인하지 않았다. 구성 서명 export와 호출자 측 검사를 추가하면서, 검출 가능한 불일치는 게임 실행 후의 불명확한 증상 대신 시작 시점의 명시적인 오류로 바꿀 수 있게 했다.

Engine에 빌드 서명 API를 추가하고 Client와 MapEditor의 진입점에서 검사하도록 연결했다. 빌드 구성 불일치를 초기에 차단하는 장치이며, 실행 중 잘못된 메모리 접근까지 막는 기능은 아니다.

빌드와 배포 구성의 전체 맥락은 vcpkg와 서드파티 의존성 관리에 정리했다.
