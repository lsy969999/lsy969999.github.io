# 블록 공급·점수 계산과 배틀 공격 큐

## 보드 판정을 한 판의 게임으로 연결하기

Rust 보드 코어가 이동·회전·줄 제거의 타일 판정을 담당한다면, 상위 게임 로직은 다음 블록을 공급하고 홀드를 제한하며 점수를 계산한다. 배틀에서는 이 결과를 공격 이벤트로 해석해 다른 참가자의 보드에 전달한다.

클라이언트의 `TetrisBoard`에 진행 정책을 구성하고, `Controller`를 통해 보드 변경과 WebSocket 액션 송신을 연결했다. 서버는 배틀 공격 대상과 대기 큐를 관리한다. 이 글은 보드 판정이나 메시지 직렬화 자체보다 그 사이의 게임 규칙을 다룬다.

## 7-bag와 Next 공급

`getTetriminoFromSevenBag()`은 저장된 블록이 없을 때 I·O·T·J·L·S·Z 목록을 만든다. 남은 목록에서 무작위 인덱스를 골라 하나씩 제거하며 새 순서를 구성하고, 이후에는 앞에서 하나씩 꺼낸다. 한 묶음 안에서 일곱 종류를 각각 한 번 공급하는 방식이다.

클라이언트 난수는 `Math.random()`을 사용한다. 시드와 난수 상태를 공유하는 재현 가능한 블록 공급 시스템까지 구현한 것은 아니다. 멀티플레이에서는 생성·Next 변경 액션을 전달하는 경로와 함께 이해해야 한다.

초기 Next는 다섯 개를 준비한다. `spawnFromNext()`는 다음 순서로 진행한다.

1. `shiftNext()`로 맨 앞 종류를 꺼낸다.
2. 생성 계획의 각 위치가 빈 칸인지 확인한다.
3. 생성 가능한 경우 낙하 블록을 배치한다.
4. 7-bag에서 하나를 받아 Next 뒤에 보충한다.

생성 검사는 `trySpawnFalling()`이 반환한 위치와 현재 보드를 비교하는 상위 로직이다. 실패를 반환하면 ticker에서 보드 종료를 요청한다. 다음 블록이 생성된 뒤 `stepTick`을 크게 설정해 다음 진행 tick에서 낙하 처리가 일어나도록 한다.

## Hold는 고정 전까지 한 번만

`actHold()`는 보드 활성 상태, 낙하 블록 존재 여부, `isCanHold`를 검사한다. 홀드를 사용하면 즉시 재사용을 막고, `placing()`에서 블록 고정 처리를 마친 뒤 다시 허용한다.

기존 Hold가 있으면 현재 종류를 저장하고 낙하 블록을 제거한 다음 보관된 종류를 생성한다. Hold가 비어 있으면 현재 종류를 저장하고 낙하 블록만 제거한다. 비어 있는 낙하 상태는 다음 ticker에서 감지해 Next를 공급한다.

다만 기존 Hold와 교환할 때는 `spawnFromNext()`의 생성 가능 여부 검사 함수를 통과하지 않고 `ctrl.spawn()`을 직접 호출한다. 일반 Next 생성과 홀드 교환의 게임 오버 검사 경계가 같다고 설명하지 않는다.

## 고정·줄 제거·점수 갱신의 순서

`placing()`은 다음 과정을 하나의 진행 단계로 묶는다.

```text
낙하 블록 고정
  → 제거 가능한 줄 수 조회
  → 누적 줄 수·레벨·콤보 갱신
  → 실제 줄 제거
  → 줄 수와 T-Spin 상태로 점수 종류 결정
  → 총점 갱신 및 SetInfo 전달
  → Hold 재허용·T-Spin 상태 초기화
```

초기 레벨은 1이며, 누적 10줄마다 한 단계 올라가 최대 20으로 제한한다. 레벨을 갱신한 뒤 점수 계산에 사용하므로, 레벨 경계를 넘기는 줄 제거에는 갱신된 레벨 배율이 적용된다.

기본 점수는 상수 표로 관리한다.

| 점수 종류 | 기본 점수 | 배틀 기본 공격 줄 수 |
| --- | ---: | ---: |
| Single | 100 | 없음 |
| Double | 300 | 1 |
| Triple | 500 | 2 |
| Tetris | 800 | 4 |
| TSpinZero | 400 | 없음 |
| TSpinSingle | 800 | 2 |
| TSpinDouble | 1200 | 4 |
| TSpinTriple | 1600 | 6 |

점수 이벤트가 있으면 `기본 점수 × 현재 레벨 + 200 × 콤보`를 더한다. 점수와 공격 표는 서로 다른 정책이다. 공격 줄 수에는 위 점수 배율이나 콤보 값을 곱하지 않는다. 클라이언트에도 `attckLine` 표가 있지만, 실제 배틀 송신량은 서버의 `attack_line()`이 결정한다.

소프트 드롭은 한 칸 이동에 성공하면 1점을 더한다. 하드 드롭은 코어 반환 카운트에 2를 곱하고 즉시 고정·줄 제거를 진행한다. 현재 코어의 카운트에는 마지막 실패 시도가 포함되므로 정확한 이동 칸 수와 같지 않다는 한계는 보드 테스트 문서에서 다뤘다. 여기서도 이를 정확한 거리 기반 점수가 검증된 상태로 표현하지 않는다.

## 콤보는 시간 제한 기반

줄을 지웠을 때 `comboTick`이 남아 있으면 콤보를 증가시키고, 유지 시간을 150 tick으로 다시 설정한다. ticker가 이를 감소시키고 만료 후 콤보를 0으로 만든다. 60Hz 진행 기준으로 약 2.5초의 유지 구간이다.

줄을 지우지 않은 블록을 고정했다고 즉시 콤보를 끊지는 않는다. 유지 시간이 남아 있는 동안 다시 줄을 지우면 이어진다. 따라서 현재 구현은 시간 내 줄 제거를 연결하는 방식이며, 매 블록의 연속 줄 제거 여부만 검사하는 규칙으로 설명하면 부정확하다.

## T-Spin 판정의 구현 범위

회전에 성공하면 `tSpinCheck()`를 호출한다. T 블록의 내부 타일 ID 2를 중심으로 네 대각선 위치를 검사하고, 고정 타일 또는 코드가 벽으로 처리하는 위치가 세 곳 이상이면 T-Spin 플래그를 설정한다. 이후 고정 시 제거한 줄 수와 조합해 점수 종류를 선택한다.

현재 구현에는 다음과 같은 경계가 있다.

- 회전 이후 좌우 이동·낙하에서 해당 플래그를 다시 계산하거나 해제하는 처리가 없다.
- 코너 검사 조건은 보드의 최대 X·Y만 비교하고 음수 좌표를 명시적으로 제외하지 않는다.
- Mini 구분이나 마지막 회전의 벽 킥 후보를 활용하는 세부 판정은 포함하지 않는다.

따라서 T 블록의 회전 결과를 점수 이벤트에 연결한 구현으로 설명하고, 모든 세부 규칙을 완성한 판정이라고 주장하지 않는다.

## ScoreEffect를 배틀 공격으로 해석하기

고정 처리에서 점수 종류가 반환되면 `ctrl.scoreEffect(kind, combo)`가 로컬 텍스트 효과를 표시하고 같은 정보를 서버에 보낸다. 서버는 `MultiBattle`일 때만 문자열을 점수 종류로 해석해 공격 표를 조회한다.

공격량이 있으면 자신을 제외하고 종료되지 않은 보드 중 한 곳을 무작위로 선택한다. 그 보드에 공격자 식별값·줄 수·수신 tick·`Queued` 상태를 가진 항목을 추가하고, 큐 변경 액션을 전달한다. 모든 상대에게 동시에 공격하는 방식은 아니다.

`ScoreEffect`라는 이름이지만 현재는 시각 효과뿐 아니라 배틀 규칙의 입력 역할도 한다. 서버가 클라이언트의 점수 종류를 받아 공격을 발생시키므로, 서버가 보드에서 T-Spin·줄 제거 결과를 독립적으로 다시 판정해 검증하는 구조는 아니다. 점수 무결성을 강화하려면 표시 이벤트와 검증된 게임 결과를 구분할 필요가 있다.

## 공격 대기·상쇄·실제 적용

공격 큐의 상태는 `Queued → Ready`로 바뀐다. 서버가 수신 tick보다 180 tick을 초과해 진행하면 Ready로 전환하므로, 정상적인 60Hz 진행에서는 약 3초 뒤 적용 가능한 상태가 된다. Ready가 되는 즉시 타일을 올리는 것은 아니다.

실제 소비는 서버의 `line_clear()`에서 `garbage_add(clear_len)`를 호출할 때 처리한다. 이 호출은 고정 후 줄 제거 단계에 있으며, 실제로 지운 줄이 0개인 경우도 포함한다.

먼저 이번에 제거한 줄 수만큼 큐 앞에서부터 공격 줄을 차감한다. 이 상쇄 단계는 Queued와 Ready를 구분하지 않는다. 이어서 앞쪽의 Ready 항목들을 꺼내 실제로 올릴 쓰레기 줄 목록을 만든다. 아직 Queued인 항목을 만나면 멈춘다.

예를 들어 4줄짜리 Ready 공격을 받은 상태에서 2줄을 제거하면 2줄을 상쇄하고 나머지 2줄이 적용 대상으로 남는다. 같은 공격이 아직 Queued라면 남은 2줄은 대기 큐에 유지한다. 이는 제거 줄 수 기준의 방어 상쇄이며, 별도로 발생하는 점수 종류별 공격량과 같은 계산이 아니다.

구멍의 X 위치는 큐 항목마다 무작위로 고르고, 그 항목의 여러 줄은 같은 구멍 위치를 사용한다. 만들어진 위치 목록은 `DoGarbageAdd` 액션으로 전달한다.

```text
서버: Ready 큐 소비·구멍 위치 결정
  → DoGarbageAdd 수신
  → 클라이언트: pushGarbageLine으로 보드 적용
  → 내 보드의 Controller: AddGarbageQueue 송신
  → 서버: 같은 구멍 위치로 자신의 보드에 적용
```

상대 보드 표시에도 같은 적용 액션을 전달하지만 로컬 플레이어 보드에 연결된 송신기가 서버에 결과를 돌려보낸다. 클라이언트에서 쓰레기 줄 추가에 실패하면 보드 종료를 요청한다. 서버의 해당 추가 함수는 실패 반환값에 대해 별도 종료 처리를 하지 않으므로, 공격 적용과 종료 판정이 완전히 서버에서 확정되는 방식은 아니다.

## 결과와 한계 {/* #구현-결과와-후속-보강 */}

블록 공급·홀드 제한·줄 제거·점수 표시를 한 판의 진행으로 연결하고, 같은 점수 이벤트를 배틀 공격 큐로 확장했다. 공격을 바로 타일 변경으로 처리하지 않고 대기·상쇄·적용 단계로 나눠 방어할 시간과 큐 표시를 마련했다.

후속 보강은 시드 기반 블록 공급, Next와 Hold 생성 검사의 통일, T-Spin 상태 수명, 하드 드롭 카운트 계약, 서버의 점수·공격 검증으로 구분할 수 있다. 이는 현재 코드에서 확인한 개선 경계이며, 이번 문서 작업에서 게임 코드를 수정한 것은 아니다.
