# Rust 인증 API·WebSocket 서버 분리와 배포 구성

## 웹에서 접속해 게임에 들어가기까지

게임 규칙과 렌더링 외에도 브라우저 접속, 사용자 식별, 토큰 갱신, 실시간 연결, 실행 파일 배포가 필요했다. Rust workspace에서 HTTP API와 WebSocket 서버를 나누고, 인증·DB 접근·공통 DTO를 `common`에 모아 사용했다.

현재 일반 화면의 주 경로는 닉네임을 입력하는 게스트 로그인이다. 이메일·Google OAuth 서버 코드도 존재하지만 화면 연결과 토큰 전달 방식까지 동일하게 완성된 기능으로 묶지 않는다. 이 문서는 실제 연결된 경로와 준비·실험 단계의 코드를 구분한다.

## API·실시간 게임·공통 코어의 역할

| 구성 | 현재 역할 |
| --- | --- |
| `api` | Axum HTTP 라우터, 로그인·토큰 갱신·사용자 조회 |
| `ws` | WebSocket 연결, 인증된 연결과 사용자 매핑, 로비·방·게임 상태 |
| `common` | JWT, DB 연결 풀·추출기, 사용자·세션·게임 백업 저장소, DTO·오류 처리 |
| `tetris-lib` | 서버와 WASM 웹이 공유하는 보드 규칙 |
| `front` | React 화면, 사용자 인증 상태, WASM 게임과 WebSocket 송수신 |

API는 4000, WebSocket 서버는 4001 포트로 구성한다. 별도 실행 파일이므로 각 프로세스가 공통 코드를 링크하고 자신의 연결 풀을 생성한다. `common`이라는 crate를 공유한다고 런타임 메모리나 연결 풀 하나를 두 프로세스가 공유하는 것은 아니다.

PostgreSQL에는 사용자·세션과 종료 게임 백업을 저장한다. 진행 중인 방과 게임 상태는 WebSocket 서버의 인메모리 world에 있다. HTTP 처리와 실시간 게임 처리의 책임을 나눈 것이며, 여러 WebSocket 서버가 하나의 world를 공유하는 분산 구성은 아니다.

## 게스트 로그인과 DB 세션 등록

게스트 로그인 요청은 닉네임 검증 후 DB 트랜잭션 안에서 사용자와 세션을 생성한다. 사용자 ID를 만들고 access token과 refresh token을 발급하며, refresh token의 `jti`를 세션 ID로 사용한다. 세션에는 사용자 ID·User-Agent·IP·만료 시간을 기록한다.

```text
닉네임 입력
  → POST /api/auth/guest/login
  → 사용자·세션 생성 후 트랜잭션 commit
  → accessToken + refreshToken 응답
  → 웹 인증 store 저장·사용자 조회
  → WebSocket userLogin 전송
```

현재 게스트 경로는 두 토큰을 JSON 응답으로 전달한다. 프런트엔드의 Zustand persist store는 사용자 정보와 두 토큰을 저장 대상으로 지정한다. 쿠키만으로 인증 상태를 유지하는 방식과 구분하며, JavaScript에서 접근 가능한 토큰 저장이라는 보안 경계를 가진다.

`HomePage`는 토큰 저장 뒤 사용자 정보를 조회하고, access token을 담은 `userLogin` 메시지를 WebSocket에 보낸다. HTTP 로그인 성공과 실시간 연결의 사용자 인증을 명시적으로 연결한 부분이다.

## access token과 refresh token의 역할

JWT access claim에는 사용자 식별자인 `sub`, 발급 시각, 만료 시각을 담는다. refresh claim에는 세션을 식별하는 `jti`가 추가된다. 두 종류의 토큰은 각각의 키 설정을 사용하고 검증은 `jsonwebtoken`에 위임한다. 실제 비밀키나 설정값은 문서에 포함하지 않는다.

HTTP 보호 경로는 `CheckAccessToken` 추출기를 통해 Authorization Bearer를 읽고 토큰을 검증한다. 선택형 추출기도 있어, 해당 구현에서는 인증 추출 실패를 `None`으로 바꾼다. 이 선택형 경로를 사용하는 핸들러는 미인증 상태의 허용 범위를 별도로 결정해야 한다.

클라이언트의 `beforeTokenCheckAndRefresh()`는 저장된 access token의 만료 여부를 보고 필요할 때 refresh token을 Bearer로 전송한다. 서버는 refresh token을 검증한 뒤 `jti`에 대응하는 삭제되지 않은 DB 세션이 있는지 확인하고 새 access token을 발급한다.

현재 갱신은 access token만 재발급한다. refresh token 회전, 재사용 탐지, 동시 갱신 요청 합치기까지 갖춘 구현으로 설명하지 않는다. 클라이언트의 만료 확인은 갱신 시점을 고르는 용도이고 서버의 토큰 검증을 대체하지 않는다.

## WebSocket 연결 허가와 사용자 인증을 나눈다

클라이언트는 `/api/auth/wstoken`에서 연결용 토큰을 받아 WebSocket URL의 쿼리에 넣는다. 서버 upgrade 핸들러는 토큰을 디코딩한 후 연결을 연다. 연결이 열리면 프런트엔드는 저장된 사용자 access token을 확인하고 `userLogin` 메시지를 보낸다.

`userLogin` 수신에서는 사용자 토큰을 검증하고 DB에서 `sub`에 해당하는 사용자를 조회한다. 이후 world 명령으로 연결의 인증 상태를 갱신하고 사용자 ID·닉네임·연결 ID를 등록한다. 로비 입장과 게임 참여 가드는 이 연결의 인증 상태를 사용한다.

현재 연결용 토큰은 공개 API에서 일반 access token 생성 함수를 재사용해 발급한다. upgrade 단계도 전용 용도나 일회 사용 여부를 별도로 검사하지 않는다. 따라서 로그인 사용자만 소켓을 열 수 있게 하는 기능이나 일회용 연결 티켓으로 소개하지 않는다. 사용자 인증은 뒤의 `userLogin` 단계와 구분해야 한다.

연결 끊김에는 재연결 시도와 지수형 대기 시간이 설정되어 있지만, 소켓 재연결과 이전 게임의 완전한 복원은 다른 문제다. 보드 스냅샷·방 퇴장·진행 상태의 한계는 앞선 네트워크 문서에서 다룬다.

## 이메일·OAuth·로그아웃에서 남아 있는 차이

서버에는 이메일 가입·로그인과 Google OAuth의 인증 코드 교환·사용자 정보 조회·가입 또는 로그인 처리도 있다. 이메일 암호는 Argon2 해시·검증 함수를 사용한다. 다만 일반 프런트엔드의 이메일 API 함수는 TODO이며, 관련 호출 화면은 테스트 경로에서 확인된다.

이메일·Google 응답은 refresh token을 쿠키로 전달하는 코드가 남아 있다. 반면 현재 토큰 갱신 API는 Bearer refresh token을 요구하고 일반 게스트 흐름은 두 토큰을 store에 저장한다. 게스트 경로를 바꾸었다고 모든 인증 수단의 계약까지 함께 통일된 것은 아니다.

Google 로그인에는 state를 생성하는 코드가 있지만 콜백에서 저장된 값과 대조하는 검증은 확인되지 않는다. 또한 access token을 리다이렉트 URL에 넣는 코드가 있다. 보안적으로 완결된 소셜 로그인 성과로 확대하지 않고, 전달 방식·state 검증·로그 기록 범위를 보강할 대상으로 구분한다.

일반 화면의 로그아웃은 서버 로그아웃 요청, 로컬 인증 store 비우기, WebSocket `userLogout` 순으로 진행한다. 현재 HTTP 로그아웃은 refresh 쿠키를 만료시키지만 DB 세션을 폐기하지 않는다. 로컬에서 토큰을 지웠다고 서버에서 해당 refresh token을 무효화한 것은 아니다. 세션 저장과 세션 취소를 별도 계약으로 정리해야 한다.

## Redis 준비와 실제 메시지 경로는 다르다

공통 app state에는 Redis client·pool이 있고 Compose에도 Redis 서비스가 있다. WebSocket 유틸리티에는 publish·분산 락 함수와 락 테스트가 존재한다.

그러나 현재 게임의 `WsPubSub`는 프로세스 안의 `HashMap`과 Tokio broadcast channel로 토픽을 관리한다. 락 호출도 테스트 밖의 게임 경로에서는 확인되지 않는다. Redis를 설치·연결할 기반과 실제 로비·게임 메시지를 Redis로 분산 처리했다는 성과를 구분한다.

현재 구조에서 WebSocket 서버를 여러 개로 늘리는 문제는 방 소유권·사용자 라우팅·서버 간 메시지 공유를 추가로 설계해야 하는 영역이다.

## 컨테이너 실행 구성

Compose는 웹·API·WebSocket 애플리케이션 묶음과 Nginx·PostgreSQL·Redis 인프라 묶음을 나누고 공유 네트워크로 연결한다. 운영용 Nginx 설정은 HTTPS를 받고 `/`를 웹 컨테이너, `/api`를 API, `/ws`를 WebSocket 컨테이너로 전달한다. WebSocket 경로에는 Upgrade·Connection 헤더 전달도 설정했다.

웹 Dockerfile은 Node 빌드 단계에서 `npm ci`와 웹 빌드를 수행한 뒤 정적 결과만 Nginx 실행 이미지로 옮긴다. 웹 컨테이너의 `try_files`는 직접 접근한 SPA 경로를 `index.html`로 연결하고 gzip을 설정한다.

API와 WebSocket Dockerfile은 Rust 빌드 단계에서 `aarch64-unknown-linux-musl` 대상으로 각각의 실행 파일을 만든 뒤 Alpine 실행 이미지에 복사한다. 각 이미지에는 해당 애플리케이션의 `Settings.toml`도 복사한다. 설정 파일에 비밀값이 포함될 수 있는 구조인 만큼 이미지에 포함할 기본 설정과 배포 시 주입할 비밀 설정의 경계를 검토해야 한다. 이번 문서 작성에서는 설정 파일의 실제 값을 열지 않았다.

이 설명은 저장소의 컨테이너·프록시 구성에 대한 분석이며, 현재 운영 서버나 TLS 인증서가 정상 가동 중인지 확인한 결과는 아니다.

## WASM을 먼저 만들고 웹과 서버 이미지를 게시한다

현재 활성 GitHub Actions 워크플로는 두 경로로 나뉘며 둘 다 `workflow_dispatch`로 수동 실행한다.

| 경로 | 빌드·게시 순서 | 도착 지점 |
| --- | --- | --- |
| GitHub Pages | WASM 패키지 → 웹에 패키지 복사 → 웹 빌드 | 정적 사이트 게시 |
| Docker 이미지 | WASM 패키지 → 웹 이미지 → API·WS 이미지 | GHCR 이미지 게시 |

WASM 스크립트는 공용 코어와 TypeScript 타입을 패키징한다. 웹 빌드 스크립트는 결과를 로컬 `tetris-lib-pkg` 의존성 위치로 복사한다. 게임 규칙을 웹에서 실행하려면 웹 빌드 전에 코어 패키지가 필요하다는 의존 순서를 빌드 과정에 반영했다.

Pages 스크립트는 `build/index.html`을 `build/404.html`로 복사해 직접 경로 접근을 처리하고, Actions에서 `front/build`를 게시한다. 이 경로는 웹 파일만 배포하므로 멀티플레이를 하려면 별도 API·WebSocket 서버가 필요하다.

Docker 워크플로는 ARM runner에서 실행하며 GHCR에 로그인한 뒤 세 이미지를 `latest` 태그로 게시한다. 현재 활성 워크플로에는 게시된 이미지를 운영 호스트에서 pull하고 서비스를 교체하는 단계가 없다. 따라서 매 push마다 테스트부터 운영 반영까지 자동 완료하는 CI/CD로 소개하지 않는다.

## 다른 출처의 웹과 API 연결

GitHub Pages에서 별도의 API를 호출할 수 있도록 API CORS 허용 목록에 Pages origin을 추가했다. Authorization·Content-Type 헤더, 사용하는 HTTP 메서드, credentials 설정을 함께 지정한다. CORS를 추가하는 것은 브라우저의 출처 정책에 맞추는 일이며 사용자 인증 자체는 JWT 경로에서 처리한다.

웹의 API 주소는 Vite 환경변수로 선택한다. 빌드된 정적 사이트의 요청 주소와 API 허용 origin, Nginx 라우팅이 맞아야 웹 파일이 열리는 것뿐 아니라 로그인·게임 연결까지 동작한다. 배포 결과를 확인할 때 각각을 구분할 필요가 있다.

## 결과와 한계 {/* #성과와-보강할-운영-경계 */}

HTTP 사용자 식별과 실시간 게임 연결을 분리하고 공통 인증·저장소 코드를 재사용했다. WASM 선행 빌드, 정적 웹 게시, 웹·API·WebSocket 이미지 생성을 연결해 브라우저에서 접속하는 게임의 배포 경로를 마련했다.

현재 구현 이후의 보강은 다음 항목으로 구분할 수 있다.

- 인증 계약: 토큰 보관·전달 방식을 로그인 수단별로 통일하고 로그아웃과 DB 세션 폐기를 연결한다.
- OAuth·연결 토큰: state 검증, 토큰 용도 구분, URL·로그의 민감정보 노출 범위를 정리한다.
- 재현 가능한 빌드: 도구·이미지 버전 고정, `latest` 외 변경 추적용 태그, DB 스키마·SQLx 빌드 준비를 명시한다.
- 운영 반영: 이미지 게시와 실제 서버 배포를 구분하고 상태 확인·실패 복구·롤백 절차를 마련한다.
- 비밀 설정: 소스·이미지에 포함되는 설정과 실행 환경에서 주입할 값을 분리한다.

이는 문서 분석에서 구분한 후속 항목이다. 이번 작업에서는 인증 코드·워크플로·이미지·서버를 변경하거나 배포를 실행하지 않았다.
