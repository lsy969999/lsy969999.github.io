# Three.js 인스턴싱으로 여러 테트리스 보드 그리기

## 참가자마다 늘어나는 블록을 묶어서 그리기

멀티플레이 화면에는 내 보드뿐 아니라 다른 참가자들의 보드, Next·Hold, 착지 힌트, 점수와 공격 큐를 함께 표시한다. 각 타일을 독립적인 렌더 메시로 추가하는 대신, 같은 종류의 요소들을 `InstancedMesh`에 모으고 위치·회전·크기 행렬을 전달하는 구조로 구성했다.

묶음의 기준은 보드가 아니라 표시 종류다. 한 보드 안의 I 블록만 묶는 것이 아니라 **모든 보드의 I 블록을 공용 그룹에 모은다.** 보드별 렌더 처리기는 자신의 상태를 표시 데이터로 변환하고, 공용 `GameRender`가 이를 종류별로 모아 Three.js 장면에 연결한다.

## React Three Fiber와 명령형 게임 루프의 경계

`ClientTetris`는 GLB와 폰트를 로드하고 React Three Fiber의 `scene`을 `GameManager`에 전달한다. GLB의 `nodes.Cube`에서 가져온 geometry를 블록 계열 인스턴스가 공유한다. `useFrame()`은 프레임 delta를 `GameManager.frame()`에 넘긴다.

프레임에서는 입력과 게임 루프를 먼저 진행하고, 각 보드의 타이머·렌더 처리기를 갱신한 다음 마지막에 공용 인스턴스 행렬을 갱신한다. 타일마다 React 컴포넌트를 만들거나 타일 이동마다 React state로 장면 전체를 재구성하는 경로가 아니다.

```text
React Three Fiber useFrame
  → GameManager: 입력·게임 진행
  → 보드별 RenderHandler: 상태를 표시 데이터로 변환
  → GameRender: 종류별 인스턴스 행렬 갱신
  → 공용 장면의 InstancedMesh로 렌더링
```

React는 장면 연결과 컴포넌트 생명주기를 담당하고, 반복적인 보드 상태·행렬 갱신은 별도 TypeScript 클래스에서 수행하도록 경계를 둔 구성이다.

## 17개 표시 그룹과 공유 자원

| 분류 | 인스턴스 그룹 |
| --- | --- |
| 일곱 블록 종류 | I, O, T, J, L, S, Z |
| 보드 외형 | Case, Grid, Cover, EndCover |
| Next·Hold 제목 | Next, Hold |
| 힌트·공격 표시 | Hint, Garbage, GarbageQueue, GarbageReady |

각 그룹은 geometry·material과 인스턴스 목록을 가진다. 일곱 블록 종류는 같은 GLB geometry를 쓰되 종류별 색상의 material로 구분한다. 인스턴스마다 별도 색상을 설정해 하나의 그룹에 합친 방식은 아니다.

Case·Cover 등에는 기본 박스 geometry, Grid에는 평면 geometry를 사용한다. 고정된 제목인 `NEXT`와 `HOLD`는 `TextGeometry`로 만들어 여러 보드에서 인스턴스로 재사용한다. 반면 닉네임·점수·시간처럼 내용이 바뀌는 글자는 별도의 텍스트 객체다.

현재 각 `InstancedMesh`는 5,000개 용량으로 생성하고 초기 표시 개수 `count`는 0으로 설정한다. 이는 모든 보드를 합쳐 종류별로 예약한 용량이지, 보드 하나당 5,000개라는 뜻이 아니다. 17개 그룹이 있다는 사실을 전체 화면의 draw call이 항상 17회라는 측정 결과로 바꾸어 설명하지 않는다. 텍스트와 다른 장면 요소도 별도로 존재한다.

## 보드 좌표를 인스턴스 행렬로 변환한다

각 보드의 `RenderHandler`는 기준 위치·회전·스케일을 가진다. 변환 계산용 `Group`에 이 값을 적용하고, 자식 dummy 객체에 타일이나 보드 외형의 로컬 배치를 설정한다. 이후 월드 위치·회전·스케일을 구해 표시용 `Object3D`에 복사한다.

보드 타일의 배치는 `(tileIdx, -lineIdx, 0)`이다. Rust 보드는 아래쪽으로 Y가 증가하지만 화면에서는 음의 Y로 내려가도록 바꾼다. Next와 Hold도 별도 로컬 오프셋에 배치한 뒤 같은 보드 기준 변환을 적용한다.

이 `Object3D`들을 타일별 Mesh로 scene에 추가하지는 않는다. 공용 렌더러가 `object.updateMatrix()`로 행렬을 만들고 해당 그룹의 `setMatrixAt()`에 전달한다. 보드 변환을 이미 계산한 값이므로 최종 전달에서는 `object.matrix`를 사용한다.

## 두 단계 dirty 갱신

첫 단계는 **보드 상태의 변경 여부**다. 이동·회전·생성·동기화 등의 동작은 `RenderHandler.isDirty`를 켠다. 프레임에서 이 값이 켜져 있으면 활성 보드의 착지 힌트를 갱신하고, 보드의 표시 데이터를 다시 만든 뒤 플래그를 끈다.

표시 데이터를 만들 때는 해당 보드 ID로 등록된 블록·힌트·쓰레기 타일을 제거하고, Next·Hold와 현재 보드 전체를 순회해 다시 등록한다. 한 타일이 움직였다고 그 타일의 인스턴스만 수정하는 차등 갱신은 아니다. 고정된 보드 외형은 별도 목록으로 관리하므로 일반 블록 이동마다 외형까지 다시 만들지는 않는다.

두 번째 단계는 **표시 종류의 변경 여부**다. 데이터를 추가·제거하면 해당 종류의 `mInfos.isDirty`를 켠다. 모든 보드 처리가 끝난 뒤 공용 렌더러가 변경된 종류만 갱신한다.

```ts
if (mInfos.isDirty) {
  mInfos.objects.forEach(({ object }, idx) => {
    object.updateMatrix();
    this.instancedMeshs[mType].setMatrixAt(idx, object.matrix);
  });
  this.instancedMeshs[mType].count = mInfos.objects.length;
  this.instancedMeshs[mType].instanceMatrix.needsUpdate = true;
  mInfos.isDirty = false;
}
```

한 프레임 안에서 여러 보드가 같은 종류를 바꾸더라도 최종 행렬 반영은 그 종류에 대해 한 번의 순회로 모인다. 아무 보드도 변경하지 않은 종류는 이 행렬 재작성 경로를 건너뛴다.

반면 어느 한 보드가 I 그룹을 바꾸면 다른 보드의 I 인스턴스까지 포함해 그룹 전체 행렬을 다시 설정한다. 종류별 부분 범위 업로드나 안정적인 타일별 인스턴스 슬롯을 관리하는 구현은 아니다.

## 참가자 수에 따른 상대 보드 배치

`GameBoardLayout`은 내 보드와 다른 보드를 구분하고 상대 보드 수에 맞춰 정사각형 격자와 스케일을 선택한다. 1개면 한 칸, 2~4개면 2×2와 1/2 스케일, 5~9개면 3×3과 1/3 스케일을 사용하는 식이다.

상대 보드를 추가하기 전에는 필요한 슬롯을 다시 계산하고, 기존 보드들을 새 위치로 옮긴 뒤 빈 슬롯에 새 보드를 넣는다. 삭제 시에도 남은 슬롯을 다시 배치한다. 블록 데이터 자체의 좌표를 고치는 대신 보드 기준 변환을 바꾸는 방식이다.

`RenderHandler.move()`는 외형과 텍스트 위치를 갱신하고 공격 큐·종료 덮개·블록 표시도 새 변환에 맞춰 구성한다. 따라서 확대·축소된 상대 보드에서 Next·Hold와 공격 표시가 별도의 위치 체계를 갖지 않도록 연결했다.

배치 테이블은 10×10에 해당하는 항목까지 정의되어 있다. 이 값은 레이아웃 계산 범위일 뿐 100명 동시 플레이의 렌더링 성능이나 서버 수용량을 검증했다는 의미는 아니다.

## 변화하는 텍스트와 일시적인 표시

닉네임과 정보 텍스트는 `troika-three-text`의 `Text`를 scene에 직접 추가한다. 정보 문자열은 매 프레임 레벨·줄 수·점수·시간으로 만들고, `updateText()`에서 이전 문자열과 다를 때만 `text.text`를 바꾼다. 따라서 블록이 정지해 있어도 시간 문자열 계산까지 모두 중단되는 것은 아니다.

점수 연출은 별도 `Text`를 만들고 1.5초 뒤 제거한다. 다시 점수가 발생하면 기존 타이머를 취소하고 텍스트를 교체한다. 이는 블록 인스턴싱과는 별개인 일시적 장면 객체의 수명 관리다.

착지 힌트와 Cover·EndCover는 투명 material을 사용하고 Hint에는 별도 `renderOrder`를 지정했다. 현재 모든 인스턴스 그룹의 `frustumCulled`는 false다. 화면 밖 보드의 자동 생략까지 구현한 최적화로 소개하지 않으며, 투명 표시의 겹침은 실제 화면에서 별도로 확인해야 한다.

## 절감하는 비용과 남아 있는 비용

이 구조는 반복되는 geometry와 material을 공유하고, 여러 보드의 같은 요소를 인스턴스 단위로 묶어 그리도록 한 것이다. 타일마다 독립 Mesh를 장면에 추가하는 구조와 비교할 수 있지만, 현재 문서에 개선 배수나 FPS 측정값은 제시하지 않는다.

CPU 측에는 여전히 다음 비용이 있다.

- 변경 보드의 WASM `getBoard()` 결과 변환과 전체 타일 순회.
- 종류별 배열에서 보드 ID를 찾아 제거하는 필터 순회와 배열 생성.
- 표시 타일마다 만드는 `Object3D`, 보드 갱신 때 만드는 Group·벡터 등의 임시 객체.
- 변경 종류에 속한 모든 보드의 행렬 재계산·설정.
- 매 프레임 시간 표시용 문자열과 날짜 포맷 구성.

즉 인스턴싱으로 렌더 요소를 묶었다는 것과 게임의 CPU 갱신 비용이 사라졌다는 것은 다르다. 다음 최적화가 필요하다면 보드 수·타일 수·변경 빈도를 나눠 측정하고, 변경 보드의 표시 데이터 재구성 비용과 행렬 갱신 시간을 따로 확인해야 한다.

## 용량과 해제 경계에서 보강할 부분

현재 push 경로에는 종류별 5,000개 용량을 넘을 때 확장하거나 등록을 거절하는 검사가 없다. 데이터 목록 길이로 `count`를 설정하므로 예약 용량을 충분히 잡았다는 이유만으로 임의의 참가자 수를 안전하게 지원한다고 말할 수 없다.

보드 데이터 삭제는 `id.includes(filterId)`를 사용한다. 현재 보드 ID 사용 전제와 별개로 일반적인 식별자로 확장하려면 정확한 ID 비교나 소유 보드별 슬롯 구분이 더 명확하다. 안정적인 슬롯을 두면 매번 필터링 후 추가하는 방식 대신 변경된 슬롯을 갱신하는 방향도 검토할 수 있다.

보드 제거는 블록·외형·종료 덮개·공격 표시와 기본 텍스트를 제거한다. 하지만 점수 텍스트의 지연 타이머 취소는 보드 `destroy()`에 포함되어 있지 않다. `removeText()`도 제거한 항목을 텍스트 사전에서 삭제하지 않는다. 종료 후 지연 콜백과 재삭제 여부는 수명 관리의 보강 지점이다.

공용 렌더러 해제는 각 그룹의 geometry·material에 `dispose()`를 호출한다. 여러 그룹이 같은 geometry를 참조하고 GLB에서 가져온 자원도 있으므로, 그룹별 참조와 실제 자원 소유권을 나눠 정리할 여지가 있다. 이것을 이번 분석만으로 실행 중 누수나 크래시가 재현됐다는 주장으로 확대하지 않는다.

또한 `useRef(new GameManager())`는 참조 보존과 별개로 React 렌더 시 생성자 표현식을 평가하는 형태다. 재렌더에서 불필요한 관리자·인스턴스 자원 생성을 피하려면 초기화 경계를 검토할 수 있다. 이번 작업은 문서화이며 이런 구현들을 변경한 것은 아니다.
