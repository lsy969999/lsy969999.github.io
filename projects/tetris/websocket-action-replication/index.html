WebSocket 액션 복제와 보드 스냅샷 동기화

현재 실행 경로를 기준으로 구분하기​

멀티플레이에서는 내 입력이 즉시 화면에 반영되어야 하고, 같은 방의 다른 참가자에게도 블록 이동과 게임 진행이 전달되어야 한다. 이를 위해 로컬 보드의 동작, WebSocket 송수신, 서버 보드 처리, 다른 참가자 보드 재현을 연결했다.

현재 구조의 핵심은 로컬 즉시 실행 + 서버 액션 복제 + 요청 시 전체 스냅샷 적용이다. 과거 예측 큐와 개별 보드 보정 코드는 남아 있지만 현재 게임 경로에서 사용하지 않는다. 서버 승인 번호를 기준으로 로컬 상태를 되돌리고 미확정 입력을 재실행하는 reconciliation은 현재 경로에 연결되어 있지 않다.

로컬 보드와 다른 참가자 보드를 다르게 구성한다​

GameManager.createMultiPlayerBoard()는 내 보드에 입력 처리기, MultiTickerHandler, WsSender를 연결한다. 반면 createMultiSubBoard()로 만드는 다른 참가자 보드에는 송신기와 로컬 게임 tick 처리기를 연결하지 않는다. 다른 보드는 받은 액션으로 상태를 갱신하고 화면에 표시한다.

입력과 수신이 공통 Controller를 사용하더라도 상대 보드에는 송신기가 없으므로, 일반적인 이동·회전 재현이 다시 서버 송신으로 이어지지 않는다. 내 보드에 돌아온 일반 이동 액션은 수신 측에서 건너뛰어 이중 적용을 피한다.

왼쪽 이동 한 번의 흐름​

Plain Text
내 입력
  → ActionHandler의 활성·낙하 상태 확인
  → JsBoard에서 이동 판정·적용
  → 렌더 갱신 표시 + gameAction 송신
  → Rust 서버의 내 Board에서 이동 판정·적용
  → 액션 버퍼에 기록
  → 방 구독자에게 액션 묶음 발행
  → 상대 클라이언트의 해당 보드에서 이동 재현

ActionHandler.actMoveLeft()는 비활성 보드이거나 낙하 블록이 없으면 입력을 무시한다. Controller.moveLeft()는 WASM 보드의 tryMoveFalling()과 applyMoveFalling()을 호출한 뒤 렌더 dirty 플래그를 설정하고 moveLeft를 보낸다. 로컬 판정이 실패해 예외가 발생하면 뒤쪽 송신까지 진행하지 않고 입력 처리기의 catch로 돌아간다.

송신 형식은 WsSender에서 구성한다.

JSON
{
  "type": "gameAction",
  "data": {
    "action": "moveLeft",
    "gameId": "현재 게임 ID"
  }
}

실제 게임 ID는 방 페이지가 설정한다. 현재 메시지에는 클라이언트 입력 번호나 입력 발생 tick을 넣지 않는다. 따라서 서버에서 나중에 부여하는 액션 seq를 특정 로컬 입력에 대한 승인 번호라고 해석하면 안 된다.

서버 명령 처리와 액션 묶음 발행​

WebSocket 컨트롤러는 수신 메시지를 Game::Action으로 바꾸면서 연결에 속한 ws_id를 붙인다. 게임 액션 메시지에서 임의의 대상 보드 ID를 받아 처리하는 방식이 아니다.

명령은 Tokio의 unbounded channel을 통해 WsWorld에 들어간다. 하나의 수신 태스크가 select!로 명령과 게임 tick·정리 타이머를 처리하고, 자신의 world 상태를 변경한다. 이는 해당 태스크 안에서 명령과 tick의 상태 변경을 순차적으로 처리하는 구성이지 네트워크 작업 전체가 한 스레드에서 실행된다는 뜻은 아니다.

액션 처리기는 인증된 연결인지, 게임이 존재하는지, GameStart 상태인지, 해당 연결의 보드가 있는지, 보드가 종료되지 않았는지 확인한다. 이동·회전은 서버의 Rust Board에서도 판정한다. 성공 시 서버 보드를 변경하고 MoveLeft 같은 결과 액션을 버퍼에 추가한다.

RUST
pub fn push_action_buffer(&mut self, action: TetrisGameActionType) {
    self.act_seq += 1;
    self.actions_buffer.push(TetrisGameAction {
        tick: self.tick,
        action,
        seq: self.act_seq,
    });
}

서버 게임 타이머는 1/60초 간격으로 설정되어 있다. tick 처리에서는 각 보드의 액션 버퍼를 수집하고, 실제 액션이 하나라도 있으면 방 토픽으로 gameAction을 발행한다. 참가자별 액션 배열을 한 메시지에 담아 보내므로 동작마다 보드 전체를 전송하지 않는다. 실제 처리율과 지연 시간을 측정한 결과는 아니다.

get_action_buffer()는 전송할 버퍼를 반환하면서 actions 이력에도 누적하고 임시 버퍼를 비운다. 이 이력이 존재한다고 클라이언트 롤백이나 재전송이 자동 구현되는 것은 아니다. 장시간 게임에서는 누적 이력의 보관 범위와 unbounded 명령 큐에 대한 부하 제어도 고려할 지점이다.

수신한 액션으로 다른 보드를 재현한다​

브라우저에서는 WebSocketInitializer가 gameAction을 ClientTetris → GameManager → WsReceiver로 전달한다. 수신기는 보드 ID별 배열을 순회하고 각 action을 해당 보드의 ctrl 메서드로 바꾼다.

이동·회전·하강뿐 아니라 setup, spawn, pushNext, addHold, setInfo, scoreEffect 등도 전달한다. 현재 수신 루프는 배열 원소에서 action만 꺼내고 tick과 seq는 적용 순서 검증이나 시간 재생에 사용하지 않는다. 보드별 배열 순서대로 즉시 재현하는 방식이다.

내 보드의 일반 동작은 이미 로컬에서 실행했으므로 mainBoardId와 같으면 건너뛴다. 단, boardStart, boardEnd, 쓰레기 큐와 쓰레기 줄 적용 같은 메시지는 내 보드에도 처리한다. 모든 수신 액션에 동일한 제외 규칙을 적용하지 않는다.

낙하 진행과 서버의 신뢰 범위​

현재 MultiTickerHandler는 클라이언트에서 레벨별 하강 tick, 고정 지연, 다음 블록 생성 등을 진행하고 관련 액션을 송신한다. 서버의 중력 기반 DoStep 발행 코드는 주석 처리되어 있다. 서버가 모든 낙하 타이밍을 독립적으로 결정하고 클라이언트는 입력만 전송하는 구조가 아니다.

또한 서버는 Setup, PushNext, Spawn, SetInfo를 받아 다음 블록·생성 종류·점수·레벨·줄 수 등을 갱신한다. set_info()는 전달받은 값이 있으면 해당 멤버에 대입한다. 배틀 공격도 클라이언트가 보낸 ScoreEffect 종류를 해석하는 경로가 있다.

서버는 보드와 이동 충돌을 검사하지만, 점수·입력 빈도·진행 규칙 전체를 검증하지는 않는다. 치트 방지를 위해서는 이 검증을 서버 쪽에 추가해야 한다.

전체 스냅샷을 요청하고 적용하는 경로​

방 페이지는 사용자 목록에 맞춰 보드를 생성한다. 내 보드를 새로 만들 때 현재 게임 ID가 있으면 gameSync를 요청한다. 매 프레임 또는 액션 불일치마다 자동 호출되는 보정 루프가 아니라, 이 시점에 연결된 상태 조회 경로다.

서버 game_sync()는 게임 내 보드들의 game_sync_data()를 모아 요청 연결의 토픽으로 응답한다. 여기에는 보드 타일, Hold, Next, 쓰레기 큐, 점수, 레벨, 제거 줄 수, 종료 여부, 경과 시간이 포함된다. 방의 게임 결과 정보도 함께 반환한다.

클라이언트는 multiGameSync()에서 이미 존재하는 보드를 찾아 boardSync()를 호출한다. 수신한 타일을 WASM 보드에 대입하고 Hold·Next·점수·레벨·줄 수를 복원한다. 서버의 밀리초 경과 시간은 초로 바꿔 타이머에 반영하며 종료 상태에 따라 타이머와 종료 덮개를 처리한다.

하지만 다음 상태는 동일하게 복원되지 않는다.

  • garbageQueue는 서버 응답에 있지만 boardSync()에서는 TODO로 남아 있다.
  • isBoardActive, Hold 가능 여부, 고정 지연·tick, 7-bag 잔여 상태 등은 이 함수가 복원하지 않는다.
  • 수신 시 존재하지 않는 보드는 건너뛴다. 스냅샷이 누락된 보드를 자체 생성하지 않는다.
  • 스냅샷에는 액션 경계 번호가 없고, 수신 시점까지의 미확정 입력을 분리·재실행하지 않는다.

예측 큐와 개별 보정은 현재 비활성 코드다​

useClientPredicateStore.ts에는 액션과 seq를 담는 큐, 앞에서 꺼내 비교하는 함수가 남아 있다. 하지만 현재 프런트엔드 소스에서는 해당 함수들의 호출을 찾을 수 없고, 함수 안의 번호 비교도 주석 처리되어 있다.

gameBoardSync 메시지와 서버 board_sync() 함수도 존재하지만 WsWorld의 분기에서 실제 함수 호출을 주석 처리했다. 프런트엔드 수신 분기 역시 주석 상태다.

현재 로컬 즉시 실행은 응답을 기다리지 않는다는 특성은 있지만, 서버 결과를 확인하고 잘못 예측한 상태를 되돌리는 단계까지 포함하지 않는다.

구현 결과​

입력·서버 처리·다른 참가자 화면을 액션 단위로 연결하고, 접속 시 보드 정보를 가져오는 별도 경로를 마련했다. 공용 Rust 보드 규칙은 로컬 WASM, 서버 상태 갱신, 상대 보드 재현에 재사용된다. 로컬 보드와 상대 보드에 부여하는 송신·tick 역할을 나눠 공통 컨트롤러를 활용했다.
