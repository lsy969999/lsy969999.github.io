Rust 보드 규칙을 서버와 WebAssembly 클라이언트에서 공유하기

클라이언트와 서버가 서로 다른 판정을 하지 않도록​

웹 멀티플레이 테트리스에서는 입력 직후 클라이언트가 블록을 움직이는 동시에 서버도 해당 동작을 처리해야 한다. 이동 가능 여부와 회전 충돌 판정을 TypeScript와 Rust로 각각 구현하면 한쪽만 수정하거나 경계 조건을 다르게 처리할 가능성이 생긴다.

이를 줄이기 위해 보드와 블록 판정을 tetris-lib라는 Rust crate에 모았다. 서버는 이 crate를 직접 사용하고, 웹 클라이언트는 같은 코어를 WebAssembly로 빌드한 JsBoard를 사용한다. 공유 대상은 보드 규칙이며, 게임 전체의 진행 상태와 네트워크 동기화까지 하나로 통합한 것은 아니다.

공유하는 부분과 환경별로 남겨 둔 부분​

영역실제 구현과 책임
Rust 공용 코어Board, 타일·낙하 블록 표현, 생성·이동·회전·하강 판정, 고정·줄 제거·하드 드롭·고스트 표시·쓰레기 줄 삽입
WASM 어댑터JsBoard가 Rust Board를 소유하고 JavaScript 값과 Rust 타입을 변환
서버 진행 로직TetrisGame이 Board와 함께 점수·Hold·Next·진행 tick·공격 큐·액션 기록 등을 관리
웹 진행·표현 로직TetrisBoard가 JsBoard와 함께 Hold·Next·타이머·렌더 갱신·입력 및 WebSocket 송신을 연결

서버의 TetrisGame과 클라이언트의 TetrisBoard는 각각 10×26 크기의 보드를 생성한다. 각 환경에 별도의 상태가 존재하지만, 실제 타일 이동과 충돌 판정은 같은 Rust 구현으로 내려간다.

현재 저장소에서 확인한 실행 대상은 Web·Mobile Web과 Rust 서버다. 이 문서는 Android·iOS 네이티브 앱용 FFI를 구현했다는 근거로 사용하지 않는다.

Rust crate를 두 환경에서 사용하기​

back workspace에는 api, common, tetris-lib, ws가 있다. 서버 ws는 tetris-lib를 로컬 경로 의존성으로 참조한다. 코어의 라이브러리 출력은 rlib와 cdylib로 지정했다.

TOML
[lib]
crate-type = ["cdylib", "rlib"]

[features]
default = []
wasm = ["ts-rs", "wasm-bindgen", "serde-wasm-bindgen"]

WASM 관련 의존성은 선택 기능으로 두고 #[cfg(feature = "wasm")]일 때만 바인딩 모듈을 포함한다. 서버가 코어를 사용하는 경로에는 JavaScript 바인딩을 요구하지 않는다. 보드 데이터에는 serde를 사용하고, WASM 기능을 켰을 때 데이터 타입의 TypeScript 정의 생성도 활성화한다.

이는 서버 바이너리와 브라우저가 같은 메모리나 실행 파일을 사용한다는 뜻이 아니다. 같은 소스를 각 실행 환경에 맞춰 빌드하고, 각자 자신의 보드 상태에 적용하는 구조다.

판정과 적용을 나누는 API​

블록 이동은 즉시 타일을 고치는 단일 함수가 아니라 try_move_falling()과 apply_move_falling()으로 나눴다. 생성·회전·하강·줄 제거에도 판정과 적용을 분리한 API가 있다. 다만 hard_drop()처럼 내부에서 상태를 변경하는 함수도 있으므로 모든 API가 이 형태인 것은 아니다.

try_move_falling()은 보드를 변경하지 않는 &self 메서드다. 각 낙하 블록의 이동 목표를 계산하고, 좌우 경계와 목적지 타일을 검사한다. 이동 가능한 블록이 네 개가 아니면 InvalidShape를 반환한다. 성공하면 각 타일의 현재 위치 as_is와 목표 블록 to_be를 담은 FallingBlockPlan 목록을 반환한다.

apply_move_falling()은 먼저 모든 기존 위치를 비운 뒤 목표 위치들을 채운다. 한 칸씩 지우고 쓰면서 같은 테트로미노의 다른 타일을 덮어쓰는 문제를 피하는 순서다.

서버의 왼쪽 이동은 다음 순서다.

RUST
let plan = self
    .board
    .try_move_falling(tetris_lib::MoveDirection::Left)?;
self.board.apply_move_falling(plan);
self.push_action_buffer(TetrisGameActionType::MoveLeft);

웹 쪽도 동일한 판정·적용 순서를 거친 뒤 렌더 갱신을 표시하고, 멀티플레이 송신 객체가 있으면 액션을 보낸다.

TypeScript
const b = this.tb.board;
const plan = b.tryMoveFalling("Left");
b.applyMoveFalling(plan);

this.tb.renderHandler.isDirty = true;
if (this.tb.wsSender) {
  this.tb.wsSender.wsSend("moveLeft");
}

판정 결과는 트랜잭션이나 보드 버전이 포함된 명령이 아니다. 적용 함수가 충돌 조건을 다시 검사하지 않으므로 판정 이후 보드가 달라졌거나 외부에서 임의로 만든 계획을 안전하게 검증해 주지는 않는다. 현재와 같이 판정 직후 적용하는 사용 순서를 전제로 설명한다.

JavaScript 경계는 얇은 어댑터로 처리한다​

JsBoard는 inner: Board를 갖고, wasm-bindgen으로 생성자와 메서드를 노출한다. Rust의 try_move_falling을 웹에서는 tryMoveFalling으로 부를 수 있도록 이름을 지정했다. 판정 알고리즘을 바인딩에 다시 작성하지 않고 내부 Board에 위임한다.

이동 방향과 계획 목록 같은 복합 값은 serde-wasm-bindgen의 from_value()와 to_value()로 변환한다. Rust 오류도 직렬화한 JsValue로 넘긴다. 바인딩의 Result에서 오류가 반환되는 경로는 JavaScript 호출 측에서 예외로 처리해야 하며, 정상 결과와 오류를 같은 계획 데이터로 취급해서는 안 된다.

이 방식은 JavaScript 객체로 데이터를 다루기 편하지만, 보드나 계획을 반환할 때마다 경계를 넘는 변환이 있다. getBoard()는 Rust 보드 메모리를 그대로 공유하는 zero-copy 뷰가 아니다. WASM을 사용했다는 이유만으로 성능 향상이 입증된 것으로 설명하지 않고, 이 설계의 핵심 효과를 판정 코드의 재사용에 둔다.

실행 바인딩과 데이터 타입을 함께 패키징하기​

wasm_pkg_build.bash는 wasm-pack build --release --target bundler --out-dir ./pkg --features wasm으로 패키지를 만든 뒤 cargo test --features wasm을 수행한다. ts-rs의 타입 내보내기 결과인 bindings를 pkg로 옮기고, 타입들을 재노출하는 index.ts를 구성한다.

웹 빌드 스크립트는 생성된 pkg를 front/tetris-lib-pkg로 복사한다. front/package.json은 이를 file:./tetris-lib-pkg 의존성으로 사용하고, Vite에는 WASM 플러그인을 연결했다. 클라이언트는 실행 클래스 JsBoard를 tetris-lib에서, Board·Tile·Tetrimino 같은 타입은 tetris-lib/bindings에서 가져온다.

이렇게 데이터 구조의 TypeScript 정의를 Rust에서 생성해 수작업 중복을 줄였다. 다만 JsValue 중심의 메서드 경계 전체가 엄격한 TypeScript 시그니처로 바뀌는 것은 아니다. 데이터 타입 생성과 각 함수의 인자·반환형 검증은 별도로 살펴봐야 한다.

또한 타입 목록을 내보내는 index.ts는 스크립트에 열거되어 있다. 새 공개 타입을 추가하면 목록도 관리해야 한다. 현재 코어 빌드 스크립트에는 실패 시 즉시 종료 설정이 없고 재실행 때 기존 출력에 의존할 수 있는 mv·추가 쓰기 방식이 있으므로, 깨끗한 출력 폴더와 오류 전파를 보강할 여지가 있다. 이번 문서 작업에서는 빌드 스크립트를 변경하지 않았다.

결과와 한계​

이 구조로 보드 규칙 변경을 Rust 한 곳에 모으고 서버와 브라우저에서 재사용할 수 있게 했다. 렌더링과 네트워크 라이브러리를 코어에서 분리해 보드 규칙에 대한 Rust 테스트를 작성할 수 있는 경계도 확보했다.

그러나 동일한 판정 코드를 사용해도 입력 순서·보드 상태·Next 순서·진행 시간이 다르면 결과는 달라진다. 클라이언트와 서버의 7-bag 및 상위 진행 로직도 별도 구현이다. 따라서 공유 코어는 상태 동기화나 치트 방지의 완성형이 아니며, 서버 검증과 클라이언트 예측·상태 보정은 별도 주제로 구분한다.

유지보수 시에는 코어 변경 후 서버와 WASM 패키지를 함께 갱신하는 절차, 바인딩 오류 처리, 양쪽에 남아 있는 진행 규칙의 일치 여부를 확인해야 한다. 보드 단위 테스트와 별개로 같은 입력·초기 상태를 두 환경에 적용해 결과를 비교하는 검증도 보강할 수 있다.
