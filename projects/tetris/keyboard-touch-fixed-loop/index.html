키보드·모바일 터치 입력과 고정 tick 게임 루프

입력 장치와 보드 동작을 나누기​

테트리스의 좌우 이동은 한 번 누를 때의 반응과 길게 누를 때의 반복 속도가 모두 중요하다. 브라우저가 전달하는 키 반복 이벤트를 그대로 사용하지 않고, GameInput에서 최초 대기 시간과 반복 간격을 관리했다. 모바일 화면의 버튼도 같은 키 입력 경로에 연결해 보드 조작 코드를 공유했다.

입력은 ActionDelegation, 자동 진행은 TickerDelegation으로 나뉜다. GameManager가 내 보드를 생성할 때 ActionHandler와 Solo 또는 Multi ticker를 연결한다. 입력 클래스가 직접 Rust 보드의 타일을 바꾸는 대신, 보드의 동작 처리기를 거쳐 WASM 규칙을 호출하는 구조다.

키 매핑과 반복 정책​

동작키처리 방식
왼쪽·오른쪽 이동A·D 또는 좌우 방향키즉시 1회, 최초 대기 후 반복
오른쪽 회전W 또는 위 방향키회전 잠금 플래그로 연속 호출 제한
왼쪽 회전Z오른쪽 회전과 같은 잠금 플래그 사용
소프트 드롭S 또는 아래 방향키즉시 1회, 이후 반복
홀드Shiftkeydown에서 호출
하드 드롭Spacekeydown에서 호출

keydown()은 e.repeat를 무시한다. 좌우 이동의 최초 대기는 약 133.3ms, 이후 이동과 소프트 드롭의 반복 간격은 약 33.3ms로 설정했다. 이는 설정된 목표 간격이며 실제 콜백 실행은 렌더 프레임에서 타이머를 갱신할 때 일어난다.

좌우 동시 입력은 Set<"L" | "R">의 삽입 순서로 판별한다. 왼쪽을 누른 상태에서 오른쪽을 누르면 마지막에 추가된 오른쪽 동작만 통과한다. 오른쪽을 놓으면 남아 있는 왼쪽 반복 동작이 다시 통과한다. 방향별 타이머는 유지하므로 반대 방향을 놓았다고 최초 대기부터 다시 시작하지는 않는다.

회전은 좌우가 하나의 rotating 플래그를 공유한다. 회전 키를 누르면 설정하고 해당 키를 놓으면 해제한다. 좌우 회전을 각각 길게 눌러 반복하는 방식과는 다르다.

모바일 버튼을 기존 입력에 연결하기​

MobileButton은 포인터 이벤트를 KeyboardEvent로 변환해 window에 전달한다. 예를 들어 왼쪽 버튼을 누르면 A의 keydown을 보내고, 손을 떼면 keyup을 보낸다. 이후의 반복 간격·좌우 우선순위·보드 동작은 키보드와 같은 GameInput을 통과한다.

버튼에는 onPointerUp뿐 아니라 onPointerCancel, onPointerLeave에도 keyup을 연결했다. 버튼 밖으로 손가락이 나가거나 포인터 입력이 취소될 때 눌림 상태를 풀기 위한 처리다. 여러 손가락으로 접촉할 때 확대 동작을 막는 touchstart 처리도 포함한다.

이 UI는 싱글·멀티 방 화면에서 사용하며, 컴포넌트의 표시 기준은 화면 너비 768px 이하다. 여기서 확인한 구현은 모바일 웹의 포인터 입력 대응이다. Android·iOS 네이티브 앱이나 FFI 입력 연결을 구현한 근거로 사용하지 않는다.

input.ts에는 별도 InputDispatcher도 있지만, 현재 MobileButton은 이를 가져오지 않고 자체 dispatch 함수를 정의한다. 입력 경로는 같아도 변환 코드까지 하나의 구현으로 통합된 상태는 아니다.

프레임에서 실행하는 입력 타이머​

RaTimer는 브라우저의 setInterval을 호출하지 않는다. 콜백·누적 시간·간격·일회성 여부를 Map에 보관하고, GameInput.frame(delta)에서 실행할 시점을 검사한다. 설정은 밀리초로 받고 내부 누적은 초 단위로 계산한다.

일회성 콜백은 실행 후 제거한다. 반복 콜백은 마지막 실행 기준을 한 간격만큼 증가시킨다. 따라서 프레임 지연이 발생했을 때 현재 시간으로 기준을 덮어쓰지는 않지만, 각 타이머 항목의 검사는 while이 아닌 if라 한 번의 순회에서 밀린 횟수를 모두 실행하지도 않는다.

예를 들어 33.3ms 간격의 기존 반복 타이머에 약 100ms가 누적돼도 그 프레임에는 해당 항목의 콜백을 한 번 실행한다. 남은 지연은 후속 프레임 검사에 영향을 준다. 이를 프레임 속도와 무관하게 정확한 횟수의 입력을 보장하는 타이머라고 표현하지 않는다.

또한 타이머 콜백 안에서 같은 Map에 새 interval을 추가한다. JavaScript Map 순회는 새 항목도 방문할 수 있어, 최초 대기 종료 시 추가된 interval이 같은 프레임의 delta를 받을 수 있다. 설정 간격과 전환 프레임의 실제 실행 횟수를 구분해 검증할 부분이다.

렌더 프레임과 60Hz 게임 tick 분리​

React Three Fiber의 useFrame()이 전달한 delta는 다음 순서로 소비한다.

Plain Text
ClientTetris.useFrame(delta)
  → GameInput.frame(delta): 반복 입력 실행
  → GameLoop.gameLoopUpdate(delta): 고정 tick 소비
  → 각 보드 Timer.tick(delta): 경과 시간 갱신
  → 각 보드 renderHandler.frame()
  → 공유 InstancedMesh 갱신

GameLoop의 한 tick은 1/60초다. 렌더 프레임마다 자동 낙하를 한 번 실행하는 대신, 누적 시간이 한 tick 이상일 때만 ticker를 호출하고 소비한 시간을 뺀다. ticker는 tick 수를 세어 레벨별 중력 간격, 착지 후 고정 지연, 콤보 유지 등을 진행한다.

내 보드에는 Solo 또는 Multi ticker를 연결하지만 상대 보드는 같은 로컬 자동 진행 루프에 연결하지 않는다. 상대 보드의 동작 복제는 별도의 WebSocket 메시지 경로가 담당한다.

지연을 따라잡는 양 제한​

누적 시간은 최대 10 tick, 약 166.7ms로 제한하고 한 프레임에는 최대 5 tick을 처리한다. 이 제한은 긴 정지 이후 한 프레임에 무제한으로 연산이 몰리는 것을 방지한다.

5 tick 처리 후 남은 시간은 유지하되, 다음 프레임에도 총 누적량 상한을 적용한다. 따라서 제한 안에서는 남은 시간을 이어 처리하고, 상한을 넘는 시간은 버린다. 모든 지연을 반드시 따라잡는 구조는 아니며 지속적인 저프레임에서는 실제 시간보다 게임 진행이 느려질 수 있다.

보드의 표시 시간은 별도 Timer가 전달받은 delta를 누적하고 약 0.05초를 넘는 간격으로 info.time에 반영한다. 게임 루프의 10 tick 상한을 공유하지 않아, 심한 지연에서는 표시 시간과 진행 tick의 관계도 확인해야 한다.

시작·종료와 입력 해제의 경계​

gameLoopStart()는 누적 시간을 초기화하고 initTicking()을 호출한다. Solo ticker는 여기서 다음 블록과 보드 시작을 준비한다. 반면 gameLoopEnd()는 종료 콜백만 호출하며 루프 자체의 실행 플래그를 끄지 않는다. 현재 보드 동작과 ticker의 진행 여부는 isBoardActive 검사에 의존한다.

입력의 isActive도 새 keydown을 막는 조건이다. 이미 등록된 반복 타이머까지 중단하거나 초기화하는 기능은 아니다. keyup은 비활성 여부와 무관하게 처리해 눌림 상태를 해제할 수 있게 되어 있다.

현재 destroy()는 키 이벤트 리스너를 제거하지만 타이머 Map·방향 Set·회전 플래그를 별도로 초기화하지 않는다. 창 포커스 상실 시 키 해제가 누락되는 경우, 채팅 입력 중 게임 조작 차단, A와 왼쪽 방향키처럼 같은 동작에 연결된 복수 키의 동시 입력은 보강할 경계다. 기기별 입력 상태를 완전히 추상화한 시스템으로 설명하지 않는다.

결과와 확인 범위​

키보드와 모바일 버튼의 조작 경로를 공유하고, 입력 반복·자동 낙하·화면 갱신을 각각의 책임으로 나눴다. 고정 tick은 렌더 프레임마다 규칙 진행량이 달라지는 문제를 줄이고, 처리 상한으로 지연 이후 연산량을 제한한다. 다만 입력 타이머와 게임 tick의 지연 처리 정책은 서로 다르며, 이 차이까지 숨기지 않고 구현 범위로 정리했다.
