# 로비·방·게임 세션의 생명주기 연결

## 보드 외부의 멀티플레이 흐름

테트리스 보드가 동작해도 참가자들이 같은 게임에 모이고, 시작 시점을 공유하며, 결과를 확인한 뒤 다시 플레이하는 흐름이 필요하다. 로비의 방 목록, 방의 참가자·방장, 한 판의 보드·결과를 서로 다른 상태로 관리하고 WebSocket 메시지로 화면에 연결했다.

게임 중 액션 전달은 별도 문서에서 다룬다. 여기서는 방 생성부터 한 판 종료, 퇴장과 정리까지 이어지는 생명주기에 초점을 둔다.

## 방과 한 판의 게임은 다른 객체다

| 대상 | 주요 정보 | 유지 범위 |
| --- | --- | --- |
| 연결 | `ws_id`, 인증 사용자, 구독 토픽 | WebSocket 연결 |
| 방 `WsWorldRoom` | 방 ID·이름·방장, 참가자, 모드, 게임 ID 목록 | 같은 방에서 여러 판 진행 |
| 게임 `WsWorldGame` | 게임 ID, 참가자별 `TetrisGame`, 시간, 결과 | 한 판의 진행·종료 기록 |

방의 상태는 `Waiting`과 `Gaming`이다. 게임은 `Wait`, 카운트다운 단계, `GameStart`, `GameEnd`를 가진다. 방이 `Gaming`으로 바뀌어도 한 판은 아직 카운트다운일 수 있다. 화면의 방 상태와 실제 입력을 허용할 게임 상태를 구분한 구성이다.

`room.games`에는 새 판을 시작할 때마다 게임 ID를 추가한다. 한 판이 끝났다고 방을 삭제하지 않고 대기 상태로 되돌리므로, 동일한 참가자들이 결과를 확인하고 다음 판을 시작할 수 있다.

## 로비 목록과 방 상세의 전달 범위

홈 화면은 소켓이 열리면 `lobbySubscribe`를 보내고 화면 해제 시 구독 해제를 요청한다. 서버는 구독 요청 연결에 현재 목록을 보낸 뒤 로비 토픽을 구독시킨다. 이후 방 생성·입퇴장·게임 상태 변경이 발생하면 갱신된 목록을 발행한다.

로비의 사용자 목록은 현재 인증된 연결을 수집한 것이다. 로비 화면을 보고 있는 사람만 따로 집계한 접속자 목록은 아니다. 방 목록과 참가자 정보는 서버의 인메모리 상태를 메시지용 데이터로 변환해 전송한다.

방에 입장하면 방 전체 토픽과 해당 방 안의 개인 토픽을 구독한다. 목록·방 상세·개인 응답의 전달 범위를 나누어, 방 갱신은 방 구독자에게, 생성 완료나 전체 게임 동기화 응답은 해당 연결에 전달한다.

프런트엔드의 `WebSocketInitializer`는 메시지를 분류해 Zustand store를 갱신한다. `useLobbyStore`는 목록·로비 채팅을, `useRoomStore`는 방 상세·방 채팅·게임 결과·카운트다운 값을 관리한다. 채팅은 두 store 모두 최근 100개만 유지한다. 서버가 지난 채팅 전체를 재조회해 주는 영속 채팅 구조로 설명하지 않는다.

## 방 생성과 입장을 두 단계로 연결하기

방 생성 요청에서는 인증 연결을 확인하고 새 방 ID를 만든다. 생성한 방의 방장은 요청 연결이며, 초기 모드는 `MultiScore`, 상태는 `Waiting`이다. 이 시점의 참가자 목록은 비어 있다.

서버가 `RoomCreated`를 보내면 클라이언트는 `/room/{roomId}`로 이동한다. 방 페이지는 초기 WebSocket 로그인 처리가 끝났을 때 `roomEnter`를 요청한다. 생성 함수가 곧바로 사용자를 참가자 목록에 넣는 것이 아니라, 응답과 페이지 전환 이후 입장이 이어진다.

입장에서는 방·개인 토픽을 구독하고 참가자를 등록한다. 참가자의 `is_game_ready` 초기값은 **true**다. 방장이 없는 방이면 입장자를 방장으로 지정한다. 이후 개인 입장 응답, 방 상세, 입장 안내 채팅, 로비 목록 갱신을 발행한다.

중복 사용자 검사가 있지만 현재는 오류를 발행한 뒤 `return`하지 않는다. 따라서 같은 계정의 중복 입장을 확실하게 차단하는 기능으로 소개하지 않는다. 다른 연결 ID로 같은 계정이 입장하는 사례와 동일 연결의 중복 요청을 구분해 보강할 여지가 있다.

## 준비 상태와 방장 권한

서버에는 준비·준비 취소 API가 있다. 인증과 방 존재 여부, `Waiting` 상태, 해당 사용자의 방 참가 여부를 검사한 후 준비 플래그를 바꾸고 방 상세를 다시 발행한다.

다만 현재 일반 방 화면에서는 준비 버튼보다 자동 준비 상태와 방장의 시작 버튼을 사용하는 흐름이다. 준비 요청 코드는 테스트 화면에서 확인되며, 서버 기능이 있다는 이유로 일반 화면에 준비·취소 UI가 모두 연결됐다고 설명하지 않는다.

모드 변경과 시작은 서버에서 방장 연결인지 검사한다. 프런트엔드도 방장에게 모드 선택 UI를 보여주고 대기 상태에서만 조작할 수 있게 한다. 화면이 제공하는 모드는 점수 경쟁, 40줄, 배틀 세 가지다.

시작 시 서버가 확인하는 조건은 인증, 방 존재, 방장, 대기 상태, 모든 참가자의 준비 여부다. 통과하면 방을 `Gaming`으로 바꾸고 현재 참가자마다 `TetrisGame`을 만든다. 새로운 게임 ID를 방 목록에 추가하고 해당 게임을 `Wait` 상태로 등록한다.

배틀 최소 두 명 조건은 현재 프런트엔드 시작 버튼 처리에서 확인한다. 서버 시작 함수에는 동일한 최소 인원 검사가 없으므로 서버까지 보장하는 조건으로 적지 않는다. 또한 모드 문자열을 서버 enum으로 파싱하는 것과 방에서 허용할 모드 집합을 제한하는 것은 별도 검증이다.

## 카운트다운과 시작 신호

```text
방 Waiting
  → 시작 조건 검사
  → 방 Gaming + 새 게임 Wait
  → 카운트다운 3 → 2 → 1 → 0
  → 게임 GameStart + 참가자별 BoardStart
  → 모든 보드 종료
  → 게임 GameEnd + 방 Waiting
```

게임 tick은 `Instant`로 생성 시점부터 경과 시간을 계산한다. 10밀리초를 넘으면 3, 1초를 넘으면 2, 2초를 넘으면 1, 3초를 넘으면 0 메시지를 보내도록 단계별 상태를 변경한다. 한 번의 tick에서는 현재 단계의 분기만 수행하므로 지연이 생기면 한 번에 모든 단계를 따라잡는 방식은 아니다.

클라이언트는 `gameStartTimer` 메시지로 store의 값을 갱신해 카운트다운을 표시한다. 실제 보드 활성화는 서버 게임 루프에서 보내는 `BoardStart` 액션과 연결된다. 숫자 0 표시 자체가 보드 상태 변경의 전부는 아니다.

카운트다운 중에는 게임이 아직 `GameStart`가 아니므로 서버 액션 처리기가 게임 동작을 받아들이지 않는다. 로비·방 UI와 보드 입력의 시작 조건을 분리한 부분이다.

## 종료 조건, 결과 표시, 재시작

게임 루프는 참가자 보드의 종료 상태를 확인한다. 40줄 모드에서는 제거 줄 수가 40 이상이면 해당 보드의 완료·종료 플래그를 설정한다. 배틀에서는 종료되지 않은 보드가 하나 남으면 승리로 처리한다. 모든 보드가 종료되면 한 판의 종료 처리를 수행한다.

종료 시 게임은 `GameEnd` 및 삭제 예약 상태가 되고 모드별 결과 배열을 만든다. 방은 `Waiting`으로 돌아가며 남은 참가자들의 준비 플래그는 다시 true가 된다. 이어서 게임 결과, 방 상세, 로비 목록을 발행한다.

프런트엔드는 `gameEnd`의 배열을 결과 데이터로 변환해 store에 추가하고 최신 결과 창을 연다. 방 화면에서는 이전 판들의 결과도 표시할 수 있다. 이후 같은 방에서 다시 시작하면 기존 결과를 가진 게임 객체와 별개로 새로운 판을 생성한다.

결과 정렬의 실제 동작도 구분해야 한다. 점수 모드는 점수 내림차순이고, 40줄 모드는 완료자를 앞에 둔 뒤 경과 시간 내림차순으로 정렬한다. 따라서 현재 40줄 결과를 빠른 완주 순위로 구현했다고 주장하지 않는다. 배틀은 승리 여부를 우선한 뒤 경과 시간 내림차순을 적용한다.

점수 등 서버 상태에 클라이언트 보고값을 반영하는 범위는 액션 동기화 문서에서 설명했다. 이 결과 표시 경로가 독립적인 점수 무결성 검증이나 공인 랭킹을 의미하지는 않는다.

## 퇴장과 연결 종료를 같은 방 정리 경로로 연결하기

방 페이지가 해제되면 `roomLeave`를 보내고 방 정보·결과·서버 메시지를 정리한다. 소켓 상태가 `CLOSED`가 되면 홈으로 이동하는 처리도 있다. 따라서 연결이 끊겨도 기존 방 화면과 진행 상태를 그대로 유지하는 재접속 기능으로 설명하지 않는다.

서버 퇴장은 참가자 제거, 필요 시 방장 이전, 퇴장 응답·안내, 방·로비 갱신, 구독 해제 순으로 이어진다. 기존 방장이 나가면 남은 참가자 `HashMap`의 첫 항목을 새 방장으로 정한다. 입장 순서가 보장된 큐가 아니므로 가장 먼저 입장한 사람에게 승계되는 정책은 아니다.

마지막 게임에 퇴장자의 보드가 있으면 종료 플래그와 `Exit` 액션을 남기고 보드를 초기화한다. 다만 현재 함수는 마지막 게임의 활성 상태를 별도로 검사하지 않으므로, ‘진행 중인 게임에서만 처리한다’고 단정하지 않는다.

연결 정리 `cleanup_ws()`도 해당 사용자와 관련된 방을 찾아 `room::leave()`를 호출한 후 사용자·연결 매핑과 구독을 제거한다. 정상 퇴장과 연결 종료에 공통 방 정리 동작을 활용했다. 같은 계정의 여러 연결이 섞일 때는 방 조회가 사용자 ID 기준이고 제거가 연결 ID 기준이라는 차이를 확인해야 한다.

## 빈 방 정리와 종료 게임 백업

정리 타이머는 10초 간격으로 설정되어 있으며 빈 방을 제거하고 종료된 게임의 백업·메모리 정리를 수행한다. 빈 방은 참가자가 0명일 때 바로 제거 대상으로 수집한다. 방 생성과 입장이 분리되어 있으므로, 생성 직후 아직 입장하지 않은 방이 정리 시점과 겹치는 경계가 코드 TODO로도 남아 있다.

종료 게임은 방 ID·게임 ID·참가 연결 ID·사용자 ID·직렬화한 게임 데이터를 PostgreSQL의 `tb_game_room_backup`에 저장하는 비동기 작업으로 넘긴다. 이때 인메모리 게임 데이터와 액션 이력도 직렬화 대상에 포함된다. DB 저장을 기다리며 world 명령 처리를 막지 않도록 별도 태스크를 사용한 구성이다.

현재 `is_backuped`는 DB 쓰기 성공 이후가 아니라 태스크를 시작하기 전에 true로 설정된다. DB 연결 획득이나 INSERT가 실패해도 플래그를 되돌리거나 재시도하지 않는다. 따라서 정확한 의미는 성공이 확인된 백업이라기보다 백업 시도를 예약한 상태에 가깝다.

게임 메모리는 종료·백업 플래그가 모두 켜졌더라도 해당 방이 남아 있으면 유지한다. 방이 없어졌을 때 제거한다. 이 덕분에 같은 방에서 과거 게임 결과를 조회하는 경로가 있지만, 방이 오래 유지되면 종료 게임과 액션 이력도 쌓인다. 저장 성공 확인·보관 기간·실패 재시도를 갖춘 영속화 정책은 보강 범위로 남긴다.

## 결과와 한계 {/* #성과와-확인할-경계 */}

방 생성과 화면 이동에서 끝내지 않고, 방장 권한·시작 카운트다운·결과 표시·반복 플레이·퇴장·종료 기록 저장을 하나의 흐름으로 연결했다. 방과 게임 세션을 분리한 덕분에 한 방에서 여러 판을 이어가고, 로비와 방 상세를 서로 다른 구독 범위로 갱신할 수 있다.

현재 구현을 보강한다면 다음 항목을 우선 확인할 수 있다.

- 생성 직후 입장과 빈 방 정리의 충돌 방지, 중복 입장 요청의 조기 종료.
- 진행 중 입장 허용 여부와 서버 측 최소 인원·허용 모드 검증.
- 40줄 결과의 시간 정렬 방향, 방장 승계 순서의 명시적 정책.
- 방을 바꿀 때 store의 카운트다운·모드·게임 ID 등 모든 상태를 일관되게 초기화하는 계약.
- 종료 기록의 저장 성공 확인과 재시도, 장시간 방의 결과·액션 이력 보관 한도.

이 항목들은 문서 분석에서 구분한 한계이며, 이번 작업에서 게임 코드를 수정한 것은 아니다.
